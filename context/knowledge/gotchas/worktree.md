## Worktree Management

- **Orphan sweep must use `App.wtRoot`, never hardcode `~/.argus/worktrees/`.** Tests MUST set `app.wtRoot = t.TempDir()` — without this, `sweepOrphanedWorktrees` scans real worktrees and deletes them (including running agents' working directories).
- **`testGuard` prevents tests from operating on real `~/.argus/` worktrees (defense-in-depth).** `agent.RemoveWorktree` and `agent.RemoveWorktreeAndBranch` call `testGuard(path)` which detects `go test` (via `os.Args[0]` suffix `.test`) and blocks operations on real `~/.argus/` paths. Last-resort safety net — tests should still use `t.TempDir()` correctly.
- **`testGuard` exempts paths under `os.TempDir()` even when they match `db.DataDir()`.** Tests that `t.Setenv("HOME", t.TempDir())` (required for `CreateAndStart` tests because `WorktreeDir` resolves through HOME) otherwise trip the guard — the computed "real" data dir becomes a test path. The exemption compares the cleaned path against `os.TempDir()` so only genuinely-real home paths block.
- **`CreateWorktree` must prune stale refs first.** `git worktree prune` runs at the top (best-effort). Without it, a deleted worktree directory leaves a stale entry that locks the branch, causing exit status 255. After cmd failure, check `os.Stat(wtDir)` for partial success from post-checkout hook failures.
- **Worktree creation must succeed before task persistence.** Never `db.Add(task)` without a valid worktree. `CreateWorktree` returns `(wtPath, finalName, branchName, err)` — store `branchName` on `task.Branch` so cleanup deletes the correct `argus/*` branch.
- **Fresh-task creation must go through `agent.CreateAndStart`.** It is the only fully-transactional entry point: worktree → OnWorktreeCreated hook → DB row → SessionID → runner.Start, each step registering a LIFO compensating cleanup. Any failure unwinds every prior side effect (worktree removed, branch deleted, DB row deleted) so no ghost "Pending + no session" row is left behind. `HeadlessCreateTask`, the new-task form, and fork all route through it. `startSession` is for _existing-task restart only_ — on failure it reverts status without deleting, because the task already existed before the attempt.
- **`RemoveWorktree` must validate paths before `os.RemoveAll`.** The `IsWorktreeSubdir` guard ensures the path contains `/.argus/worktrees/` or `/.claude/worktrees/` before any removal.
- **Worktree cleanup must always `os.RemoveAll` after `git worktree remove`.** The git command can exit 0 but leave behind empty dirs. Run `git worktree prune` before `git branch -D` — git refuses to delete branches with stale worktree references.
- **`CreateWorktree` fetches all remotes before resolving the base branch.** `git fetch --all` runs best-effort before `resolveStartPoint()`. Without this, newly pushed remote branches or updates won't be visible and the worktree starts from stale data.
- **`git fetch --all` must NOT use `--prune` on macOS.** On case-insensitive filesystems, `--prune` deletes `origin/HEAD` (confusing the symbolic ref with a stale branch `origin/head`), which causes `origin/master` to be lost on alternating fetches — making worktree creation fail intermittently with "invalid reference: origin/master".
- **`git worktree add` requires a valid local ref or remote-tracking ref.** `resolveStartPoint()` checks `git rev-parse --verify` and falls back to `upstream/<branch>` then `origin/<branch>`.
- **Task names must be sanitized before branch/dir creation.** `sanitizeBranchName()` strips git-invalid characters. Without this, characters like `?` cause exit status 255.
- **`CreateWorktree` must NEVER run on the tview main goroutine.** It performs `git fetch --all` (up to 15s) plus multiple git commands. Always wrap in `go func()` with `QueueUpdateDraw` for the DB persist + UI update. Close the form/modal first so the UI feels instant. See `handleNewTaskKey` and `executeFork` for the pattern.
- **New task with worktree shows a pending agent view during creation.** `enterPendingAgentView` switches to agent view with `agentPane.SetPending(true)` immediately after form close. The create goroutine's post-success `QueueUpdateDraw` checks `a.mode == modeAgent && a.agentState.TaskID == ""` to decide whether the user is still on the pending view. Empty `agentState.TaskID` is the pending-slot marker — `onTaskSelect` only sets it for concrete tasks.
- **Error handlers must guard `exitAgentView` with a mode+taskID check.** Calling `exitAgentView()` unconditionally would disrupt a session the user has since navigated to. Use `a.mode == modeAgent && a.agentState.TaskID == ""` (pending slot) before calling `exitAgentView` from `CreateAndStart` failure callbacks.
- **Don't call `startSession` on the created task after `CreateAndStart`.** The session is already live. `onTaskSelect` sees `runner.Get(task.ID) != nil && sess.Alive()` and skips auto-start. Calling `startSession` manually would hit the "session already exists for task" error and revert the task row to Pending.
- **Every task-delete entry point must call `agent.RemoveWorktreeAndBranch`, not just `db.Delete`.** Skipping it leaves the worktree dir on disk as an orphan; it only disappears later when `pruneCompletedTasks` runs the orphan sweep, making it look like task completion (not deletion) is what removed the worktree. The TUI's `App.deleteTask` does this correctly; the HTTP API's `handleDeleteTask` previously did not. Mirror the TUI pattern (background goroutine; `agent.ResolveDir(task, cfg)` for repoDir) when adding any new delete path.
- **Safe-name sanitization must strip `/` so worktree paths stay at exactly two levels under wtRoot.** `walkOrphanedWorktrees` is hardcoded to `wtRoot/<project>/<task>`. If a stored worktree path is deeper (e.g. `wtRoot/nexus/Rebase-https-/github` because a legacy task name had `https://...`), the walker matches the parent `Rebase-https-` against `knownPaths` (which holds the full deeper path), sees no hit, classifies it as an orphan, and `os.RemoveAll`s the entire subtree — including the live worktree of an active task. macOS keeps the running session alive with cwd-in-deleted-dir, so the failure surfaces hours later on resume as `worktree path missing`. `invalidBranchChars` now includes `/`, and `walkOrphanedWorktrees` defends with `firstKnownDescendant` — touch both if you change the wtRoot layout.
- **Project paths must be persisted absolute — a relative project path silently breaks worktree creation.** The daemon `chdir`s the project path for `git worktree add`, but its cwd is non-deterministic: the launchd plist pins `WorkingDirectory=$HOME`, while the TUI's auto-start fallback (`autostart_fork.go`) execs the daemon without setting `cmd.Dir`, so it inherits wherever `argus` was launched. A relative path like `Development/Personal/hera` "works" only when those happen to agree (both `$HOME`); from any other cwd it fails with `chdir …: no such file or directory` and the agent silently never spawns. The directory autocomplete (`dirCompletions` in `quickaddform.go`) used to emit relative matches for bare relative input (`parentDir = filepath.Dir(".")`), so accepting a completion stored a relative path. Fixed by absolutizing in `dirCompletions` (relative input resolved via `filepath.Abs`, trailing slash restored after `Clean` strips it) and authoritatively in `ProjectForm.pathValue` (always `filepath.Abs` the saved value).
- **`BuildCmd` must pre-flight `os.Stat(task.Worktree)`.** A missing `cmd.Dir` surfaces post-fork as `fork/exec /bin/sh: no such file or directory` — Go's `forkExec` reports the chdir failure using the exec path, masking the real cause. The worktree can be erased between task creation and start by the orphan sweeper, by `RemoveWorktreeAndBranch` on task delete, or by manual `rm -rf`. Pre-flight stat in `BuildCmd` returns a clear `worktree path missing: <path>` error before Go gets to the syscall. The check narrows but does not eliminate the race: concurrent removal between the stat and `cmd.Start` can still produce the original cryptic error in a narrow window.
- **All branch refs (`refs/heads/*` AND `refs/remotes/*`) are shared across every worktree of a repo — only `HEAD` is per-worktree.** `gitutil.findMergeBase` (the diff-view's branch-comparison base) used to fall back to the local `master`/`main` branch when no upstream was configured, which is the common case since `CreateWorktree` never sets up branch tracking. A local branch is exposed to an arbitrary rewrite (rebase, reset, amend) from any other worktree or the primary checkout, silently jumping every task's merge-base to a stale ancestor on the next 3s refresh and making the file diff view show files the task never touched. Fixed by trying remote-tracking branches (`upstream/master`, `origin/master`, `upstream/main`, `origin/main`) before the local fallback — remote-tracking refs are shared too (NOT worktree-isolated), but they only ever change via an explicit `git fetch`, a deliberate sync to real upstream state, not an arbitrary rewrite. Residual risk: if `origin/master` exists but hasn't been fetched recently in that repo, the diff base can resolve against a stale (but valid, non-empty) remote-tracking ancestor instead of falling through to a fresher local `master` — same failure mode, rarer trigger.
- **Bulk Hera cascade-nuke "crash" (silent freeze, no panic anywhere) was a synchronous-blocking-on-the-tview-goroutine bug, NOT a data race.** Ground-truth log mining (BUG-062) showed the TUI going totally silent for ~6.76s after deleting 6 coordinators + ~40 roles in a 6s window, then restarting — but a real repro under `go test -race` ruled out both suspected races: concurrent `RemoveWorktreeAndBranch` goroutines against a shared repo shell out to independent `git` subprocesses (no Go memory to race on — git-level lock contention degrades to logged non-fatal errors, not a panic), and `Session.Stop()`/`RemoteSession` never mutate anything a pane poller (`SyncPanes`) reads without its own lock. What actually reproduces: `heraReclaimAndArchiveTask` used to call `a.runner.HasSession`/`Stop` *synchronously* on the tview main goroutine once per nuked task — in a daemon-connected TUI that's a blocking RPC round-trip (possibly double-hopped through the session-supervisor), so a bulk cascade blocked Draw/input/tick for N × per-call latency with nothing to panic on (a freeze, indistinguishable from a crash to the operator). Fixed by backgrounding that call (`heraGoSafe`, mirroring the existing worktree-removal goroutine) — see `TestHeraCascadeNuke_BulkDeleteDoesNotBlockCaller`.
- **Concurrent `RemoveWorktreeAndBranch` calls against the SAME repo are now serialized per-repo (`agent.lockRepo`), not globally.** A bulk delete (Hera cascade, prune) fans out one goroutine per task; without a per-repo lock, dozens of concurrent `git worktree remove`/`prune`/`branch -D` calls can contend on that repo's shared `.git` lock files. The lock is keyed by `repoDir` (`sync.Map[string]*sync.Mutex`, entries never removed — the key space is the small set of configured repos) so unrelated repos still clean up fully in parallel; only same-repo work is bounded to one in-flight cleanup at a time. See `TestLockRepo_SerializesSameRepoParallelizesAcrossRepos`.
- **Detached cleanup goroutines (worktree removal, session stop) now recover their own panics via `heraGoSafe`.** Before this, a panic in `go func(){ agent.RemoveWorktreeAndBranch(...) }()` or the session-stop goroutine would crash the whole TUI process with no other backstop — the main goroutine's `recover` in `cmd/argus/main.go` only covers its own stack, not a detached goroutine's. `heraGoSafe` logs the panic + stack via uxlog and lets the goroutine end instead of taking the process down.
- **`hera_bindings` has no foreign key to `tasks`, so any bulk task-deletion path must explicitly exclude live-bound tasks or it silently orphans Hera roles.** `db.PruneCompleted` (Ctrl+R / `POST /api/maintenance/prune-completed`) used to `DELETE FROM tasks WHERE status='complete'` unconditionally, across every project — a live investigation found 16 of 140 currently-complete tasks still held a live (`ended_at IS NULL`) Hera binding, 5 of them not even archived (ordinary Projects-tab entries). Since nothing cascades a task delete into `hera_bindings`, confirming that prune would have deleted the task row, worktree, and branch (local + remote) while leaving the Hera role pointing at a task that no longer exists, instead of properly ending it. Fixed (`fix-prune-protects-hera-bindings`) by excluding `id IN (SELECT argus_task_id FROM hera_bindings WHERE ended_at IS NULL)` from both the SELECT and DELETE, and reporting the skip count (`PrunePlan.SkippedHeraBound`) through `uxlog` and a statusbar/toast notice on all three surfaces (local TUI, remote TUI, web SPA) so a bulk prune that skips work is visible, not silent.
- **`RemoveWorktree` must stop a worktree's devbox/process-compose dev stack (mysqld/redis-server/postgres/caddy) before deleting the worktree's files, or it leaks forever** (`fix-devstack-orphaning`). Argus has zero code that launches these — an agent session running `devbox services up` inside the worktree starts them, entirely outside argus's knowledge, and process-compose reparents to launchd (by design, to survive the launching shell exiting) the instant its parent session ends. A live investigation found 8/8 running `process-compose` instances already reparented, and 12 processes still running against worktrees already deleted from disk. Fixed via `internal/agent/devstack.go`'s `stopDevStackFor`, called from the one choke point every worktree-removal path already funnels through (`RemoveWorktree`): `pgrep`-scan the process table for the 5 known binary names, filter to an EXACT match on the extracted worktree root (not a substring — a sibling worktree whose name is a string-prefix, e.g. `Sherlock/3b` vs `Sherlock/3b-more`, must not get killed), SIGTERM every match directly, wait a grace period, SIGKILL survivors. Do NOT rely on `devbox services stop -c <dir>` for this: empirically it can hang 15+ seconds ("Ensuring packages are installed...") on a worktree whose devbox environment isn't fully materialized, unacceptable for a step that runs unconditionally on every removal. Do NOT rely on the process-compose supervisor cascading a signal to its children either — a sibling `redis-server`/`caddy` under the same supervisor was observed surviving SIGTERM to their parent while `mysqld` died; every matched process is signaled directly, not just the supervisor. The worktree-path extraction regex must exclude `=` AND `:` from the path prefix, not just whitespace — mysqld's `--datadir=<path>` and redis-server's `unixsocket:<path>` glue the flag directly onto the path with no space, and excluding only whitespace lets the flag text leak into the extracted path, silently breaking the exact-match comparison (caught via a live `argus doctor` smoke test, not a unit test — it reported real redis-server orphans with `unixsocket:/Users/...` as the "worktree path"). Known accepted limitation: extraction assumes exactly the `wtRoot/<project>/<task>` two-level layout (matching `WorktreeDir` and the orphan-sweep's `firstKnownDescendant` assumption); a legacy task predating the slash-stripping fix (see the safe-name-sanitization bullet above) with a deeper stored path won't exact-match and won't get its dev stack torn down — narrow and pre-existing, not introduced by this fix. `argus doctor` gained a matching read-only advisory check (`internal/doctor/devstack.go`) reporting any dev-stack process whose embedded worktree path no longer exists — never auto-kills, mirrors the Stop-hook/diligence-profile-library tri-state (Found/None/Unknown) pattern.
- **`CreateWorktree` fails on a repo with zero commits (unborn `HEAD`) unless it uses `--orphan`** (BUG-080). `resolveStartPoint`'s `"HEAD is always valid"` short-circuit is false the moment a repo is freshly `git init`'d with no commits — `git rev-parse --verify --quiet HEAD` fails, so `git worktree add -b <branch> <dir> HEAD` fails with `fatal: invalid reference: HEAD`, and the existing attach-to-existing-branch fallback fails identically since the branch was never created either. Adding a project never runs a git command (`db.SetProject` is pure SQL), so this only surfaces when the FIRST task is created. Fixed by checking `isUnbornRepo` (same `rev-parse --verify --quiet HEAD` check) up front and, when true, skipping fetch/`resolveStartPoint` entirely and building the command as `git worktree add --orphan -b <branch> <dir>` (no start-point). Requires git ≥ 2.42 for that path only; every other (non-empty-repo) path is unaffected.
