# Events ring + SSE stream — gotchas

## Emission MUST happen outside `db.mu`

`db.Add`, `db.Update`, `db.Rename`, `db.SetArchived`, `db.InsertMessage`, and `db.AckMessages` each emit via `events.Emit` AFTER releasing `d.mu`. The installed sink (`api.Server.Emit`) re-acquires `d.mu` inside `db.InsertEvent`, so emitting from a still-locked region deadlocks the entire DB. Every wired method uses a `*Locked` helper + post-unlock `events.Emit(...)` to keep the two phases separate. If you add a new emission site inside the `db` package, follow the same split — do NOT call `events.Emit` between `d.mu.Lock()` and the matching unlock.

## SSE handler subscribes BEFORE snapshotting `LatestEventID`

`internal/api/events_stream.go:handleEventsStream` subscribes to the bus first, then captures `replayEnd := db.LatestEventID()`, then replays `EventsSince(since, 0)`, then drains live events skipping any `ev.ID <= replayEnd`. Reversing the order (snapshot-then-subscribe) opens a window where an event committed mid-snapshot would be delivered twice (replay tail + live) or land out of order. The fence is the only thing keeping the stream lossless and dupe-free; don't reorder it.

## Do NOT build a hera reconcile loop on the events ring

The DB events ring is populated ONLY by the `api.Server` sink installed via `events.SetSink(apiSrv)` in `daemon.Serve` — and that runs only under `cfg.API.Enabled`. With the REST API disabled, `events.Emit` is a no-op (atomic nil sink), so any consumer reading from the ring silently sees nothing whenever the API is off. This is why `internal/heraadopt` re-derives from task + binding ground truth (its startup `ReconcileBindings` sweep keyed on task-row existence) instead of consuming the ring — independent of API state, inherently at-least-once and idempotent. There is no `events.Ring.Subscribe`; the only live consumer is the SSE handler in `internal/api`, which reads the DB ring via `EventsSince`. (The retired `depends_on` auto-adopt watcher consumed `link.created`-style events; it and `link.created` are both gone.)

## `events.SetSink` is global; tests must save/restore

The package-level sink is one atomic pointer. Tests that install a recording sink MUST register a `t.Cleanup` that restores the prior sink — otherwise a subsequent test inherits the recorder and sees events from unrelated work. `events.SetSink` returns the previous sink for this round-trip pattern.

## Ring eviction is based on `id` rank, not row count delete

`db.InsertEvent` evicts via `DELETE FROM events WHERE id NOT IN (SELECT id FROM events ORDER BY id DESC LIMIT eventsCapForTest)`. Using `NOT IN` rather than a row-count math keeps the AUTOINCREMENT counter intact — cursors stay monotonic across evictions, so a plugin reconnecting with `since=<old>` triggers the `resync` path correctly. A naive `DELETE FROM events ORDER BY id ASC LIMIT <overflow>` would work too but is harder to reason about under concurrent inserts; the current form is purely declarative against the desired post-state.

## Idle watcher runs unconditionally

`api.Server.New` starts `idleWatcher` even when `push == nil`. The watcher does two things: emits `session.idle` events (plugin-visible, always) and triggers Web Push (gated on `s.push != nil` inline). Before PR 2 this goroutine was push-gated; now the gate is per-call so plugins running on a daemon without push still see idle transitions. The `idleTransitioned` helper is a stateless predicate that reads `state.idleNow[id]` BEFORE the mutation inside `shouldFireIdlePush` — the two helpers must run in order (transition check, then push gate) because they share state.

## `task.completed` is emitted in addition to `task.status_changed`

When `db.Update` detects a status change to `StatusComplete`, it emits BOTH events (in that order). Plugins filtering on `task.completed` get a precise hook; plugins watching `task.status_changed` see the full transition stream. This double-emit is intentional — there is no "promote status_changed to completed" downstream; the contract is "both fire."

## `session.needs_input` is daemon-authoritative, idle-gated, and sticky

`api.Server.detectNeedsInputTick` (called each `idleWatcherTick`) scans idle sessions with the shared `agent.DetectNeedsInput` heuristic and publishes the set onto the runner (`SetNeedsInputIDs`) so `/api/tasks`' `needs_input` field is correct with NO TUI attached. Two invariants are load-bearing and non-obvious:

- **Idle-gate + sticky carry-forward, or the SSE events oscillate.** Detection only runs on idle tasks (a still-streaming agent that flashes `❯ 1.` transiently is not blocked). But Claude's prompt UI emits periodic animation bytes that briefly knock a blocked session OUT of the idle set — without the sticky pass in `computeNeedsInput` (re-check previously-flagged tasks that are still running), the flag and its `session.needs_input` events would flap every few ticks. Mirrors the TUI's `detectNeedsInputSticky`; do not drop either half.
- **Reads the session ring (`RecentOutputTail`), not the on-disk log.** The daemon is the sole PTY reader so the ring is always populated — correct without a TUI. The TUI's `detectNeedsInput` reads the disk log instead, because in daemon-client mode its local ring only fills after the user opens a stream. Same heuristic, different byte source by process.

One event type carries both edges: the payload `{"needs_input":true|false}` distinguishes enter from clear (there is no separate "cleared" type). `state.needsInputNow` is replaced wholesale each tick, so an exited session (absent from running/idle) drops out of the set and fires a clear event via the diff automatically.

## A never-idle session parked at a prompt is flagged via content stability, NOT idle (BUG-032)

The idle gate alone misses a session that sits at a prompt while emitting continuous redraw/animation bytes (spinner, cursor blink, alt-screen repaint): each byte bumps `Session.lastOutput`, so `IsIdle()` never fires, the session never enters the idle set, and the idle-gated detector never scans it once — so the sticky carry-forward (which only re-checks already-detected sessions) can't rescue it either. The fix: `computeNeedsInput` adds a **content-stability pass** that scans RUNNING (not just idle) sessions and flags one when the **unambiguous selection-widget** signal is present AND `agent.ContentFingerprint(tail)` is unchanged from the previous tick. Two guards together prevent false-positiving a busy agent: (1) the pass gates on `agent.DetectSelectionPrompt` (the `❯ 1.` cursor / chooser footer), NOT the full `DetectNeedsInput` — the fuzzy trailing-question heuristic (`endsInQuestion`, last line ends in `?`) is reliable only behind the idle gate, and this pass removes that gate, so it must use the stricter signal; (2) the fingerprint strips animation chrome (`fingerprintVolatileLine`: spinner/timing `decorationLine`s + the leading-`❯` input/cursor line) and de-duplicates repaint frames, so a **streaming** agent's meaningful content changes every tick → fingerprint differs → never flagged, while a **parked** agent's content is stable → flagged on the 2nd qualifying tick. The idle and sticky passes still use `DetectNeedsInput` (the question heuristic is safe behind their idle gate — unchanged behavior). `idleWatcherState.contentFP` carries fingerprints tick-to-tick. `Session.IsIdle()` and the idle-push / `session.idle` paths are deliberately untouched — only the needs-input detector gained the pass. The TUI mirror (`detectNeedsInputSticky`, fingerprints on `App.needsInputFP`) applies the same pass over the disk-log tail; keep the two in lockstep.

## Needs-input sticky flag clears on input-delivered-or-archive, NOT on signal decay (BUG-034)

**A free-text-question flag (`endsInQuestion`) leaves its `?` in the 16 KB tail forever, so the entry heuristic re-matches every tick — the flag MUST be cleared by an explicit condition, never by waiting for the question to scroll out or by elapsed/idle time.** The flag persists indefinitely while the signal is present (desired: an away user wants to see a waiting agent) and clears ONLY when (a) the user delivers new input to THAT session after the flag was raised, or (b) the task is archived. The clear is deterministic via `agent.NeedsInputClear(candidates, prevBaseline, lastInputOf, archivedOf)`: it freezes the session's `LastInput()` timestamp observed when a task first entered the set (its "baseline") and drops the task once `lastInputOf(id)` advances past that baseline — so it fires **even while the stale `?` still matches the tail** (the crux), and does NOT depend on content changing. The baseline is dropped when the task leaves the candidate set (signal gone), so a fresh question after the response re-arms it. Input to a DIFFERENT session never clears this one (per-session baseline). Both detectors call the SAME helper and carry a `needsInputSince` map: the daemon (`computeNeedsInput`, `idleWatcherState.needsInputSince`, `lastInputOf` = `runner.Get(id).LastUserInput()`, `archivedOf` from `db.Tasks()`) and the TUI (`detectNeedsInputSticky`, `App.needsInputSince`, `lastSessionInput` via the local handle, `archivedTaskSet` from `a.tasks`). **Authority caveat:** the daemon's `runner.Get(id).LastUserInput()` is authoritative for ALL USER input surfaces (TUI socket / REST funnel through the daemon's single supervisor-client handle); the TUI's local `LastUserInput()` only sees input sent through ITS OWN agent pane — cross-surface input (e.g. the user answers via the PWA while watching the TUI) clears in the TUI via the natural log-content change (the new output replaces the `?` as the last line → `endsInQuestion` false), not the deterministic baseline path. Entry heuristic, idle gate, sticky pass, and the BUG-032/033 guards are unchanged — this governs only signal REMOVAL.

**The clear filter MUST read `LastUserInput()`, NEVER `LastInput()` (BUG-034 regression fix).** `LastInput()` is advanced by EVERY `WriteInput`, including reliable-notify pane delivery (`internal/notify` writes `Ctrl+U`+text+`CR` for hera/task messages). A coordinator message reliably delivered to a parked, idle worker is SYSTEM input, not the user answering the prompt — so wiring the clear filter to `LastInput()` (the original BUG-034 implementation) made any delivered message permanently clear the worker's autonomous `(?)`, silently regressing the BUG-032/033 alt-screen detection for every hera worker. Fix: a session tracks `lastInput` (any write) AND `lastUserInput` (user keystrokes only); the user-facing `WriteInput` advances both, the system path `WriteInputSystem` advances only `lastInput` (so the idle-push gate still sees new work), and notify delivery uses `WriteInputSystem`. The clear filter reads `LastUserInput()`; the idle-push gate keeps reading `LastInput()`. `WriteInputSystem`/`LastUserInput` are on `agent.SessionHandle` + `notify.SessionHandleIface` (impl by `*agent.Session`, `*client.RemoteSession`, `*apiclient.Session`).

## The never-idle pass flags FREE-TEXT questions only when the agent is AWAITING input, not working (BUG-035)

**On a fullscreen (alt-screen) agent `Session.IsIdle()` is never true (continuous repaint bumps `lastOutput`), so the idle-gated pass — the only one that honors `endsInQuestion` — never runs for it; the never-idle content-stability pass deliberately excluded `endsInQuestion` (BUG-032), so a fullscreen worker parked at a free-text question ("Should I go ahead? (yes/no)") was caught by NEITHER pass and never surfaced `(?)`.** Fix: the never-idle pass (`agent.AwaitingInputFingerprint`, replacing `SelectionPromptFingerprint`, used by both `computeNeedsInput` and `detectNeedsInputSticky`) additionally flags a free-text trailing question on the EMULATED screen — BUT gated on the ABSENCE of Claude's "working" affordance. **Content stability ALONE is NOT a sufficient guard for `endsInQuestion`** (the BUG-032 reviewer proved this: a busy agent that narrates a `?`-ending line then stalls on a spinner frame for ~2 ticks is content-stable AND ends in `?` → would falsely flag). The load-bearing discriminator is `needsInputWorkingRe` (`(?i)(?:esc|ctrl-c|ctrl\+c) to interrupt`): Claude renders this interrupt hint WHILE generating and REMOVES it at the idle input prompt, so `awaitingInputText` = (selection widget) OR (`endsInQuestion` AND working-affordance ABSENT). The selection-widget branch needs no such gate (a streaming agent flashing it is caught by the fingerprint). **Do NOT swap the never-idle pass to `detectNeedsInputText`/`DetectNeedsInput`** — that re-introduces the exact BUG-032 false positive. `Session.IsIdle`/`IsActive`/spinner precedence/idle-push are untouched; this is a local emulated-screen discriminator inside the needs-input pass only. The idle and sticky-carry-forward passes still use `DetectNeedsInput` (the question heuristic is safe behind their idle gate). **Uncertainty flagged for live dogfood:** that the real Claude working frame always contains "esc to interrupt" (vs a spinner-only working frame with no interrupt hint, which would re-break BUG-032).

**Selection detection matches ANY numbered option + a wording-tolerant chooser footer (BUG-035 GAP B).** `needsInputSelectionRe` was broadened from `❯[ \t]*1\.` to `❯[ \t]*\d+\.` so a permission cursor the user navigated to option 2/3 still matches (anchoring on "1." missed it). `needsInputChooserFooterRe` was widened to `(?i)(?:enter|⏎|↵) to (?:select|confirm|choose)[^\n\r]*esc to` — an Enter-action affordance and an Esc-action affordance on the SAME line, tolerant of verb drift across Claude releases, case, and `·`/`↑↓` separators; a lone affordance or the two split across lines still does not fire. These are unambiguous widgets → safe, no false-positive guard needed.

## Idle/active is CONTENT-aware for fullscreen agents, computed off `Session.IsIdle()` (BUG-036)

**A fullscreen (alt-screen) agent parked at its prompt never goes raw-idle (`Session.IsIdle()` keys off `lastOutput`, which continuous repaint bytes bump forever), so the Hera rail spinner (`RoleView.IsActive`) animated forever and idle-push never fired for it.** Fix: a content-idle signal, `agent.ContentIdle(running, rawIdle, tailOf, sizeOf, screen, prev, now)` — a running session NOT already raw-idle whose animation-stripped EMULATED-screen fingerprint (`ContentIdleFingerprint` over `fingerprintText`, the BUG-033 `ScreenRenderer` reused) is UNCHANGED for ≥ `idleThreshold` AND shows no "working" affordance (`needsInputWorkingRe`, "esc to interrupt"). **Both guards are load-bearing**: content stability ALONE would false-idle a thinking agent stalled on a spinner frame (the spinner line is volatile-stripped from the fingerprint), so the working-affordance ABSENCE is required (same discriminator as BUG-035); and a streaming agent's content changes tick-to-tick so its stable-since timer resets. Threshold-based timer (stable-since wall-clock, not a tick count) so it honors `idleThreshold` at any tick cadence (daemon 5s / TUI 1s). `ContentIdle` always fingerprints the EMULATED screen (raw never stabilizes for fullscreen; BUG-033) and SKIPS raw-idle sessions (already idle).

**`Session.IsIdle()` itself is deliberately UNCHANGED — content-idle is a parallel, tick-computed signal, NOT folded into `IsIdle`.** `IsIdle` is a stateless, cross-process (daemon↔supervisor RPC), widely-consumed predicate; content-idle is inherently stateful (fingerprint history + a stability timer + an emulator) and belongs on the watcher/TUI tick. This mirrors the existing dual daemon/TUI needs-input detector rather than mutating the shared method, so reliable-pane delivery (`notify` gates on raw `IsIdle()`), the resize-kick gate, and `/api/tasks` keep their raw-idle semantics. Two callers, ONE helper: the daemon (`idleWatcherTick` → `agent.ContentIdle`, `idleWatcherState.contentIdle`, reusing `state.screen`) folds it into `idleSet` for idle-push + `session.idle`; the TUI (`refreshTasksWithIDs` → `agent.ContentIdle`, `App.contentIdle`, reusing `needsInputScreen` over the disk-log tail) unions it with `idleIDs` and feeds `HeraPage.SetSessionIdle` → `RoleView.SessionIdle` → `IsActive() = Live && in_progress && !SessionIdle`.

**Idle-push fires EXACTLY ONCE on the content-idle transition — the once-only guarantee is `shouldFireIdlePush`'s per-work-cycle gate, NOT content stability.** Content-idle is OR'd into the push `idleSet`, so a fullscreen agent's busy→content-idle edge fires one push; the existing gate (no re-push until `LastInput()` advances past the last `pushedAt`) means a re-asserted content-idle signal cannot storm, and a never-input session (autonomous worker) never fires (the input-presence gate). Non-fullscreen agents are already in the raw `idleSet`, so behavior is unchanged. **The TUI task-list spinner (`TaskStatusIcon`) shares the same raw-idle root but was deliberately left unchanged (out of scope; the Hera rail was the reported surface).**

## Needs-input / selection detection must match the EMULATED screen, not `StripANSI(raw)` (BUG-033)

**`sanitize.StripANSI` removes escape sequences but does NOT apply cursor positioning, so a FULLSCREEN (alt-screen) agent's prompt is invisible to a raw-text match.** Claude paints an alt-screen prompt with cursor-addressed in-place redraws — the `❯` cursor and `1.` first option are separated by (or reordered relative to) CSI cursor-moves, so after strip they aren't linearly adjacent and `❯[ \t]*1\.` never matches. The session is then never flagged needs-input until the user opens the pane and `ForceResyncPTY`→SIGWINCH forces a linear repaint. Fix: `agent.DetectNeedsInputScreen` / `agent.AwaitingInputFingerprint` (was `SelectionPromptFingerprint` pre-BUG-035) reconstruct the visible screen via a vt emulator sized to the session's PTY dims and re-run the SAME regexes/fingerprint against the rendered text. **Raw match stays the fast path** (linear agents byte-identical, emulator untouched); emulate only on a raw miss. The content-stability fingerprint is computed over the emulated screen for alt-screen (a parked screen is naturally stable; raw bytes never are), preserving the BUG-032 streaming false-positive guard. **Reuse ONE `agent.ScreenRenderer` per detector context** (`idleWatcherState.screen`, `App.needsInputScreen`) — it drives one drain goroutine for its lifetime and resets via RIS between renders; allocating-and-`Close`-ing a fresh drained emulator per render races the unlocked drain `Read` against `Close` under `-race` (see `terminal.NewDrainedEmulator`'s lifecycle note). Size comes from the session-size sidecar (`agent.LoadSessionSize`, a non-blocking local file read — safe on the tview main goroutine, unlike `PTYSize()`), falling back to 80×24.

## A never-converging content fingerprint escalates via a bounded consecutive-tick counter, NOT by loosening the chrome allowlist (BUG-029)

**The BUG-032 content-stability pass requires the FULL fingerprint to match across exactly two consecutive ticks — any line that legitimately varies tick-to-tick but isn't one of the two recognized chrome shapes (`fingerprintVolatileLine`'s `decorationLine`/leading-`❯`) permanently defeats that match, so a genuinely-parked session can be flagged "active" forever** (rail spinner never stops, `(?)` never appears) if its tail happens to carry ANY other varying content — an unrecognized status/timer/counter line from some other rendering path, or genuinely new but irrelevant output still streaming elsewhere in the 16 KB window. This was reproduced live: a worker parked at a permission prompt for HOURS, only flipping to `(?)` the instant the user manually focused it (which triggers `ForceResyncPTY`, coincidentally landing on a settled frame — not a real fix path).

The fix does **NOT** loosen `fingerprintVolatileLine`/`decorationLine` (that allowlist is shared, load-bearing logic behind BUG-032/033/035/036; loosening it risks reintroducing the false-positive class those bugs fixed). Instead it adds a **separate, bounded escalation path** at both call sites: `agent.ParkedSelectionSignal(r, buf, cols, rows)` reports whether the tail (raw-first, emulated-screen fallback — same pattern as `AwaitingInputFingerprint`) shows the UNAMBIGUOUS selection-prompt widget (`detectSelectionPromptText`) with the "working" affordance (`needsInputWorkingRe`) ABSENT — deliberately narrower than `awaitingInputText`, since only the unambiguous selection shape is trusted to escalate on its own (a free-text trailing question is not). `agent.EscalateParkedSelection(prevTicks, qualifies)` is a pure step function: a qualifying tick increments a per-session counter, and escalation fires once the counter reaches `agent.NeedsInputEscalationTicks` (currently 8, tuned in the 5-10 range: long enough that a transient/coincidental match — e.g. scrolling a `❯ 1.`-looking line while still generating — can't misfire, short enough to bound the worst case from "forever" to "~N ticks"). **The original design reset the counter to zero on ANY non-qualifying tick — BUG-060 (below) replaced the all-or-nothing reset with a one-tick grace period; a single non-qualifying tick no longer discards an ongoing streak.**

Both call sites carry the counter forward exactly like the existing fingerprint/since maps (rebuilt fresh each tick from the currently-running set, so a task that stops running or breaks the streak is dropped, not leaked): `ContentIdleState.esc` (used by `agent.ContentIdle`, ORs into the `idle` return alongside the existing wall-clock `idleThreshold` check) and `App.needsInputEscalation` (used by `detectNeedsInputSticky`, calls `flag(id)` alongside the existing 2-tick fingerprint match). Both are computed from the SAME already-fetched tail/renderer as the existing fingerprint call at that site — a second `ScreenRenderer.render` per tick for a candidate session, consistent with the existing double-render cost profile (each tick already re-renders separately for needs-input AND content-idle). This is a genuinely SEPARATE path: it does not change what `ContentFingerprint`/`fingerprintText` themselves compute, and new genuinely-varying transcript content still does not converge the ordinary fingerprint (that guard is untouched) — escalation is purely an additional way to recognize "parked" when the fingerprint path structurally cannot.

## The BUG-029 escalation counter's all-or-nothing reset made it fragile against an isolated single-tick miss — a genuinely parked hera worker could NEVER escalate (BUG-060)

**`EscalateParkedSelection`'s original reset-to-zero-on-any-miss policy assumed a broken streak only happens when the session stops being parked — but a genuinely, continuously-parked session can still produce an ISOLATED single-tick miss** from two real sources: (1) Claude's own fullscreen redraw can blink the `❯` selection-cursor glyph off for a single frame as a visual animation, and (2) `readSessionLogTailBytes` has NO synchronization with the daemon's concurrent `logFile.Write` in `readLoop` (`internal/agent/session.go`), so an occasional read can land on a torn/partial frame mid-redraw. Live bug-bash repro (real dogfood session, 4 screenshots): under one coordinator with 3 sibling hera workers, the FIRST sibling to hit a permission prompt correctly surfaced `(?)` (on itself and rolled up to both ancestors); LATER siblings that hit their OWN permission prompt — same UI shape, same code path — never did, even though the Agent pane clearly showed the live, unanswered prompt. The reported "first sibling always, later siblings never" asymmetry was **not** about ordinal position or a shape the detector didn't recognize (all 4 prompts were identically-shaped, and the first was detected fine) — it was luck: whichever sibling's tick cadence happened to land on ≥`NeedsInputEscalationTicks` (8) **CONSECUTIVE** clean ticks converged; any sibling whose stream hit even one isolated miss within that window had its counter reset to zero and had to restart the wait from scratch — and if misses recurred often enough (e.g. one every 3 ticks), the counter could **never** reach 8, a permanent miss, not merely a delay.

**Fix: a non-qualifying tick that follows an ONGOING streak is held in a one-tick GRACE period instead of being discarded**, encoded as a negative sentinel on the SAME `int` (no map-value-type change needed): `EscalateParkedSelection` returns `-prevTicks` when the streak's first miss occurs, preserving the magnitude. The very next tick either resumes the streak in full (qualifying again negates `-prevTicks` back to the positive streak length and increments by one — full recovery, not a restart from 1) or, if it ALSO misses, confirms a genuine break (two CONSECUTIVE non-qualifying ticks reset to zero for real — the original anti-false-positive guarantee is unchanged: a busy/streaming agent showing only sparse, isolated coincidental matches still never accumulates credit, because each such match is surrounded by 2+ misses that confirm the non-parked state). **A grace tick's `escalated` return also STAYS true if the streak had already crossed the threshold before the miss** — otherwise an already-flagged worker would visibly flicker `(?)` off for the one tick a blip is being confirmed or forgiven, then back on the next tick, which is what the sticky carry-forward pass alone could not prevent (its own single-shot `DetectNeedsInputScreen` re-check has the identical isolated-miss fragility, so it cannot rescue a grace-covered miss the escalation pass didn't also cover).

Both callers (`internal/tui/app.go`'s `detectNeedsInputSticky` and `internal/agent/needsinput.go`'s `ContentIdle`) had a pre-existing `if newTicks > 0 { store }` guard around persisting the counter into its map — correct under the old design (a miss always returned exactly `0`, and a missing map key already reads back as `0`), but it silently DROPPED the new negative grace sentinel, defeating the fix if left unchanged. Both were updated to `if newTicks != 0`. See `TestEscalateParkedSelection` (`internal/agent/needsinput_test.go`) for the full state-machine pin (isolated-miss recovery, already-escalated-stays-escalated, two-consecutive-misses-confirms-a-break, sparse-matches-never-accumulate) and `TestBUG060_Integration_*` (`internal/tui/bug060_integration_test.go`) for the end-to-end rail-render repro (a continuously-parked worker with a periodic blink-off frame, and two hera siblings sharing the single App-level `agent.ScreenRenderer` within one tick, converging independently).

## A fixed-size tail window can be flooded PERMANENTLY by Claude's blinking-cursor redraw, not just occasionally torn (BUG-061)

**BUG-060's "torn read" theory (source (2) above) was plausible but incomplete — live repro (three throwaway hera workers driven to a real Bash permission prompt, on-disk logs read directly and re-run through the production detectors) showed a DETERMINISTIC, not probabilistic, miss: `DetectNeedsInputScreen`/`ParkedSelectionSignal` returned `false` on 100% of 6 read-rounds sampled over 9 seconds.** The cause: Claude Code renders a blinking cursor/status glyph even while genuinely parked at a prompt with the "esc to interrupt" working-affordance correctly absent — a fixed ~130-byte cursor-reposition + 24-bit-color + single-glyph redraw (observed toggling a space and `⏺` at one screen position), repeating forever, never stopping. `needsInputTailWindow`/`detectNeedsInputTailBytes` (16 KB) scan only the last 16 KB of raw bytes — given enough real time, this redraw alone exceeds that window and pushes the actual prompt render permanently out of reach: on one still-open repro session, the last occurrence of "proceed" in the on-disk log sat at byte offset 21896 while the file had grown to 59436 bytes (37 KB+ behind) after roughly 4 minutes parked. The gap only grows — this is why a session could stay stuck "for HOURS" (BUG-060's own repro) and why no amount of escalation-counter tuning can fix it: escalation (`EscalateParkedSelection`/`ParkedSelectionSignal`) requires the raw per-tick signal to be true SOMETIMES; once the window floods it is false ALWAYS, permanently, not intermittently. Selecting a row "fixes" it only because `ForceResyncPTY` forces an unconditional resize (even to the same size) → SIGWINCH → Claude repaints the ENTIRE current screen fresh → those new bytes land at the tail end of the log → the very next tick's 16 KB read contains the complete repaint and matches immediately — the coincidental "settled frame" BUG-060 already flagged as **not a real fix path**, now explained precisely.

**Fix: `agent.SubstantiveTail` (`internal/agent/needsinput.go`) replaces the flat "last N raw bytes" read with an expand-on-degenerate-tail read.** `degenerateSuffixStart` recognizes a long run — ending at the very end of a buffer — of some short byte sequence (≤`blinkMaxPeriod`=512 bytes) repeating at least `blinkMinRepeats`=6 times (a cheap, bounded-cost check over a `blinkProbeWindow`=4096-byte probe, THEN a linear backward walk to find the run's true start); `TrimToSubstantiveTail` drops that trailing run. `SubstantiveTail(readN, wantBytes, maxBytes)` calls `readN` with doubling sizes (capped at `NeedsInputMaxExpandBytes`=2 MiB) until the trimmed result has real content or the cap/source is exhausted, then returns the last `wantBytes` of that real content — so the EXISTING 16 KB-capped detection/emulation functions receive a window anchored on genuine content instead of literal EOF, with **zero added cost in the common case** (an actively-producing session's tail is never degenerate, so the check fails fast on the first probe and no expansion happens). Both consumers of the shared heuristic were wired through it: the TUI's `readSessionLogTailBytes` (`internal/tui/app.go`, reading the on-disk log — `readSessionLogRawTail` is now the flat-read primitive it wraps) and the daemon's Web Push watcher (`internal/api/push.go`'s `tailOf`, reading the in-process ring buffer, naturally capped by the ring's own 256 KB `defaultBufSize`). The periodicity check operates on RAW bytes (not ANSI-stripped text) so it is agnostic to the specific glyph/escape sequence Claude uses — it will keep working if the blink animation's exact rendering changes.

**Companion fix: the sticky carry-forward pass in both `detectNeedsInputSticky` and `computeNeedsInput` no longer re-requires a fresh tail match to keep a previously-flagged task flagged** — it now stays flagged unconditionally once running, and `agent.NeedsInputClear` (BUG-034: real user input past baseline, or archive) is the ONLY way it clears. The old re-match requirement meant a row correctly flagged on a lucky tick could silently lose `(?)` on the very next tick once the window flooded — indistinguishable, at that layer, from a genuine answer. This does not weaken BUG-034's clear semantics (nothing here changes when a real answer is detected), it only removes a SECOND, unintended clearing path that fired on a tail-content quirk rather than a real answer.

**Do not re-attempt this class of bug as "retune the escalation grace period again."** BUG-029 and BUG-060 both correctly diagnosed real, narrower defects in the escalation counter's tick-to-tick bookkeeping, but neither could fix a signal that is structurally ABSENT from the scanned window rather than merely flickering — the counter never gets a qualifying tick to escalate from. Always verify against a REAL live repro (spawn a throwaway session, drive it to the exact prompt shape, read its actual on-disk log/ring tail and run the production detectors against it) before assuming the fix lives in `EscalateParkedSelection`'s state machine.

## A cleared needs-input flag can get PERMANENTLY re-stuck by a stale re-candidacy after a candidacy gap (BUG-063)

**`agent.NeedsInputClear`'s per-candidate baseline map is rebuilt from scratch every call, scoped ONLY to that tick's `candidates` list — so the baseline is forgotten the instant a task drops out of candidacy, even for a single tick.** A cleared task normally stays out of candidacy forever (correct: the user answered). But `detectNeedsInputSticky`'s content-stability fingerprint pass and BUG-029/060 escalation pass (and `computeNeedsInput`'s fingerprint pass on the daemon side) scan every RUNNING session each tick independent of candidacy — that is what lets a never-idle session get flagged in the first place. If, on some LATER tick, one of those passes re-presents an ALREADY-CLEARED task as a candidate because its tail still shows the same stale, already-resolved content (a rendering/log-write catch-up lag, or a widget that hasn't visually cleared yet) — with `lastInputOf(id)` unchanged since the real clear — `NeedsInputClear` had no way to tell this apart from the task's first-ever candidacy: it recaptured `baseline = lastInputOf(id)`, and `lastInputOf(id).After(baseline)` can never become true when compared against itself. The task stuck in the candidate set until the user produced a strictly NEWER timestamp — explaining the reported symptom exactly: "clears briefly [when idle-gated re-detection first flags then baseline-clears within the same tick], flaps back [a later stale re-candidacy after a gap], needs a fresh nudge [`ForceResyncPTY` forces a full repaint, which can coincidentally change the fingerprint enough to stop the stale match for a while], sometimes flaps again [the repaint eventually settles back to visually-identical content]." Both hera rail row kinds hit it identically — `RoleView.NeedsInput` (`internal/tui/hera/model.go`) is just the same daemon/TUI-published needs-input set filtered by task ID, no separate coordinator path.

**Fix: `agent.NeedsInputClear` gained a `running []string` parameter (a superset of `candidates`, both callers already have it) and a `prevCleared`/`newCleared map[string]time.Time` "cleared marker" threaded alongside the existing baseline map.** When a real clear fires, the `lastInputOf` value at that moment is recorded as the task's cleared marker. Unlike the baseline map, the cleared marker is carried forward for every ID in `running` regardless of whether it is a candidate THAT tick — closing the exact gap that let a stale re-candidacy recapture a stuck baseline. A later candidacy is checked against the marker BEFORE the ordinary fresh-baseline path: if `lastInputOf(id)` has not advanced past the marker, the candidacy is stale and is suppressed outright (no baseline recaptured, not added to `out`); a genuinely NEWER `lastInputOf(id)` fails that check on its own — no explicit expiry needed — and falls through to re-arm normally. The marker is dropped (not carried into `newCleared`) when a task is archived or leaves `running`, mirroring the baseline's existing archive-drop behavior, so a restart or un-archive re-arms cleanly. Scoping the marker's lifetime to `running` (rather than tracking indefinitely, or a fixed tick-count cooldown) needs no new tunable constant and is self-pruning — mirrors the SAME rebuilt-fresh-from-a-running-set idiom this file already uses for `needsInputFP`/`needsInputEscalation`/`ContentIdleState`.

**Accepted, deliberate scope limit:** this cannot distinguish "the exact same already-answered content re-detected" from "a second, textually distinct, still-unanswered prompt that happens to arrive with `lastInputOf(id)` unchanged" (e.g. the agent shows a second permission prompt immediately after the first is answered, before the user types anything else) — both present as the same task ID at the same timestamp, and `NeedsInputClear` has no visibility into content, only (ID, timestamp). This was evaluated and accepted rather than threading a content fingerprint into the clear/suppress decision (a larger, riskier change to a pure/heavily-tested function's contract) because BUG-063 was a confirmed, frequently-hit PERMANENT stuck bug, while the traded-off scenario is bounded (the flag surfaces the moment ANY newer input reaches that session, and the user can still see the live prompt by opening the pane). See `openspec/changes/archive/*-fix-bug-063-needsinput-stuck/design.md` for the full trade-off analysis; a content-fingerprint-aware refinement is a named follow-up, not required by this fix.

Both callers were updated in lockstep and carry the state the same way as the other per-tick maps in this file: `internal/tui/app.go`'s `detectNeedsInputSticky` (`App.needsInputCleared`, threaded alongside `App.needsInputSince`) and `internal/api/push.go`'s `computeNeedsInput` (`idleWatcherState.needsInputCleared`). See `TestNeedsInputClear`'s `BUG-063` subtest (`internal/agent/needsinput_test.go`) for the state-machine pin, and `TestDetectNeedsInputSticky_BUG063_StaleReflagDoesNotReStick` / `TestComputeNeedsInput_BUG063_StaleReflagDoesNotReStick` for the end-to-end repro through the real caller (clear → gap tick with no candidacy → stale re-candidacy at the same timestamp → must not re-stick, across multiple subsequent ticks, until a genuinely newer input arrives).

## A hera coordinator's relayed answer can never clear the needs-input flag through BUG-034's own clear path — only demonstrated SUSTAINED resumed activity can (BUG-065)

**BUG-034's clear-on-input filter deliberately reads `LastUserInput()`, never `LastInput()`, specifically so a coordinator's reliable-notify delivery (`WriteInputSystem`) does not falsely clear a genuinely-parked worker's `(?)`.** That guard is correct on its own terms, but it has a blind spot the BUG-034 design didn't anticipate: when the coordinator's relayed message actually **is** the human's real answer to the exact question that raised the flag, and the worker visibly resumes real work afterward (running shell commands, ticking off task checkboxes — sustained, genuine activity, confirmed live via a screenshot repro on orchestrator "old-sherlock-cli", node "1a-clicore"), there was still no path back to clearing the flag: `WriteInputSystem` never advances `LastUserInput`, the BUG-061 sticky pass keeps a flagged task flagged unconditionally once raised (no re-match required), and needs-input `(?)` OUTRANKS the `IsActive` spinner in `RoleStatusIcon`'s precedence (BUG-A/BUG-F, see gotchas/hera-view.md) — so the rail showed `(?)` on a task that was provably no longer waiting on anyone, forever, until the task was archived.

**Fix: `agent.NeedsInputClear` gained a third clear condition, `resumedOf func(string) bool`, alongside the existing `lastInputOf`/`archivedOf` — sitting between them in priority (user-input clear, then resumed-activity clear, then the ordinary baseline/candidate path) and reusing the SAME `newCleared` cleared-marker mechanism as the user-input clear, so it inherits the BUG-063 stale-recandidacy guard for free (no separate bookkeeping needed).** `resumedOf` is fed by a new pure step function, `agent.ResumeActivityTick(prevTicks int, workingNow bool) (newTicks int, resumed bool)`, structurally the mirror image of `EscalateParkedSelection` (BUG-029/060) but for the OPPOSITE direction: it counts CONSECUTIVE ticks a flagged session shows Claude's "working" affordance (`ContentIdleFingerprint`'s `working` return — the same "esc to interrupt" discriminator BUG-035/036 use for "genuinely generating or executing a tool") and reports `resumed=true` once the streak reaches `agent.NeedsInputResumeTicks` (5). **Unlike `EscalateParkedSelection`, there is deliberately NO grace period on a miss** — the risk asymmetry runs the other way here: clearing too SLOWLY (the flag lingers a few extra ticks after a genuine resume) is safe, while clearing a still-stuck agent is not, so a single non-working tick resets the streak to zero outright, even one tick before threshold. This is also why a brief single-utterance acknowledgment from an agent that is still genuinely blocked ("still waiting on X", a few seconds of `working=true` while composing, then re-parking at the same or a new prompt) cannot cross the threshold before the streak breaks.

Both callers compute the per-session streak the same way the BUG-029 escalation counter is computed — over every RUNNING session each tick, independent of candidacy, using the SAME already-fetched tail/cols/rows the other passes in that tick use — and thread the counter map exactly like the other per-tick maps in this file: `internal/tui/app.go`'s `detectNeedsInputSticky` (`App.needsInputResume`) and `internal/api/push.go`'s `computeNeedsInput` (`idleWatcherState.needsInputResume`, `computeNeedsInput`'s signature grew a `prevResume map[string]int` parameter and a 5th `newResume` return value — every existing call site, including tests, needed the extra threaded argument). See `TestResumeActivityTick` (`internal/agent/needsinput_test.go`) for the step-function pin (threshold-exact escalation, no-grace immediate reset, sparse-ticks-never-accumulate), the `NeedsInputClear` "resumed activity" subtests for the pure-function clear-path pin (including its own BUG-063 interaction), and `TestComputeNeedsInput_ResumedActivityClears` / `TestDetectNeedsInputSticky_ResumedActivityClears` (with their `..._BriefBurstDoesNotClear` regression-guard siblings) for the end-to-end repro through the real callers: `lastInputOf` frozen for the whole scenario (modeling `WriteInputSystem`-only delivery) while the tail sustains the working affordance for `NeedsInputResumeTicks` ticks — clears; the same setup for one tick short of the threshold, then reverting to the identical blocking prompt — stays flagged.

**The resumed-activity clear path is entry-heuristic-agnostic by construction — it never inspects which signal originally raised the flag, only whether `working` has since been sustained — and this is verified with an explicit repro per entry shape, not left to that reasoning alone.** `TestComputeNeedsInput_ResumedActivityClears_ChooserFooter` (+ its `..._BriefBurstDoesNotClear_ChooserFooter` sibling) pins the SAME clear/no-clear behavior for a flag raised by Claude's `AskUserQuestion` tool-call chooser widget (`needsInputChooserFooterRe`, no `❯ N.` glyph — distinct from the numbered permission-check selection shape `TestComputeNeedsInput_ResumedActivityClears` already covers), and `TestComputeNeedsInput_ResumedActivityClears_FreeTextQuestion` pins it for a plain conversational trailing question (`endsInQuestion`, entered via the BUG-032 content-stability pass rather than the idle-gated pass) — confirming all three of the codebase's needs-input entry shapes clear identically once sustained resumed activity is observed.

## BUG-063's own accepted scope limit resurfaces in a multi-question AskUserQuestion/brainstorm flow — a SEPARATE, pre-existing bug from BUG-066, not a regression (BUG-067)

**Live repro, same day as BUG-066/#904 (orchestrator "sketch-handoffs", roles `12a-blueprint-ui-lifecycle`/`13a-blueprint-restore-version`, both freshly-spawned `/brainstorm` sub-coordinators): both roles' rail `(?)` correctly appeared, then both went "dormant" within ~2 minutes while GENUINELY still parked on an unanswered `AskUserQuestion` chooser (confirmed live: the pane showed "Question 2 of 3" with a numbered `❯ 1.` widget, prompt empty, session not working).** Investigated as a possible #904 regression (that PR's `autoClearBlockedHeraRoles` reuses the SAME shared `agent.ScreenRenderer`/`ContentIdleFingerprint` machinery `detectNeedsInputTick`/`detectNeedsInputSticky` use) — ruled out by reading the live DB directly: neither role had ANY `hera_role_status` row at all (the self-reported-blocked pass never touches a role that never called `hera_status`), and a synthetic test running both passes in the same tick against the SAME shared renderer for two unrelated tasks confirmed no cross-contamination (`TestComputeNeedsInput_BUG067_DistinctSequentialPromptReflagsAlongsideUnrelatedAutoClear`).

**Actual root cause: BUG-063's own explicitly-documented "accepted scope limit" — this cannot distinguish 'the exact same already-answered content re-detected' from 'a second, textually distinct, still-unanswered prompt that happens to arrive with `lastInputOf(id)` unchanged' — hit in practice, not just in theory.** Claude Code's `/brainstorm`/`AskUserQuestion` flow routinely asks several DISTINCT questions in sequence within one session, each answered directly in the pane: (1) question 1 shown → flagged; (2) the human answers question 1 directly (a real keystroke) → `LastUserInput` advances past baseline → `NeedsInputClear` correctly clears, recording a cleared marker keyed on `(taskID, lastInputOf-timestamp)`; (3) Claude asks question 2 — a GENUINELY DIFFERENT, unanswered prompt — moments later, before the human types anything else, so `lastInputOf(id)` is still the EXACT SAME timestamp as the marker. `NeedsInputClear` had no visibility into content, only `(id, timestamp)` (by design — see BUG-063's original trade-off analysis), so it could not tell "the stale, already-resolved question-1 content re-detected" apart from "question 2, a brand-new unanswered prompt" — both present identically at that layer — and suppressed question 2 as a stale re-candidacy, exactly as BUG-063 predicted for the case it deliberately left unhandled. Confirmed via a synthetic tick-by-tick repro against the UNMODIFIED `NeedsInputClear` before any fix was applied (`TestZZRepro_SequentialDistinctPromptsSuppressed`, not committed — see the fix's own regression tests below for the permanent pin).

**Fix: `agent.NeedsInputClear` gained an 8th parameter, `fingerprintOf func(string) (uint64, bool)`, and its cleared-marker map changed from `map[string]time.Time` to `map[string]agent.ClearedMarker{At, FP, HasFP}` — implementing the exact follow-up BUG-063's own doc comment named but deferred ("a content-fingerprint-aware refinement... not required by this fix").** The stale-recandidacy check now suppresses ONLY when the content ALSO matches (or can't be compared — `!marker.HasFP || !curOK`, preserving the pre-fix behavior as the safe default when a fingerprint isn't available on either side): `curFP, curOK := fingerprint(id); if !marker.HasFP || !curOK || curFP == marker.FP { continue /* suppress */ }` — otherwise the candidacy falls through and re-arms with a fresh baseline, exactly like a first-ever candidacy. Both callers already computed the needed fingerprint every tick (`agent.AwaitingInputFingerprint`, the SAME value the BUG-032 content-stability pass already uses) — no new render pass was added. The fingerprint fed in is a MERGE of this tick's and the PREVIOUS tick's value (current wins): the tick a flag actually clears on is frequently the same tick the screen has already moved on to a busy/narrating frame with no awaiting-input signal of its own (so this tick's fingerprint map has no entry for it), while the previous tick's value still holds the fingerprint of the content that just got answered — `internal/tui/app.go`'s `detectNeedsInputSticky` captures `prevFP := a.needsInputFP` BEFORE reassigning it, and `internal/api/push.go`'s `computeNeedsInput` already receives `prevFP` as an existing parameter, so no NEW threaded state was needed in either caller beyond the merge itself.

**Scope: this widens what gets SURFACED, never what gets SUPPRESSED — a nil `fingerprintOf`, an unavailable fingerprint on either side, or a matching fingerprint all degrade to the exact pre-BUG-067 (timestamp-only) behavior, so BUG-063's original guarantee (a stale re-detection of truly-identical content stays suppressed) is unchanged and still covered by its own existing tests (updated only to pass a trailing `nil` for the new parameter).** See `TestNeedsInputClear`'s `BUG-067` subtests (`internal/agent/needsinput_test.go`) for the pure-function pin (distinct fingerprint re-arms; identical or unknown fingerprint still suppresses), `TestDetectNeedsInputSticky_BUG067_DistinctSequentialPromptReflags` (`internal/tui/app_test.go`) for the end-to-end repro through the real TUI caller, and `TestComputeNeedsInput_BUG067_DistinctSequentialPromptReflagsAlongsideUnrelatedAutoClear` (`internal/api/needsinput_test.go`) for the daemon-side repro that ALSO runs the unrelated BUG-066 auto-clear pass against a second task in the same tick sharing the same `*agent.ScreenRenderer`, directly disproving the cross-contamination hypothesis this bug was first suspected of.

## A worker that resolves its own block and settles FASTER than the resumed-activity threshold has NO clear path at all — stuck until an incidental keystroke (BUG-072)

**Live repro (Aaron dogfooding): the Details pane already showed the session idle and the task status `in_review` — i.e. the worker had already resolved whatever raised `(?)` and moved on — yet the rail still showed `(?)`. Focusing the role's pane and pressing a no-op key (space) in the PTY cleared it within one tick.** Root-caused by tracing the mechanism, not guessing from the symptom (per `feedback-argus-ui-bug-get-ground-truth` in memory): the three existing `NeedsInputClear` paths (BUG-034 `lastInputOf`, archive, BUG-065 `resumedOf`) all structurally cannot fire here. `lastInputOf` never advances (nobody typed). The task isn't archived. And `agent.ResumeActivityTick` (BUG-065) `if !workingNow { return 0, false }` resets its streak to zero the INSTANT the session goes idle — a worker that resolves its own block and wraps up in FEWER than `NeedsInputResumeTicks` (5) consecutive ticks of visible work settles into idle before the streak can ever reach threshold, and once idle it can NEVER show the working affordance again, so the streak can never resume either. The keystroke's only effect was advancing `LastUserInput()` past the baseline via the ORIGINAL BUG-034 path (a) — a coincidental fix, not a real one; any keystroke, however meaningless, would have worked. This is a genuinely new gap distinct from BUG-065: that fix's own design explicitly accepted that a brief working burst which RE-PARKS at a blocking prompt must not clear (the risk its no-grace-period reset policy defends against) — but never considered the sibling case where the brief burst is followed by genuine resolution (idle, signal gone) rather than re-parking.

**Fix: `agent.NeedsInputClear` gained a FOURTH clear condition, `settledOf func(string) bool`, checked alongside `resumedOf` — the complementary case.** `agent.SettleTick(prevTicks int, idleNow, awaitingNow bool) (newTicks int, settled bool)` tracks CONSECUTIVE ticks a flagged session is genuinely RAW-IDLE (`Session.IsIdle()`, not "not currently generating") AND its CURRENT tail shows NONE of the three `DetectNeedsInput` signals — literally the SAME idle-gated check (`agent.DetectNeedsInputScreen`) that RAISES the flag in the first place, re-applied here as a negative/clearing signal. Reaching `NeedsInputSettleTicks` (2 — deliberately much smaller than `NeedsInputResumeTicks`=5 or `NeedsInputEscalationTicks`=8) consecutive qualifying ticks clears, recording a cleared marker via the SAME mechanism `resumedOf` uses (inherits the BUG-063 stale-recandidacy guard for free). No grace period on a miss, mirroring `ResumeActivityTick`: not idle, OR the signal still present, resets the streak to zero outright.

**Why re-running the idle-gated signal check as a clear condition does NOT resurrect BUG-061 (the tail-flooding false-negative bug that pre-BUG-061 fixed by REMOVING exactly this kind of re-match requirement): the discriminator is genuine raw idleness.** BUG-061's flooding mechanism (Claude's continuous blinking-cursor redraw permanently pushing real prompt content out of the scanned window) REQUIRES the session to keep producing bytes indefinitely — which is precisely what raw idleness means has NOT happened. A session that has gone genuinely `Session.IsIdle()` has, by construction, stopped producing those bytes for the idle threshold, so it cannot be mid-flood; a fresh read of its tail is exactly as trustworthy as the read that raised the flag originally. `SettleTick`'s `idleNow` gate is the load-bearing guard that keeps this narrowly scoped to "genuinely resolved," never to "a still-parked session whose signal transiently missed one tick" — a session that is idle but STILL shows the blocking signal (the ordinary still-blocked case) never qualifies, by design (accepted as the base-spec scenario "A previously-flagged, still-running task stays flagged when the tail no longer shows the signal" narrowing to add "but the session is not idle").

**Both callers thread a new per-tick counter map exactly like the other maps in this file** (`only store if != 0`, rebuilt fresh from the currently-running set): `internal/tui/app.go`'s `detectNeedsInputSticky` (`App.needsInputSettle`, computed only for sessions in `idleIDs` — a busy session never even gets a tail read for this pass) and `internal/api/push.go`'s `computeNeedsInput` (`idleWatcherState.needsInputSettle`; `computeNeedsInput`'s signature grew a `prevSettle map[string]int` parameter and a 6th `newSettle` return value — every existing call site, including tests, needed the extra threaded argument). One PRE-EXISTING daemon test (`TestDetectNeedsInputTick`'s BUG-061 subtest) had its fixture corrected: it modeled the flooding scenario as `idle=["a","b"]` with the tail switched to plain content for TWO consecutive ticks — which is now, correctly, the exact scenario BUG-072 resolves, not the true BUG-061 case (a session that NEVER goes idle). Fixed by dropping "a" from the `idle` list for those ticks (genuinely busy/flooding, `settledOf` never engages) while keeping the original "must not clear from tail-decay alone" assertion intact.
