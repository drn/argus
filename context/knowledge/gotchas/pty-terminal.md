## PTY & Terminal Rendering

- **`pty.Setsize` (which calls `os.File.Fd()`) races with `os.File.Close()`.** `Fd()` reads the internal fd field without synchronization, while `Close()` modifies it. `Read()`/`Write()` are safe (they use internal `fdMutex`). Fix: `ptmxClosed` bool flag under Session mutex; `waitLoop` sets flag + closes under lock; `Resize` checks flag under lock before calling `Setsize`.
- **`Session.Done()` blocks on `readDone`, not just process exit.** `waitLoop` waits for `readLoop` to drain the kernel PTY buffer before closing `done`. Without this, `Done()` fires while bytes are still in transit — `RecentOutput()` returns partial or empty data, and CI tests polling for output flake out (was the original `TestSession_RecentOutput` flake). The guarantee relies on `readLoop`'s `defer close(s.readDone)`.
- **`waitLoop` waits for `readDone` BEFORE closing `ptmx` in the fast path, with a `ptmxDrainTimeout` escape hatch.** Closing the master mid-Read interrupts the syscall with "file already closed" and discards any kernel-buffered bytes — exactly the bytes a short-lived child like `echo` produces just before exiting. After `Cmd.Wait()` returns, the caller-process copy of the slave fd is already closed (creack/pty closes it immediately after `cmd.Start`), so for a well-behaved child the master EOFs naturally within ms and `readLoop` exits on its own. If a grandchild inherited the slave fd (a Node subprocess without `stdio: 'ignore'`, say), the master never EOFs — `ptmxDrainTimeout` (5s) then triggers a force-close to keep `waitLoop` from hanging forever and leaking the task from `runner.sessions`. Reverse order = sporadic `TestSession_Attach_WithReplay` / `TestSession_RecentOutputTailWithTotal` failures on loaded CI runners.
- **PTY needs real terminal size at launch** (`pty.StartWithSize`), not 0x0. TUI apps won't render with zero dimensions. Start at actual panel width, not 80x24 — agents format initial output for launch PTY size.
- **Single-reader-tee pattern is critical.** Two goroutines reading the same fd causes data loss.
- **`AddWriter` must replay before registering.** Register first → live bytes arrive before replay → duplicate data → rendering corruption.
- **x/vt `SafeEmulator` hangs on terminal query sequences.** Use `newDrainedEmulator()` which starts `go io.Copy(io.Discard, emu)` to drain the response pipe. Never use bare `xvt.NewSafeEmulator()` in tui.
- **Discarding query responses silently degrades color-aware agent CLIs — the pane's LIVE emulator now answers instead.** `NewDrainedEmulator`'s `io.Discard` drain (above) avoided a hang but also meant an agent process's `OSC 10`/`OSC 11` ("what's your fg/bg color?") queries got no reply. Codex sends this on every startup and, per a captured real session, never draws its composer/placeholder highlight background in any occurrence when the query goes unanswered — it only ever colors the separately-unconditional submitted-prompt history box (bare `\x1b[7m`). Fix (`NewLiveEmulator`, used only by `newTrackedEmulatorWithCallback`, the pane's live-emulator path): set `SetBackgroundColor`/`SetForegroundColor` to an assumed dark-terminal default (Argus itself never assumes a background — chrome uses `tcell.ColorDefault` throughout — so this is a best-effort guess, not a queried truth), and forward the drained response bytes into `TerminalAdapter.WriteInput` instead of `io.Discard`. Replay/preview emulators (`newTrackedReplayEmulatorWithCallback`, `previewvt.go`) deliberately keep the discard-only behavior — they reconstruct historical output for a process that may not be live, so forwarding would be meaningless or cross-wired.
  - **Forwarding must run off the drain loop, or it reintroduces the exact hang class it fixes.** Unlike `io.Discard.Write` (never blocks), `TerminalAdapter.WriteInput` reaches a real PTY write that CAN block if the agent isn't reading its stdin. If that blocking write ran inline in the goroutine that calls `emu.Read()`, a stalled agent would stop the loop from ever calling `Read()` again — and the emulator's *next* query response would then block on the unbuffered response pipe with nobody left to read it, hanging the main-goroutine `emu.Write()` call. Fix: the drain loop only does `emu.Read()` + a non-blocking bounded-channel send (drops on a full channel); a separate goroutine performs the actual (possibly blocking) forward.
  - **A stale/superseded emulator's in-flight response must be dropped, not misdelivered.** `forwardEmulatorResponse` takes an `owner` captured at emulator-creation time (the pane's session at that moment) and only forwards if `tp.session` is *still* `owner` — not just non-nil. `SetSession` always replaces `tp.emu` when the session pointer changes, so a live, non-orphaned emulator's owner and `tp.session` never diverge; the check exists for the narrow race where an old emulator's drain goroutine had already read a response before the pane moved on to a new session, which would otherwise deliver a stale answer into the new (unrelated) session.
- **x/vt can panic on replay from differently-sized terminals.** Use `safeEmuWrite()` which wraps with `recover()`.
- **Cursor rendering respects `CursorVisibility` callback.** Tracked via `cursorVisible` field, updated by x/vt callback. Defaults to `false` on emulator creation.
- **Plugin terminalpane cursor: force emulator to hidden state in `New()` or the first `\e[?25h` is a silent no-op.** `xvt.SafeEmulator` starts with cursor visible (`Hidden=false`). The `CursorVisibility` callback only fires on state CHANGES (`changed := s.cur.Hidden != hidden`). So if you initialize tracking to `false` (via `atomic.Bool` zero value) but leave the emulator in the visible state, the plugin's first `\e[?25h` hits the emulator already visible → no change → callback doesn't fire → cursor stays hidden in tracking. Fix: write `\x1b[?25l` directly to the emulator in `New()` BEFORE starting the consumer goroutine; this changes the emulator's state from visible to hidden, fires the callback (sets tracking to `false`), and ensures the first `\e[?25h` triggers the callback correctly. The task terminal uses a different fix (calls the callback manually with `false` and relies on agents always sending `\e[?25l` early) — both approaches are valid for their respective contexts.
- **Ring buffer must be bounded (256KB).** Unbounded causes CPU spikes and OOM. Session log file provides full scrollback.
- **Live scrollback reads from session log file, not ring buffer.** `readLogTail` seeks from EOF — gives infinite scrollback while live follow-tail stays on the fast ring buffer path.
- **Anchor-lock keeps scrolled-up content pinned when new output arrives.** Track `anchorTotalLines`; bump `scrollOffset` by the delta. Reset to 0 on scroll-to-bottom.
- **Real user INPUT snaps `scrollOffset` to 0; OUTPUT does not (BUG-008).** Typing while scrolled up echoes at the off-screen live tail, so every input-writing path must `ResetScroll()` BEFORE `WriteInput`: the task page (`handleAgentKey`, already via the "reset scroll on any other key" block), Hera panes (`HeraPage.forwardKey`, after the PgUp/PgDn early-return), and the pane's `PasteHandler`. Scrollback-nav keys (PgUp/PgDn/Shift-arrows/End) must NOT snap — they return before the write. Output-driven growth stays pinned by anchor-lock — snapping is input-only. This is `scrollOffset=0` only; no `screen.Sync()` (the normal damage-tracked Draw repaints the live tail with the cursor).
- **`asyncReplayRebuild` must signal `anchorTotalLines` reset via `replayRebuildPending`.** The replay emulator (fed from log tail) has far more scrollback than the live emulator (256KB ring buffer). Without reset, anchor-lock sees the totalLines jump as "new output" and bumps scrollOffset by the delta, causing a half-page jump on the first Shift+Up.
- **`ScrollUp`/`AccelScrollUp` must invalidate `replayEmu` AND `anchorTotalLines` on the 0→>0 transition.** Two bugs: (1) stale replay emu content — built during a previous scroll, its bottom doesn't match current live output, so `scrollOffset=1` shows content from hundreds of lines ago; (2) stale anchor — `anchorTotalLines` from live mode causes `paintEmu` to bump scrollOffset by `(replayTotal - liveTotal)`. Fix: `tp.replayEmu = nil; tp.anchorTotalLines = 0` when `scrollOffset == 0`, forcing a fresh rebuild from current log tail.
- **Replay emulator is cached and reused when only scroll offset changes.** Rebuild only when input size or dimensions change. For **live sessions scrolled up**, treat cache as always valid (new bytes arrive below viewport) — checking log size growth invalidates on every Draw since the agent is writing. For dead sessions, stat the log file (~1us) instead of reading it to check validity.
- **`replayEmuMaxScroll` must reflect actual emulator scrollback capacity, not the build-time scroll offset.** Setting it to `tp.scrollOffset` caused a full rebuild (log read + emulator feed) on every scroll step beyond the initial offset — the primary cause of slow scrollback in long sessions. Compute from `emu.ScrollbackLen() + lastContentRow + 1 - viewportHeight` after building.
- **Draw's `replayRebuildPending` consume block must clamp `scrollOffset` to the fresh `replayEmuMaxScroll`.** `ScrollUp`/`AccelScrollUp` can't clamp (no emu yet → no maxScroll), so the user can scroll past the available scrollback. Without snapping after a rebuild, the cache-validity check (`scrollOffset <= replayEmuMaxScroll`) fails every frame, each Draw kicks another async rebuild, and rebuild completion fires `notifyBranchChange` → `screen.Sync()` — visible as continuous flicker at the top of the scrollback. The clamp lives in Draw (main goroutine, under `tp.mu`), not in `asyncReplayRebuild` which is on a background goroutine and can't safely write `scrollOffset`.
- **Replay emulator rebuild must happen off the main goroutine.** `readLogTail` (up to 8MB) + `safeEmuWrite` blocks the main goroutine for hundreds of milliseconds with large session logs, freezing the UI because `QueueUpdateDraw` is synchronous. `asyncReplayRebuild` runs in a background goroutine; Draw() paints stale cache while it runs. The `replayRebuildPending` flag signals the main goroutine to reset `anchorTotalLines` and `paintCacheValid` (which are owned by the main goroutine). `readLogTailForTask` (not `readLogTail`) must be used from the background goroutine to avoid racing with `SetTaskID`.
- **Replay emulators use `newDrainedReplayEmulator` with 50K-line scrollback (vs 10K default).** This allows deep scrolling without rebuilds. The 8MB minimum log read populates ~60-70% of the buffer on first scroll.
- **First scroll-up must fall back to the live emulator while the replay builds.** `invalidateReplayCache` nils `replayEmu`, and `asyncReplayRebuild` takes ~1s for large logs. Without a fallback, the user sees "Waiting for output..." for the entire rebuild. `tp.emu` (10K scrollback) provides instant content. Priority: stale replay emu > live emu > placeholder. `scrollOffset`/`anchorTotalLines` must be saved/restored because the fallback emu's smaller scrollback may clamp them.
- **Agent view replay must use current panel dimensions, not stale PTY size.** Override `ptyCols/ptyRows` with current dimensions for dead/nil sessions.
- **Preview panel must use PTY dimensions (both cols AND rows), not panel dimensions, for VT emulation.** Width mismatch causes double-wrapping. Height mismatch causes blank space at top — ANSI cursor positioning formatted for a tall PTY gets clamped in a shorter emulator, leaving content in the wrong rows. `RefreshOutput` takes separate emu and viewport dimensions; the viewport selects which rows to display.
- **Dead-session previews need the `.size` sidecar (`agent.SaveSessionSize`/`LoadSessionSize`) — the PTY size dies with the process, but the log bytes stay formatted for it.** Re-emulating a wide session's log tail at pane width clamps CSI nG/CUP at the right edge and autowraps the tail onto the next row, overwriting it — the "scrambled preview" (holes in words, orphan chars down the right edge). `StartSession` and `Session.Resize` persist `~/.argus/sessions/<task>.size`; `previewEmuSize` resolves live PTY size → sidecar → pane (last-resort for pre-sidecar logs). Prune must remove the sidecar with the log.
- **`Session.Resize` must NOT rewrite the sidecar after `ptmxClosed`.** A post-exit Resize is a no-op on the PTY, so recording its size would lie about the width the log bytes were actually rendered for.
- **Never resize the agent's real PTY from the preview path.** A Resize RPC per cursor move would SIGWINCH every live agent the user scrolls past, triggering full repaints. Width mismatch is resolved emulation-side only (emulate wide, clip to pane).
- **New emulators must default `cursorVisible` to `false`.** Agents send `\e[?25l` early, but after ring buffer wrap or emu rebuild, that sequence is lost. Defaulting to `true` causes a phantom cursor at bottom-left. Also, `lastContentRow` must not extend to cursor position when cursor is hidden.
- **`renderLive` must skip `RecentOutput()` when `newBytes == 0`.** The 256KB ring buffer copy on every draw causes typing lag — keystroke redraws trigger `Draw()` before PTY echo arrives, so copying is wasted. `emuFedTotal` must only advance when bytes are actually fed to the emulator; advancing it on an empty `raw` silently skips those bytes permanently.
- **The live incremental-feed path must read `raw` and its paired `total` from ONE atomic call (`RecentOutputTailWithTotal`), never `TotalWritten()` and `RecentOutput()` as two separate calls (BUG-075).** `readLoop` is a live, independent goroutine — for an actively streaming session (no bind, no resize, nothing but ordinary agent output arriving), bytes can land in the gap between two unsynchronized calls, making `raw` (sampled later) longer than the earlier `totalWritten` accounts for. Slicing `raw[len(raw)-newBytes:]` against that stale `newBytes` then feeds the WRONG suffix: it silently skips the true next bytes (visible as a couple of dropped characters, e.g. "Independent" → "Indepe dent") and instead feeds bytes from further ahead, recording `emuFedTotal` short of what was actually fed — the very next frame then re-feeds that same already-fed tail (visible as a short recent phrase duplicating). Both artifacts land together, on a pane that's actively being watched with no bind/resize/rebuild involved at all, which made this easy to mistake for the bind-time reconstruction defects (BUG-068/BUG-073/BUG-074) — it is a distinct, plain TOCTOU race in the steady-state live-feed path, not a reconstruction-from-history problem. `agent.Session.RecentOutputTailWithTotal`'s own doc comment already named this exact hazard (for the `/output` HTTP endpoint's cursor) — `renderLive`'s live-feed path just hadn't been updated to use it. Fix: fetch `(raw, totalWritten)` together via `sess.RecentOutputTailWithTotal(256*1024)` and recompute `newBytes` from that SAME call, but only when `!emuMissing` — the `emuMissing` (fresh-attach) branch is unconditionally `fullReplay` regardless of `raw`/`newBytes` (short-circuited by the `||`) and calls `readLiveRebuildHistory`, which does its own independent ring read, so fetching here too would just be a wasted extra 256KB copy. Regression test: `TestRenderLive_LiveFeedUsesAtomicSnapshotNotStaleTotal` (a `raceAdapter` mock whose `TotalWritten()` always reports an earlier snapshot than `RecentOutputTailWithTotal()`, simulating readLoop advancing in between — confirmed to fail on the pre-fix code with exactly the predicted "HELLOLD" garble before being fixed).
- **`paintEmu` must cache cells for replay on idle redraws.** tview's `screen.Clear()` defeats tcell's dirty tracking (fills all cells with spaces → every `SetContent` marks cells dirty → full terminal I/O). On no-change redraws, replay cached `[]cachedCell` directly — skips 10K+ mutex ops, allocations, and style conversions per frame. Invalidate cache on scroll, reset, or session change.
- **`startAgentRedrawLoop` must skip `QueueUpdateDraw` when idle.** Keystroke and resize events trigger their own tview redraws; the 200ms loop only needs to fire when new PTY output arrives (`TotalWritten` changed).
- **`spinnerLoop` must only fire redraws for active (non-idle) running tasks.** Idle tasks show a static moon icon, not the spinner. Firing `QueueUpdateDraw` at 100ms when all tasks are idle causes unnecessary full-screen repaints that interfere with tmux hyperlink hover and waste CPU.
- **`uvCellToTcellStyle` must map ALL ultraviolet attributes.** Missing `AttrFaint→Dim` caused Ink-based CLIs (Codex) to lose visual contrast. Keep in sync with `uv.Attr*` constants: Bold, Faint, Italic, Blink, Reverse, Strikethrough. Also map underline styles (curly/dotted/dashed/double), underline color, and hyperlinks (OSC 8).
- **PTY keystroke follow-up redraw must guard on `TotalWritten`.** The immediate tview draw (from returning `nil`) fires before the PTY echo arrives. A 16ms delayed `QueueUpdateDraw` catches the echo; the `sess.TotalWritten() != tw` guard skips the redraw when no new output arrived, avoiding wasted work when the keystroke produced no echo.
- **tcell emits ~10K cells per keystroke as an unavoidable cost of tview's screen-wide `Clear()`.** After `Clear()` sets `currStr` on every cell, even a widget that re-SetContent's the identical original value gets marked dirty because `Put()` sees `cl != c.currStr` and calls `setDirty(true)` (clearing `lastStr`). A prior `lazyScreen.skipClear` hack bypassed `Clear()` entirely for PTY-keystroke frames, but it leaked stale cells on any layout shift between a skipped frame and the next real-clear frame, and was removed. Do not re-add it without a mechanism to invalidate the skip on resize/page-swap/layout-change — correctness beats peak typing throughput.
- **`RingBuffer.total` is `atomic.Uint64` — the only lock-free field.** All other RingBuffer fields (`data`, `pos`, `full`) require the caller's mutex. `TotalWritten()` is safe to call without any lock. `Session.TotalWritten()` and `RemoteSession.TotalWritten()` are lock-free.
- **`readLoop` data alias (`tmp[:n]`) requires all writers to consume synchronously.** Avoids a per-read heap allocation. Safe because `buf.Write`, `logFile.Write`, and all `io.Writer.Write` implementations copy or consume before returning. A future async writer that stores a reference to `p` would silently corrupt data.
- **`refreshPreview` TotalWritten guard fields must be protected by `a.mu`.** `lastPreviewTaskID` and `lastPreviewTW` are accessed from both the tick goroutine and `onTaskCursorChange` goroutines concurrently.
- **Never use `len(raw)` as a cache key for ring buffer content.** Once the ring buffer fills (256KB), `len(Bytes())` is constant — same length but different content on every wrap. Use `TotalWritten()` for change detection instead.
- **Panel-size delta is not a sufficient trigger for PTY resize.** `Draw()` only queues a resize when `ptyCols != wantCols`, but a stuck PTY (dropped SIGWINCH, daemon RPC timeout, session started in a smaller window) can have `ptyCols` already match the panel without Claude ever having received the new size. Agent-view entry calls `TerminalPane.ForceResyncPTY()` to repost the resize unconditionally on the next Draw. Keep the flag armed across dead/nil-session Draws so the next live session consumes it.
- **In tests, `bytes.Buffer` is NOT thread-safe with `Session.AddWriter`.** `readLoop` writes to every registered writer asynchronously; concurrent reads from the test goroutine race the writes even after `<-sess.Done()`, because there's no happens-before relationship between the writer-goroutine writes and the test-goroutine reads. `go test -race` flags this. Use the file-local `syncBuffer` (mutex-wrapped `bytes.Buffer` with `Write`/`Len`/`String` methods) in `internal/agent/session_test.go` for any AddWriter consumer in tests.
- **Don't `time.Sleep` after `<-sess.Done()` to drain readLoop.** Even 100ms is unreliable on CI under `-race`. The PTY drain happens in a separate goroutine that may still be running. Poll instead with a 2-second deadline, breaking when the expected output appears. Pattern: `for time.Now().Before(deadline) { if strings.Contains(string(sess.RecentOutput()), expected) { break }; time.Sleep(20 * time.Millisecond) }`. Both `TestSession_RecentOutput*` and `TestSession_MultiWriter` were converted from sleep to poll after CI flakes.
- **`computePTYSize` must NOT trust `agentPane.GetInnerRect` before tview has laid the pane out.** tview's `NewBox` returns a default rect of 15x10 when no `SetRect` has run, and `pw > 0 && ph > 0` doesn't reject it. The agent-view entry path is `SetSession → SwitchToPage → ForceResyncPTY → forceRedraw → startSession`, where `startSession` calls `computePTYSize` synchronously before tview's queued Draw can lay out the pane. After a daemon restart, the auto-start path read 15x10, derived a 20x8 PTY, started Claude narrow, and no SIGWINCH-triggered redraw could re-flow the already-emitted narrow cursor positions in the ring buffer (`\e[5;3H` still places content at col 3 even when re-emulated at 190 cols). Fix: compute from `term.GetSize(stdout)` first using the zoomed (single-pane, full-width) layout; fall back to the pane rect only when it's larger than tview's default (>30 cols). NOTE: `ptySizeFromHostTerm` always seeds at the zoomed full width (`tw - agentViewColOverhead` for cols — NOT the 3/5 ratio), regardless of the `ui.default_agent_zoom` setting. When the configured default is zoom (the default), this matches the laid-out pane and no SIGWINCH fires. When the configured default is split (1:3:1), the pane lays out narrower and the terminal pane's own `Draw()` recompute corrects the size on the next frame — one SIGWINCH repaint on entry, an accepted trade-off (see gotchas/keybindings.md). Do NOT make `ptySizeFromHostTerm` layout-aware to chase that single repaint; the added coupling isn't worth it.
- **`ptySizeFromHostTerm` deducts 4 rows, not 5 — the tab header is always hidden in agent view.** The row deduction is `agentHeader(1) + statusbar(1) + pane border(2) = 4`. Earlier code deducted 5 (including 1 for the tab header) as defense against the fork path running before the header was hidden, but every callsite (new-task `enterPendingAgentView`, auto-start `onTaskSelect`) hides the header BEFORE `computePTYSize` runs. Deducting 5 produced an off-by-one row mismatch: agent forked at `th-5` but pane inner is `th-4` once visible, so `forceResync` fired a Resize RPC ~200ms after the user reached the agent view, the kernel sent SIGWINCH, and Claude repainted — a visible content jump the user perceived as tearing. Fork still works: PTY at `th-4` exceeds the still-header-visible pane inner (`th-5`) by 1 row briefly, but the pane isn't on screen yet, and `onTaskSelect` hides the header before the user sees the agent view.
- **`SetSession` must seed `ptyCols/ptyRows` from the visible INNER rect, not `GetInnerRect()`'s outer rect.** `TerminalPane` is a bare `tview.Box` with no native border, so `GetInnerRect()` returns the outer rect of the pane; `DrawBorderedPanel` paints a 1-cell custom border inside it, so the actual content area is 2 cells smaller in each dimension. Seeding with the outer rect made `sizeChanged` fire on every agent-view entry (e.g. `192x84 -> 190x82`), triggering a Resize RPC and SIGWINCH that caused Claude to repaint visibly. Fix: subtract 2 from each dimension in the seed (with `w > 30 && h > 10` guard, matching `ptySizeFromPaneRect`'s threshold so tview's `NewBox` 15x10 default is rejected); Draw still self-corrects if the pane was reshaped between SetSession and the first frame.
- **Width-mismatched scrollback can only be repaired by kill+resume, not by SIGWINCH.** ink (Claude Code) re-renders live UI elements on SIGWINCH but the conversation scrollback is committed bytes — the cursor codes are baked in (`\e[5;3H` still places content at col 3 even when re-emulated at 190 cols). `Session.initialCols/initialRows` (set once in `StartSession`, exposed via `SessionInfo.InitialCols/Rows` and `SessionHandle.InitialPTYSize`) are immutable so callers can detect drift after the fact. The fix is bidirectional and fires from THREE sites: (1) TUI agent-view entry calls `maybeKickRerender`, sets `pendingRerenderRestart[taskID]`, and `handleSessionExitUI` immediately resumes via `--session-id`; (2) the API's `handleResize` calls `Server.maybeKickRerender` → `Runner.KickRerender`, which queues a daemon-side restart consumed by the runner's exit goroutine; (3) the native Hera view's `bindPane`/`Draw()` call `App.heraKickRerender` (BUG-074 — see gotchas/hera-view.md), added well after the first two and exposed as a genuine gap until then since `ForceResyncPTY()` alone (what Hera already had) only fixes the resize-repair case, not this one. All three sites use the shared `agent.ShouldKickRerender` predicate (margin = `RerenderMargin`, currently 15 cols, |panelCols-initCols| in either direction). Gated on `IsIdle()` to avoid killing mid-tool-call; gated on `task.SessionID != ""` because Codex captures its session ID post-exit and can't resume mid-conversation.
- **The rerender-kick must short-circuit when the panel cols are unchanged since the last attach.** `IsIdle()` is true whenever the PTY has been silent for ≥3 s, and a Claude `AskUserQuestion` overlay is silent by definition while it waits for input. Without an unchanged-size gate, every agent-view reopen (TUI `onTaskSelect` and web xterm.js mount → `/resize`) re-evaluates `ShouldKickRerender`; if the panel cols are ≥15 off `initialCols`, the predicate fires, the daemon kills the session, and the `--session-id` restart rehydrates the conversation but not the ephemeral modal — so the question silently disappears on reopen. The TUI gates via `App.isRedundantAttach(taskID, panelCols)` (caches the last attach's cols and bails before launching the RPC goroutine) and the API gates via `Server.isRedundantResize(taskID, cols)` (mutex-protected map indexed by task ID). Genuine viewport resizes still fall through because the new cols differ from the cached value. Test coverage: `TestIsRedundantAttach`, `TestIsRedundantResize`.
- **The rerender-kick must ALSO defer when the idle agent is blocked on a user prompt — the unchanged-size gate alone is insufficient.** `isRedundantAttach`/`isRedundantResize` only suppress the kick on a same-size reopen; a *genuine* resize (the user actually widened/narrowed the pane) crosses the 15-col margin, falls through the cache gate, and — because a prompt-blocked agent reads as `IsIdle()` — fires `RerenderKick`, killing the session and dismissing the `AskUserQuestion`/permission/plan-confirm overlay on the `--session-id` restart. `ShouldKickRerender` takes a `needsInput` arg (checked after `idle`) and returns the dedicated `RerenderDeferPrompt` decision when set. The TUI computes `needsInput` from the **disk log** (`readSessionLogTailBytes` + `agent.DetectNeedsInput`, gated behind `idle`) — not the session ring, which is empty until a stream attaches in daemon-client mode. The API computes it via `agent.BlockedOnPrompt(sess)` (reads the server-side ring, always populated since the daemon owns it). Both treat the defer like `RerenderDeferBusy`: invalidate the cols cache so a later resize re-evaluates once the user answers and the agent moves on. **Stale-log tradeoff (TUI path only):** the session log is truncated only on `StartSession` (`O_TRUNC`) and appended thereafter, so a selection-prompt marker lingers in the 16 KB tail after the user answers — until ~16 KB of newer output rolls it out or the session restarts. During that window a genuine TUI resize defers the (purely cosmetic) re-render rather than firing it; the API path reads the live ring so it has no such lag. Deferring a cosmetic re-render is strictly preferable to the bug this gate prevents (killing a session that's actually waiting on a question). Test coverage: `TestShouldKickRerender` (`defer when idle but blocked on prompt`), `TestBlockedOnPrompt`, `TestSessionBlockedOnPrompt`, and end-to-end `TestMaybeKickRerender_DefersWhenBlockedOnPrompt` (API) / `TestMaybeKickRerender_TUIDefersWhenBlockedOnPrompt` (TUI).
- **The rerender cache must invalidate on every "predicate matched but kick suppressed" outcome so a missed kick can retry at the same cols.** Without invalidation, any non-retryable state at the same cols (busy agent, transient daemon hiccup) would freeze the gate forever — the user would have to manually resize the terminal to clear the cache. Helpers `App.invalidateAttachCache(taskID)` (TUI, main-goroutine-only) and `Server.invalidateColsCache(taskID)` (web, mutex-protected) wrap the delete. Invalidating branches: `RerenderDeferBusy` / `!IsIdle()` (busy agent), `RerenderDeferPrompt` / `BlockedOnPrompt` (agent blocked on a user prompt), `sess.Stop()` error / `runner.KickRerender()` error (transient daemon failures), `db.Get()` error (transient DB failures). Only the `task.SessionID == ""` early-return on the web side intentionally leaves the cache populated — Codex backends can never resume mid-conversation, so there is no retry semantic.
- **Daemon-side kick-restart must skip the InProgress→Review status flip and report Alive=true during the restart gap.** When `Runner.KickRerender` queues a stop+restart, the runner's exit goroutine fires `onFinish` (which would normally `transitionTaskOnExit` to InReview) before the new session is in place. The daemon's onFinish guards on `Runner.HasPendingRestart(taskID)` to skip the transition; without that, the row briefly flips to InReview and the API's `idleWatcher` / web SPA's status polling races the restart and pops a Resume modal. Symmetrically, `RPCService.SessionStatus` must report `Alive=true` when `HasPendingRestart` is set even though `runner.Get` returns nil — otherwise the TUI's stream client treats the gap as a real exit and tears down the session. The pending entry is held until the new `runner.Start` returns, closing the window.
- **`renderLive`'s ring-buffer-wrap full-replay path must read from the on-disk session log, not just the 256KB ring buffer.** Ring wrap (the incremental tail no longer covers everything since the last feed) → emulator rebuild → feeding only `sess.RecentOutput()` (≤256KB) would drop history that was in the _previous_ emulator's 10K-line scrollback because it never enters the new emu. The live agent then re-emits a status bar at the new bottom row while the previous status bar — still in the 256KB ring — gets re-played and lands adjacent to it. Visible artifact: two status bars stacked at the pane bottom, no scroll indicator (still in live mode). Fix: `readLiveRebuildHistory` reads the 8MB log tail, merges with `RecentOutputTailWithTotal` to cover bytes that arrived between log read and snapshot, and feeds the result through `AlignToEscBoundary`. **This path is no longer used for a pure dimension change** (see the Resize-in-place entry below) — only for a genuine ring-wrap data gap, where there is no alternative to re-deriving from disk.
- **`readLiveRebuildHistory`'s log/ring merge must NEVER splice non-contiguous byte ranges together, even when the gap between them is genuinely unrecoverable (BUG-076).** When the on-disk log lags the ring by MORE than the ring's own 256KB capacity — rare under normal operation (readLoop flushes log writes chunk-by-chunk), but reachable under a heavy output burst that outpaces a momentarily-slow disk write (e.g. a bulk git/tag operation streaming a lot of output quickly) — the old code clamped the overflow and concatenated the log-covered prefix directly with the ring's overflow tail as if they were adjacent. They are NOT: the bytes in between were evicted from the ring before the log could catch up, and are unrecoverable from either source right now. Splicing them anyway feeds x/vt content whose escape sequences and cursor state were never actually adjacent — visible as unexplained missing characters/words and garbled symbols at the seam (a stray "%", a dropped letter mid-word), on an actively-streaming pane with no bind/resize event at all, which made this easy to mistake for BUG-075 (same "no bind involved" signature, different mechanism — BUG-075 was a plain incremental feed with no log involved). Fix: when the gap is unrecoverable, return just the log-covered prefix and ITS total (`logSize`, not `ringTotal`) — the caller records this as `emuFedTotal`, so understating it defers the unrecoverable range to the next Draw's ring-wrap check, which naturally retries the exact catch-up (`readLogRangeForTask`, BUG-073) once the log has had a chance to catch up, instead of permanently losing content and mis-splicing what little was captured. Regression test: `TestReadLiveRebuildHistory_UnrecoverableGapDoesNotSpliceNonContiguousBytes`.
- **A PTY dimension change must resize the EXISTING live emulator in place (`emu.Resize(cols, rows)`), never discard it and replay from the on-disk log tail.** `readLiveRebuildHistory`'s 8MB tail read (`liveRebuildHistorySize`, meant for the ring-wrap case above) is not a safe substitute for a resize: for any session with more than ~8MB of cumulative PTY output, an arbitrary mid-stream 8MB window has no memory of the terminal's true prior state (scrollback depth, cursor position, alt-screen mode) — x/vt reconstructs an internally-consistent but WRONG screen from it, and multiple historical redraw frames land on top of each other. Confirmed against real ~10-14MB dogfood session logs: feeding the true full history into one emulator vs. just the last-8MB tail into another (mirroring the exact rebuild-on-resize code path) produced literally dozens of overlapping historical lines (old git/CI status updates, slash-command menu text, PR fragments all jammed together character-by-character on the same rows) — this is BUG-068, the "old content bleeds through and overlaps with new content" report. **Why toggling fullscreen (Ctrl+Z) and back "fixed" it before this was patched:** that toggle is itself a dimension change and re-triggered the identical lossy rebuild, but it *also* makes the agent process (ink/React) redraw its entire UI fresh at the new size — that genuine incremental repaint painted over the garbage. The resize appeared to be the fix; it was actually incidental cover for a bug in argus's own reconstruction. Regression test: `TestTerminalPane_ResizePreservesEmulatorState` (nils the mock session's output after establishing alt-screen content, so a history-rebuild attempt would find nothing and show a placeholder — proving the resize path never attempts one).
- **Ring-wrap (`newBytes > len(raw)`, `emu != nil`) must recover the EXACT missing bytes from the on-disk log at the precise offset, not discard the emulator and rebuild from the approximate 8MB tail window (BUG-073, the ring-wrap sibling of BUG-068).** BUG-068 fixed the resize trigger of the "old content bleeds through and overlaps with new content" bug but explicitly left the ring-wrap trigger alone — there IS no alternative to a log read when the ring has genuinely evicted bytes, so it seemed unavoidable. It isn't: `Session.readLoop` (internal/agent/session.go) writes the ring buffer and the on-disk log from the identical `data` slice in the same iteration, so a `TerminalPane`'s `emuFedTotal` is in the EXACT same coordinate space as the log file's byte offsets — a precise incremental catch-up is always possible when the log still has those bytes (it almost always does; the log is append-only and only truncated once, at session start). Ring-wrap is reached by an everyday trigger distinct from resize: `SetSession` only resets `tp.emu`/`emuFedTotal` when the session POINTER changes, so simply viewing a different task's pane (or the rail/task list) while the backgrounded agent produces more than the ring's 256KB capacity leaves the SAME live emulator in place with a stale `emuFedTotal` — on return, the incremental tail no longer covers the gap and the old code fell all the way back to the lossy 8MB-window rebuild, discarding the (perfectly fine) existing emulator for no reason. Fix: `readLogRangeForTask(taskID, offset, length)` reads `[emuFedTotal, totalWritten)` straight from the log and feeds it into the EXISTING emulator (no discard, no `AlignToEscBoundary`/oscStrip-reset needed — it's contiguous with what's already parsed, exactly like the ordinary incremental-feed branch). Bounded by `logRangeCatchUpMaxBytes` (reuses the 8MB `liveRebuildHistorySize` budget) and falls back to the old approximate rebuild when the exact range isn't on disk (missing log, external truncation) — no regression in that residual case. Regression test: `TestRenderLive_RingWrapRecoversExactBytesWithoutDiscardingEmulator` (establishes alt-screen content, forces a ring-wrap gap the mock's short `RecentOutput()` can't cover, asserts the emulator POINTER is unchanged and both pre- and post-gap content survive; fails if the catch-up branch is disabled, confirmed by deliberately breaking it before writing the fix).
- **Byte slices from arbitrary file/ring positions can start mid-CSI; align to first ESC before feeding the emulator.** `readLogTailForTask` reads `[fileSize - N, fileSize)` and the ring's `Bytes()` returns whatever wrapped-around position the buffer holds. Either tail can start in the middle of a `\e[5;3H` parameter list. x/vt's parser sees the orphan `5;3H` as printable text and renders a smudge of digits/punctuation at the top of a fresh emulator. `terminal.AlignToEscBoundary` skips to the first ESC byte; if there isn't one, the slice is treated as plain text. Apply to **every** fresh-emulator feed from a tail-positioned source: `renderLive`'s full-replay, `asyncReplayRebuild`'s replay-emu, and `terminal.PreviewVT.Feed`'s full-replay branch (task switch / dimension change / ring wrap). The preview path went unaligned for months and produced visibly torn previews under long sessions — doubled status bars and orphan digit smudges in the agent preview rectangle.
- **The Preview pane uses a persistent, incrementally-fed emulator (`terminal.PreviewVT`), NOT a throwaway emulator rebuilt per refresh.** A throwaway emulator replays only a short output tail, so escape sequences that erase superseded in-place progress frames (e.g. a Claude Code Task-tool counter shrinking "20"→"9") fall outside the window and the stale digits survive as ghost cells floating right of collapsed lines. `PreviewVT` advances the same way the live agent pane does: it tracks `fedTotal` and feeds only the new suffix of the ring tail, full-replaying only on task switch, dimension change, or ring wrap (`newBytes > len(tail)`). - **`PreviewVT.rebuild` must REUSE its emulator (reset via RIS `ESC c`), never allocate a fresh one per rebuild.** `NewDrainedEmulator` spawns a drain goroutine (`io.Copy(io.Discard, emu)`) that blocks in `Read` forever and is only stopped by `Emulator.Close`. But `SafeEmulator.Read` is unlocked, so `Close` races that read on `e.closed` (the `-race` detector flags it) — Close is unusable for cleanup here. Since rebuild fires on every task-list cursor move, allocating per rebuild would leak one goroutine per scroll. Reusing one emulator and feeding RIS (drives x/vt `fullReset`: both screens, cursor, scroll region, tab stops, modes, charsets, parser state) keeps it at exactly one drain goroutine for the panel's lifetime. The only residual leak is one goroutine per recovered `SafeEmuWrite` panic (rare; the emulator may be corrupt so it's dropped, not reused) — the same posture as the live pane.
- **`PreviewVT` bounds scrollback to 1 line AND calls `ClearScrollback()` on every rebuild.** The preview is a snapshot of the agent's *current* screen bottom, never history; the now-long-lived emulator would otherwise accumulate scrollback from every `ESC[2J` (erase-with-scrollback) frame. Two non-obvious x/vt traps: (1) `SetScrollbackSize(0)` is a **no-op** — `Scrollback.SetMaxLines` early-returns for `maxLines <= 0` — so 1 is the smallest *effective* cap. (2) RIS (`ESC c`) / `fullReset` resets the screens but does **NOT** clear scrollback line content, so reusing the emulator across a task switch would carry the prior task's pushed rows into the new task and render them via the grid's `sbLen>0` branch (cross-task ghosting). `rebuild` must `ClearScrollback()` explicitly after the RIS write.
- **`TaskPreviewPanel.RefreshOutput` must hold `vtMu` across the whole `PreviewVT.Feed` + grid-build region.** It runs on BOTH the tick goroutine and `onTaskCursorChange`'s background goroutine; `PreviewVT` is stateful, so concurrent `Feed` calls corrupt the emulator, and the grid build reads emulator cells that a concurrent feed would mutate. `Draw` takes only `tp.mu` (never `vtMu`), so painting is never blocked by a heavy feed. A recovered emulator-write panic in `Feed` returns `(nil, err)` and drops the emulator so the next call rebuilds — the panel shows "Preview unavailable".
- **Both the task-list preview AND unfocused `TerminalPane` paint in grayscale — both are deliberate view-identity signals, not styling oversights.** The grayscale transform (`terminal.DesaturateStyle`/`terminal.GrayscaleColor`, Rec. 601 luminance) lives in `internal/tui/terminal/color.go` and is shared by the preview panel (`taskpreview.go`) and `paintEmu` (applied when `grayscale=true`). `paintEmu`'s `grayscale` arg is `!tp.focused`; cursor cells are exempted (hard-coded `cursorFG/cursorBG` overwrites the grayscale style so the agent position remains visible). `SetFocused` invalidates `paintCacheValid` on state change so the next Draw re-renders with the new color mode. `ColorDefault` passes through unchanged (`!c.Valid()`) so the panel keeps the terminal's own background instead of a forced hard gray. `GrayscaleColor` resolves palette indices through `Color.Hex()` (a palette color is NOT inherently r==g==b). `tcell.Style.Decompose()` returns only fg/bg/attrs, so the **underline color is a third channel** `DesaturateStyle` must gray separately (`GetUnderlineColor` → `Underline(gray)`) or SGR 58 colored underlines leak through.
- **Replay rebuild's `firstByteOffset` must be monotonically non-increasing across rebuilds for an alive session.** The default 8MB tail read positions `firstByteOffset = fileSize - 8MB`. When the agent writes more bytes between rebuilds, fileSize grows, so a naive re-read moves firstByteOffset forward and drops the oldest bytes the previous build cached. User-visible: scrolling past `replayEmuMaxScroll` triggers a rebuild → the deepest-cached content jumps out from under the cursor. Fix: `asyncReplayRebuild` accepts `prevFirstByte`, grows `needed` so the new firstByteOffset ≤ prevFirstByte, capped at `replayRebuildMaxBytes` (64MB).
- **`asyncReplayRebuild` must not trigger `onDone` when it bails out empty.** Calling onDone schedules another Draw, which immediately re-enters the slow path and kicks a fresh no-op goroutine — a CPU-burning spin loop while the placeholder is on screen. Set `replayNoDataUntil` to gate re-kicks for a short cooldown and skip `onDone` so external events (tick, keystroke, agent output) drive the retry.
- **A ceiling-hit replay rebuild must EXTEND the read by an absolute byte chunk, not trust the `(scrollOffset+viewport)*cols*3` line heuristic (BUG-E).** That heuristic maps visible lines→log bytes, but escape-dense agent output (Claude's in-place spinner/stream repaints) packs far more bytes per NET scrollback line, so 8MB of log yields far fewer net lines than the heuristic assumes. Because `scrollOffset` is clamped back to `replayEmuMaxScroll` after every rebuild (`consumeReplayRebuildPendingLocked`), pressing Up at the loaded ceiling re-asks for the SAME 8MB window → same `maxScroll` → a feedback-loop DEADLOCK: older on-disk history is unreachable even though the 64MB/50K-line caps aren't hit (raising the 8MB floor only moves the stall, never breaks the loop). Fix: `Draw` passes `extend=true` to `asyncReplayRebuild` when `alive && dims match && replayEmuFirstByte > 0 && scrollOffset > replayEmuMaxScroll`; `replayRebuildReadSize` then grows `needed` to `(fileSize - prevFirstByte) + scrollExtendChunk` (8MB), so each ceiling hit reads strictly further back until firstByte reaches 0 — independent of density. `extend` requires the dimension match so a dimension-change rebuild reads fresh at the new size rather than extending. Still bounded by `replayRebuildMaxBytes` (64MB) and the 50K-line replay scrollback (deliberate memory ceilings). This is the lazy, on-demand path — it never eagerly replays the whole (multi-MB) log on reattach. Dead-session replay is unaffected (its cache validity is log-size-based, not maxScroll-based, so it never re-reads on scroll).
- **The scroll-mode replay emulator must be built at the width the scrollback bytes were AUTHORED for (`replayEmuDims`: live `sess.PTYSize()` → `.size` sidecar → pane floor), NOT the raw pane width.** A LIVE session viewed in a pane NARROWER than its PTY (a resize the agent hasn't re-emitted for, a split layout, or a second wider viewer) has scrollback committed at the wider PTY width. Re-emulating that in a pane-width emulator clamps absolute cursor positioning (CSI nG / CUP) at the right edge and turns the agent's in-place redraws into fake garbage scrollback — the reported live-scroll corruption: fragmented ~one-word-per-line reflow, a stranded single-char column down the far-right edge (two widths overlaid), and the live footer + PTY input prompt re-shown inside scrollback. At the authored width the redraws stay in place (`sbLen≈0`) and the view is clean; `paintEmu`'s `renderCols = min(emuCols, w)` clips to the pane. This is the SAME emulate-wide-clip fix the dead-session preview uses (`previewEmuSize`); the live agent-view scroll path just never adopted it. `replayEmuDims` never returns NARROWER than the pane, so the common pane==PTY case is a no-op. `Draw`'s scroll path must use the resolved `replayCols/replayRows` for the emu build, the cache-validity dim check, the `extend` dim check, and `paintEmu`'s emuCols/emuRows — while `width/height` stay the pane clip; the in-flight FALLBACK paint must use each fallback emulator's OWN build dims (stale replay = `replayEmuCols/Rows`, live = `emuCols/Rows`), not the freshly-resolved dims. The residual known limit (mixed-width history from a mid-session resize) still needs the kill+resume kick; this fixes the dominant single-authored-width case.
- **`EagerReplayBuild` must skip when ptyCols/ptyRows are still zero.** Substituting 80×24 defaults produces a cache that the first Draw at the real panel size immediately invalidates (`replayEmuCols != ptyCols`). Defer the eager build until the first Draw has resolved the panel dimensions.
- **`paintEmu` must explicitly blank rows below the last content row.** When content shrinks frame-to-frame (cleared rows, scrollback contraction, dimension reduction), the row loop breaks early at `lineIdx > endLine` and leaves the trailing rows untouched. tcell's per-cell diff retains stale cells from the prior paint, and on the next keystroke redraw the paint cache (`replayPaintCache`) serves them again — visible as ghost lines below new content. Track `contentRows` from the row loop, then run a fill-with-spaces pass over `[contentRows, h)` and append those blanks to `paintCacheCells`.

- **`tp.emu` rebuild must invalidate `paintCacheValid` before falling through.** Dimension change in `renderLive` creates a fresh emulator but the paint cache from the prior frame may still be flagged valid. The replay path (when no new bytes arrive but viewport matches) would serve stale cells for one frame before the next paintEmu refreshes. - **OSC sequences MUST be stripped before feeding the emulator (`oscfilter.go`), because x/ansi treats a 0x9C byte inside an OSC string as a C1 String Terminator even when it's a UTF-8 continuation byte.** `charmbracelet/x/ansi` `parser_decode.go` (StringState, `case ST:`) ends the OSC at the first 0x9C. Many glyphs encode 0x9C — e.g. Claude's spinner title `ESC]2;✳ …BEL` where ✳ = `E2 9C B3`. The parser truncates the title at the `9C` and renders the tail (" …") as printable ground text. An in-place `AskUserQuestion` repaint then overwrites most of the leak, but Claude positions each option label with `ESC[6G` (cursor to column 6), skipping column 5 — so exactly one leaked character survives in that gap, appearing between `1.` and the option label (the "stray character in AskUserQuestion"). tmux/xterm never reproduce it: in UTF-8 mode they don't treat a continuation byte as ST. The fix is the `oscFilter` streaming state machine that drops `ESC] … (BEL | ESC\)` entirely — it deliberately does **not** treat 0x9C as a terminator (that's the bug), and is safe because the pane never displays window titles and OSC-8 hyperlink text is ground text that survives. The persistent `tp.oscStrip` filter must be `reset()` whenever `tp.emu` is recreated (so it re-syncs to the clean escape boundary of the re-fed history) and carries state across incremental feeds (an OSC can split across two deltas). Upgrading x/ansi does not help — v0.11.7 has the identical code. - **A full-screen agent (alternate screen) gets the mouse WHEEL forwarded to it, NOT the pane's own scrollback (BUG-026).** Agents like Claude Code / Codex run as full-screen TUIs (`ESC[?1049h` + cursor-home `ESC[H` in-place redraws) that push ~zero lines into terminal scrollback, so wheel-up on the pane's own scrollback was a silent no-op (confirmed by feeding real session logs through the replay emulator: a coordinator that emitted scrolling output → sbLen≈2791, scrollable; a worker that redrew in place → sbLen=0, `maxScroll`=0). `TerminalPane.MouseHandler` now calls `agentOwnsWheel()` (live session AND `tp.emu.IsAltScreen()`) and `forwardWheel()`s the event as an SGR frame (`ESC[<64|65;Cx;Cy M`, button 64=up/65=down, 1-based inner-rect coords clamped like the plugin forwarder #681) to the agent via `sess.WriteInput`, so the agent scrolls its OWN view — mirroring how a real terminal hands the wheel to the foreground app. A non-alt-screen agent or a finished/replay session keeps the pane's terminal scrollback (its on-disk log replay is the only way to scroll its history). This is NOT a routing/click-to-focus bug — the wheel always reached the pane (scroll-DOWN visibly redrew); there was simply no scrollback to reveal.
- **The LIVE emulator's scrollback must be capped well below x/vt's 10K-line default — an unbounded/high cap causes real input lag on long, high-output sessions, not just memory growth.** The vendored `x/vt` library's `Scrollback.Push` evicts the oldest line via `slices.Delete(s.lines, 0, 1)` once at capacity — an O(cap) shift of the entire backing slice, paid on every line that scrolls off the top of the screen (`Screen.DeleteLine` → `scrollback.PushN` → `Push`). `newTrackedEmulatorWithCallback` never overrode x/vt's 10K-line default, so any live session whose output scrolled past 10K total lines paid that shift on every subsequent scrolled line, synchronously inside `SafeEmuWrite` on the tview main goroutine — the SAME goroutine that processes keyboard input. Regression test: `TestTerminalPane_LiveEmulatorHasBoundedScrollback`.

- **`readLiveRebuildHistory`'s "no log" ring-only fallback can return a tail that does not start at a clean escape boundary, and `AlignToEscBoundary`'s "no ESC found → likely plain text, safe to feed" assumption is WRONG for that specific case (BUG-079, a sibling of BUG-068/073/074/075/076 in the same reconstruction family, but a distinct mechanism).** Every OTHER return path in this function is safe: a log-backed read (`readLogTailForTask`) always starts at position 0 for any session under `liveRebuildHistorySize` (8MB), and the merge-overflow path only appends a small ring tail onto that already-from-0 prefix — so `AlignToEscBoundary` always has an earlier, real ESC to realign to. The ring-ONLY fallback (`len(logRaw)==0` — no on-disk log, e.g. `StartSession`'s `os.OpenFile` error is silently discarded, so any transient disk/permissions hiccup at session start disables logging for that session's entire lifetime with no operator-visible signal) is the ONE path that can return an ARBITRARY, non-zero-start cut: once `ringTotal` exceeds the ring's read size (256KB), `RecentOutputTailWithTotal` no longer covers back to position 0.
