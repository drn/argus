# Usage budget routing gotchas

Budget-aware routing is advisory steering, not enforcement.

- **`[hera.worker_budget]` is RETIRED, not renamed (`fix-backend-routing-semantics`).** Its `enabled` flag was a trap name — it meant "force the fallback backend unconditionally, ignoring `threshold_pct`," not "turn on threshold routing" — and this forced every hera worker spawn onto the fallback (codex) regardless of actual Claude headroom (confirmed: 26 live tasks stamped `backend=codex` while Claude usage sat at ~40%, well under the user's configured 90% threshold). `usagebudget.ResolveWorkerBackend` and its two call-site wrappers are deleted outright. `[backend_routing]`'s tier list (below) is now the sole mechanism for both hera worker/freelance spawn and general task-creation default resolution — there is no replacement one-way switch. The user must delete `[hera.worker_budget]` from `~/.argus/config.toml` by hand; no migration shim exists.

- **Claude `/usage` is reachable from a headless PTY-backed Claude Code subprocess.** The daemon probe relies on the rendered "Current week (all models)" line and reset timestamp from that client-side screen, without creating an Argus task or spending model tokens.

- **The probe and parser fail open by design.** Probe failures, parse drift, missing cache, or stale cache all leave the tier-list resolver treating that tier as available (never block resolution) — see `backend-tier-routing` below for the resolver that now consumes these readings.

- **Daemon-side probe logging is a confirmed, structural silent void, not merely under-observed.** `uxlog.Init` is called only from `cmd/argus/main.go`'s `runTUI()` and `cmd/argus/remote.go`'s remote-TUI entry point — never from the daemon subcommand path — and `uxlog.Log` is a documented no-op when `Init` was never called. Every `[usagebudget]`/`[backendtier]` log line the probe goroutines emit (`internal/daemon/daemon.go`'s `runUsageBudgetPoller`/`runCodexProbePoller`, both correctly wired and ticking every 30 min) is unconditionally discarded today. This is why the TUI status bar now surfaces both cached readings directly (see `tui-shell`'s usage-readout requirement) instead of relying on logs — logs were never a viable observability path for daemon-side probe health. **This bit the fix itself, not just the pre-existing code**: a first draft of `resolveCoordinatorBackend`'s non-Claude-capable warnings and the Codex-PTY-fallback-disabled notice used `uxlog.Log` alone — fine for `SpawnHeraCoordinator` (TUI-initiated) but invisible for `MaterializeHeraSubCoordinator` (gater-triggered, daemon-side) and for `backendtier.Probe` (always daemon-side). Fixed by emitting through BOTH `uxlog.Log` and `slog.Warn` at every such call site — `slog` always reaches somewhere real in both processes (the daemon's `daemon.log`, or the TUI's own redirected default-logger destination), so a caller doesn't need to know which process will execute the code to get a warning that is actually observable. Any new probe- or routing-related warning added to this area should follow the same emit-both pattern, not just `uxlog.Log` alone.

- **The Codex probe's free (rollout-file) path can be silently dead even though the mechanism is correctly implemented**, because Argus-spawned Codex sessions use an isolated `CODEX_HOME` overlay (`internal/skills/builtin.go`'s `ArgusCodexHome`, normally `~/.local/share/argus/codex-home`, which symlinks the real `~/.codex` tree's `sessions` dir in) — if that overlay directory was never successfully created (observed on one machine: the directory didn't exist at all, despite 26 DB rows stamped `backend=codex`), rollout files never land anywhere `backendtier.codexSessionsRoot()`'s hardcoded `~/.codex/sessions` lookup can see. Before `fix-backend-routing-semantics` this silently fell through to the costed live PTY fallback on EVERY tick (~48 codex sessions/day spent purely asking codex how much quota is left, confirmed against this machine's own history); the fallback is now opt-in and off by default (`config.BackendRoutingConfig.CodexPTYFallbackEnabled`, `backendtier.SetCodexPTYFallbackEnabled`, reflected live from config every probe tick in `Daemon.probeCodexOnce`) — a dead rollout path with the fallback left off now simply leaves the cache stale/unknown, the same as any other fail-open probe miss, never a silent spend. **Root-causing WHY `ensureCodexSkills` never created that directory is a separate, not-yet-filed investigation, not fixed here**: its own failure path (`internal/agent/agent.go`'s `ensureCodexSkillsFn()` call site) logs through the identical `uxlog.Log` channel confirmed structurally discarded in the daemon process (see the bullet above) — so on this machine it is impossible to tell "it has been failing silently every single spawn" from "no codex session has actually completed `BuildCmd`'s codex branch at all" without first fixing the daemon-side uxlog gap, which is a materially larger, orthogonal change (daemon-wide logging, not backend routing) left for its own follow-up.

## Tiered backend routing (`internal/backendtier`, `add-tiered-backend-routing`, re-scoped by `fix-backend-routing-semantics`)

Generalizes usage-aware routing to task-backend resolution via an ordered, user-configurable `[backend_routing]` tier list, consulted through `agent.ResolveBackend`'s precedence chain (`explicit > project.Backend > backendtier.ResolveBackend(cfg) > cfg.Defaults.Backend`).

- **This tier list is now the ONLY budget-aware resolution mechanism in the codebase — general task creation AND hera worker/freelance spawn both resolve through it.** `add-tiered-backend-routing` originally scoped this to "general (non-hera)" resolution on the premise that `agent.ResolveBackend`'s tier branch was reachable at session-start/resume time even though `CreateAndStart` stamped a concrete backend at creation time first. That premise was wrong in a way that mattered: `CreateAndStart` (`internal/agent/create.go`) blindly stamped `cfg.Defaults.Backend` onto every task created with no explicit backend, which made the tier branch (and a project-level `Backend` override) **permanently unreachable for every freshly created task**, hera or otherwise — confirmed empirically (114 live tasks, zero with a backend chosen by anything but an explicit value or the global default). `fix-backend-routing-semantics` collapsed the two independent copies of this precedence chain (`agent.ResolveBackend`'s and `CreateAndStart`'s own ad hoc version) into one shared unexported `resolveDefaultBackendName`, called from both places, so the tier list and project.Backend are reachable wherever either function runs. `usagebudget.ResolveWorkerBackend` (the old hera-only Claude→single-fallback valve) and its two call-site wrappers in `internal/mcp/hera.go`/`internal/heragater/heragater.go` are deleted outright — hera worker/freelance spawn now just passes its caller's explicit `backend` (or empty) straight through to `CreateAndStart`, which resolves the same way any other task does. `usagebudget.CachedClaudePct`/`CachedReading` remain and are still what `backendtier.ResolveBackend`'s `claude_usage` probe kind reads.

- **Hera coordinator and sub-coordinator spawn are the ONE deliberate exception, enforced structurally, not by omission.** coord-hook's context-size stamping, token/cost accrual, and the recycle machinery are Claude-Code-only, so a coordinator must never land on a non-Claude-capable backend regardless of tier state. Unlike the old design (where coordinators were safe only incidentally, because nothing ever routed anywhere non-default), `internal/agent/hera_spawn.go`'s unexported `resolveCoordinatorBackend(explicit, project, cfg)` is called by both `SpawnHeraCoordinator` and `MaterializeHeraSubCoordinator` before the backend ever reaches `CreateInput`: an explicit caller-supplied backend still always wins (operator override, mirroring the old worker-budget precedent), but a non-Claude-capable explicit choice is never accepted silently — a `uxlog` warning names what breaks. With no explicit backend, ordinary resolution runs and its result is kept only if `agent.IsClaudeBackend` (exact command-basename match, an include-list) says so; otherwise this fails open to the literal `"claude"` backend. `hera_new_orchestrator` (binds an EXISTING task as a coordinator, never calls `CreateAndStart`) is NOT covered — a worker already running on a non-Claude backend that self-promotes to coordinator keeps that backend, a known follow-up, not an oversight (you cannot swap a live session's backend out from under it).

- **Probe kinds are hardcoded per-provider and dispatched by a kind string (`claude_usage`/`codex_usage`/`none`), not a plugin interface.** `backendtier.ResolveBackend`'s tier-list walk `switch`es on `tier.Probe`; adding a new kind (e.g. a hypothetical Gemini probe) means a new `case` plus one new hardcoded probe function, never a generic `Prober` registration mechanism. An unrecognized probe kind is skipped (never available), not an error.

- **The Codex probe prefers a free rollout-file read over a costed PTY probe, in that order.** `backendtier.Probe` tail-scans the most recently modified `~/.codex/sessions/**/rollout-*.jsonl` for the last record carrying `rate_limits`; the costed headless `codex` PTY `/status` fallback runs only when that yields nothing AND `codex_pty_fallback_enabled` is on. It genuinely spends Codex quota to check Codex quota (accepted trade-off), and its `/status` parser is defensive-by-necessity (openai/codex#15281).

- **The TUI status bar's always-visible `cla 42% · cdx 76%` readout is relayed, not locally computed — the TUI process has no probe cache of its own.** The probe tickers (and their in-memory caches) live only inside the daemon process; a separate TUI process (the normal local-mode shape once a daemon is running) or `argus doctor` has an empty cache even when the daemon's is fresh. `daemon.BootInfoResp` gained four additive fields (`ClaudeUsagePct`/`ClaudeUsageKnown`/`CodexUsagePct`/`CodexUsageKnown`, populated in `RPCService.BootInfo` from `usagebudget.CachedClaudePct()`/`backendtier.CachedCodexPct()`) — additive-safe with no `ProtocolVersion` bump needed, since the TUI↔daemon `BootInfo` RPC is plain JSON-RPC (`net/rpc/jsonrpc`), unrelated to the supervisor R/S protocol `ProtocolVersion` actually gates. `App.reevaluateUsage`/`claimUsageCheck` poll it on `usageRecheckInterval` (1 minute, mirroring the pre-existing skew-recheck cadence — far more frequent than needed since the daemon's own probes refresh only every 30 minutes, but reusing an established, already-proven-cheap cadence beat inventing a third one) via the same `skewProvider` the binary-skew recheck already holds, so it is nil (and the bar permanently shows unknown) in exactly the cases BootInfo is unreachable anyway: `--remote` mode and the in-process-runner fallback. `*Known` folds in staleness already (mirrors each package's own `CacheMaxAge` fail-open check), so the status bar needs no freshness math of its own — a stale OR never-probed reading renders as a literal `—` (never a 0% or a stale-but-plausible-looking percentage), which is the one hard requirement this feature exists to satisfy: a silently-stale number here would reproduce the exact silent-failure mode that motivated building it. Web SPA and macOS app parity is an explicit, named non-goal (see the `tui-shell` delta spec) — both are real daemon clients that get nothing from this change; REST exposure was judged more scope than this change should carry.

- **config.toml wins wholesale over the DB — no per-tier merge.** `db.Config()` loads `cfg.BackendRouting.Tiers` from the `backend_tiers` DB table *before* `cfgLoader.Apply` runs, so a non-empty `[[backend_routing.tier]]` table in config.toml fully replaces the slice during TOML decode (same mechanism `Backends`/`Projects` already rely on for "config.toml wins"). There is no world where config.toml supplies tiers 1–2 and the DB supplies tier 3; whichever source is present governs the entire list. `db.BackendTiersFromConfigToml()` (via `FileLoader.DefinesBackendRoutingTiers()`) is the TUI's read-only signal — it reflects only the *last* `Config()` call's finding, so it's meaningless before one has run, and is always `false` for an in-memory/remote store.

## Probe mechanics (`fix-backend-usage-routing`)

- **`claude -- /usage` is interactive and never exits.** Waiting for the process to finish just times out every probe; `usagebudget.Probe` streams PTY output into the emulator, parses after each chunk, and terminates the process group (SIGTERM, then kill) as soon as the reading renders — never `Wait` for a natural exit.

- **A 24-row PTY hides the weekly section below the fold.** "Current week (all models)" only renders on-screen with ≥80 rows, so the probe PTY is 100x80; the percentage sits on the line after the header, not on the header line itself.

- **Folder-trust and external-imports dialogs block the probe outright.** The probe runs in a dedicated, empty `~/.argus/usage-probe` and answers only a trust dialog that names that directory (any other dialog aborts + logs); answering the instant it appears lands on "No, exit", so the probe waits for the dialog to settle before pressing Enter.

- **The first `/usage` paint is a stale cached screen, followed by a "Refreshing…" redraw.** Only parse between synchronized-update frames (never mid-frame) and skip any screen still showing "Refreshing…", or the probe caches the stale number.

- **Probe logs must go through `slog` as well as `uxlog`.** `uxlog` is a no-op in the daemon (see above), so `logInfo`/`logWarn` emit both; a `uxlog`-only probe line is invisible in `daemon.log`.

- **Codex's weekly window lives in `primary`, not `secondary`.** Identify windows by `window_minutes` (10080 = weekly, 300 = 5h), never by slot name. A depleted record has both windows `null` plus `rate_limit_reached_type`; record it as 100% held 24h anchored to the rollout file's mtime (when the limit was hit), not probe time, or every re-probe re-extends the hold. A live weekly reading is valid until its `resets_at`.

- **`strategy = "headroom"` prefers a known reading over an unknown one.** Among capped tiers it picks the most room under threshold; an unknown/stale reading (or a `none` probe) is only taken when no known reading qualifies — the opposite of `ordered`'s fail-open-in-list-order.

- **Daemon tests must never reach the real probes.** The pollers probe immediately at startup, so `daemon.New` wires the defaults through `defaultProbe` (`internal/daemon/probeguard.go`), a no-op under `isTestBinary()`. This covers `daemon.New` callers outside the package (`cmd/argus`, `internal/daemon/client`) that can't reach the seams; the guard sits on the daemon's default wiring, not inside `usagebudget.Probe`/`backendtier.Probe`, so those packages' own tests still drive Probe end to end via their internal seams.
