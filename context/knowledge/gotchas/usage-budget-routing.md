# Usage budget routing gotchas

Budget-aware routing is advisory steering, not enforcement. Exhausted tiers can still fall back to the existing default when no eligible tier remains.

- **`[hera.worker_budget]` is RETIRED, not renamed (`fix-backend-routing-semantics`).** Its `enabled` flag was a trap name — it meant "force the fallback backend unconditionally, ignoring `threshold_pct`," not "turn on threshold routing" — and this forced every hera worker spawn onto the fallback (codex) regardless of actual Claude headroom (confirmed: 26 live tasks stamped `backend=codex` while Claude usage sat at ~40%, well under the user's configured 90% threshold). `usagebudget.ResolveWorkerBackend` and its two call-site wrappers are deleted outright. `[backend_routing]`'s tier list (below) is now the sole mechanism for both hera worker/freelance spawn and general task-creation default resolution — there is no replacement one-way switch. The user must delete `[hera.worker_budget]` from `~/.argus/config.toml` by hand; no migration shim exists.

- **Claude routing uses the fuller valid five-hour/session or seven-day/all-models window.** Keep both windows until read time: session reset must immediately expose a still-valid weekly limit; neither heartbeats nor re-reading old state refreshes a measurement.

- **The probe and parser fail open by design.** Probe failures, parse drift, missing cache, or stale cache all leave the tier-list resolver treating that tier as available (never block resolution) — see `backend-tier-routing` below for the resolver that now consumes these readings.

- **Probe and routing outcomes must emit through both uxlog and slog.** The daemon never initializes uxlog, so uxlog alone silently discards warnings; log the chosen backend/account and strategy/reading reason at creation, and invalid tier accounts when skipped.

- **The Codex probe's free (rollout-file) path can be silently dead even though the mechanism is correctly implemented**, because Argus-spawned Codex sessions use an isolated `CODEX_HOME` overlay (`internal/skills/builtin.go`'s `ArgusCodexHome`, normally `~/.local/share/argus/codex-home`, which symlinks the real `~/.codex` tree's `sessions` dir in) — if that overlay directory was never successfully created (observed on one machine: the directory didn't exist at all, despite 26 DB rows stamped `backend=codex`), rollout files never land anywhere `backendtier.codexSessionsRoot()`'s hardcoded `~/.codex/sessions` lookup can see. Before `fix-backend-routing-semantics` this silently fell through to the costed live PTY fallback on EVERY tick (~48 codex sessions/day spent purely asking codex how much quota is left, confirmed against this machine's own history); the fallback is now opt-in and off by default (`config.BackendRoutingConfig.CodexPTYFallbackEnabled`, `backendtier.SetCodexPTYFallbackEnabled`, reflected live from config every probe tick in `Daemon.probeCodexOnce`) — a dead rollout path with the fallback left off now simply leaves the cache stale/unknown, the same as any other fail-open probe miss, never a silent spend. **Root-causing WHY `ensureCodexSkills` never created that directory is a separate, not-yet-filed investigation, not fixed here**: its own failure path (`internal/agent/agent.go`'s `ensureCodexSkillsFn()` call site) logs through the identical `uxlog.Log` channel confirmed structurally discarded in the daemon process (see the bullet above) — so on this machine it is impossible to tell "it has been failing silently every single spawn" from "no codex session has actually completed `BuildCmd`'s codex branch at all" without first fixing the daemon-side uxlog gap, which is a materially larger, orthogonal change (daemon-wide logging, not backend routing) left for its own follow-up.

## Tiered backend routing (`internal/backendtier`, `add-tiered-backend-routing`, re-scoped by `fix-backend-routing-semantics`)

Generalizes usage-aware routing to task-backend resolution via an ordered, user-configurable `[backend_routing]` tier list, consulted through the shared backend/account choice used by task creation and backend resolution.

- **Resolve backend and account together before creation side effects.** Explicit/project backend names restrict backend choice but still permit account routing; account precedence is explicit nonblank/inherited pin → project_accounts → routed tier account → default_account → default, and stored tasks never change account on resume.

- **Coordinators filter tiers to Claude-capable backends, including their accounts.** Ordinary workers omit backend; reserve an explicit Claude backend for actual worker self-promotion, Claude-only connectors/MCP, or in-session Claude review panels. If no eligible Claude tier resolves, retain the literal Claude fallback; self-promotion on a non-Claude task is rejected.

- **Probe kinds are hardcoded per-provider and dispatched by a kind string (`claude_usage`/`codex_usage`/`none`), not a plugin interface.** `backendtier.ResolveBackend`'s tier-list walk `switch`es on `tier.Probe`; adding a new kind (e.g. a hypothetical Gemini probe) means a new `case` plus one new hardcoded probe function, never a generic `Prober` registration mechanism. An unrecognized probe kind is skipped (never available), not an error.

- **The Codex probe prefers a free rollout-file read over a costed PTY probe, in that order, every tick.** `backendtier.Probe` first tail-scans the most recently modified `~/.codex/sessions/**/rollout-*.jsonl` for the last record carrying a `rate_limits` object and only falls back to a headless `codex` PTY session + `/status` scrape (opt-in, see above) when that read yields no valid reading. The PTY fallback genuinely spends Codex quota to check Codex quota, and its `/status` text parser is defensive-by-necessity since the upstream format was unstable at design time (openai/codex#15281).

- **Codex's weekly window lives in `primary`, not `secondary` (`fix-backend-usage-routing`).** Real rollouts carry `primary: {window_minutes: 10080, ...}` with `secondary: null`, so `weeklyCodexWindow` selects by `window_minutes == 10080`, never by slot; any other window (5h) is ignored. A depleted account's records have BOTH windows null plus a non-null `rate_limit_reached_type` — read as 100% with an unknown reset, held `NoResetHold` (24h) from the rollout file's **mtime** (`Reading.HeldFrom`), not the probe time, so re-probing the same file every 30 min can't extend the hold forever.

- **Codex readings are valid until their weekly `resets_at`, not for a fixed age (`fix-backend-usage-routing`).** The old 1-hour rollout-mtime gate rejected every reading whenever Codex hadn't been used in the last hour; but every Codex use writes a new rollout, so the newest rollout stays the best reading until its own reset. `Reading.validAt` is the single validity rule shared by `rolloutReading` (so an expired rollout still falls through to the opt-in PTY fallback) and the cache snapshot (so a cached reading goes unknown the instant its reset passes, with no re-probe needed).

- **Headroom strategy treats `none`-probe tiers as "no reading", not "infinite headroom".** Otherwise an uncapped local backend would always win in `headroom` mode. Unknown readings are only considered when no tier has a known under-threshold reading — the old fail-open "unknown = available" is exactly what let a broken probe silently steer all work in `ordered` mode. An unrecognized `strategy` is warned once per distinct value (`sync.Map`), since `ResolveBackend` runs on every task creation.

- **The Claude startup/30-minute poller probes each distinct configured Claude tier account with its own CLAUDE_CONFIG_DIR and cache.** A fresh bridge measurement skips only that account’s hidden probe; remove inherited auth overrides and parent-session markers before launch. Daemon tests must stub both probe seams to avoid real accounts and subprocesses.

- **The TUI readout is a BootInfo relay from daemon caches, never a TUI-local probe.** `cla 96%s` means session binds and `cla 75%w` means week binds; stale/absent readings remain `—`, and remote/in-process fallback has no cache. Web/macOS controls/readouts remain the named follow-up `web-macos-routing-settings-parity`.

- **config.toml wins wholesale over the DB — no per-tier merge.** `db.Config()` loads `cfg.BackendRouting.Tiers` from the `backend_tiers` DB table *before* `cfgLoader.Apply` runs, so a non-empty `[[backend_routing.tier]]` table in config.toml fully replaces the slice during TOML decode (same mechanism `Backends`/`Projects` already rely on for "config.toml wins"). There is no world where config.toml supplies tiers 1–2 and the DB supplies tier 3; whichever source is present governs the entire list. `db.BackendTiersFromConfigToml()` (via `FileLoader.DefinesBackendRoutingTiers()`) is the TUI's read-only signal — it reflects only the *last* `Config()` call's finding, so it's meaningless before one has run, and is always `false` for an in-memory/remote store.

- **A blank coordinator DB account is unpinned; explicit `default` must remain nonblank.** Hera inherits the stored value as-is so existing blank-account coordinators can route workers onto overflow accounts, while named or explicit-default coordinators preserve their account pin. Forks retain their separate PinnedAccount behavior.

- **A headless session-only partial frame must not end the probe before weekly usage paints.** Time-only session resets can cross midnight; infer the next day only within the five-hour window, and never revive an explicitly dated expired reset.

- **Never score a named Codex tier using the default account’s rollout.** Named Codex usage remains unknown until an account-scoped Codex reader exists; Claude named tiers are measured by their own bridge or headless probe.
