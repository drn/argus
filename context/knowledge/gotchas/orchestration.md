# Orchestration Gotchas

Hera orchestration + task-creation invariants that caused bugs when violated.

> **The `depends_on` DAG / depswatcher / stacked-PR auto-gating subsystem was retired** — Hera (coordinator-driven worker spawning) is the single orchestration model. Removed: `model.Task.DependsOn`/`PlanSlug` (+ DB columns), `internal/depswatcher`, `internal/orch`, `agent.StartPendingBlocked`, the CreateAndStart dep short-circuit, `task_link`/`unlink`/`deps`/`halt_downstream`/`set_plan_slug` (MCP + REST), `/api/dag`, the standalone TUI DAG tab, and the SPA DAG view. `base_branch` (git-stacking mechanic) was KEPT — a coordinator sequences workers itself and branches them off each other. Tasks always start immediately on creation now.

## task_set_result

- **Re-encode via json.Marshal before persisting.** The raw bytes from the wire can include trailing whitespace, integer formatting quirks, or key ordering. Re-marshalling produces deterministic storage so test assertions and orchestrator diffs work.
- **64 KiB cap is on the serialized form.** Counting input bytes would let a pathological input expand on re-encode; counting output is the safe order.
- **Result is opaque to the daemon.** SQLite stores it as TEXT, the watcher never reads it, the MCP server renders it inside a code block. Adding any daemon-side parse of the result would couple the orchestration contract to the daemon — keep it agent-owned.

## ARGUS_TASK_ID env var

- **Skip the export when task.ID is empty.** CreateAndStart sequences db.Add → ID assignment → BuildCmd, so task.ID is non-empty in practice. The defensive `if task.ID != ""` guard ships an explicit no-export instead of `ARGUS_TASK_ID=` (empty value) if that invariant ever changes.
- **cmd.Env starts from os.Environ().** Replacing without inheriting breaks PATH, HOME, NODE_PATH, and every other env var the agent backend relies on. The append-after-os.Environ pattern is the only safe form.

## task_create idempotency

- **Only applies when name was user-supplied.** AutoName (no `name` arg) skips the duplicate check because two prompts producing the same first-40-chars slug are coincidental, not orchestrator restarts. If you flip this, schedule-fired tasks would collide with each other on the timestamp suffix.
- **Archived rows are skipped.** Archive is the user's "kill this stack" signal; re-using the slug after archive must work, otherwise the orchestrator can't retry a failed stack with the same naming scheme.

## Schema migration

- **base_branch / result are idempotent ALTER ADDs; depends_on / plan_slug are idempotent ALTER DROPs.** The CREATE TABLE has base_branch+result; the migration block ADDs them (fresh + migrated DBs converge). The retired depends_on+plan_slug columns are dropped via idempotent `ALTER TABLE tasks DROP COLUMN` in the same block (safe on fresh DBs where they never existed — mirrors the `todo_path`/`pr_url` drops). If you reorder taskColumns without updating the INSERT/UPDATE/scan strings in lockstep, the scan will mis-bind columns silently (status into worktree, etc.).

## Hera schema / store (M1)

- **FK cascade in the hera_* tables requires `foreign_keys(on)` on the connection DSN.** SQLite defaults `PRAGMA foreign_keys` OFF per-connection, and Argus's DSN historically didn't set it. Both `Open` and `OpenInMemory` now append `_pragma=foreign_keys(on)` (modernc applies it to every pooled connection). Without it, `DeleteHeraOrchestrator`/`DeleteHeraRole` would orphan child rows instead of cascading — and the failure is silent (no error, just leftover rows). Safe to enable globally because no other Argus table declares an FK.
- **Nullable timestamp columns (archived_at/pinned_at/ended_at/end_reason) must be real `NULL`, never `''`.** The partial indexes (`WHERE archived_at IS NULL`, `WHERE ended_at IS NULL`) only index rows where the column is actually NULL; storing an empty string (the convention Argus's `tasks` uses for absent times) would exclude "live"/"active" rows from the partial unique index and silently break the uniqueness backstop. This is why the hera scanners use `sql.NullString`→`*time.Time` and writes set `= NULL`, diverging from the task-side `formatTime('')` convention.
- **Multi-binding live-uniqueness is per-`(task, orchestrator)`, not per-task** (Hera migration 0004). `orchestrator_id` is denormalized onto `hera_bindings` so the partial unique indexes need no JOIN. One task can be a worker in orchestrator A and a coordinator in B simultaneously. The orchestrator-agnostic single lookups (`HeraLiveBindingByTask`, `HeraLiveBindingByWorktree`) return `ErrHeraAmbiguous` when 2+ live rows match — callers must use the `…AndOrchestrator` / `List…` variants. Role-side stays one-live-binding-per-role.
- **Task deletion ends live bindings; archive does NOT.** `tasks.go Delete` inlines an `UPDATE hera_bindings SET ended_at=… WHERE argus_task_id=… AND ended_at IS NULL` inside its existing tx (it can't call the `*DB` method `EndHeraBindingsForTask` because `WithTx` holds `d.mu` and the mutex is non-reentrant). `SetArchived` deliberately leaves bindings live because archive is resumable. There is intentionally NO FK from `hera_bindings.argus_task_id` to `tasks` — argus_task_id is plain TEXT — so this app-level hook is the only thing that severs the link on delete.
- **Role+binding creation is transactional in one tx** (`CreateHeraRoleWithBinding`), fixing Hera's deferred debt where it was two non-transactional execs. If the binding insert violates a live-uniqueness index, the role insert rolls back too — no orphan role. Born-bound spawn (M4) builds on this.
- **The partial unique indexes are the race backstop, not just the app-level pre-checks.** `CreateHeraOrchestrator`/`CreateHeraRole` pre-check for an existing active row, but two concurrent creates resolve deterministically at the index (INSERT fails) rather than corrupting state.

## Hera MCP tools (M3)

- **`heraEnabled()` requires both heraSvc AND taskMgmtEnabled()** — caller resolution (cwd → task → binding) goes through `resolveTask`, which dereferences `s.taskDB` without a nil check. A server with `heraSvc` wired but no `taskDB` would panic. Always call both `SetHeraService` and `SetTaskManager` before starting the server.
- **dup-tool guard is scope-based, not name-based.** When `heraEnabled()`, all plugin registry entries with `Scope == "hera"` are filtered from `tools/list`. This suppresses the external Hera daemon's registered tools during the native cutover. Non-hera scopes (iris, plannotator, …) pass through regardless of name.
- **`hera_inbox` marks messages as read via an explicit `MarkRead` call after `Inbox`.** `Service.Inbox` only fetches unread messages and cancels deliveries — it does NOT stamp `read_at`. `toolHeraInbox` calls `MarkRead` immediately after to match the tool description's "marks messages as read" contract. `toolHeraJoin` (claim mode) deliberately calls only `HeraStore.HeraInbox` (not `Service.Inbox`) so join reporting doesn't consume the inbox.
- **`SetHeraService` must be called before `ListenAndServe`** — `heraSvc` and `heraStore` are read at request time without a mutex, following the `SetMessageManager` precedent. All `Set*` calls must precede server start.
- **`SetMeta` calls are best-effort soft-fail.** Any failure in `SetMeta` (task_meta mirror) logs a warning but never returns an error to the caller and never undoes the primary DB write. This is structural, not an oversight — meta is a display aid, not authoritative state.
- **`resolveCallerRole` with `orchestratorName=""` returns `ErrHeraAmbiguous` when 2+ live bindings match the task.** Callers get a human-readable list of orchestrator names. Supply `orchestrator=<name>` to disambiguate. This mirrors the `HeraLiveBindingByTask` M1 rule.

## Hera born-bound spawn + auto-adopt (M4)

- **Born-bound spawn is `agent.CreateAndStart` + an `AfterPersist` hook, NOT a post-hoc binding write.** The hook (`CreateInput.AfterPersist`) runs after the task row is persisted but BEFORE the session starts; it stamps `meta:hera.role=worker`, creates the role+binding (`CreateHeraRoleWithBinding`), and returns a compensating closure pushed onto CreateAndStart's LIFO stack. A role/binding-insert failure (return error from the hook) unwinds the task+worktree+row; a later `runner.Start` failure invokes the returned cleanup (`DeleteHeraRole`, which cascades the binding). No orphan task and no orphan role/binding in EITHER failure direction.
- **Spawn unwind LIFO order matters.** Cleanups are appended `[worktree, db.Delete(row), hook-cleanup]` and run LIFO, so `DeleteHeraRole` runs FIRST (cascading the binding away), THEN `db.Delete` (whose inline end-bindings hook finds nothing live), THEN worktree removal. Reorder and you reintroduce the orphan-role risk Hera's two-exec spawn had.
- **The depends_on-driven auto-adopt Watcher was REMOVED with the DAG.** It adopted a task linked via `depends_on` under a coordinator's task as a worker role (rule D4). Born-bound workers (`SpawnHeraWorker`) already create their bindings transactionally at spawn time, so with `depends_on` gone there is nothing to adopt across. `internal/heraadopt` now hosts ONLY `ReconcileBindings`.
- **`heraadopt.ReconcileBindings` survives — it is keyed on task-ROW existence, not depends_on.** The daemon-startup sweep (`bounce.go` calls it in both supervisor + in-process modes) ends every live binding whose `argus_task_id` no longer resolves to a task row, stamping `end_reason="task_missing"`. Needed because a task deleted while the daemon was down skips the delete-cascade hook that normally ends its bindings. Idempotent.
- **The spawn project defaults to the caller TASK's `.Project`, never `role.ArgusProject`.** Roles created before the M4 fix have an empty `argus_project`; the live task row is authoritative. The M4 fix sets `ArgusProject` on new coordinator/worker roles in `toolHeraNewOrchestrator`/`toolHeraJoin`, but every consumer must still tolerate historical empty values.

## Hera subtree TLDR roll-up (M5)

- **The subtree (TLDR roll-up) and the orchestration tree share the SAME nesting graph now.** `SubtreeOrchIDs` walks the orchestrator *nesting* graph (multi-binding bridges) for message roll-up; `heraTreeNodes` (the Details-pane graph) walks the SAME nesting in-memory for rendering. Both derive from role bindings — there is no longer a separate `depends_on` dependency graph to conflate them with (it was retired). A message roll-up is still a distinct concern from the rendered tree, but they no longer use orthogonal data sources.
- **`SubtreeOrchIDs` nesting bridge is the multi-binding shape, NOT a parent column.** Orchestrator S is a child of R when S's live, non-archived COORDINATOR role is bound to an argus task that ALSO holds a live binding (any kind) under R. There is no `parent_orch_id` column — the tree is re-derived each call by BFS over `hera_bindings` joined on shared `argus_task_id`. The Argus binding shape matches Hera's exactly (role_id/orchestrator_id/argus_task_id/ended_at), so the traversal SQL ports verbatim with only table-name changes (`orchestrators`→`hera_orchestrators`, etc.).
- **`SubtreeOrchIDs` cycle guard is a visited-orchestrator set, not a depth cap.** Hera's port carried a `maxDepth`/`truncated` pair; Argus drops both because the visited set already guarantees termination over a finite orchestrator set (a task could theoretically bridge into a loop). Never re-enqueue a seen orchestrator id. The root is ALWAYS included (the caller resolved it as their own live orchestrator); only *descendants* are subject to the archived-exclusion filter.
- **Archived orchestrators are pruned mid-traversal, taking their descendants with them.** The BFS filters `child_orch.archived_at IS NULL`, so an archived mid-tree orchestrator is never enqueued — and because nesting flows *through* it, every orchestrator hanging off it becomes unreachable too. Archiving a sub-coordinator's orchestrator silently drops that whole branch from the roll-up.
- **`tree_read_cursors.role_id` MUST be `ON DELETE CASCADE` (BUG-034).** With `PRAGMA foreign_keys=ON` (Argus enables it), a bare `REFERENCES hera_roles(id)` (default NO ACTION) makes a cursor row PIN its parent role — deleting the role or its orchestrator fails with "FOREIGN KEY constraint failed (787)". CASCADE lets the delete clean the cursor. Regression-tested by `TestHeraTreeCursor_FKCascade`.
- **The per-role tree cursor is advisory, not an at-least-once event cursor.** `hera_tree_updates` is a DB *query* over the message store, not an event consumer — so unlike Hera's old `event_cursor` (which advanced regardless of handler success and lost adoptions), this cursor is just a disposable read bookmark, re-seeded to the max id returned on every read. Auto-advance happens ONLY when the caller omits `since`; an explicit `since` overrides without clobbering the stored cursor (so a one-off historical scan doesn't reset the role's live position).
- **`HeraTreeUpdatesSince` is TLDR-only by projection, capped at `HeraTreeUpdatesLimit` (200).** The `HeraMessageTLDR` struct has no `Body` field — bodies require a follow-up `hera_get_messages` (Aaron: "super useful, don't lose it" = the token-efficient whole-tree snapshot). `nextCursor` is the max id returned (or `since` when empty), so with the LIMIT a busy subtree pages forward across repeated calls rather than returning unbounded rows. Role/orchestrator *names* are resolved in the MCP handler (cached per call), not joined in SQL, keeping the store projection id-only.
- **`hera_get_messages` access scope is the SUBTREE, not the single orchestrator (M5 expanded M3).** A message is readable when its sender OR recipient role lives in any orchestrator of the caller's `SubtreeOrchIDs`. The per-ID error-entry contract is preserved: missing/denied ids get an `error` field in their entry, never a top-level error. A message in an UNRELATED (non-nested) orchestrator stays denied.

## Linking + DAG

- **orch.Link stages the hypothetical edge on a child *copy*, not the snapshot's pointer.** A `Store` implementation that shares pointers between `Get()` and `Tasks()` (e.g. the MCP test mock) would otherwise see the parent appended twice — once via the snapshot mutation, once via the post-cycle-check `Update`. Production `*db.DB` returns fresh scanned objects so this never bites in real code, but the defensive copy keeps tests using a sharing mock from emitting duplicate edges.
- **orch.FindCycle returns the cycle path, not a bool.** A "cycle detected" error without the offending sequence is unactionable in the linking UI. Callers (web modal, TUI banner, MCP error) render `"A → B → C → A"` directly from the returned slice.
- **HaltDownstream re-queries each row's status inside the loop.** The depswatcher can flip a `pending` row to `in_progress` between the snapshot and the per-row decision; the re-query catches that and falls back from archive→stop. Without it, a racy halt would archive a row whose agent had just started, leaving an orphan PTY.
- **HaltDownstream archives `in_review` rows, not just `pending`.** An `in_review` task has no live session (the agent already exited) — calling `stopper.Stop` on it returns session-not-found and would falsely pad `report.Stopped`. The switch folds `in_review` into the archive bucket alongside `pending` so the halt summary reflects what actually happened.
- **HaltDownstream archive path uses the narrow `SetArchived` column write, not `db.Update`.** The full-row write would clobber a concurrent depswatcher-driven `pending → in_progress` status flip. Same pattern as `Link`/`Unlink`/`SetPlanSlug`.
- **HaltDownstream does NOT halt the seed task.** The seed is the user-supplied "this milestone failed" anchor; halting it would clobber the result.failed payload the orchestrator just wrote. Only the seed's transitive descendants are stopped/archived.
- **plan_slug is opaque to the daemon — same contract as result.** The daemon never inspects it, never auto-derives it, never enforces uniqueness. The orchestrator stamps every sub-task in a stack with the same slug; the DAG view uses it as a filter key. Empty string = unaffiliated.
- **Per-task linking endpoints AND halt-downstream are open to any authenticated token** (single-tier auth — see `web-remote.md` "Per-device tokens"). Halt-downstream affects multiple rows in one call and is destructive cross-task, but carries no RCE/credential risk, so it is not on the master-only denylist (backends CRUD, self-update, token mint/revoke).
- **DAG layout assumes acyclic input.** `dagview.Compute`'s Kahn topological sort uses a small cycle guard (the in-progress visit map) to avoid infinite recursion if a stale snapshot leaks a cycle past the daemon's gate. The result is a degraded but bounded layout, not a crash — but the real fix lives upstream in the cycle DFS.
