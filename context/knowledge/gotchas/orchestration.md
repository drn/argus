# Orchestration Gotchas

Hera orchestration + task-creation invariants that caused bugs when violated.

> **The `depends_on` DAG / depswatcher / stacked-PR auto-gating subsystem was retired** — Hera (coordinator-driven worker spawning) is the single orchestration model. Removed: `model.Task.DependsOn`/`PlanSlug` (+ DB columns), `internal/depswatcher`, `internal/orch`, `agent.StartPendingBlocked`, the CreateAndStart dep short-circuit, `task_link`/`unlink`/`deps`/`halt_downstream`/`set_plan_slug` (MCP + REST), `/api/dag`, the standalone TUI DAG tab, and the SPA DAG view. `base_branch` (git-stacking mechanic) was KEPT — a coordinator sequences workers itself and branches them off each other. Tasks always start immediately on creation now.
>
> **The hera-native plan-DAG (add-hera-plan-substrate) is the SUCCESSOR, not a revival.** It lives ENTIRELY in hera roles/edges (`hera_blocks`), never on `model.Task` — a planned node is a bindingless worker role, gated on hera ROLE-status `done`, materialized by `internal/heragater` (mirroring depswatcher's tick-loop shape). See "Hera plan-DAG substrate" below. The VIEW (re-pointing `dagview` at the new edges) is a separate future change — this is substrate only.

## task_set_result

- **Re-encode via json.Marshal before persisting.** The raw bytes from the wire can include trailing whitespace, integer formatting quirks, or key ordering. Re-marshalling produces deterministic storage so test assertions and orchestrator diffs work.
- **64 KiB cap is on the serialized form.** Counting input bytes would let a pathological input expand on re-encode; counting output is the safe order.
- **Result is opaque to the daemon.** SQLite stores it as TEXT, the watcher never reads it, the MCP server renders it inside a code block. Adding any daemon-side parse of the result would couple the orchestration contract to the daemon — keep it agent-owned.

## ARGUS_TASK_ID env var

- **Skip the export when task.ID is empty.** CreateAndStart sequences db.Add → ID assignment → BuildCmd, so task.ID is non-empty in practice. The defensive `if task.ID != ""` guard ships an explicit no-export instead of `ARGUS_TASK_ID=` (empty value) if that invariant ever changes.
- **cmd.Env starts from os.Environ().** Replacing without inheriting breaks PATH, HOME, NODE_PATH, and every other env var the agent backend relies on. The append-after-os.Environ pattern is the only safe form.

## task_create idempotency

- **Only applies when name was user-supplied.** AutoName (no `name` arg) skips the duplicate check because two prompts producing the same first-40-chars slug are coincidental, not orchestrator restarts. If you flip this, schedule-fired tasks would collide with each other on the timestamp suffix.
- **Archived rows are skipped.** Archive is the user's "kill this stack" signal; re-using the slug after archive must work, otherwise the orchestrator can't retry a failed stack with the same naming scheme.

## Schema migration

- **base_branch / result are idempotent ALTER ADDs; depends_on / plan_slug are idempotent ALTER DROPs.** The CREATE TABLE has base_branch+result; the migration block ADDs them (fresh + migrated DBs converge). The retired depends_on+plan_slug columns are dropped via idempotent `ALTER TABLE tasks DROP COLUMN` in the same block (safe on fresh DBs where they never existed — mirrors the `todo_path`/`pr_url` drops). If you reorder taskColumns without updating the INSERT/UPDATE/scan strings in lockstep, the scan will mis-bind columns silently (status into worktree, etc.).

## Hera schema / store (M1)

- **FK cascade in the hera_* tables requires `foreign_keys(on)` on the connection DSN.** SQLite defaults `PRAGMA foreign_keys` OFF per-connection, and Argus's DSN historically didn't set it. Both `Open` and `OpenInMemory` now append `_pragma=foreign_keys(on)` (modernc applies it to every pooled connection). Without it, `DeleteHeraOrchestrator`/`DeleteHeraRole` would orphan child rows instead of cascading — and the failure is silent (no error, just leftover rows). Safe to enable globally because no other Argus table declares an FK.
- **Nullable timestamp columns (archived_at/pinned_at/ended_at/end_reason) must be real `NULL`, never `''`.** The partial indexes (`WHERE archived_at IS NULL`, `WHERE ended_at IS NULL`) only index rows where the column is actually NULL; storing an empty string (the convention Argus's `tasks` uses for absent times) would exclude "live"/"active" rows from the partial unique index and silently break the uniqueness backstop. This is why the hera scanners use `sql.NullString`→`*time.Time` and writes set `= NULL`, diverging from the task-side `formatTime('')` convention.
- **Multi-binding live-uniqueness is per-`(task, orchestrator)`, not per-task** (Hera migration 0004). `orchestrator_id` is denormalized onto `hera_bindings` so the partial unique indexes need no JOIN. One task can be a worker in orchestrator A and a coordinator in B simultaneously. The orchestrator-agnostic single lookups (`HeraLiveBindingByTask`, `HeraLiveBindingByWorktree`) return `ErrHeraAmbiguous` when 2+ live rows match — callers must use the `…AndOrchestrator` / `List…` variants. Role-side stays one-live-binding-per-role.
- **Task deletion ends live bindings; archive does NOT.** `tasks.go Delete` inlines an `UPDATE hera_bindings SET ended_at=… WHERE argus_task_id=… AND ended_at IS NULL` inside its existing tx (it can't call the `*DB` method `EndHeraBindingsForTask` because `WithTx` holds `d.mu` and the mutex is non-reentrant). `SetArchived` deliberately leaves bindings live because archive is resumable. There is intentionally NO FK from `hera_bindings.argus_task_id` to `tasks` — argus_task_id is plain TEXT — so this app-level hook is the only thing that severs the link on delete.
- **Role+binding creation is transactional in one tx** (`CreateHeraRoleWithBinding`), fixing Hera's deferred debt where it was two non-transactional execs. If the binding insert violates a live-uniqueness index, the role insert rolls back too — no orphan role. Born-bound spawn (M4) builds on this.
- **The partial unique indexes are the race backstop, not just the app-level pre-checks.** `CreateHeraOrchestrator`/`CreateHeraRole` pre-check for an existing active row, but two concurrent creates resolve deterministically at the index (INSERT fails) rather than corrupting state.

## Hera MCP tools (M3)

- **`heraEnabled()` requires both heraSvc AND taskMgmtEnabled()** — caller resolution (cwd → task → binding) goes through `resolveTask`, which dereferences `s.taskDB` without a nil check. A server with `heraSvc` wired but no `taskDB` would panic. Always call both `SetHeraService` and `SetTaskManager` before starting the server.
- **dup-tool guard is scope-based, not name-based.** When `heraEnabled()`, all plugin registry entries with `Scope == "hera"` are filtered from `tools/list`. This suppresses the external Hera daemon's registered tools during the native cutover. Non-hera scopes (iris, plannotator, …) pass through regardless of name.
- **`hera_inbox` marks messages as read via an explicit `MarkRead` call after `Inbox`.** `Service.Inbox` only fetches unread messages and cancels deliveries — it does NOT stamp `read_at`. `toolHeraInbox` calls `MarkRead` immediately after to match the tool description's "marks messages as read" contract. `toolHeraJoin` (claim mode) deliberately calls only `HeraStore.HeraInbox` (not `Service.Inbox`) so join reporting doesn't consume the inbox.
- **`SetHeraService` must be called before `ListenAndServe`** — `heraSvc` and `heraStore` are read at request time without a mutex, following the `SetMessageManager` precedent. All `Set*` calls must precede server start.
- **`SetMeta` calls are best-effort soft-fail.** Any failure in `SetMeta` (task_meta mirror) logs a warning but never returns an error to the caller and never undoes the primary DB write. This is structural, not an oversight — meta is a display aid, not authoritative state.
- **`resolveCallerRole` with `orchestratorName=""` returns `ErrHeraAmbiguous` when 2+ live bindings match the task.** Callers get a human-readable list of orchestrator names. Supply `orchestrator=<name>` to disambiguate. This mirrors the `HeraLiveBindingByTask` M1 rule.
- **`hera_join` attach mode now rejects+redirects instead of silently double-binding (fix-hera-join-move-binding).** When the caller already holds a live binding under a DIFFERENT orchestrator, `toolHeraJoin` errors before creating anything, pointing the caller at the new `hera_move` tool (`toolHeraMove` + DB-layer `MoveHeraBinding`, which ENDS the old binding with `end_reason="moved"` and creates the new role+binding in one tx — never a second live binding). `hera_new_orchestrator`'s worker self-promotion path remains the ONLY sanctioned way a task holds 2+ live bindings simultaneously.

## Hera born-bound spawn + auto-adopt (M4)

- **Born-bound spawn is `agent.CreateAndStart` + an `AfterPersist` hook, NOT a post-hoc binding write.** The hook (`CreateInput.AfterPersist`) runs after the task row is persisted but BEFORE the session starts; it stamps `meta:hera.role=worker`, creates the role+binding (`CreateHeraRoleWithBinding`), and returns a compensating closure pushed onto CreateAndStart's LIFO stack. A role/binding-insert failure (return error from the hook) unwinds the task+worktree+row; a later `runner.Start` failure invokes the returned cleanup (`DeleteHeraRole`, which cascades the binding). No orphan task and no orphan role/binding in EITHER failure direction.
- **Spawn unwind LIFO order matters.** Cleanups are appended `[worktree, db.Delete(row), hook-cleanup]` and run LIFO, so `DeleteHeraRole` runs FIRST (cascading the binding away), THEN `db.Delete` (whose inline end-bindings hook finds nothing live), THEN worktree removal. Reorder and you reintroduce the orphan-role risk Hera's two-exec spawn had.
- **The depends_on-driven auto-adopt Watcher was REMOVED with the DAG.** It adopted a task linked via `depends_on` under a coordinator's task as a worker role (rule D4). Born-bound workers (`SpawnHeraWorker`) already create their bindings transactionally at spawn time, so with `depends_on` gone there is nothing to adopt across. `internal/heraadopt` now hosts ONLY `ReconcileBindings`.
- **`heraadopt.ReconcileBindings` survives — it is keyed on task-ROW existence, not depends_on.** The daemon-startup sweep (`bounce.go` calls it in both supervisor + in-process modes) ends every live binding whose `argus_task_id` no longer resolves to a task row, stamping `end_reason="task_missing"`. Needed because a task deleted while the daemon was down skips the delete-cascade hook that normally ends its bindings. Idempotent.
- **The spawn project defaults to the caller TASK's `.Project`, never `role.ArgusProject`.** Roles created before the M4 fix have an empty `argus_project`; the live task row is authoritative. The M4 fix sets `ArgusProject` on new coordinator/worker roles in `toolHeraNewOrchestrator`/`toolHeraJoin`, but every consumer must still tolerate historical empty values.
- **`HeraCoordinatorOrientation`'s headline rule is DISPATCH-don't-implement: a coordinator with actual work (code, a bug fix, tests) calls `hera_spawn_worker` — regardless of repo — and never does the work in its own session.** The real bug behind the phantom nested "sub-coordinator" was a coordinator using `hera_new_orchestrator` on ITSELF as a relabel and then implementing solo in that same session (it never spawned a worker) — self-promotion was the symptom, coordinator-implementing-instead-of-delegating was the disease. `hera_new_orchestrator` binds the CALLING task's OWN session (never creates a new one), so self-invoking it yields a duplicate coordinator binding the rail renders as a phantom nested "sub-coordinator" row driving the identical PTY. `project=` already dispatches cross-repo, so "another repo" is NOT a reason for a new orchestrator; reserve a NEW coordinator session (worker-promotion, or a `kind=subcoord` plan node the gater materializes) for genuine multi-project/multi-phase decomposition — and even then the sub-team's WORKERS do the work, not the sub-coordinator. Worker self-promotion via `hera_new_orchestrator` is fine — a worker's own task is already an isolated session, so `HeraWorkerOrientation` keeps that instruction.
- **`hera_new_orchestrator` (MCP `toolHeraNewOrchestrator`) hard-rejects a caller already holding a live coordinator binding under a DIFFERENT orchestrator — the code backstop under the `HeraCoordinatorOrientation` prose.** Prose is advisory (an LLM ignored it in the live repro); this guard makes the footgun impossible. It runs right after `resolveTask` and BEFORE `CreateHeraOrchestrator` (so a rejection leaves no orphan orchestrator), scans `ListHeraLiveBindingsByTask` for a coordinator-kind role, and errors with guidance to `hera_spawn_worker` / `kind=subcoord`. Scoped to a DIFFERENT orchestrator: a same-orchestrator re-call falls through to the pre-existing same-orch guard (`hera_join` guidance), and worker/freelance-only bindings (worker self-promotion) + unbound tasks (fresh bootstrap) pass. Only the MCP tool is guarded — programmatic coordinator creation (`SpawnHeraCoordinator` rail `n`, gater `MaterializeHeraSubCoordinator`) never routes through it. Fail-open on a bindings-list error, matching the sibling same-orch guard.

## Hera plan-DAG substrate (add-hera-plan-substrate)

- **A planned node is a worker role with NO binding EVER — not "binding ended".** `CreateHeraPlannedRole` inserts a worker-kind `hera_roles` row and writes NO binding. `ListHeraPlannedNodes` keys on `NOT EXISTS (binding for role)`, so a role that was materialized and whose binding later ended does NOT reappear as planned — the gater never re-materializes. This is the idempotency backbone: a node leaves the planned set the instant `MaterializeHeraWorker` inserts its binding, so a blocker status flap (done→working→done) cannot double-spawn.
- **The gate is hera ROLE status `done`, NEVER argus TASK status.** A finished hera worker rolls its task to `in_review` (BUG-050), never auto-`complete`. Gating on task status would fire prematurely (on `in_review`) or never (on `complete`). The gater reads `HeraRoleStatusFor(blockerID).Status == done`. A blocker still `working` (e.g. CI churn) keeps the dependent planned.
- **An ALIVE coordinator blocker is PENDING, never failed (BUG-003).** A coordinator's session is alive for the whole orchestration and never reaches role-status `done`, so the gater MUST treat a coordinator-as-blocker with a live binding as `blockerWorking` (dependent stays planned, no false "failed blocker" hold-ping) even after its bound task leaves `in_progress`. `blockerOutcome` checks `HeraRole(bid).Kind == HeraKindCoordinator && HeraLiveBindingByRole(bid)==nil-err` BEFORE the had-binding-ended path. Belt-and-braces with `AddHeraBlock`, which now REJECTS a coordinator-as-blocker edge (`ErrHeraBlockCoordinator`, blocker-side only — a coord may be the blocked endpoint); the gater guard protects edges already in the live DB that predate the validation. Regression: `TestGater_AliveCoordinatorBlockerKeepsDependentPlanned`, `TestAddHeraBlock_RejectsCoordinatorBlocker`.
- **"Failed blocker" = session ended without role-status done; a NEVER-bound planned blocker is PENDING, not failed.** `blockerOutcome` returns `failed` only when the blocker is not `done` AND had a binding that ended without success (no live binding now, but `ListHeraBindingsByRole` is non-empty), OR its bound task is no longer `in_progress`/`pending`. A blocker with **no binding EVER** (still a planned node waiting on its own blockers) returns `working` — it has not failed, it simply has not started — so the dependent stays PLANNED, not held. Conflating the two was the dogfood bug: it held every transitive dependent (A→B→C held C the instant the tick ran while B was still planned), breaking all DAGs deeper than two levels. Regression: `TestGater_TransitivePlannedBlockerKeepsDependentPlanned`. A genuinely failed blocker HOLDS the dependent and pings the coordinator (deduped per (node,blocker) in `heldPings` so it pings once, not per tick).
- **The hold-ping sender is the HELD node's role, not the coordinator.** `hera.Service.Send` rejects self-send (`from==to`). The gater pings FROM the held planned node's role (a real `hera_roles` row even without a binding) TO the coordinator, so the self-send guard never trips. Sending coord→coord would be rejected and the hold would silently never reach the coordinator.
- **Materialize ENDS the binding on unwind, never DELETEs the role.** `MaterializeHeraWorker`'s LIFO cleanup (for a `runner.Start` failure) calls `EndHeraBinding`, NOT `DeleteHeraRole` — the planned role is authored plan data that must survive a failed materialize. Contrast `SpawnHeraWorker` (born-bound), whose cleanup DELETEs the freshly-minted role. Deleting the role here would silently drop a plan node on a transient start failure.
- **`hera_blocks` FK CASCADE on both endpoints is load-bearing (mirrors tree_read_cursors BUG-034).** Under `PRAGMA foreign_keys=ON`, a bare `REFERENCES hera_roles(id)` would PIN the role and block role/orchestrator delete with error 787. CASCADE also IS the missing-blocker prune: deleting a blocker role removes its edges, so `HeraBlockersOf` returns only extant blockers and the dependent is treated as no longer blocked by the vanished one (never fatal).
- **The cycle check runs inside the insert transaction.** `AddHeraBlock` walks the existing graph (DFS, visited-set guarded against a malformed pre-existing loop) FROM the blocker looking for the blocked role, inside the same `WithTx` as the INSERT, so a concurrent edge insert cannot slip a cycle past the check. Cross-orchestrator endpoints are rejected (`ErrHeraBlockCrossOrchestrator`) — v1 sequences sub-teams at the parent level (an edge between two sub-coord WORKER roles, both in the parent orchestrator), never a boundary-piercing edge.
- **The materialized worker's check-in is PULLED, never pushed.** `HeraCheckInOrientation` (prepended to the materialized worker's prompt) tells it to message its coordinator then POLL `hera_inbox` in a loop for go/wait BEFORE real work. Building it as "wait to be messaged" would hang the worker — a known hera gotcha is that mid-flight pushed doorbells to a busy/fresh worker are unreliable; durable inbox reads are not. The daemon gate itself never consults the coordinator before spawning (purely state-driven).
- **The gater is inert when no plan exists and gated on `cfg.Hera.Enabled`, NOT on KB.** It runs as its own daemon goroutine (independent of the KB/MCP server) so it materializes already-authored plans even with KB off; an empty `ListHeraPlannedNodes` every tick is a cheap no-op.
- **A ROOT node's base branch resolves explicit-orchestrator → coordinator-branch → "" (add-hera-plan-base-branch).** `resolveBaseBranch` first tries the most-recently-bound `done` blocker's branch (unchanged); only when NO blocker branch resolves (a root node) does it fall to `resolveRootBaseBranch`: the orchestrator's explicit `base_branch` (nullable column, set once at `hera_new_orchestrator` time) when non-empty → else the coordinator role's bound-task branch (`coordinatorBranch`, live-then-latest binding fallback) → else `""` (CreateAndStart applies `projCfg.Branch`, the pre-change behavior). Every miss degrades to `""`, never a panic. Backward-compatible: a coordinator on the project default branch yields roots on the project default. The default-to-coordinator-branch (not project-default) is intentional — it lets a plan seed onto the coordinator's WIP feature branch. Blocker-having nodes never reach this fallback.
- **Fan-in materialization (2+ blockers) still silently picks ONE blocker's branch — unchanged — but now pings the coordinator naming the winner and the un-merged siblings (add-hera-fanin-notify).** `materializeNode` fetches `blockerIDs` and the new second return value of `resolveBaseBranch` (`winningBlockerID`, 0 on the root-fallback path); when `len(blockerIDs) > 1`, `pingFanIn` sends a one-shot notice (same `CoordinatorPinger` seam as `holdAndPing`/`emitRecoveryNotice`, from the node's own role) naming the chosen `base_branch`/blocker and the sibling blocker(s)' names+branches that were NOT merged in. Unlike `holdAndPing`, a delivery failure is logged and dropped, never retried — the event (materialization) already happened. This closes a real, not hypothetical, gap: inspecting 5 live fan-in materializations across 3 active feature builds found all 5 coordinators had hand-authored a prompt-level mitigation (unconditional merge, wait-for-go, or a separate integration branch) because nothing told them the pick had happened; one relied on a self-guard that only worked because a sibling's tip commit happened to already be an ancestor of the chosen base (DAG-topology coincidence, not a real safeguard).

## Hera sub-coordinator nodes (add-hera-subcoord-nodes)

- **A `subcoord` planned node is still a worker-kind role in the PARENT — `node_kind` is a SEPARATE discriminator.** `CreateHeraPlannedRole` always inserts `kind=worker`; `node_kind` (nullable, `subcoord`/empty) sits in its own column and is only read by the gater at materialize time. The parent's DAG model — worker roles, `hera_blocks` edges, role-status gating — is byte-identical to a plain worker node; only the materialize step diverges.
- **Materializing a `subcoord` node writes TWO bindings on ONE new task: parent worker + child-orch coordinator.** The new task is simultaneously a worker under the parent orchestrator (against the pre-created planned role) AND the coordinator of a freshly-created child orchestrator. Nesting is the existing `SubtreeOrchIDs` multi-binding bridge — no new parent_orch_id column, no separate nesting graph.
- **LIFO unwind on failed `runner.Start` ends the parent binding (soft) + deletes the child orchestrator (hard, FK-cascades its coordinator role + binding); the planned role SURVIVES.** This mirrors `MaterializeHeraWorker`'s "planned role survives" rule and `SpawnHeraCoordinator`'s orchestrator-unwind. The ended-but-extant binding is picked up by `ListHeraPlannedNodes`'s `NOT EXISTS` check, so the node leaves the planned set and is never re-materialized (same idempotency backbone as workers).
- **The parent hands only a goal — no child-orch or coord-role names are stored or accepted.** The child-orchestrator name is auto-derived from the node name and de-collided via `UniqueHeraOrchestratorName` at materialize time; the coordinator role defaults to "coord". The sub-coordinator owns its own decomposition and plan.
- **The daemon MUST call `SetSubCoordMaterializer` before `heragater.Start`.** The gater has a defensive nil-seam fallback (falls back to the worker materializer), but that path logs `slog.Warn` with "MISCONFIGURATION" and produces a semantically-wrong agent — treat the warning as a bug, not a graceful degradation.
- **`heragater.go`'s package doc and the substrate spec still say "worker-kind roles"; this is intentional staleness.** `node_kind=subcoord` is additive; the "worker default" framing remains accurate for every other node. The central archive pass (`openspec archive`) will reconcile the wording once the change is merged.

## Hera living plan-DAG (make-hera-plan-living)

- **`hera_send` status is applied SYNCHRONOUSLY in the send handler, never via the async delivery bus.** `applyRoleStatus` (the shared path for both `hera_send` and `hera_status`) runs inside the send handler before the call returns; it is NOT enqueued on `notify.Notifier`. A worker's role-status update is therefore authoritative the instant `hera_send` returns, independent of whether the doorbell delivery ever fires.
- **`status` is REQUIRED for worker/freelance senders on `hera_send`; omitting it is a hard error.** The shared `applyRoleStatus` path is called only when `status` is present; the handler errors on omission with the full valid-values list. Optional/ignored for coordinator senders.
- **`failed` is a fifth role-status value (rail red ✕), distinct from `done`.** A worker reporting `failed` rolls its task to `in_review` WITHOUT `ready_to_close` (needs-attention, not ready to check off). The gater's `blockerOutcome` treats a blocker whose role-status is explicitly `failed` as `blockerFailed` — without waiting for session death. A worker that `done` stamps `ready_to_close`; `failed` does not.
- **The gater held-ping RE-ARMS when a failed blocker recovers.** When a `(node, blocker)` key in `heldPings` clears because the blocker's outcome is no longer `blockerFailed`, a one-time "unblocked" recovery notice fires to the coordinator (from the held node's role). A subsequent re-failure re-arms the dedup and re-pings. There is NO notice when a blocker reopens after an ALREADY-MATERIALIZED node (that case is physics — a spawned worker cannot be un-spawned).
- **Cancelled nodes: `cancelled_at` column, excluded from materialization, treated as blockerDone so dependents proceed.** `ListHeraPlannedNodes` filters `AND cancelled_at IS NULL`, so the gater never materializes a cancelled node. `blockerOutcome` returns `blockerDone` for a cancelled blocker (the dependent is unblocked). The role row is kept (not deleted) so planview renders it as grey ✕ (`StateCancelled`). Dependents of a cancelled node materialize as normal.
- **Reopen is structural, not a watcher.** A `done`/`failed` worker that re-engages is required to send `status="working"` on its next `hera_send` by enforcement — the required-status rule is the reopen mechanism. No observed-reopen daemon watcher was added.

## Hera coordinator context management (add-coordinator-context-management)

- **`argus coord-hook` (a Claude Code `Stop` hook) MUST be registered in the user's GLOBAL `~/.claude/settings.json`, never a project's** — every agent argus spawns inherits the daemon's real `HOME` regardless of which repo the worktree lives in (`cmd.Env = append(os.Environ(), …)`), so a per-project hook registration would never fire for a coordinator spawned into a project argus doesn't own. There is no code path that writes this for the user; it's a documented one-time manual step (`README.md` → Context-budget Stop hook).
- **The hook self-gates on `ARGUS_TASK_ID` FIRST, before decoding stdin at all** (`cmd/argus/coord_hook.go`) — an empty/unset env var returns immediately with zero side effects, since it fires on every Claude Code Stop event on the machine, including ordinary non-argus sessions. Only after that gate does it resolve the bound role kind (`GET /api/tasks/{id}/meta?namespace=hera`, key `role`); anything other than `"coordinator"` (including unbound) is also a silent no-op. This ordering is why the hook is safe to register globally.
- **`context_size` is stamped unconditionally on every Stop event; the block decision is a SEPARATE, budget-gated step.** The transcript JSONL is scanned start-to-end (not tail-seeked — JSONL has no fixed record size) for the last `type=="assistant"` line's `message.usage.cache_read_input_tokens`; the scanner buffer is raised to 10 MiB because the 64 KiB default truncates large tool-output lines and silently drops the read. `task_meta(hera, context_size)` is written regardless of budget; only when `size >= coordinator_context_budget` does the hook additionally write `{"decision":"block","reason":…}` to stdout.
- **The block decision is a "presence = block" contract with no cooldown at the Claude Code layer.** Claude Code treats an empty stdout as "allow stop"; there's no separate "under budget" signal to write — a hook change that always emits *some* JSON (even `{}`) would wedge every coordinator's Stop event permanently. (The reach-a-seam nudge's own recurrence IS throttled independently — see the next bullet; this bullet is only about Claude Code's stdout contract, superseding the old claim that the nudge reargues every single turn.)
- **The nudge's recurrence is throttled by growth, not by turn count (throttle-coord-hook-nudge).** A new scalar `task_meta(hera, last_nudged_context_size)` (`db.HeraMetaKeyLastNudgedContextSize`) records the `context_size` at which the nudge last fired; a new config field `coordinator_nudge_increment` (`HeraConfig.CoordinatorNudgeIncrement`, default `50000`) sets how much growth is required before it's allowed to fire again. The gate in `runCoordHook` is `hadLastNudged && size >= lastNudged && size < lastNudged+increment` — the `size >= lastNudged` half is load-bearing: without it, a fresh over-budget episode right after a recycle (context_size reset low, but a stale-and-larger `last_nudged_context_size` still on record from the prior session) would be wrongly suppressed by `size < lastNudged+increment` alone, since a stale-and-larger `lastNudged` makes that comparison trivially true. Both new reads (`ReadLastNudgedContextSize`, `NudgeIncrement`) fail open on error (treated as "no prior nudge" / "no increment configured"), matching the existing `PendingRecycleAlready` error-fallback precedent — a read failure must never silently suppress the nudge. See design.md at `openspec/changes/archive/2026-07-19-throttle-coord-hook-nudge/design.md` D2 for the full trap writeup.
- **`hera_status`'s `handoff_note`/`request_recycle` params are accepted from ANY hera-bound role kind, not just coordinator (add-worker-bounce).** The original coordinator-only gate in `internal/mcp/hera.go`'s `toolHeraStatus` (which rejected both params for worker/freelance callers with a naming error) was removed entirely — the same `task_meta` writes (`handoff_note`, `pending_recycle`) now happen regardless of `caller.role.Kind`. This exists to support the rail's `B` bounce action (see the hera-view bullet below), not to extend `coord-hook`'s automated budget nudge to workers/freelance — that stays coordinator-only, unchanged.
- **`request_recycle=true` only flips a flag; it never restarts anything itself.** It stamps `task_meta(hera, pending_recycle="true")` — the same soft-fail-write pattern as the existing status mirror — and the recycle watcher's own 5 s ticker (`RecycleWatcher`, matching `ReliableNotify`'s cadence) is what later scans for that flag and acts. Calling `hera_status(request_recycle=true)` from a coordinator that then immediately goes idle is the entire self-service path; there is no synchronous "recycle now" return.
- **Self-service recycle waits for `runner.IsIdle(taskID)`; human-forced does not check it at all — same code path, different trigger.** `RecycleCoord(store, runner, roleID, sessionID, trigger)` only consults idleness when `trigger == RecycleSelfService`; a busy role's pending flag is simply skipped and retried on the watcher's next tick. `RecycleHumanForced` (the `B` rail key on a COORDINATOR selection only) skips the idle check unconditionally — the whole point of the forced path is recovering a coordinator that will never self-report idle because it's actually wedged. `RecycleWatcher.tickTask` no longer filters bindings to `role.Kind == coordinator` (add-worker-bounce): it picks the coordinator-kind binding when the task holds 2+ live bindings (unchanged disambiguation), else the first binding found — so a worker/freelance role's `pending_recycle` flag now drives it through this same self-service path, never the human-forced one (that stays reachable only via a coordinator selection).
- **`RecycleRunner.Restart` must resolve its binding via the caller-supplied `roleID`, never re-derive it from `taskID` alone (fix-recycle-restart-ambiguous-binding).** `tickTask`/`RecycleCoord` already disambiguate a dual-bound task (worker in one orchestrator, coordinator in another) down to one `roleID` before calling `runner.Restart`, but the interface's original `Restart(taskID string) error` signature dropped that resolved role — `daemon.HeraRecycleRunner.Restart` re-derived the binding itself via the single-binding `HeraLiveBindingByTask(taskID)`, which returns `ErrHeraAmbiguous` for exactly the case the caller had already solved, permanently wedging that task's self-service recycle (the watcher retries every 5 s tick forever, logging `hera: lookup ambiguous`). Fixed by widening the signature to `Restart(taskID string, roleID int64) error` and resolving via `HeraLiveBindingByRole(roleID)` instead — any future `RecycleRunner` implementation must do the same, not just the shipped one.
- **The old `SessionID` MUST be cleared and persisted BEFORE calling `runner.Recycle`, not after.** `BuildCmd`'s non-resume branch pins any non-empty `SessionID` via `--session-id`; if the recycle wrote a fresh empty prompt but left the stale UUID on the task row, the "restart" would try to resume the just-killed (already-terminal) session instead of starting clean. This is the entire mechanism behind "same task, same worktree, fresh context" — no new task row, no new binding, just a session-ID reset plus a fresh `BuildCmd`.
- **Stray background-job cleanup runs before every restart and is best-effort against an unspecified schema.** `internal/agent/stray.go` shells `claude agents --json`, matches entries by `session_id`/`sessionId`/`session` against the outgoing session UUID, and runs `claude stop <id>` per match — addressing the known `task_stop`-doesn't-kill-everything failure mode (a `run_in_background` sub-job surviving under the killed session's UUID, causing worktree-write EPERM on the next start). A non-match is silently possible (logged, never surfaced) since the CLI's JSON shape isn't a stable contract argus owns.
- **The seed prompt requires zero follow-up tool calls from the recycled session by construction, not by convention.** `BuildRecycleSeedPrompt` concatenates the role's stored mission prompt + a plan-DAG section (sibling role names/statuses) + the `handoff_note` meta value (if any) into one static string assembled server-side, handed to the new session as its literal opening prompt (`task.Prompt`). Only the role lookup is fatal; a missing plan-DAG or absent `handoff_note` degrades to an empty section rather than blocking the recycle.
- **The `B` rail key now bounces a worker/freelance selection instead of no-op'ing (add-worker-bounce); only an empty selection stays a true no-op.** `page.go`'s `case 'B'` switches on `sel.IsCoordinator()` (unchanged: confirm modal → `RecycleCoord(..., RecycleHumanForced)` directly, restarting mid-turn without waiting — the intended behavior for a session the self-service path can't reach because it's wedged) vs `sel.IsWorkerOrFreelance()` (new: confirm modal → `heraDoBounceWorker` → `sess.WriteInputSystem` sends a plain instruction asking the role to call `hera_status(handoff_note=..., request_recycle=true)` ITSELF — no direct kill/restart, no new `RecycleTrigger`; the now-widened self-service pipeline above completes the recycle once the role goes idle and makes that call). Nothing polls for a response and nothing times out if the role never calls it (D6, explicit scope decision) — the human can just press `B` again.

## Hera plan-DAG hygiene (add-hera-plan-hygiene)

Three independently-verified data-hygiene bugs, found live in `~/.argus/data.sql` — deliberately NOT unified under one root cause; two got code fixes, one did not.

- **A planned node outliving its archived/nuked orchestrator needs BOTH a write-time cascade AND a read-time filter — neither alone is sufficient.** `ArchiveHeraOrchestrator`/`NukeHeraOrchestrator` (`internal/db/hera.go`) cascade-cancel (`cancelled_at`) their still-planned (never-materialized) worker-kind child roles via `cancelStillPlannedChildRoles`, so a FUTURE archive/nuke never orphans a pollable dead node. But that alone does not repair rows that predate the fix (a real live bug: roles 343/358 retried `heragater` materialization every ~60s tick for over a month behind orchestrators archived+nuked a month earlier, spamming `hold: no coordinator to ping: <nil>`). `ListHeraPlannedNodes` (`internal/db/hera_plan.go`) therefore ALSO joins `hera_orchestrators` and requires `archived_at IS NULL AND nuked_at IS NULL` on the parent, independent of the node's own `cancelled_at` — this is what makes the fix retroactive with zero data migration. Both exist for the same reason the nuked-orchestrator check is duplicated in `internal/tui/hera/model.go`'s `BuildModel` even though the DB list query already excludes nuked rows: list queries are this codebase's belt-and-braces layer, not just the write path.
- **`heragater.materializeNode`'s "stays planned, retry next tick" failure path had no escalation — a permanently-broken node (e.g. blank `argus_project`) retried in total silence forever.** Fixed by a bounded consecutive-failure counter (`Watcher.materializeFailures`/`escalatedMaterializeFailures`, `materializeFailureEscalationTicks=5`) that sends ONE coordinator notice on crossing the threshold, mirroring `holdAndPing`'s ping-once-per-condition dedup shape (NOT `agent.EscalateParkedSelection`'s 8-tick threshold — that guards isolated torn reads on a sub-second polling loop, a noise source that doesn't exist for a synchronous, deterministic materialize call). Escalation is advisory ONLY: it never auto-cancels or reconfigures the node — a node with zero remaining blockers is presumptively genuine pending work, and only a human can say what's actually wrong with it. Both maps are swept every `Tick()` for any node id no longer in the planned set (`sweepMaterializeFailures`, mirroring `rearmHeldPings`'s cleanup of `heldPings`) — an unbounded per-node-forever map would itself be exactly the class of hygiene defect this fix exists to close.
- **A `kind=freelance` role stuck in the Hera rail's flat top-level Freelance section with an intact role→orchestrator→binding→task chain is a data-hygiene gap, not a display bug.** `internal/tui/hera/model.go`'s rule (`role.Kind == HeraKindFreelance && role.ArchivedAt == nil && o.ArchivedAt == nil` → flat section) is intentional and working as designed; a `kind=worker` role nests under its orchestrator unconditionally regardless of archived state, but a freelance role escapes the flat section only by being archived. Two live rows (roles 813/814) simply were never archived once their work finished (tasks already `in_review`/`complete`) — the identical "task finished, binding still open" shape is the NORMAL, common case for ~150 other historical `kind=worker` roles that render fine. No `Clean`/`Prune`/`Sweep`-named function touching hera data exists anywhere in this codebase; whatever produced this pair's un-archived state was very likely a manual/ad hoc action outside argus. Resolution is a one-time data cleanup (`ArchiveHeraRole` + `EndHeraBinding` on the two rows), NOT a code change — auto-archiving a freelance role on binding-end would be a genuine, separately-scoped behavior change with its own design surface (when exactly does "binding ended" count?), deliberately not smuggled into a three-bug hygiene fix.

## Hera subtree TLDR roll-up (M5)

- **The subtree (TLDR roll-up) and the orchestration tree share the SAME nesting graph now.** `SubtreeOrchIDs` walks the orchestrator *nesting* graph (multi-binding bridges) for message roll-up; `heraTreeNodes` (the Details-pane graph) walks the SAME nesting in-memory for rendering. Both derive from role bindings — there is no longer a separate `depends_on` dependency graph to conflate them with (it was retired). A message roll-up is still a distinct concern from the rendered tree, but they no longer use orthogonal data sources.
- **`SubtreeOrchIDs` nesting bridge is the multi-binding shape, NOT a parent column.** Orchestrator S is a child of R when S's live, non-archived COORDINATOR role is bound to an argus task that ALSO holds a live binding (any kind) under R. There is no `parent_orch_id` column — the tree is re-derived each call by BFS over `hera_bindings` joined on shared `argus_task_id`. The Argus binding shape matches Hera's exactly (role_id/orchestrator_id/argus_task_id/ended_at), so the traversal SQL ports verbatim with only table-name changes (`orchestrators`→`hera_orchestrators`, etc.).
- **`SubtreeOrchIDs` cycle guard is a visited-orchestrator set, not a depth cap.** Hera's port carried a `maxDepth`/`truncated` pair; Argus drops both because the visited set already guarantees termination over a finite orchestrator set (a task could theoretically bridge into a loop). Never re-enqueue a seen orchestrator id. The root is ALWAYS included (the caller resolved it as their own live orchestrator); only *descendants* are subject to the archived-exclusion filter.
- **Archived orchestrators are pruned mid-traversal, taking their descendants with them.** The BFS filters `child_orch.archived_at IS NULL`, so an archived mid-tree orchestrator is never enqueued — and because nesting flows *through* it, every orchestrator hanging off it becomes unreachable too. Archiving a sub-coordinator's orchestrator silently drops that whole branch from the roll-up.
- **`tree_read_cursors.role_id` MUST be `ON DELETE CASCADE` (BUG-034).** With `PRAGMA foreign_keys=ON` (Argus enables it), a bare `REFERENCES hera_roles(id)` (default NO ACTION) makes a cursor row PIN its parent role — deleting the role or its orchestrator fails with "FOREIGN KEY constraint failed (787)". CASCADE lets the delete clean the cursor. Regression-tested by `TestHeraTreeCursor_FKCascade`.
- **The per-role tree cursor is advisory, not an at-least-once event cursor.** `hera_tree_updates` is a DB *query* over the message store, not an event consumer — so unlike Hera's old `event_cursor` (which advanced regardless of handler success and lost adoptions), this cursor is just a disposable read bookmark, re-seeded to the max id returned on every read. Auto-advance happens ONLY when the caller omits `since`; an explicit `since` overrides without clobbering the stored cursor (so a one-off historical scan doesn't reset the role's live position).
- **`HeraTreeUpdatesSince` is TLDR-only by projection, capped at `HeraTreeUpdatesLimit` (200).** The `HeraMessageTLDR` struct has no `Body` field — bodies require a follow-up `hera_get_messages` (Aaron: "super useful, don't lose it" = the token-efficient whole-tree snapshot). `nextCursor` is the max id returned (or `since` when empty), so with the LIMIT a busy subtree pages forward across repeated calls rather than returning unbounded rows. Role/orchestrator *names* are resolved in the MCP handler (cached per call), not joined in SQL, keeping the store projection id-only.
- **`hera_get_messages` access scope is the SUBTREE, not the single orchestrator (M5 expanded M3).** A message is readable when its sender OR recipient role lives in any orchestrator of the caller's `SubtreeOrchIDs`. The per-ID error-entry contract is preserved: missing/denied ids get an `error` field in their entry, never a top-level error. A message in an UNRELATED (non-nested) orchestrator stays denied.
- **`hera_spawn_worker` / `hera_plan_node` prompts carry the worker's MISSION only — never a prepended org/security policy (improve-hera-node-descriptions).** The tool `prompt` param descriptions document this contract; argus keeps storing the prompt VERBATIM on the role (no stripping, no transformation — argus must never parse prompt content). Rationale baked into the descriptions + the hera skill: every spawned worker session receives its org instructions independently via its OWN session's harness injection (an `<organizationInstructions>` block, empirically present in every spawned session regardless of parent), so a manually prepended copy is a redundant duplicate that also pollutes the stored role prompt and the plan-DAG node description (which renders the prompt's opening lines). Fix is at the source (prompt hygiene), enforced only by the documented contract — NOT by view-side or store-side stripping.
- **`argus coord-hook` widened from coordinator-only to any hera-bound role (add-worker-context-indicator).** The Stop-hook gate moved from `kind != coordinator → no-op` to `kind == "" → no-op` — a worker or freelance session now gets `task_meta`(`hera`, `context_size`) stamped on every Stop event exactly like a coordinator (this is what feeds the hera-view rail's context-pressure indicator), but never reaches the budget/nudge/hard-stop/recycle machinery, which stays gated on `kind == coordinator` placed AFTER the now-unconditional stamp. No new config field: the indicator reuses `coordinator_context_budget` as the percentage denominator for workers too, since it's "how many tokens counts as a lot on this project," not something inherently coordinator-specific.

## Hera accept-and-complete lifecycle (add-hera-accept-lifecycle)

Fills the structural gap `RollHeraWorkerToReview`'s own doc comment names: nothing had ever had a reachable way to advance a task to `complete` in normal operation. `hera_accept` (coordinator-only MCP tool) and the plan-DAG gater's auto-accept-on-materialize both flip a role's bound task to `complete` via one shared primitive, `internal/hera.AcceptRole` – never `RollHeraWorkerToReview`/`RollHeraWorkerFailed`, which are unchanged and still own the worker-self-reports-done→`in_review` half of the lifecycle.

- **`AcceptRole`'s idempotency is "second+ call against an already-complete task is a FULL no-op" – no status write, no notification, not just a status-write no-op.** This matters specifically for the gater: a blocker gated by N dependent nodes gets an accept call once per dependent that materializes, so without this the blocker would receive N "you're marked complete" notifications instead of one. Check the task's current status BEFORE the `SetStatus` write and return early – do not rely on `SetStatus`'s own idempotency alone, since that would still let the notification fire every time.
- **The gater's `acceptBlockers` fires from the SAME `blockerIDs` slice `materializeNode` already resolves for the fan-in notice – no second query.** It is scoped to the ordinary worker-kind materialize path only, mirroring `pingFanIn`'s own existing worker-kind-only scope: a `subcoord` node's OWN materialization (`materializeSubCoord`) does not call it, so a subcoord node's blockers are only accepted when some OTHER, ordinary dependent of theirs later materializes through the normal path. The `coordRoleID` passed to the `Accepter` hook is resolved once per `materializeNode` call (already needed for `coordName` in the check-in prompt) – a zero value means no coordinator exists, in which case `acceptBlockers` logs and skips rather than calling accept with a bogus sender id.
- **`ReviveHeraWorkerToInProgress` now accepts `complete` as a second valid source status (alongside `in_review`), with the SAME `heraWorkerAwaitingCloseout` guard re-evaluated, not bypassed, for that source.** This is what makes `hera_accept`'s completion revocable: an accepted task whose session is later stopped (e.g. via the Hera rail's `a` HIDE key) can still be revived back to `in_progress`. The guard still refuses if the task carries `ready_to_close` or a terminal role-status – an accepted-then-stopped task's role status is whatever it was AT ACCEPT TIME (not forced to any particular value by `AcceptRole`), so in practice this rarely fires for the accept-then-revive path, but the guard is left in force defensively rather than special-cased away.
- **`gitutil.PRResult` gained a `Merged bool` field distinct from `State` – `State` collapses GraphQL `MERGED` and `CLOSED` into one `PRMergedClosed` value, but the PR-merge coordinator nudge (`internal/daemon.notifyCoordinatorOfMergedPR`) must never fire for an unmerged close.** `mapBatchNode` sets it from the raw `prJSON.State == "MERGED"` check before the existing collapsing switch runs. The nudge itself is deliberately NOT `AcceptRole` – a merged PR is a nudge-only signal to the resolved coordinator, never an automatic status flip, per Aaron's explicit call that "confirmed merged" is genuinely ambiguous for Hera-descended tasks (squash merges, folded-in workers with no PR of their own).
- **`heraWorkerAwaitingCloseout` is now EXPORTED as `db.HeraWorkerAwaitingCloseout` — a THIRD trigger reuses it besides `ReviveHeraWorkerToInProgress`'s own two callers, and it's a REFUSE decision this time, not a restore.** Live-testing `hera_accept` (accept a self-reported-done, session-dead worker, then press `Enter` on the now-`complete` row) found that `internal/tui/heraactions.go`'s `heraReattach` dead-session branch called `startSession` unconditionally for every role kind, oblivious to Hera close-out state — `startSession` flips the task to `in_progress`, the resumed session exits almost immediately (nothing to resume), and the ordinary post-exit rule then rolls it back to `in_review`, silently undoing the accept even though `Enter` isn't an explicit revive. This was a pre-existing gap in the `Enter` wiring, not `hera_accept`-specific — it applied equally to any `ready_to_close` worker with a dead session before `hera_accept` ever existed. Fix: for a worker/freelance selection, `heraReattach` now calls a new `heraTaskClosedOut` wrapper around the exported guard BEFORE `startSession`, refusing (no status write, no session start, statusbar error) when awaiting close-out. Coordinators are unaffected (no `ready_to_close` concept, always restarted unchanged).
- **Constructing `hera.New(store, notifier)` with a Daemon's nil `*notify.Notifier` field passed directly panics** – a nil CONCRETE pointer wrapped into the `hera.Notifier` INTERFACE parameter is a non-nil interface holding a nil value, so `Service.Send`'s own `s.notifier == nil` guard never trips and it calls a method on the nil receiver. `d.notifier` is always set by the time `Serve()`'s own `gaterSvc := hera.New(d.db, d.notifier)` line runs (set earlier in the same function), so this was latent, not a live bug, until `notifyCoordinatorOfMergedPR` needed to construct a service from a bare `Daemon` (a shape every daemon-package test uses via `New(database)` with no `Serve()`). Fixed by explicitly assigning through a `var notifier hera.Notifier; if d.notifier != nil { notifier = d.notifier }` guard rather than passing the concrete field straight through – do the same anywhere else a concrete `*notify.Notifier` reaches a `hera.Notifier`-typed parameter outside `Serve()`'s own already-guaranteed-non-nil window.
