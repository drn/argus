# Native Hera View (`internal/tui/hera`)

M6a scaffolds the native Hera view: a `HeraPage` (rail | coordinator pane | agent pane) replacing the old DAG tab. Only the LEFT rail is live and READ-ONLY; the two right panes are placeholders (6b adds PTY feeds; 6c adds mutations). M6b makes the two right panes REAL terminal feeds and wires rail selection to them.

## Display label is "Projects"; every internal name stays "Hera"

- **The second tab is user-facing "Projects" (TUI `widget.TabLabels[TabHera]`, web `.tab[data-tab="hera"]` text, macOS `HeraTab`'s `navigationTitle`) but every identifier behind it — `TabHera`, `CtxHeraRail`, the `hera` tview/DOM page ID, `hera.enabled`, the `hera_*` MCP tools/tables, `HeraPage`/`HeraTab` types — is intentionally untouched.** Only the rendered strings a user reads (tab label, `?` help overlay section titles "Projects View (rail|plan DAG)", the "switch to Projects tab" help row, and the bottom-bar `2`→`projects` hint) were renamed; grepping for "Hera" still finds the real implementation. Don't "finish the rename" by touching Go/Swift/JS identifiers — that was an explicit non-goal.

## M6b — pane feeds from the in-process runner

- **Panes are fed from the in-process runner's ring buffer, NOT SSE — Hera's `proxy/` fan-out has no Argus equivalent and is not ported.** The coord/agent panes are `terminal.TerminalPane`s (the same widget the main agent view uses). A `SessionResolver func(taskID) agentview.TerminalAdapter` seam (App wires it to `runner.Get`) hands the pane a live session; the TerminalPane POLLS that session's ring via `RecentOutput*` on every Draw (it does NOT `AddWriter`). The daemon-owned PTY ring is the single source — there is no SSE/HTTP hop and no `ArgusStateCache` polling. Remote mode (`nil` reader) never sets a resolver and never feeds the panes.
- **The coord-vs-agent session-selection rule (LOCKED — documented in `panes.go`):** the AGENT (right) region is mode-switched by whether the selection is a coordinator: a **coordinator** selection renders the read-only `DetailsView` worker roster + plan graph (no terminal, agent pane unbound) and feeds the HERA (middle) pane from *that orchestrator's coordinator* task; a **plain worker/freelance/leaf** selection feeds the AGENT terminal from the role's bound task and the HERA pane from the *selected orchestrator's coordinator* (`Selection.CoordTaskID()`). `applySelection` computes the Details target via `detailsOrch()`, NOT bare `Selection.IsCoordinator()` — see the BUG-004 bullet for why a worker-bridge sub-coordinator also counts as a coordinator here.
- **A worker-bridge sub-coordinator selection is a COORDINATOR selection for pane routing (BUG-004).** A sub-coord nests as a worker ROW (`Role.Kind==worker`) that bridges a child orchestrator, so `Selection.IsCoordinator()` is false — keying `detailsMode` on it dumped the sub-coord into the AGENT terminal and made its Details view unreachable. Fix: `detailsOrch()` returns the bridged CHILD orchestrator when `Selection.BridgeChildOrchID != 0` (the marker `Rail.Selection` sets from the row's `collOrchID`), so `detailsMode` is `detailsOrch() != nil`. Details/plan (`rebuildPlan(root)`, `SetOrch`) render the CHILD's roster + plan DAG and the HERA pane feeds from the child's coordinator (== the sub-coord's own session) — symmetric with a top-level coordinator. A coordinator-spawned sub-coord that already renders as its own header is unaffected (it selects as a header → `IsCoordinator()` true). CRITICAL: only the pane/details/plan ROUTING follows the child; `p.sel` (the `SelectionContext` mutation context) stays on the PARENT worker role, so Ctrl+D and other mutations still act on the worker, never the child orchestrator (the conservative multi-binding safety the rail nesting documents).
- **Multi-binding is disambiguated by the role's orchestrator, NEVER the bare task ID.** `Rail.Selection()` resolves the containing `OrchView` from the selected `RoleView.OrchID` (`Model.OrchByID`), so a task that is worker in A and coordinator in B yields two different `Selection`s: selecting the A-role feeds the AGENT pane from the shared task + the HERA pane from A's coordinator; selecting the B-role feeds the HERA pane from the shared task (B's coordinator = itself) + renders B's roster. `Selection` is the single value threaded to the 6c mutation extension point (`HeraPage.SelectionContext()`).
- **PTY size alignment (CLAUDE.md rule 5): a hera pane and the main agent pane compute the SAME size for the same rect — they are the same `TerminalPane` widget.** When binding a session, `bindPane` calls `ForceResyncPTY()` so a session previously sized for the full-width main agent view gets resized DOWN to the narrower hera pane on the next Draw (without it, the seeded `ptyCols` matches `wantCols` and no resize fires, leaving the agent painting at the stale width). `SyncPanes()` (App tick GOROUTINE + spinner loop, never a QueueUpdateDraw callback) issues the Resize RPC off the main thread. It is safe to call off-tab: a pane that wasn't drawn this frame has zero `pendingResize`, so an off-tab `SyncPanes` can't fight the main agent view's resize of the same task. Never reach for `Sync()` to fix a size mismatch — fix the alignment.
- **A plain `ForceResyncPTY()` resize can't repair scrollback already committed at a different width — Hera panes never had the main agent view's kill+resume safety net for that (BUG-074), and are MORE exposed to it than the main view.** SIGWINCH re-flows only live UI; cursor-positioning codes baked into earlier PTY output stay wrong once re-emulated at a new size (the `agent.ShouldKickRerender`/`RerenderMargin` mechanism exists precisely for this — see `App.maybeKickRerender`/gotchas/pty-terminal.md — but it was wired ONLY into the main agent view's entry path, never into `bindPane`). Reproduced offline against a real dogfood session log (small, well under any 8MB-window concern — this is independent of BUG-068/BUG-073's lossy-tail-rebuild mechanism): a session resized once during its real life shows a duplicated footer/blank-frame pattern when replayed at a fixed size, exactly matching a live screenshot report. Hera panes hit this MORE than the main view because `bindPane` calls `ForceResyncPTY()` unconditionally on every single bind — any task viewed repeatedly in Hera accumulates real size transitions in its history over time. Fix: `App.maybeKickRerenderAtWidth(task, sess, panelCols)` is the width-parameterized core extracted from `maybeKickRerender` (which now just supplies `computePTYSize()`'s result); `App.heraKickRerender(taskID, panelCols)` is the Hera-facing entry point, wired via `HeraPage.SetRerenderKicker` (mirrors `SetSessionResolver`'s pattern — resolves `task`/`sess` by ID itself so `internal/tui/hera` never needs direct `db`/`runner` access). Shares `isRedundantAttach`'s cache (keyed by task ID only, not by which surface asked — a task alternately viewed from the main view and a Hera pane can kick once per surface-switch; accepted, see design.md for `fix-hera-pane-rerender-kick`).
- **The kick check is evaluated from `Draw()` (`HeraPage.maybeKickPaneRerender`), never from `bindPane` itself, despite `bindPane` being where the session is actually resolved.** `bindPane` runs synchronously in the input handler, BEFORE Draw() has had a chance to give a newly-shown pane its real rect — the clearest case is a coordinator selected first (details mode: the agent pane is never shown, never `SetRect`, tracked width stays 0) then a worker selected for the first time this session: at THAT bind moment the agent pane's width is still 0, so a synchronous read there would silently skip the check for the very first coordinator→worker transition every session. Fix: `Draw()` calls `maybeKickPaneRerender(bound, kickedFor, cols)` right after each of its four `SetRect` call sites (fullscreen coord/agent, split coord/agent) — `cols` there is always the JUST-computed, correct value. `coordKickedFor`/`agentKickedFor` (paired with `coordBound`/`agentBound`) suppress a redundant call every frame while the same task stays bound and visible — NOT a correctness gate (that's still `isRedundantAttach`, downstream), purely an optimization to skip the DB+runner lookup; `bindPane` resets the marker to `""` on unbind so a later rebind to the SAME task still gets evaluated.
- **The kick itself is debounced by a 300ms wall-clock dwell (`hera.KickDebounce`, fix-hera-tick-and-kick-perf) — ordinary rail nav ALONE (no resize, no fullscreen toggle) swings a bound pane between full-width and split-width, crossing `RerenderMargin` on every hop of a fast Cmd+Arrow traversal and kicking every transiently-bound task ("kick storm").** `maybeKickPaneRerender` now arms a per-pane `kickPending{taskID, cols, deadline}` on first seeing a newly-bound task past the margin instead of firing immediately; only a LATER call, once the dwell elapses AND the same task is STILL bound, actually invokes `kickRerender`. A rebind to a DIFFERENT task before the dwell re-arms against the new task, discarding the old one un-fired. **`bindPane` also zeroes `pending` on unbind** — omitting this (the first implementation attempt) left a stale, already-past deadline surviving an unbind+rebind-to-the-SAME-task, firing the kick immediately instead of dwelling afresh (caught by `TestPanes_KickDebounce_UnbindMidDwellThenRebindSameTask`). No new goroutine/timer — checked on the same Draw cadence, mirroring `Refresher`'s goroutine-free style, via an injectable `kickNow`/`SetKickClock` seam for tests.
- **Main-thread-safe pane reads only.** Pane operations on the tview thread use the lock-free/local SessionHandle methods (`Alive`, `RecentOutput*`, `WriteInput`, `Session()`) — never the RPC-blocking `PID/IsIdle/PTYSize/InitialPTYSize`. The blocking `SyncPTYSize`→`Resize` RPC runs only from the tick goroutine via `SyncPanes`. `SetSession`/`SetTaskID`/`applySelection`/`reconcileSessions` are main-goroutine-only (SetSession resets emulator state).
- **`reconcileSessions` (App tick, main thread) does the nil→live late bind AND the dead→live re-resolve (BUG-013).** A pane bound to a task with no live session yet (coordinator/worker still starting) gets its session attached on a later tick. `doRefresh` re-runs `applySelection` after `SetModel` because the rebuild replaces the model's backing arrays, invalidating the prior `Selection` pointers (task IDs usually match, so `bindPane` no-ops and emulators survive).
- **A present-but-DEAD pane session MUST be re-resolved, not just a changed taskID (BUG-013).** When the daemon tears a pane's stream down (StreamLost relay / daemon bounce) while the agent PTY is still alive, `RemoteSession.Alive()` flips false but the agent lives. The pane held the dead handle forever: `reconcileOne` used to bail on ANY present session and `bindPane` no-ops on the unchanged taskID, so `forwardKey` dropped every keystroke (silently) until a full TUI restart re-dialed the stream. Fix: `reconcileOne` treats `!Alive()` like nil and re-resolves — the daemon client re-dials a fresh stream on a cache-miss `Get` when the daemon reports the process alive. Replace ONLY with a live, DISTINCT handle; leave the pane alone when the resolver yields nil (process gone → replay) or the same not-yet-evicted handle (retry next tick), or you reset the emulator every tick. `forwardKey` now logs the drop (`[hera-view]`) and re-resolves before dropping. Orthogonal to the `Enter`-reattach path, which leaves a LIVE coordinator navigate-only and restarts a truly dead PROCESS — BUG-013 is a live process with a stale handle.
- **PR indicator reads the daemon-populated `"pr"` namespace (keys `state`/`url`), like the task list — best-effort, never fetched.** The plan said `meta:iris.pr_url`, but Argus's canonical cached PR state is `task_meta` namespace `"pr"`; `DetailsView` shows a `PR` mark for a roster task ONLY when `kv["state"]` parses (`model.ParsePRState`) to an actionable review state (`model.PRState.IsActionable` — awaiting-review / changes-requested / approved). The poller retains `url` after a PR merges (state flips to `merged-closed`, url stays), so gating on url presence alone (the BUG this superseded) kept showing `PR` forever on merged/closed PRs; gating on state matches `theme.PRGlyph`'s task-list filtering, and `IsActionable` is the single shared predicate both call. `doRefresh` reads the namespace once via `ListMetaByNamespace("pr")`.
- **`TerminalPane.SetBorderTitle` is the only change to the shared agent surface.** It defaults to `" Agent "`; the hera coordinator pane sets `" Coordinator "` so the same widget reads correctly in both surfaces. The DAG render mode of the Details pane is deferred to M7; mutations to M6c.

- **The second tab is `TabHera` (enum slot `widget.TabHera == 1`), so the `2` hotkey is stable.** `switchTab`'s second arm always routes to the `"hera"` page via `switchToHeraTab2` — the native Hera view is the only second-tab option now (the legacy `"dag"` page was deleted along with `depends_on`). `cfg.Hera.Enabled` no longer toggles the view; it only gates daemon-side MCP native-vs-plugin tool registration on the next daemon start.
- **Multi-binding fan-out is structural, not special-cased.** One argus task bound under two orchestrators is reached through two DISTINCT `hera_roles` rows (one per orchestrator). `BuildModel` walks orchestrators → their roles → each role's live binding, so the task surfaces once under EACH orchestrator with zero fan-out logic. The smoke test `TestSmoke_HeraRailMultiBindingUnderTwoOrchestrators` and unit `TestBuildModel_MultiBindingFanOut` pin this — do NOT "optimize" the model into a per-task dedupe, which would collapse the two appearances the locked Q2/Q3 design requires.
- **Freelance-kind roles are HOISTED into a top-level Freelance section, not nested under their orchestrator.** `BuildModel` skips active freelance-kind roles when filling an orchestrator's `Roles` and appends them to `Model.Freelance` instead. This is a 6a read-only interpretation of the "freelance" section (Hera derived it from unmanaged live argus tasks; that data source is out of scope for the read-only hera store). 6b can revisit if real unmanaged-task freelance is wanted.
- **`ready_to_close` (M4) is read from the task-addressed `task_meta` "hera" namespace, NOT the hera tables.** `BuildModel` does one `ListMetaByNamespace("hera")` batch read and flags `RoleView.ReadyToClose` when the role's bound task has `ready_to_close=true`. The rail renders it with the distinct `theme.IconReview` mark, which WINS over the role's idle/working/blocked/done status icon but LOSES to needs-input `(?)` (BUG-A: an actively-blocked worker is not ready to close). A meta read error is non-fatal (the flag just doesn't render).
- **The rail rebuild runs on the tview thread; that's fine because hera-store reads are mutex-guarded and fast — the "never on the UI thread" rule is about GIT, not DB reads.** `Refresher` (the Argus-native analog of Hera's `RailRefresher`) is goroutine-/timer-free: `Schedule()` is driven by the app tick + tab entry and coalesces bursts into one rebuild per debounce window via an injected clock (`SetNow`), so it's deterministic to test. `refreshHera` is `heraPage.Refresh()` on tab entry (forces a flush) and `ScheduleRefresh()` on the tick while `ActiveTab()==TabHera`.
- **`doRefresh`'s `BuildModel`+`SetModel` pass is gated by cheap change-detection (`HeraPage.shouldRebuild`/`markRebuilt`, fix-hera-tick-and-kick-perf) — the debounce above only bounds how OFTEN a rebuild opportunity arrives, not whether one that arrives is actually worth paying for; every rebuild used to run `ListHeraOrchestrators(true)` (archived included) + all bindings + `Rail.buildRows()`'s full `canonicalParents`/`structuralReach` graph walk UNCONDITIONALLY, once a second, scaling with TOTAL historical role/orchestrator/binding count (Aaron's ~900+) regardless of active-agent count — measured at 34ms/30MB/133k allocs per rebuild at that scale (`internal/tui/hera/doRefresh_bench_test.go`).** The gate combines a cheap SQLite `PRAGMA data_version` fingerprint (`db.DB.DataVersion`, near-O(1), catches any OTHER connection's write — the dominant real source, since daemon/MCP-driven hera mutations use a separate connection from the TUI's own) with a `maps.Equal` comparison of the four per-tick RUNTIME maps also fed into the model (`needsInput`/`sessionIdle`/`sessionRunning`/`sustainedActive` — bounded by LIVE session count, cheap even at 900+ total roles); either changing triggers a rebuild, so a quiet DB with active agents still animates the spinner/`(?)` glyphs correctly. Post-gate steady-state cost measured at ~850ns/400B/12 allocs per tick (idle) — a ~35,000x reduction.
- **`PRAGMA data_version` does NOT change what a connection reads back after ITS OWN write (SQLite's documented same-connection blind spot, verified against `modernc.org/sqlite` under this repo's WAL DSN) — the TUI's `a.db` both reads (the tick) and writes (hera mutations, reconciliation) through ONE connection.** Closed not by ignoring the blind spot but by `HeraPage.Refresh()` (the general "force it now" primitive — tab entry, every `App.heraRefresh()`-driven mutation, and tests) calling `InvalidateChangeGate()` before flushing, so ITS OWN "forces an immediate rebuild" doc contract holds regardless of the gate. **Scoping the invalidation to `heraRefresh()` alone (the first implementation attempt) broke `TestRefresh_StatusStepReprojectsPlanNode`**, which writes through the same `*db.DB` the page reads from and calls `Refresh()` directly, expecting an unconditional rebuild — `Refresh()` itself is the right chokepoint, not each individual caller. `ScheduleRefresh` (the tick's own periodic, non-forced call) is deliberately left subject to the gate.
- **Explicit non-goal, not silently dropped: the gate does NOT cover `refreshTasksWithIDs`'s own base reads** (`db.Tasks()`, `ListMetaByNamespace("pr")`/`("hera")`, `ManagedTaskIDs()`) or lazy-load archived rows out of `Rail.buildRows()`'s graph algorithms — see `openspec/changes/archive/.../fix-hera-tick-and-kick-perf/proposal.md`'s Impact section for why both were scoped out (more un-audited local-write call sites; risk to `rail.go`'s heavily invariant-laden fold logic, respectively). The double `Tasks()` fetch per tick (once in `refreshTasksWithIDs`, once inside `BuildModel`) IS de-duplicated — `HeraPage.SetTasks` + an internal `tasksReader` wrapper serve `BuildModel`'s `Tasks()` call from the App's already-fetched snapshot instead of a second query, constructed transiently at the `BuildModel` call site (never stored back into `p.reader`) so it can't interfere with the fingerprint's own type-assertion against the unwrapped reader.
- **`HeraPage.Machine()`, not `Focus()`.** A method named `Focus()` collides with `tview.Primitive.Focus(func(tview.Primitive))` and silently breaks the Primitive interface (the page stops being a valid tview widget). The focus-machine accessor is `Machine()`. The `FocusMachine` is wired for 6b (Advance/Retreat/present-pane rebalance); 6a keeps focus on the rail and only reads `State()` to pick the border-highlight palette.
- **The rail navigates with `j`/`k`/Up/Down and folds with Space — never arrows-for-parent-nav like Hera's upstream rail did.** Historically the rail was BARRED from binding Left/Right because the global handler ate them for tab switching; that arrow-key tab-cycling has since been removed (tab nav is `1`/`2`/`3` only), so Left/Right now fall through to the page: a terminal-focused pane (coord/worker-agent) forwards them to the PTY, a coordinator's details region routes them to the embedded plan widget's cursor (slot/member nav, M7), while the rail leaves them unused (free for future horizontal navigation).
- **`Ctrl+Alt+Left/Right` walk the focus ladder (Retreat/Advance), mirroring `Tab`/`Backtab`.** Handled in `HeraPage.InputHandler`'s top-level key switch BEFORE the per-region forward, so they reach `FocusMachine.Retreat`/`Advance` rather than being forwarded to a focused terminal pane's PTY (a plain Left/Right still forwards). The modifier check is `Modifiers()&(ModCtrl|ModAlt) != 0` — **either** modifier, not strictly both — matching the main agent view's Ctrl+Alt+arrow pane switch (`app.go`); terminals are inconsistent about which of Ctrl/Alt they report for this chord, so the loose check is the proven pattern. This binding lives in the page handler (not `handleGlobalKey`) precisely because plain Left/Right intentionally fall through the global handler to the focused view.
- **Enter on a worker row focuses FocusAgent (right pane); Enter on a coordinator/header focuses FocusCoord (middle pane).** The Enter handler in `handleRailMutation` routes based on `p.detailsMode` (already computed by `applySelection` on cursor move): when `detailsMode` is false (plain worker selection, right region = agent terminal) it calls `SetRegion(FocusAgent)` directly; when `detailsMode` is true (coordinator or worker-bridge sub-coordinator, right region = Details summary) it calls `Advance()` → FocusCoord. Do NOT use `sel.IsCoordinator()` alone here — a worker-bridge sub-coordinator has `IsCoordinator()==false` but `detailsMode==true`, and the right pane is the Details view, not a terminal.
- **No `screen.Sync()`; cover the full bounding rect.** Every region (`Rail.Draw`, `DetailsView.Draw`, `drawRemoteBanner`, and the two `TerminalPane`s) paints through `widget.DrawBorderedPanel` (which blanks its interior) so stale cells can't survive — per the CLAUDE.md UX-rendering rules. The panes' `OnBranchChange` is wired to `a.forceRedraw` (log-only, never Sync); `OnNeedRedraw` bounces a `QueueUpdateDraw`. `TestPanes_NoSyncOnDraw` pins that drawing the full view (live panes + details) calls `Sync` zero times.

## M6c — keyset + thin in-process mutations

- **Mutations are a THIN layer over M1/M4 — single source of truth, no re-implementation.** `internal/tui/hera/ops.go` (`Ops` + the narrow `MutateStore` interface) is a set of small adapters over EXISTING `*db.DB` M1 methods (Archive/Unarchive/Pin/Unpin/Rename/Delete for orchestrators+roles, `UpsertHeraRoleStatus`, `RollHeraWorkerToReview`); it adds targeting + toggle-direction reads + the status ladder + uxlog, nothing more. Worker spawn does NOT live in `Ops` — it reuses the shared `agent.SpawnHeraWorker` primitive (extracted from `daemon.heraSpawnWorker`; the daemon MCP arm is now a thin adapter to it). If you find yourself re-deriving transactional spawn or cascade-delete, STOP and call the shared primitive.
- **The rail keyset routes through `HeraPage` callback fields, mirroring the DAG widget's `OnEnter`/`OnLink` pattern — NOT through a mutator injected into the rail.** `HeraPage` exposes `OnSpawnWorker`/`OnRename`/`OnArchiveToggle`/`OnPinToggle`/`OnStatusAdvance`/`OnStatusRevert`/`OnDelete`/`OnReattach func(Selection)`. `HeraPage.handleRailMutation` (rail-focus only) maps keys → callbacks passing `rail.Selection()`, then falls through to rail nav. The App wires the callbacks to handlers (`heraactions.go`) that own the modal/confirm/refresh orchestration. nil-safe: an unwired callback (remote mode) makes the key inert; `fire()` consumes a key when its callback is wired even on an empty selection so the keystroke never leaks to nav.
- **Every op acts on the SELECTED `(role, orchestrator)` from `Selection`, never the bare task ID — multi-binding isolation.** Deleting role R in orchestrator A removes only R's row (its binding cascades via `DeleteHeraRole`'s FK); the SAME task's role in orchestrator B is a distinct row and survives. `Ops` re-reads the row (`HeraRole`/`HeraOrchestrator`) to decide archive/pin TOGGLE DIRECTION from current state (not the possibly-stale model flag).
- **Delete (Ctrl+D) = ARCHIVE every DB row + reclaim ONLY the worktree/branch/session — ZERO hard deletes (BUG-017, Aaron's explicit rule "the database doesn't get any deletes").** Delete NEVER calls `db.Delete` / `DeleteHeraRole` / `DeleteHeraOrchestrator` / message deletes. It ARCHIVES: role rows via `RetireRole(r, false)` (ends the live binding `user_deleted` + `ArchiveHeraRole` — the same archive-not-delete primitive the `R` key uses), the orchestrator via `Ops.ArchiveOrchestrator` (`ArchiveHeraOrchestrator`, NOT delete), and the argus task via `db.SetArchived` (NOT `db.Delete`) — done by `heraReclaimAndArchiveTask`, which also stops the session and removes the worktree + LOCAL and REMOTE branch (`agent.RemoveWorktreeAndBranch`). The role's INBOX is archived implicitly: because the role is archived (not deleted), its `hera_messages` rows are simply retained attached to an archived role — there is NO message-archive primitive and NONE was added (Option A; `hera_messages` has no `archived_at`). NET: only the worktree dir + git branch are reclaimed; everything else lives in the Archive section. Difference from the `a` key: `a` archives but KEEPS the worktree/session; Ctrl+D archives AND reclaims them. ROLE delete: reclaim+archive the task only when sole-bound (`heraTaskSolelyBoundTo` → `ListHeraLiveBindingsByTask` len==1); a MULTI-bound task is PRESERVED (left fully alone — not archived, worktree kept). COORDINATOR / orchestrator HEADER delete runs the same cascade over the whole subtree (see the cascade bullet below). (One non-hera-row delete remains, accepted + out of scope: `db.SetArchived` on a TASK drops that task's queued LEGACY `task_messages` — a different table from `hera_messages` — established retire/archive behavior; the "no deletes" rule is scoped to hera role/orch/inbox rows.)
- **`heraReclaimAndArchiveTask` ALSO advances the argus task status from in_review to complete, but ONLY from that exact source status (fix-hera-archive-status)** — mirrors `RollHeraWorkerToReview`'s own never-clobber-active-work invariant one step later in the chain (BUG-050 rolls a finished worker `in_progress→in_review`; this rolls the archive step `in_review→complete`). Without it, an archived+reclaimed task was left stranded wherever its status happened to be at nuke time — almost always `in_review`, since the normal worker finish path already parked it there — making it PERMANENTLY invisible to `PruneCompleted` (which only ever looks at `status='complete'` rows, even after the #927 live-Hera-binding exclusion). A task still `pending` or `in_progress` when nuked (e.g. an operator force-killing a live, still-working role, or a cascade catching an actively-running coordinator) is archived with its status left untouched AT THAT INSTANT — never forced to complete synchronously. The gate reads the task's OWN `Status` column, so it is uniform across coordinator/worker/freelance roles even though `RollHeraWorkerToReview` itself is worker-kind only. But see the next bullet (fix-nuke-completion-race) — the `in_progress` case isn't left stranded forever either.
- **A task `in_progress` (actively live) at nuke time used to get PERMANENTLY stranded at `in_review` once its own reclaim-triggered stop settled — fixed via `App.pendingHeraReclaim` (fix-nuke-completion-race)** — `heraReclaimAndArchiveTask`'s stop is backgrounded (BUG-062, above), so its exit notification reaches `handleSessionExitUI` independently and later than the synchronous archive-time check (previous bullet), which found nothing to do because the task wasn't `in_review` yet. `handleSessionExitUI` has no way to tell a deliberate, terminal nuke stop apart from an ordinary recoverable one — it applied the normal crash/stop/fast-fail rule and landed the task at `in_review`, by which point the task was already archived with its hera binding ended and its worktree/branch reclaimed: nothing left to ever revisit it. Fixed by arming `pendingHeraReclaim[taskID]` on the tview main goroutine BEFORE backgrounding the stop (guaranteeing `handleSessionExitUI`'s later, separate `QueueUpdateDraw` dispatch sees it set); `handleSessionExitUI` consumes it (checks-and-clears, exactly once, regardless of which branch fires) at the same point it already runs the `RollHeraWorkerToReview` PR #707 check, and forces `complete` — instead of the ordinary clean/non-clean rule — only when that roll didn't fire, so a task somehow still holding a live worker-kind binding at exit time is unaffected. Guarded by `a.mu` (not `tapp.QueueUpdateDraw`) specifically because several existing `heraReclaimAndArchiveTask` unit tests construct a bare `New(...)` App with no `tview.Application.Run()` loop, and a background-goroutine `QueueUpdateDraw` call blocks forever without one. The two "no exit notification is ever coming" branches (no live session at stop time; `Stop()` itself errors) clear the marker immediately so it can't leak into a later, unrelated exit of the same task ID — the one known accepted gap is a task simultaneously subject to BOTH a nuke AND an in-flight `pendingRerenderRestart` kick, where the marker survives the kick's own exit (correctly skipped via the existing `pendingRestart` guard) and is instead consumed by whatever that task's NEXT real exit turns out to be.
- **`s`/`S` step the HERA ROLE STATUS (idle→working→blocked→done ladder), NOT the argus workflow status.** The rail renders role status, so the rail key steps role status — a pure `UpsertHeraRoleStatus` call. The argus task status (pending→…→complete) stays owned by the session lifecycle + the M4 finish policy. Reaching `done` on a WORKER-kind role also calls `RollHeraWorkerToReview` (mirrors the `hera_status("done")` MCP arm, BUG-050) — soft-fail so the status update always lands.
- **Stepping a WORKER OUT of `done` MUST clear `ready_to_close`, else the step is invisible — BUG-024.** `ready_to_close` (stamped by the done-roll) WINS the `statusIcon` precedence over the hera role status, so a `done`/ready_to_close worker renders the review `✓`. ## Ctrl+Z fullscreen + suspended-pane revive

- **The Hera view MUST trap `Ctrl+Z` — dropping it created worse than a suspend footgun.** `0x1A` (Ctrl+Z) reaching a focused pane's PTY is NOT a recoverable kernel SIGTSTP — Claude Code's CLI runs its own terminal in raw mode and interprets a literal `0x1A` itself as its native "background this session" command, which detaches the conversation onto Claude Code's OWN per-user supervisor process (see [[daemon-rpc]] "Claude Code's own supervisor-hosted background sessions"). That process is permanently outside argus's spawned process tree — no `Session.Stop()` SIGTERM can ever reach it again, unlike a real SIGTSTP which `fg`/SIGCONT could resume in place. The external plugin never suffered this because it bound `^Z`→fullscreen, which *consumed* the byte. Native omitted that binding and the raw byte fell through to the pane PTY. `HeraPage.InputHandler` now traps `Ctrl+Z`→`FocusMachine.ToggleFullscreen` and ALWAYS returns (consumes) — even on the rail, where it's a no-op — so the byte can never again reach a PTY. Don't "simplify" this by only consuming `^Z` when a pane is focused: the rail-focus no-op MUST still consume. **This guard exists only in the TUI (both the classic single-task agent view and this native Hera view) — the web/PWA and macOS clients have no equivalent interception** (see gotchas/web-remote.md and gotchas/macos-app.md); a human pressing Ctrl+Z while attached to a worker's terminal from either surface can still orphan it today.
- **Fullscreen is an attribute of the FOCUSED pane, cleared on any return to the rail.** `FocusMachine.fullscreen` is carried by `Advance` (zoom moves to the next pane) but cleared by `Retreat`-to-rail, `ToRail` (Ctrl+Q), `rebalance`-to-rail (a pane disappearing), and `SetRegion(FocusRail)` (rail click). The rail has no fullscreen mode. Present-pane flags in `Draw` are computed from the NORMAL split geometry regardless of fullscreen, so the ladder can still traverse the hidden pane (`fullscreenForward` COORD→AGENT needs `agentPresent`).
- **The fullscreen `Draw` branch records the hidden pane's hit-test rect as zero width.** When zoomed, only the rail + focused pane draw; the other region's `coordW`/`agentW` is set to 0 so a stale click/scroll can't land on a region that isn't painted. Same no-Sync + full-rect-coverage rules as the split path.
- **`Enter` revives a STOPPED (suspended) worker, not just a DEAD one — but the two states need different primitives.** `Alive()` cannot tell a SIGTSTP-stopped process from a running one (both keep the session "alive"; the process just stopped, `Wait` hasn't returned). So the page broadens the `Enter` gate to fire `OnReattach` for a dead session (any role) OR a live worker/freelance role (a live coordinator stays navigate-only — operators type into it). `heraReattach` then branches: dead→`startSession`; live worker→`reviveHeraWorker`.
- **`heraReattach`'s DEAD-session branch used to call `startSession` unconditionally for every role kind — a real gap in the close-out guard, not a `hera_accept`-specific bug (add-hera-accept-lifecycle, found via live-testing).** `startSession` unconditionally flips the task to `in_progress` with zero Hera awareness; the resumed session then exits almost immediately (nothing to resume), and the ordinary post-exit rule rolls the task back to `in_review` — silently undoing an explicit `hera_accept`, or a self-reported-done worker's `ready_to_close` stamp, even though `Enter` is not itself an explicit revive. Fixed: for a worker/freelance selection (`sel.IsWorkerOrFreelance()`), `heraReattach` now calls `heraTaskClosedOut` — a thin wrapper around the newly-EXPORTED `db.HeraWorkerAwaitingCloseout` (renamed from the previously-unexported `heraWorkerAwaitingCloseout`; same predicate `ReviveHeraWorkerToInProgress` already used) — BEFORE `startSession`, and refuses (no status write, no session start, statusbar error) when the task is awaiting close-out. Coordinators are unaffected (no `ready_to_close` concept; always restarted, unchanged). This is the THIRD trigger site sharing the close-out predicate, alongside `ReviveHeraWorkerToInProgress`'s own two callers (the live-session kick, `hera_revive`) — but it's the read-only predicate reused for a REFUSE decision, not a call into `ReviveHeraWorkerToInProgress` itself (which restores to `in_progress`, the opposite action a dead session needs).
- **`heraReattach`'s Enter-path guard (above) only covered the KEYPRESS entry point — `handleSessionExitUI`'s `pendingRerenderRestart` branch (the size-drift kill+resume "kick", BUG-074/BUG-076) is a SIBLING, keypress-less entry point into the SAME gap (add-fix-resize-kick-closeout).** Confirmed live via `daemon.log` correlation: a task `hera_accept`'d to `complete` had its session merely navigated onto (a different terminal width than the session's last-recorded size) — the kick fired, found the operator still viewing the row, and unconditionally flipped the task back to `in_progress` + `startSession`, with zero Enter keypress involved. Fixed the same way: the branch now calls `heraKickRestartClosedOut` — which resolves `TaskHoldsLiveHeraWorkerOrFreelanceBinding` itself (this call site has no `hera.Selection` to ask `IsWorkerOrFreelance()`, only a bare `taskID`) before delegating to the SAME `heraTaskClosedOut`/`HeraWorkerAwaitingCloseout` predicate — and skips the restart silently (no status write, no session start) when closed out, leaving the task exactly as close-out left it. SUBTLETY that broke the naive version of this fix: the guard must be evaluated from a snapshot taken BEFORE `handleSessionExitUI`'s own `StatusInProgress` branch runs, not after — that branch's BUG-050 `RollHeraWorkerToReview` roll stamps `ready_to_close=true` as a side effect of ANY in-progress worker's exit (kick-induced or not, since the TUI's own `Stop()` call never sets the runner-level `pendingRestart` `KickRerender` uses, so the exit hook's `pendingRestart` param is always `false` here) — checking the guard AFTER that roll would misread a perfectly healthy, merely-idle in-progress worker's OWN fresh stamp as a pre-existing close-out and wrongly refuse to restart it. `handleSessionExitUI` now computes `kickClosedOut`/`kickClosedOutErr` once, immediately after the initial `db.Get`, gated on the same `!cleanExit && a.pendingRerenderRestart[taskID]` condition the restart branch itself checks, and reuses that snapshot later instead of re-querying.
- **`reviveHeraWorker` uses `runner.KickRerender`, NOT the TUI-side `pendingRerenderRestart`+`Stop` path.** The TUI rerender-restart in `handleSessionExitUI` only fires while the operator is viewing the task in the AGENT view (`stillViewing`); from the Hera tab (which is `modeTaskList`) it would settle the worker at `InReview` instead of resuming it. `KickRerender` owns the stop+resume inside the runner/daemon, so the worker comes back via `--session-id` regardless of which tab is active. It needs `a.runner.(agent.SessionRunner)` (both `*Runner` and the daemon client satisfy it; remote apiclient does not → skip).
- **The revive is idle-gated and prompt-aware so it never clobbers real work.** `reviveHeraWorker` only kicks when the session `IsIdle()` (no recent output — the signature of a stopped/stuck agent) AND is not `sessionBlockedOnPrompt` (don't dismiss a pending question). A busy worker is left alone. Reads hit the daemon over RPC → run on a goroutine, dispatch the decision via `QueueUpdateDraw` (mirror of `maybeKickRerender`). `task.SessionID == ""` (Codex pre-capture) skips revive — there's nothing to resume in place.
- **On darwin, `SIGTERM`/`Stop` DOES terminate a stopped process** (so `KickRerender`'s stop reaps a suspended agent and the resume brings it back). This differs from Linux, where a stopped process only reacts to `SIGKILL`/`SIGCONT` — relevant if a future contributor relies on stop-reaps-suspended on the Linux CI runner; the revive's correctness on the operator's machine (darwin) is what was validated live.
- **`Enter` revives from the FOCUSED PANE too, not only the rail (BUG-001).** A focused pane's keys route through `HeraPage.forwardKey`, which used to SILENTLY DROP the keystroke once the session was nil/`!Alive()` (the BUG-013 re-resolve path) — so `Enter` on the "Session not running - press Enter to start" overlay did nothing. Fix: `terminal.TerminalPane` gained `OnReattach func()` + an `InputHandler()` that fires it ONLY when `Enter` is pressed AND the session is nil/`!Alive()`; `forwardKey`'s dead-session branch now routes the event to that `InputHandler` instead of dropping. `bindPane` wires `tp.OnReattach = func() { p.reattachPane(tp) }`; `reattachPane` targets the pane's OWN task (agent pane → `p.sel` worker, coord pane → `Selection{Orch:…}` for the coordinator it shows) and routes through the page's `OnReattach` → `App.heraReattach` — the SAME revive the rail uses. INVARIANT: only-when-not-alive (a live pane's `Enter` must reach the PTY) and nil-guarded, so the task page (which mounts the same widget but never wires `OnReattach`, and writes the PTY via `handleAgentKey` not the pane `InputHandler`) stays inert and unchanged. No new key — `Enter`-to-revive is already documented, so help/README are untouched.

## Two-state EOL — hide vs nuke (BUG-022, supersedes the retire/prune ladder)

> BUG-022 replaced the five-key EOL surface (`a`/`R`/`C`/`Ctrl+R`/`Ctrl+D`) with a TWO-state model and three keys. `R` (retire) and the rail-wide `Ctrl+R` (prune) are REMOVED — their keys, handlers, and the `Model.IsFinished`/`FinishedRoles`/`FullyFinishedOrchestratorIDs` helpers are gone. The bullets below describe the new world; the old "retire → prune ladder" notes were deleted with the keys.

- **BEDROCK RULE: no EOL path hard-deletes a hera row, ever.** "Done with" = gone from the rail + worktree gone from disk + role/orchestrator/inbox/task all retained & retrievable. `DeleteHeraRole` / `DeleteHeraOrchestrator` were REMOVED from the `MutateStore` interface (`ops.go`) so the EOL surface can't even call them — the type system enforces the invariant. Message rows are never deleted either.
- **TWO resting states, distinguished by a second `nuked_at` column on `hera_orchestrators` AND `hera_roles`** (additive, alongside `archived_at`/`pinned_at`): HIDDEN (Tier 1) = `archived_at` set, `nuked_at` NULL → renders in the parent coordinator's nested Archive expando, reversible; NUKED (Tier 2) = `nuked_at` set (and `archived_at` set, so the row leaves the active-name partial unique index and frees its name) → invisible to the rail entirely. The rail-feeding lists (`ListHeraOrchestrators`/`ListHeraRoles`) filter `nuked_at IS NULL`; id lookups (`HeraOrchestrator`/`HeraRole`) still return nuked rows for DB recovery. BuildModel ALSO skips `nuked_at`-set rows defensively (so the model is self-contained even if a reader doesn't filter).
- **`a` = HIDE, worker / sub-coordinator ONLY.** `heraHide` rejects a coordinator-kind role / orchestrator-header selection ("Hide applies to workers and sub-coordinators") because a top-level coordinator has no parent archive to nest under. Hide is the existing archive TOGGLE (`Ops.ArchiveToggle`) — it archives the hera ROLE row ONLY (it does NOT `db.SetArchived` the argus task — Q2 decision: HIDE is RAIL-ONLY, the worker keeps running and still shows in the Tasks tab), KEEPS the session + worktree alive (no `Stop`, no `RemoveWorktreeAndBranch`), is reversible (press `a` again to un-hide → clears `archived_at`, the rail row returns to its exact prior spot), and has NO confirmation. - **Q3 — hiding a bridging sub-coord folds its whole subtree INTO the parent's Archive expando (`rail.go appendOrchWorkers`).** ALL archived workers (leaf AND bridging sub-coords) route into the per-coordinator `Archive (N)` expando; the expando's `appendWorkerRow` nests a bridging sub-coord's bridged sub-team beneath it (dimmed) when open. The historical orphaning hazard (an archived bridging worker hoisted into the COLLAPSED expando while its child orchestrator was left unplaced → safety-swept flat to a top-level root) is now closed by `structuralReach`: a child whose canonical-parent chain reaches a root is never re-leaked by `buildRows`' safety sweep, so a collapsed expando keeps the child hidden under its hidden parent. This is the deliberate REVERSAL of the earlier "archived bridging worker renders in-place dimmed" rule (which predated `structuralReach`). MUST stay tested at ≥2 levels in BOTH fold states — `TestRail_HiddenSubCoordCollapsesSubtreeIntoExpando` + `TestRail_ArchivedBridgingWorkerHoistsSubtreeToExpando` pin it.
- **`Ctrl+D` = NUKE, any role or coordinator (incl. top-level).** `heraOpenDelete` → `heraNukeRole` (single role) or `heraCascadeNukeFrom` (coordinator / orchestrator header / bridging-sub-coord row → whole `BridgeSubtree`). Confirm modal is worded "removes … from the rail" + "reclaims … worktree(s)" + "rows retained (recoverable via the DB)".

Scoped to the SELECTED coordinator's archive, NEVER a global sweep; empty → "nothing to clear". This is the rework of the old `heraPruneDescendants` — the terminal op changed from complete-task-+-`DeleteRole` (a hard delete!) to archive-task-+-`NukeRole`.

A plain top-level coordinator (no `BridgeChildOrchID`) is unchanged.

- **Q2 DECISION (locked): HIDE is RAIL-ONLY — it does NOT archive the argus task.** `heraHide` archives only the hera role row; it never calls `db.SetArchived` on the bound task, so a hidden worker keeps running and still shows in the Tasks tab. Only NUKE (`Ctrl+D`/`C`) touches the argus task (archives it + reclaims the worktree). This corrected an earlier design note that said "db.SetArchived in BOTH tiers" — that was wrong for hide. ## Left arrow — rail parent navigation (BUG-016)

- **Left arrow is scoped exclusively to `FocusRail` — it does NOT intercept Left from a focused pane.** When a content pane (coordinator or agent terminal) is focused, Left must pass through to `forwardKey` unchanged so the PTY receives it (cursor motion in the shell, vim navigation, etc.). ## Ctrl+G problem-child excursion + Ctrl+B restore (add-ctrlg-excursion)

- **The excursion snapshot is captured ONLY at the rebuild-time 0→≥1 needs-input-count transition (`Rail.noteExcursionTransition`, called from `SetModel`) — NEVER at `ctrl+g`/`ctrl+b` keypress time.** Capturing at keypress would snapshot whatever the operator has already done in reaction to the problem, not their true pre-interruption layout; `ctrl+g`'s own `EnsureExcursionArmed` call is a belt-and-suspenders no-op in the normal case, not the primary arming path.
- **A snapshot already held is NEVER overwritten while the count stays >=1 — a second or third interruption folds into the SAME excursion.** Recapturing on every transition (rather than only the 0→≥1 edge) would silently replace the operator's original layout with whatever they'd already fussed with by the time a SECOND problem appeared, defeating the entire point of capturing early.
- **BUG-069 (live dogfood repro, 2026-07-24): re-arming on the raw `excursion == nil && count >= 1` edge — freezing unconditionally on the VERY NEXT rebuild after any restore — was WRONG, not "intentional, not a bug" as this bullet previously (incorrectly) claimed.** A bare count cannot distinguish "the same still-outstanding, never-resolved role reappearing" from "a genuinely new, distinct interruption" — a long-stuck (?) that never clears (e.g. a stale needs-input flag from an unrelated orchestrator) kept the count at >=1 forever, so the re-arm fired on literally the first rebuild after every `ctrl+b`, freezing whatever the rail happened to look like at that instant and then staying frozen — silently discarding ANY fold/selection change the operator made afterward until the next explicit restore. Two back-to-back live tests confirmed it: a `ctrl+b` replayed a stale, much-earlier layout instead of the operator's actual prior position. **The fix (`Rail.armedNeedsInputIDs`, `Model.needsInputRoleIDs`, `hasNewNeedsInputID`) tracks the needs-input set by ROLE IDENTITY, not count.** While `excursion == nil` and the set is non-empty, the tracked baseline is continuously refreshed to the CURRENT set on every rebuild for as long as it stays a subset of (or equal to) that baseline — so the operator's ongoing manual navigation is captured, not lost — and a fresh snapshot freezes ONLY the instant a role id appears that was NOT in the baseline. The baseline is updated unconditionally on every rebuild, including while an excursion is already frozen, so an entrant that merely folds into an open excursion (no recapture, per the bullet above) doesn't look "new" all over again the instant the excursion is later discharged. See `internal/tui/hera/excursion_test.go`'s `TestRail_ExcursionSnapshot_StaleItemDoesNotFreezeAwayManualNavigation` / `_DoesNotReArmAfterRestoreWithoutNewEntrant` / `_EntrantAbsorbedWhileFrozenDoesNotReFreezeAfterDischarge`. Do not reintroduce a count-only re-arm check — role-id set membership is required.
- **Separately confirmed (not fixed): `currentRef()`/`restoreCursor` have a narrow, pre-existing gap shared with the BUG-002 persisted-selection mechanism** — a cursor resting on a selectable fold row with no role/orch identity (the bottom Archive expando, a per-coordinator Archive expando, or the Freelance fold header) at capture time yields `selRef==0`, and `restoreCursor(0)` is a silent no-op, leaving the cursor wherever it already was instead of re-pinning it. Confirmed via `TestRail_CurrentRef_ZeroOnArchiveExpandoRow`; left unfixed (BUG-069 is fully explained by the set-membership bug alone in the clean, isolated repro) but worth a dedicated follow-up if it recurs.
- **BUG-070 (live dogfood repro, 2026-07-25, discovered testing the BUG-069 fix — reproduced once, then "worked as expected" on a retry without relaunching, the tell that it's a cold-start-only trigger): the identity-tracking fix above still froze a BOGUS snapshot on a Rail's very first-ever `SetModel` call (right after a TUI launch/relaunch) when a stale, pre-existing needs-input role already predated the launch.** `noteExcursionTransition`'s `len(r.armedNeedsInputIDs) == 0 && len(current) >= 1` case is satisfied unconditionally on that first call (`armedNeedsInputIDs` is `nil`, a permanently-stuck "?" makes `current` non-empty) — but `r.rows` is still `nil` (`buildRows` has never run once), so `captureExcursionSnapshot`'s `currentRef()` call has no rows to search and returns 0, and `r.collapsed` at that instant holds whatever the PREVIOUS session's `SetStateStore` load persisted, not anything from the current session. The live repro: `ctrl+b` left both panes empty (`selRef==0` silently no-op'd the cursor restore) and flipped fold state to a stale prior-session layout — collapsing an orchestrator the operator had just expanded and leaving a different one expanded that they'd never touched this session. **Fix: `noteExcursionTransition` early-returns (seeding `armedNeedsInputIDs` only, no capture) whenever `r.rows == nil`** — i.e. on literally the first-ever call, regardless of whether the needs-input set is already non-empty. From the second call onward the normal arm/re-arm rules apply unchanged; if nothing new interrupts the operator by the time they first press `ctrl+g`, `EnsureExcursionArmed`'s belt-and-suspenders call arms from their real live position instead (there is no earlier "pre-interruption layout" to capture when the problem already existed before the app ever opened). See `internal/tui/hera/excursion_test.go`'s `TestRail_ExcursionSnapshot_ColdStartDoesNotCaptureBogusSnapshot` / `_ColdStartWithNoPriorNeedsInputArmsNormally`, and `internal/tui/ctrlg_test.go`'s two `TestSmoke_CtrlG/BRestoresRail*` tests (each needed an explicit empty-needs-input priming `Refresh()` before their first real interruption, matching the real app's own natural startup tick, once the guard stopped the literal first `SetModel` call from arming).
- **The whole-rail needs-input count (`Model.NeedsInputTotalCount`) is deliberately NOT derived from `len(Rail.rows)`.** `Rail.rows` reflects only the currently-focused kanban group and expanded folds; keying the excursion state machine off the RENDERED row set would let folding/unfolding itself arm or discharge an excursion, which must never happen — the count instead sums `needsInputOwn()` across every role (including coordinator-kind) in every model section, independent of rail rendering state.
- **`ctrl+b`'s key is a deliberate substitute for the originally-approved `ctrl+shift+g` — `ctrl+<letter>` is a C0 control byte with no room for a Shift bit at the wire level, so `ctrl+g` and "ctrl+shift+g" are indistinguishable on the wire regardless of keymap support, and `keymap.Parse` independently documents and rejects combining `shift` with `ctrl+<letter>`.** A future feature wanting a "shifted" control-key pairing can't get a real Shift modifier this way — pick a distinct, unused `ctrl+<letter>` instead (see `internal/tui/keymap/actions.go`'s default-spec table for what's already taken).

## Rail partial-fold reveal for hidden needs-input descendants (add-hera-jump-question)

- **A closed coordinator whose subtree needs input still reveals the specific ancestor chain(s) down to each needs-input leaf — a NEW rendering mode inside the EXISTING `appendOrchWorkers`/`appendWorkerRow`/`appendOrch` traversal, not a parallel one.** `appendOrch`'s collapsed branch, when `o.SubtreeNeedsInput` is true, calls `appendOrchWorkers(..., revealOnly: true)` instead of returning outright; that mode recurses ONLY into children whose own `SubtreeNeedsInput` is true (worker rows via `appendWorkerRow(..., revealOnly)`, coordinator-spawned children via the new `appendOrchRevealPath` helper), pruning every other sibling with NO placeholder row. A revealed bridging worker's own child recurses in `revealOnly` too, UNCONDITIONALLY ignoring that child's own collapse flag — while inside a hidden ancestor's subtree, a descendant's individual fold state is not meaningful (the operator can't see or toggle it). Archived and pinned-floated roles are skipped in reveal mode exactly as in normal mode (they have their own, independent visibility mechanisms — Archive expando / Pinned section — so reveal doesn't layer a third), and the per-coordinator Archive expando itself never renders in reveal mode.
- **Fold state is NEVER mutated by the reveal — it is a pure `buildRows`-time rendering overlay.** `Space` (`ToggleCollapse`) means exactly what it meant before: toggling a partially-revealed coordinator fully expands it (all previously-pruned siblings return) or fully re-collapses it (back to the reveal-only view, not to nothing).
- **Revealed rows are ordinary, fully selectable `railRow`s — no new row kind, no special-casing in `step()`/`selectable()`/drawing/mutation-by-`Selection`.** Because they're just rows in `r.rows` like any other, cursor navigation, `Enter`, and every mutation key act on them exactly as if the ancestor had been manually expanded; this is also why the implementation extends the one true traversal rather than forking a parallel one — `rail.go`'s nesting logic carries ~15 individually-hard-won invariants (`canonicalParents`, `structuralReach`, bridge-cycle guards, pinned-vs-active ordering, archive-expando hoisting) that a second implementation would have to re-satisfy independently and would drift the moment either path changed.
- **Filtering and reveal never overlap in practice** — the `/` rail filter force-expands every fold (`isCollapsed` reports expanded while `filterActive()`), so `appendOrch`'s `isCollapsed`-gated reveal branch structurally can't trigger during filtering; `appendWorkerRow`'s `revealOnly` path therefore skips the filter-visibility check entirely rather than reconciling two visibility mechanisms that can't actually coexist.
- **A pinned non-root role's own bridged child gets the same reveal treatment** (`appendPinnedRole`'s `!isCollapsed(child.ID)` branch gained an `else if child.SubtreeNeedsInput` sibling calling `appendOrchWorkers(..., revealOnly: true)`) — a pinned role floating into the Pinned section can still bridge a closed sub-team with a hidden blocked worker.
- **BUG-064: `appendWorkerRow`'s bridged-child branch needed the SAME `else if child.SubtreeNeedsInput` fallback `appendPinnedRole` already had** — normal (non-`revealOnly`) traversal reaching a bridging worker row whose child is STILL collapsed had no branch at all (only `revealOnly` or `!isCollapsed(child.ID)`), so expanding an outer coordinator while a nested sub-coordinator stayed collapsed silently dropped the nested needs-input leaf instead of re-revealing it. Two independent call sites implement the identical reveal rule (`appendWorkerRow` for normal nesting, `appendPinnedRole` for the pinned-role bridge) — when one gains a case, check the other.
- **Worker/freelance context-pressure indicator (add-worker-context-indicator).** A reserved trailing 2-column slot on every live worker/freelance rail row (`contextIndicator` in `rail.go`) — blank under 40% of `RoleView.ContextPercent`, `•` pale-yellow 40-65%, `•` hot-orange 65-90%, `!` red-bold 90%+. The slot is reserved for the row's WHOLE lifetime regardless of current percentage, not only once it goes warm, so a name never reflows the instant a row crosses a threshold; it's reserved BEFORE the PR-tag reservation so the two compose (PR tag draws inside whatever width remains) rather than one overwriting the other. Coordinators are explicitly excluded — they already have the coord-hook's budget/nudge/recycle guard — and keep the live-count badge in that row position instead, which this same change flipped from `(17)` to a bare `17` (no parens). `RoleView.ContextSize` (the raw stamp) is a pure `buildRoleView` read off the already-fetched `heraMeta` map and reaches both local and remote mode; `RoleView.ContextPercent` (the derived 0-100 the indicator actually reads) is resolved ONLY by the existing local-mode-only `resolveHeraTier`/`SetTierResolver` seam — so the indicator itself never renders in remote/web/macOS, a named gap mirroring the diligence-tiering readout's own local-only scope, not a new one.
- **The percent denominator is kind-dependent, NOT a single shared config value (fix-worker-context-window-denominator).** `resolveHeraTier` divides by `cfg.Hera.CoordinatorContextBudget` (200000, a coordinator recycle-nudge POLICY threshold, deliberately set well below a coordinator's real ceiling) for a coordinator role, but `cfg.Hera.WorkerContextWindow` (1000000, a worker's actual real context window) for a worker or freelance role — reusing the coordinator's budget for workers (the original `add-worker-context-indicator` shipped this way) made the 40/65/90 tiers fire at 80k/130k/180k tokens instead of the intended 400k/650k/900k, a false alarm at a small fraction of a worker's real capacity.
- **BUG-071: the reveal was stateless across rebuilds — recomputed purely from the FRESH model's `SubtreeNeedsInput` every `SetModel` call, with no memory of what was visible a moment ago — so a role revealed only via this mechanism, currently selected, vanished the INSTANT its own needs-input flag cleared (the operator answering its prompt), yanking the cursor (and the panes bound to it) onto whatever row the stale cursor INDEX happened to land on once `restoreCursor`'s identity lookup failed to find the now-gone row.** Fixed via `Rail.applyStickyReveal(ref)`, called from `SetModel` right after resolving the effective previous-selection ref (including the one-shot `pendingSelRef` override) and BEFORE `buildRows` — it forces `SubtreeNeedsInput` true on `ref`'s own role (role ref) or orchestrator (header ref), then walks `canonicalParents()` up to the root forcing every ancestor `OrchView.SubtreeNeedsInput` true and, for each worker-bridge (non-coord-spawn) hop, the PARENT's bridging role's `SubtreeNeedsInput` too (via the new `Model.roleByID` / `OrchView.bridgingRoleFor` helpers) — reusing the EXISTING reveal gates verbatim rather than forking a parallel "sticky" code path or threading a second condition through `appendOrch`/`appendOrchWorkers`/`appendWorkerRow`/`appendPinnedRole`/`appendOrchRevealPath` individually. **Re-derived from the CURRENT cursor identity on every `SetModel` call, never cached beyond one rebuild** — as long as the operator's selection doesn't move, each subsequent rebuild re-arms the same forced path; the instant the cursor lands on a different row (operator navigates away, or a rebuild's own cursor-restore already moved on), the NEXT rebuild computes stickiness from the NEW identity and the old row folds away exactly like any other row whose reveal condition no longer holds. Safe by construction when the previously-selected row was already visible through ordinary (non-collapsed) expansion — forcing the rollup flag is a no-op there, since the non-`revealOnly` render path never consults `SubtreeNeedsInput` at all (confirmed: this field drives NOTHING but the reveal gates — no icon, no `ctrl+g` candidacy — per the `remove-needs-input-rollup-glyph` doc on the field itself). See `internal/tui/hera/rail_sticky_reveal_test.go`.
- **`readContextSizeReal`'s undercounting root cause is `transcript_path`'s documented ASYNC-WRITE LAG, not sidechains (fix-context-stop-lag).** Claude Code's hooks reference states `transcript_path` "is written asynchronously and may lag the in-memory conversation," so at the exact moment a Stop hook fires it "may not yet include the current turn's most recent messages" — matching the reported symptom exactly (the rail dot missed real ~41-42% usage, only appearing once a LATER turn's read happened to already be fresh). Verified empirically (via Claude Code's hooks docs + the shipped `last_assistant_message` feature, github.com/anthropics/claude-code#10610) that **no Stop-hook field can route around this**: `last_assistant_message` is a plain string of the final response TEXT, never a usage object, and no hook event of any kind exposes token usage directly — the docs are explicit that "hooks that need token usage information must parse `transcript_path` themselves." So `readContextSizeReal` still has to scan the file; the fix is a bounded retry (`contextSizeRetryInterval`=20ms × up to `contextSizeRetryBudget`=200ms) that re-scans and keeps the MAX size observed across polls — safe because context size is monotonically non-decreasing within one transcript file, so a later, larger read can only ever correct a stale earlier one, never regress it. A prior investigation (originally landing as a separate `isSidechain`-skip PR) suspected a dispatched Task-tool sub-agent's own assistant turns (same `"type":"assistant"` tag, `isSidechain:true`, tiny fresh usage) physically interleaving into the main transcript and landing last — checked empirically (~900 real `isSidechain:true` entries across a month of `~/.claude/projects` history, CLI 2.1.216) and found to be a **no-op under the current CLI**: sub-agent turns are always written to a separate `subagents/<agentId>.jsonl` sibling file, never inline, and Argus's Stop-only hook registration (no `SubagentStop`) never even fires for one. The `isSidechain` skip is folded into `scanContextSize` anyway as defensive, forward-compatible hardening (near-zero cost, in case a future CLI ever does interleave sidechain lines), but the async-write-lag retry above is the fix for the actual reported bug. **The retry loop has an early exit, not an always-on tax** — added after review flagged that this hook now runs on every hera-managed Stop event (coordinator, worker, AND freelance, per `add-worker-context-indicator` above), so an unconditional ~200ms retry budget would be a per-turn latency cost across the whole fleet. `readContextSizeReal` does one scan first and compares it against the task's previously-stamped `context_size` (`contextSizeReadPrevious`, a package-level func-field test seam over `readPreviousContextSizeReal`'s REST round trip, mirroring `readLastNudgedContextSizeReal`'s shape): a scan already at or above the prior stamp returns immediately (the common case, since usage only grows turn over turn); the bounded retry only runs when the scan comes back BELOW the prior stamp (the actual lagging-write symptom) or there's no prior stamp yet (the task's first Stop event ever, no baseline to judge against). A failed previous-stamp read fails open into the retry path rather than trusting an unverified single scan.

## Rail mouse-wheel scroll (rail-scroll)

- **`Rail.MouseHandler` (mirrors `gitpanel.FilePanel` and `taskview.TaskListView`) is the FIX for the routing test's own stale comment: the rail previously had NO `MouseHandler`, so a wheel event that `page.go`'s `regionAt` misrouted to the rail column silently hit `Box`'s default (which only handles `MouseLeftDown`) and was never consumed — a genuinely broken scroll, not just an untested one.** `page.go`'s `MouseHandler` already gates dispatch on `regionAt(x) == FocusRail` before calling `p.rail.MouseHandler()`, so the new handler's own `InRect` check is a second, redundant-in-practice guard for direct callers (tests) rather than the thing doing the real gating.
- **Wheel up/down call the SAME `CursorUp`/`CursorDown` (→ `step()`) the `k`/`j`/arrow keys already use — no separate scroll-offset path.** `step()` already handles selectable-row skipping, kanban-group boundary crossing, and persistence (`setCursor`'s `persist()` call), so a wheel notch is indistinguishable from a keyboard nav step; `adjustOffset` (Draw-time) keeps the cursor in view exactly as it does for keyboard nav. This holds regardless of `filterInput` — `MouseHandler` calls `CursorUp`/`CursorDown` directly, bypassing the `InputHandler`'s filter-vs-nav key routing entirely, but both paths bottom out in the same `step()`.
- **`tview.MouseScrollUp` maps to `CursorDown` and `MouseScrollDown` maps to `CursorUp` — INVERTED relative to `gitpanel.FilePanel`'s pane-scroll convention, deliberately (dogfood feedback, same day as ship).** `FilePanel` (and `terminalpane`/`dagview`/`modal.HelpModal`/`SettingsView`) scroll a content PANE, where `ScrollUp` conventionally reveals earlier/upper content. This widget scrolls the CURSOR itself — the fingers are "dragging the cursor," not "dragging the pane" — so the intuitive mapping is the cursor moving in the SAME direction as the trackpad gesture, which on a Mac with natural scrolling reaches this widget as the OPPOSITE tview event from what a pane-scroll would want. Do not "fix" this to match `FilePanel` without re-confirming on an actual trackpad — the first shipped version used the pane-scroll direction and Aaron reported it backwards on his first test.

## BUG-076: Hera-pane size-drift kick never auto-restarts (false "Session not running" after ordinary rail nav)

- **Root cause was NOT a liveness misclassification — the session really did get stopped, by a legitimate-looking size-drift kick (`heraKickRerender`, BUG-074) whose auto-restart then unconditionally skipped itself because `handleSessionExitUI`'s "is the user still watching" gate (`stillViewing`) checked ONLY `a.mode == modeAgent` — the classic fullscreen agent view's mode. The native Hera view never sets `a.mode` to `modeAgent`; it stays `modeTaskList` with `header.ActiveTab()==TabHera` regardless of which pane the rail cursor is on. So EVERY kick fired from a Hera pane — and BUG-074 made that nearly every task's first Hera-view bind, since Hera panes are narrower than the main agent view and almost any previously-wider-attached (or never-attached) task exceeds `RerenderMargin` — took the "user navigated away, settle at InReview" branch verbatim, even though the operator was staring right at the pane through the Hera tab.** The kick's own gating (`ShouldKickRerender`) requires the session to be idle, so it doesn't fire mid-stream — it fires in the gap between turns, which is exactly the "moment" a rail j/k glance-away-and-back window covers: the operator sees it fine, looks away, and by the time they look back the async kick (RPC round trip + `QueueUpdateDraw` dispatch, see `maybeKickRerenderAtWidth`) has already stopped the session and skipped the restart. The task settles at InReview with a genuinely dead session; the pane's next resolve returns nil and `terminalpane.go`'s `sess == nil && !tp.HasContent()` branch paints "Session not running - press Enter to start" — literally true at that point, just for the wrong reason. Reproduces on BOTH the coordinator and agent/worker Hera panes (both route through `heraKickRerender`); the same `stillViewing` gate is also reachable from the classic agent view if the operator switches tasks inside the kick's async window, so the bug family isn't Hera-exclusive even though Hera nav is what makes it "very frequent."
- **Fix: widen the restart gate to recognize BOTH ways of "watching" — `App.isViewingTaskSession(taskID)` returns true for the classic `a.mode==modeAgent` case OR for `a.mode==modeTaskList && ActiveTab()==TabHera && heraPage.IsBoundToTask(taskID)`.** `HeraPage.IsBoundToTask` (`internal/tui/hera/panes.go`) is a pure read of `coordBound`/`agentBound` — true if EITHER pane currently shows taskID, independent of which pane has keyboard focus (the coordinator pane stays bound the whole time any worker under it is selected, so it must count as "viewed" even while the rail cursor sits on a worker row). `handleSessionExitUI`'s `stillViewing` now calls `isViewingTaskSession` instead of the inline `modeAgent`-only check; `startSession`'s own `a.mode==modeAgent` pane-attach guard is untouched (still correctly a no-op from the Hera branch — the classic `a.agentPane` isn't shown then, and the ALREADY-RUNNING Hera reconcile tick (`reconcileOne`'s late-bind case) picks up the freshly-resumed session on its own).
- **Do not "fix" this by making the kick less aggressive (e.g. skipping it from Hera panes) — the kick itself is correct and necessary** (BUG-074's whole point: a Hera pane's narrower width needs the same kill+resume repair the main agent view gets, or scrollback stays corrupted). The bug was purely in the EXIT-TIME restart decision, not the kick decision.

## BUG-077: Hera-pane size-drift kick never retries after a deferred (busy) outcome — the "garbled artifact" report

- **A busy or prompt-blocked agent at bind time permanently loses its one shot at the kill+resume repair for the REST of that bind's lifetime, not just until it goes idle.** `agent.ShouldKickRerender`'s own doc comment on `RerenderDeferBusy` requires the caller to "retry on the next opportunity (e.g., next agent-view entry, next resize)" — the main agent view satisfies this for free (`onTaskSelect`/`enterPendingAgentView` re-evaluates on every fresh entry), but a Hera pane has no analogous "re-entry" event once bound: `maybeKickPaneRerender`'s `kickedFor` marker was set the instant `kickRerender` was CALLED, not when the decision actually resolved — so a deferred (busy/blocked) outcome was silently treated as "handled," identically to a fired kick, and never retried. Reproduced from a REAL live session (`hera-garbled-2`, the coordinator of an active bugbash, PTY sidecar-recorded at 140×69): its screenshot showed a stale scrollback line and a duplicated tail fragment overlapping Claude Code's own fixed bottom status chrome, plus corrupted glyphs inside the context-usage meter — exactly the symptom BUG-068/BUG-074 already describe for scrollback committed at a width the current viewer never got to repair via kill+resume, left exposed to nothing but the plain-SIGWINCH-only `ForceResyncPTY` path for as long as the pane stayed bound.
- **Confirmed workaround (Ctrl+Z fullscreen-and-back) is the SAME diagnostic BUG-068's postmortem already used** — it forces a genuine dimension change (one of the 3 legitimate full-repaint triggers) via a code path (the main agent view's own entry-point kick evaluation) that isn't gated by Hera's one-shot marker, so it gets exactly the retry Hera's own path was withholding.
- **Fix: `RerenderKicker` grew an `onDeferred func()` parameter.** `App.maybeKickRerenderAtWidth` invokes it (from inside its `QueueUpdateDraw` dispatch, so it's safe to touch `HeraPage` state) on `RerenderDeferBusy`, `RerenderDeferPrompt`, and a failed `Stop()` — the same three branches that already call `invalidateAttachCache` for the App's OWN cols cache. `maybeKickPaneRerender`'s callback resets `kickedFor` to `""` and re-arms `pending` for a retry after `KickRetryInterval` (10s) — deliberately much longer than the initial per-bind `KickDebounce` (300ms), since a deferred retry can recur for the entire remainder of a long busy stretch and a 300ms cadence would re-issue the daemon RPCs (`IsIdle`/`InitialPTYSize`) and repeat the "rerender deferred" uxlog line every 300ms for that whole stretch. The callback is guarded on `kickedFor` still naming the SAME task that was deferred — a rebind (same task or a different one) already reset `kickedFor` itself and must win over a late-arriving stale callback.
- **A resolved outcome (fired or skipped — no drift) must NOT retry** — `onDeferred` is simply never invoked for those branches, so the existing one-shot-per-bind behavior is unchanged there; retrying would be harmless in practice (`App.isRedundantAttach`'s cols cache short-circuits before any RPC) but pointless.
- **The main agent view's own entry point (`maybeKickRerender`) passes `nil`** — it doesn't need this mechanism since it already gets a retry for free on every re-entry, and the two callers can legitimately differ (a task viewed once in fullscreen, then background-streamed for hours under a Hera pane that binds exactly once).
- Regression coverage: `internal/tui/hera/panes_test.go`'s `TestPanes_IsBoundToTask` (pure `IsBoundToTask` semantics — coordinator bound the whole time a worker is selected, unrelated/empty task rejected); `internal/tui/app_test.go`'s `TestApp_IsViewingTaskSession` (all four `isViewingTaskSession` branches, including "Hera-bound but a different tab is active"); `internal/tui/heraactions_test.go`'s `TestHandleSessionExitUI_RerenderRestartsWhenViewedViaHeraPane` (end-to-end through a real Hera tab selection + `handleSessionExitUI`, confirmed to fail with `status=in_review` against the old `modeAgent`-only gate before asserting the fixed behavior).

## BUG-078: A deferred (never-landed) BUG-077 retry leaves the width mismatch permanently invisible once the pane settles elsewhere (fix-committed-width-drift)

- **BUG-077 fixed the RETRY mechanism (a deferred kick gets another shot once the agent goes idle at the SAME width) but left a gap for when the agent DOESN'T go idle at that width before the pane moves on.** Live-reproduced on a real coordinator pane (`sketch-provenance-bug`): session started at `initialCols=80`; a Hera bind at `panel=142` deferred repeatedly for ~15 real minutes (busy, then blocked on a user prompt) and never resolved; the pane was then navigated away from. A LATER rebind at `panel=90` — close enough to `initialCols` (delta 10 < `RerenderMargin`=15) that the margin check alone reads "no drift," and coincidentally the EXACT width some unrelated earlier viewer (the main agent view, visiting the same task independently) had already cached via `App.isRedundantAttach` — logged "panel cols unchanged since last attach (90)" and skipped, forever. Nothing in the system ever compared against 142, the width the session's real PTY had actually been sitting at (and committing new content to) the whole time, because `bindPane`'s `ForceResyncPTY()` resizes the live PTY unconditionally, independent of whether the kick decision itself fires.
- **Fix: `App.committedCols` (map, taskID → uint16), a SECOND anchor alongside the immutable `initialCols`.** Recorded (`= panelCols`) whenever `ShouldKickRerender`'s decision crosses the margin at all — `RerenderDeferBusy`, `RerenderDeferPrompt`, or `RerenderKick` — never on `RerenderSkip`. Unlike `lastAttachCols` (deliberately invalidated on every deferred outcome so a same-width retry can re-evaluate — BUG-077's own mechanism), `committedCols` is NEVER cleared by a defer: it must survive an unbind/rebind and a switch between viewers to answer "what width did this session's content actually drift to," not "what did we just check." Cleared only when a kick actually fires (the resumed session's fresh `InitialPTYSize` supersedes it) and on task delete.
- **`ShouldKickRerender` gained a `committedCols int` parameter (0 = "nothing tracked yet") and fires if EITHER `initCols` OR `committedCols` diverges from `panelCols` past the margin — an OR, not a replace.** This is the load-bearing design choice: because `initCols` is immutable and checked independently, this can only WIDEN which binds trigger a kick, never suppress the pre-existing initCols-only retry-while-busy-at-the-same-width behavior from BUG-077. An earlier design that updated `committedCols` unconditionally on every call (including repeat retries at the same width) was rejected specifically because it broke that retry loop — comparing a just-recorded value against itself reads as "no drift" and stops `onDeferred` from ever firing again.
- **`App.isRedundantAttach`'s exact-match cache ALSO needed its own bypass** — even with the margin fix, an unrelated viewer's earlier visit at the exact candidate width (90 in the repro) short-circuits BEFORE the margin check ever runs. `isRedundantAttach` now falls through (returns false, i.e. "not redundant") on an exact `lastAttachCols` match when `committedCols` shows the same margin-exceeding drift — both gates had to move together; fixing only one left the other's cache still permanently suppressing the kick.
- Regression coverage: `internal/agent/rerender_test.go`'s `TestShouldKickRerender` committedCols cases (pure predicate: kick/defer via committedCols drift when initCols alone is sub-margin, and the `committedCols==0` sentinel is never treated as a real width); `internal/tui/app_test.go`'s `TestMaybeKickRerenderAtWidth_LaterNarrowRebindStillKicksAfterDeferredWideBind` (end-to-end: busy bind at 142 defers and never lands, an unrelated cache entry at 90 is seeded directly exactly as the live trace showed, then a later idle bind at 90 is asserted to still kick — reproduces the exact numbers from the live ux.log repro).
- **`Model.SubtreeCostUSD` (add-coordinator-cost-estimate) mirrors `Model.SubtreeAgentCount`'s `BridgeSubtree` walk but sums a DIFFERENT set of roles and needs a SEPARATE, out-of-`Model` data source for one piece.** Unlike agent count (worker-kind only, coordinator excluded at every level), cost sums EVERY role kind INCLUDING each orchestrator's own coordinator — but ONLY at the subtree's root (`BridgeSubtree` visits the root first, index 0): a nested orchestrator's coordinator-kind role is skipped there, since that same underlying agent is already counted via its bridging WORKER row one level up (the identical double-count hazard `SubtreeAgentCount` already solved, just with cost summed instead of a plain count). A nuked role never appears in `OrchView.Roles` (excluded by `BuildModel`'s own Tier-2 guard, same as every other rollup on this struct) yet its recorded spend must still count — deliberately solved via a SEPARATE `OrchView.NukedRolesCostUSD` field (from a new, dedicated `SumNukedHeraRolesCostByOrchestrator` DB query bypassing `ListHeraRoles`'s unconditional `nuked_at IS NULL` filter), added in per-orchestrator during the `BridgeSubtree` walk rather than folded into the `Roles` slice itself.
- **REST's `GET /api/hera` `subtree_cost_usd` and the Details pane's "Cost" field are BOTH non-recursive (this-orchestrator-only), UNLIKE the rail header's `Model.SubtreeCostUSD` — same root cause, two independent call sites.** `handleHera`'s own doc comment states it "mirrors `hera.BuildModel`'s read logic... so the API package stays free of TUI deps" — and `internal/tui/hera` is ONE Go package (Model/BuildModel share it with `rail.go`'s tview/tcell rendering), so importing ANY part of it into `internal/api` would pull the whole thing in, not just the pure logic; reproducing `BridgeSubtree`'s cross-orchestrator bridge-discovery independently in raw SQL was judged not worth the duplication risk for a field with no shipped consumer yet (web/macOS Hera cost rendering is a named, deferred follow-up — see design.md Decision 5). `internal/tui/hera/details.go`'s `deriveCoordMeta` has the SAME shape of limitation for an unrelated reason: it's a pure `*OrchView` projection (`DetailsView.SetOrch(o *OrchView, ...)`) with no access to the whole `Model`, so its new `coordMeta.Cost` field sums only the passed-in orchestrator's own `RoleView.CostUSDAccrued` values, never recursing into a bridged child. Local-mode TUI rail rendering is unaffected either way — `Model.SubtreeCostUSD` (previous bullet) computes the full recursive figure directly against the database with no REST round-trip; only remote-mode/REST consumers and the Details-pane summary see the narrower, per-orchestrator figure.

### fix-hera-reclaim-status: BUG 1 (silent/misleading compute progress) + BUG 2 (no mouse scroll)

- **BUG 1 root cause was TWO stacked issues, not one.** (a) `runCleanupCompute` called `mergesafety.ClassifyBatch` — the all-at-once form — and cached every verdict to `task_meta` only AFTER the whole batch returned, so `GET .../cleanup-candidates` (what the popup polls every 700ms) showed every eligible task as uncached until the ENTIRE multi-repo classification pass finished. (b) the popup's own framing bucketed any uncached task (`Reason: "not yet classified"`) under the SAME "NOT-SAFE (N)" header a genuinely-confirmed-unsafe verdict uses — so on a large backlog, opening the popup immediately claimed N confirmed-unsafe verdicts when zero classification had actually happened yet, and that lie persisted for as long as the compute pass took.
- **Fix for (a): `mergesafety.ClassifyBatch` gained an incremental sibling, `ClassifyBatchFunc(ctx, candidates, onResult)`.** `ClassifyBatch` is now a thin wrapper collecting `onResult`'s callbacks into the same map it always returned — its behavior and tests are unchanged. `onResult` fires in two waves: every Tier-A-resolved (or repo-unresolvable) candidate immediately, in input order, BEFORE any Tier B network call is even issued; then each Tier B repo group's members fire together the moment THAT repo's one aliased GraphQL call returns (Tier B can't be split any finer than one call per repo). `runCleanupCompute` now calls `SetMetaBatch` from inside this callback, so the cache — and therefore the popup's next poll — reflects real progress after every repo group lands, not just at the very end.
- **Known, discovered-but-NOT-fixed-here latency characteristic: `gitutil.runAliasedRepoQuery` has a hardcoded 10s context timeout per call, and `ClassifyBatch(Func)`'s repo groups run SEQUENTIALLY, not concurrently.** A backlog spanning N distinct repos where most branches have long since had their local worktree/branch cleaned up (Tier A misses, falling through to Tier B for nearly everything) can legitimately block for up to `10s × N` with the incremental-caching fix above only helping BETWEEN repo groups, not within a single repo's one huge aliased query. This matches Aaron's live repro almost exactly: he canceled at 9.4s with zero `[cleanup]` log lines, just shy of the first repo group's own 10s timeout even firing. Making repo groups run concurrently (or chunking one huge repo group's alias count) would shrink this further but was judged out of scope for this fix — the ask was observability, not raw latency — and is a good candidate for a future, explicitly-scoped change if a real multi-repo backlog is still slow after this fix.
- **Fix for (b): `mergeSafetyCandidate` gained a `Pending bool` field (zero value false, so every classify-before-open caller — single-role nuke, cascade, clear-archive — is unaffected without touching a single call site) and the popup's `SetCandidates` now buckets into THREE sections — PENDING, then NOT-SAFE, then SAFE — instead of two.** The wire contract (`cleanupCandidateJSON` in both `internal/api/cleanup_candidates.go` and its `internal/tui/mergesafety.go` mirror) gained a matching `pending` JSON field, set true only when `GET /api/maintenance/cleanup-candidates` finds no cached verdict at all for a task. The scanning footer also now shows real `"N of M classified"` progress (`len(candidates) - pendingCount`) once the first candidate batch has landed, distinct from the pre-first-tick "Scanning for stuck tasks…" body message (which still shows before any candidates are known at all).
- **BUG 2 root cause was ALSO two stacked issues.** (a) `MergeSafetyPopup` had NO `MouseHandler` at all (unlike `Rail`/`SettingsView`, which both implement wheel scroll) — added one, mirroring `SettingsView.HandleMouse`'s DIRECT (non-inverted) scroll-to-pan mapping, not `Rail.MouseHandler`'s inverted cursor-drag convention — this widget pans a content viewport, it has no cursor to drag. (b) `drawRows`' own scroll clamp used `len(m.rows)-1` (the last ROW INDEX) as its max offset, not `len(m.rows)-h` (the largest offset that still leaves a FULL screenful showing) — scrolling to the bottom of a list taller than the visible body left only the single last row rendered, with the rest of the body blank, and reversing direction needed several "dead" presses (up to `h-1`) before the view visibly moved again, since the field could be sitting up to `h-1` past the point drawRows actually needs.
- **Fix for (b) mirrors `SettingsView`'s own pane/log-scroll clamps (`settings.go`): `drawRows` now clamps `m.scrollOff` itself (not just a local copy) to `max(len(m.rows)-h, 0)`, mutating the field in place.** Because `Draw` runs after every keystroke in the real event loop, this self-heal means there is no dead zone in practice — by the time the NEXT key/wheel event is handled, the field already holds the corrected value. `InputHandler`'s own KeyDown/PgDn bound (`len(m.rows)-1`) was deliberately left AS-IS (it has no access to the current viewport height without duplicating `Draw`'s modalH/bodyH geometry math) — it's a harmless generous upper bound now that `drawRows` is the sole source of render truth.

### 5a-cleanup-tree-view: cleanup popup grouped by originating Hera coordinator

- **`db.StuckTaskCandidates`'s per-task orchestrator resolution reaches through ENDED/ARCHIVED/NUKED `hera_bindings`/`hera_roles`/`hera_orchestrators` rows on purpose — it does NOT filter on `archived_at`/`nuked_at` at all.** Hera never hard-deletes those rows (see `NukeHeraRole`/`NukeHeraOrchestrator` — `nuked_at` stamped, row retained), so a candidate whose role and orchestrator were both later nuked still resolves and displays the orchestrator's name; only the live-binding predicate that makes a task a stuck-task CANDIDATE in the first place (`NOT EXISTS ... ended_at IS NULL`) is unaffected by this change. Don't "fix" the correlated subquery by adding an archived/nuked filter — that would silently blank out the exact context this feature exists to surface.
- **"Most recent" is `hera_bindings.started_at DESC LIMIT 1`, joined via `hera_roles.orchestrator_id` (the role's own NOT NULL FK), not `hera_bindings.orchestrator_id` (a denormalized, nullable copy).** Both are populated identically at insert time in practice (`insertHeraBinding`), but the role-side column is the one the schema actually guarantees NOT NULL — prefer it if this query is ever touched again.
- **A new non-partial index, `idx_hera_bindings_task_started ON hera_bindings(argus_task_id, started_at)`, backs this query** — deliberately NOT partial (unlike the three existing `idx_hera_bindings_live_*` indexes, all `WHERE ended_at IS NULL`), since this query's whole point is reaching ended bindings too.
- **`scanTask` is now a zero-arg wrapper around `scanTaskExtra(row, extra ...any)`** — the variadic lets `StuckTaskCandidates` scan one extra trailing correlated-subquery column (the orchestrator name, as `sql.NullString`) in the SAME `Scan` call as the standard task columns, without duplicating `scanTask`'s field-by-field unpacking for one extra field.
- **The popup's tree grouping is a sub-structure WITHIN each existing PENDING/NOT-SAFE/SAFE section, never a replacement for it** — `appendSectionRows` renders every ungrouped candidate (`Coordinator == ""`) flat first, then one group header per distinct coordinator (first-appearance order within that section), each followed by ALL of that coordinator's candidates in the section (even if they weren't contiguous in the input — a tree groups every child under its one header, not one header per contiguous run). An ungrouped-only candidate set (every existing pre-5a-cleanup-tree-view test fixture) produces byte-identical rows to before — no group header is ever fabricated for an empty `Coordinator`.
- **The single-role nuke popup's sole candidate has no `Coordinator` set and so always renders flat** — grouping only visibly matters for the global Cleanup action's cross-project backlog; the widget itself makes no distinction between the two call sites beyond the data it's given.

### add-hera-accept-lifecycle: `a` HIDE now also stops the session, hide direction only

- **`Ops.ArchiveToggle`'s signature changed from `error` to `(archived bool, err error)`** – `archived` is true only when THIS call moved the row from active to archived (the HIDE direction), false on the un-hide direction or on any error. `heraHide` reads this instead of re-deriving the direction with a second `HeraRole`/`HeraOrchestrator` read, so the two can never disagree about which branch just ran. Every pre-existing call site (tests, `heraactions.go`) needed updating for the new two-value return – a mechanical but easy-to-miss `go vet ./...` catch across the tree.
- **The session-stop only fires on `archived == true`, gated additionally on `r.TaskID != "" && a.runner.HasSession(r.TaskID)`** – hiding a role with no live session is a clean no-op on the stop path (nothing to stop), and un-hiding NEVER stops a session even if one happens to be live at that moment. The stop itself is backgrounded via the existing `heraGoSafe` helper, mirroring `heraReclaimAndArchiveTask`'s own session-stop pattern (same BUG-062 UI-freeze rationale) – it does not touch the worktree or branch, and does not touch the argus task's `archived`/status columns at all (HIDE stays rail-only, unchanged from before this change).
- **Freeing the session's memory on hide is a nice-to-have follow-through of the operator's own choice, not a requirement of Hera task completion.** This is deliberately a SEPARATE concern from `hera_accept`/the gater's auto-accept (both of which flip a task to `complete` and NEVER stop any session) – completion and detachment stay orthogonal per Aaron's explicit framing, so don't conflate "the coordinator accepted this work" with "the operator is done looking at this row."

### add-mac-hera-rail-toggle: `internal/hera/model` extraction (daemon D1/D2)

- **`RoleView`/`OrchView`/`Model`/`Selection`/`HeraReader`/`BuildModel` and the bridging helpers moved verbatim from `internal/tui/hera/model.go`+`reader.go` into a new tview-free package `internal/hera/model`**, so `internal/api`'s REST handler can call the SAME `BuildModel` the TUI rail calls instead of reimplementing nesting/needs-input logic – finishing the "named follow-up" `openspec/specs/rest-api/spec.md` had documented since the endpoint's original scope-cut. Confirmed zero tview/tcell imports in the new package (only `errors, fmt, sort, strconv, time, internal/db, internal/model, internal/uxlog`).
- **`internal/tui`'s App-level files (`heraactions.go`, `hera_tiering.go`, `commandpalette_actions.go`, `mergesafety.go`, `app.go`, and their tests) hold HUNDREDS of external `hera.Model`/`hera.RoleView`/`hera.OrchView`/`hera.Selection`/`hera.HeraReader` references** that were NOT anticipated by "confirm no other package outside `internal/tui/hera` needs updating" – they compile unchanged only because `internal/tui/hera/model_types.go` re-exports the five moved types as Go type ALIASES (`type Model = heramodel.Model`, etc.), not new types. Removing or changing these aliases silently breaks the whole `internal/tui` package's Hera action layer.
- **A package-level `func (m Model) SubtreeArchivedWorkers(...)` method defined OUTSIDE `model.go` (in `eol.go`) could not survive the move** – Go forbids defining new methods on a type from another package even via a type alias (aliases don't create a new named type). Converted to a plain function `SubtreeArchivedWorkers(m heramodel.Model, orchID int64) []heramodel.RoleView`; its one external caller (`internal/tui/heraactions.go`'s `heraDoClearArchive`) needed updating from `model.SubtreeArchivedWorkers(id)` to `hera.SubtreeArchivedWorkers(model, id)`. Grep every remaining hera-package file for `func (m Model)`/`func (m *OrchView)`/etc. method definitions before any future move out of this package – there is no compiler hint before you actually try to build.
- **`internal/tui/hera/model_test.go` is not a pure white-box test file for `model.go` – it's shared test INFRASTRUCTURE for the whole package's test suite** (`memDB`/`seedOrch`/`seedBoundRole`/`orchView`/`wk`/`coordOf`/`roleByName`/`coordSubtreeNI`/`errReader` are called from ~20 other `_test.go` files: `rail_test.go`, `plan_test.go`, `keyset_test.go`, etc.). Moving the whole file to `internal/hera/model` would have broken all of them; the fix was splitting it – the model-internals-only tests (`TestBuildModel_*`, `TestRollupNeedsInput_*`, etc.) moved to `internal/hera/model/model_test.go`, while the builder helpers were DUPLICATED (not shared) into a slimmed `internal/tui/hera/model_test.go` alongside the two tests that need hera-package-only code (`statusIcon`, `deriveCoordMeta`) and can't move.
- **Go test coverage is per-instrumented-package, not per-call** – after the extraction, ~16 `internal/hera/model` functions (`RoleByID`, `CanonicalParents`, `BridgeParentOf`, `FormatCostUSD`, `AnnotateRoles`, etc.) dropped to 0% in `internal/hera/model`'s own coverage report even though `internal/tui/hera`'s test suite genuinely exercises them through the type aliases – `go test ./...` without `-coverpkg` never attributes a caller package's test run to a callee package's coverage. Fixed by adding direct unit tests for these functions IN `internal/hera/model/model_test.go`; don't assume "well-tested elsewhere" protects a newly-split-out package's own coverage number.
- **New cross-package method, not a moved one: `Model.BridgeParentOf(childOrchID) (parentOrchID, parentRoleID int64, ok bool)`** wraps `CanonicalParents` (which only carries a parent ORCHESTRATOR id, no role) with the specific bridging ROLE id a REST consumer needs – the parent's own coordinator role for a coordinator-spawned sub-team, or the parent's `BridgingRoleFor` worker role for a worker-bridge nesting. `GET /api/hera`'s `bridge_parent_orch_id`/`bridge_parent_role_id` fields are the only caller so far.
- **`handleHera` cannot source `BuildModel`'s `needsInput`/`sessionIdle`/`sessionRunning`/`sustainedActive` maps from the TUI's own in-memory per-session state – no TUI runs inside the daemon process.** The first three come from `s.sessionStateMaps()`, the SAME daemon-authoritative helper already backing `GET /api/tasks` and the SSE `session.needs_input` events (ultimately `internal/agent.Runner.RunningAndIdle()`/`NeedsInputIDs()`) – NOT a REST-local reimplementation of idle detection. `sustainedActive` gets a hard-coded `nil`: it has no daemon-authoritative equivalent, being a TUI-only `agent.ResumeActivityTick` debounce that only affects the rail's cosmetic dimming (see the narrow-needs-input-sustained-active entry above), never role correctness. Consequence: `GET /api/hera` and the native TUI rail can legitimately show a different `needs_input`/dimming state for the SAME role for a tick or two – both are real, independently-sourced signals, not a bug to "fix" by unifying them.

### add-hera-closeout-banner: two-Enter toggle for a closed-out worker's dead pane

- **Both the "first" and "second" Enter against a closed-out row reach the IDENTICAL `App.heraReattach(sel)` call — there is no separate call site or parameter that distinguishes press #1 from press #2.** The rail's `Enter` (`HeraPage.handleRailMutation`) fires it and then unconditionally advances focus into the agent pane; a SECOND `Enter`, now captured by `TerminalPane.InputHandler()` (session still dead), fires the pane's own no-arg `OnReattach` → `HeraPage.reattachPane` → the SAME `p.OnReattach(sel)` → `heraReattach` again. Whatever distinguishes "arm the banner" from "dismiss it" has to be state `heraReattach` can read AND mutate on every call — there's no third input to key it on.
- **The toggle state (`TerminalPane.closedOutBannerShown`) deliberately lives on the PANE, not on `App` or `HeraPage`.** `ResetVT()` already runs on EVERY hera pane rebind (`panes.go`'s `bindPane`, both the unbind branch and the rebind-to-a-different-task branch) — piggybacking a bare `bool` on that existing lifecycle gets "resets per visit" for free, with no new reset call site to keep in sync. `App.heraReattachClosedOut` reaches it via the already-exported `HeraPage.AgentPane()` — no taskID-matching accessor needed, because `heraReattach`'s close-out branch only ever runs when `sel.IsWorkerOrFreelance()` is true, and `applySelection` only ever binds the agent pane (never the coordinator pane) for such a selection.
- **Dismissing the banner adds NO new rendering path.** `TerminalPane.Draw()` already renders replay content for ANY dead session with `HasContent()` — no `Enter`/`OnReattach` involvement at all (see M6b's ring-buffer/replay bullets above). The banner only needs to REPLACE that (and the placeholder) while armed, gated on `!alive` right after `Draw()` computes it, ahead of both the `sess == nil && !tp.HasContent()` placeholder branch and the replay/live branch further down. Dismissing just clears the flag and lets those pre-existing branches decide what shows.
- **A closed-out task with NO recorded session log falls through, once dismissed, to the ordinary "Session not running - press Enter to start" placeholder** — technically correct (nothing ever starts) but written for the general dead-session case, not this specific one. Accepted trade-off, not a bug: a THIRD piece of banner state for this one rare case wasn't judged worth it.
- **There is no separate third state — further Enters just keep toggling the banner on and off (a third press re-arms it, a fourth dismisses it again, …).** The task's own framing named exactly two presses; a plain `bool` toggle satisfies both with the smallest possible state and matches every other simple per-binding flag on `TerminalPane` (`pending`, `forceResync`). If a future report frames a third-press re-arm as a bug, it isn't — it's intentional (see `openspec/changes/archive/*-add-hera-closeout-banner/design.md` Decision 4 once archived).
