# Native Hera View (`internal/tui/hera`)

M6a scaffolds the native Hera view: a `HeraPage` (rail | coordinator pane | agent pane) replacing the old DAG tab. Only the LEFT rail is live and READ-ONLY; the two right panes are placeholders (6b adds PTY feeds; 6c adds mutations). M6b makes the two right panes REAL terminal feeds and wires rail selection to them.

## M6b — pane feeds from the in-process runner

- **Panes are fed from the in-process runner's ring buffer, NOT SSE — Hera's `proxy/` fan-out has no Argus equivalent and is not ported.** The coord/agent panes are `terminal.TerminalPane`s (the same widget the main agent view uses). A `SessionResolver func(taskID) agentview.TerminalAdapter` seam (App wires it to `runner.Get`) hands the pane a live session; the TerminalPane POLLS that session's ring via `RecentOutput*` on every Draw (it does NOT `AddWriter`). The daemon-owned PTY ring is the single source — there is no SSE/HTTP hop and no `ArgusStateCache` polling. Remote mode (`nil` reader) never sets a resolver and never feeds the panes.
- **The coord-vs-agent session-selection rule (LOCKED — documented in `panes.go`):** the AGENT (right) region is mode-switched by whether the selection is a coordinator: a **coordinator** selection renders the read-only `DetailsView` worker roster + plan graph (no terminal, agent pane unbound) and feeds the HERA (middle) pane from *that orchestrator's coordinator* task; a **plain worker/freelance/leaf** selection feeds the AGENT terminal from the role's bound task and the HERA pane from the *selected orchestrator's coordinator* (`Selection.CoordTaskID()`). `applySelection` computes the Details target via `detailsOrch()`, NOT bare `Selection.IsCoordinator()` — see the BUG-004 bullet for why a worker-bridge sub-coordinator also counts as a coordinator here.
- **A worker-bridge sub-coordinator selection is a COORDINATOR selection for pane routing (BUG-004).** A sub-coord nests as a worker ROW (`Role.Kind==worker`) that bridges a child orchestrator, so `Selection.IsCoordinator()` is false — keying `detailsMode` on it dumped the sub-coord into the AGENT terminal and made its Details view unreachable. Fix: `detailsOrch()` returns the bridged CHILD orchestrator when `Selection.BridgeChildOrchID != 0` (the marker `Rail.Selection` sets from the row's `collOrchID`), so `detailsMode` is `detailsOrch() != nil`. Details/plan (`rebuildPlan(root)`, `SetOrch`) render the CHILD's roster + plan DAG and the HERA pane feeds from the child's coordinator (== the sub-coord's own session) — symmetric with a top-level coordinator. A coordinator-spawned sub-coord that already renders as its own header is unaffected (it selects as a header → `IsCoordinator()` true). CRITICAL: only the pane/details/plan ROUTING follows the child; `p.sel` (the `SelectionContext` mutation context) stays on the PARENT worker role, so Ctrl+D and other mutations still act on the worker, never the child orchestrator (the conservative multi-binding safety the rail nesting documents).
- **Multi-binding is disambiguated by the role's orchestrator, NEVER the bare task ID.** `Rail.Selection()` resolves the containing `OrchView` from the selected `RoleView.OrchID` (`Model.OrchByID`), so a task that is worker in A and coordinator in B yields two different `Selection`s: selecting the A-role feeds the AGENT pane from the shared task + the HERA pane from A's coordinator; selecting the B-role feeds the HERA pane from the shared task (B's coordinator = itself) + renders B's roster. `Selection` is the single value threaded to the 6c mutation extension point (`HeraPage.SelectionContext()`).
- **PTY size alignment (CLAUDE.md rule 5): a hera pane and the main agent pane compute the SAME size for the same rect — they are the same `TerminalPane` widget.** When binding a session, `bindPane` calls `ForceResyncPTY()` so a session previously sized for the full-width main agent view gets resized DOWN to the narrower hera pane on the next Draw (without it, the seeded `ptyCols` matches `wantCols` and no resize fires, leaving the agent painting at the stale width). `SyncPanes()` (App tick GOROUTINE + spinner loop, never a QueueUpdateDraw callback) issues the Resize RPC off the main thread. It is safe to call off-tab: a pane that wasn't drawn this frame has zero `pendingResize`, so an off-tab `SyncPanes` can't fight the main agent view's resize of the same task. Never reach for `Sync()` to fix a size mismatch — fix the alignment.
- **Main-thread-safe pane reads only.** Pane operations on the tview thread use the lock-free/local SessionHandle methods (`Alive`, `RecentOutput*`, `WriteInput`, `Session()`) — never the RPC-blocking `PID/IsIdle/PTYSize/InitialPTYSize`. The blocking `SyncPTYSize`→`Resize` RPC runs only from the tick goroutine via `SyncPanes`. `SetSession`/`SetTaskID`/`applySelection`/`reconcileSessions` are main-goroutine-only (SetSession resets emulator state).
- **`reconcileSessions` (App tick, main thread) does the nil→live late bind AND the dead→live re-resolve (BUG-013).** A pane bound to a task with no live session yet (coordinator/worker still starting) gets its session attached on a later tick. `doRefresh` re-runs `applySelection` after `SetModel` because the rebuild replaces the model's backing arrays, invalidating the prior `Selection` pointers (task IDs usually match, so `bindPane` no-ops and emulators survive).
- **A present-but-DEAD pane session MUST be re-resolved, not just a changed taskID (BUG-013).** When the daemon tears a pane's stream down (StreamLost relay / daemon bounce) while the agent PTY is still alive, `RemoteSession.Alive()` flips false but the agent lives. The pane held the dead handle forever: `reconcileOne` used to bail on ANY present session and `bindPane` no-ops on the unchanged taskID, so `forwardKey` dropped every keystroke (silently) until a full TUI restart re-dialed the stream. Fix: `reconcileOne` treats `!Alive()` like nil and re-resolves — the daemon client re-dials a fresh stream on a cache-miss `Get` when the daemon reports the process alive. Replace ONLY with a live, DISTINCT handle; leave the pane alone when the resolver yields nil (process gone → replay) or the same not-yet-evicted handle (retry next tick), or you reset the emulator every tick. `forwardKey` now logs the drop (`[hera-view]`) and re-resolves before dropping. Orthogonal to the `Enter`-reattach path, which leaves a LIVE coordinator navigate-only and restarts a truly dead PROCESS — BUG-013 is a live process with a stale handle.
- **PR indicator reads the daemon-populated `"pr"` namespace (keys `state`/`url`), like the task list — best-effort, never fetched.** The plan said `meta:iris.pr_url`, but Argus's canonical cached PR state is `task_meta` namespace `"pr"`; `DetailsView` shows a `PR` mark for a roster task whose `pr` meta has a non-empty `url`. `doRefresh` reads it once via `ListMetaByNamespace("pr")`.
- **`TerminalPane.SetBorderTitle` is the only change to the shared agent surface.** It defaults to `" Agent "`; the hera coordinator pane sets `" Coordinator "` so the same widget reads correctly in both surfaces. The DAG render mode of the Details pane is deferred to M7; mutations to M6c.

- **The second tab is `TabHera` (enum slot `widget.TabHera == 1`), so the `2` hotkey is stable.** `switchTab`'s second arm always routes to the `"hera"` page via `switchToHeraTab2` — the native Hera view is the only second-tab option now (the legacy `"dag"` page was deleted along with `depends_on`). `cfg.Hera.Enabled` no longer toggles the view; it only gates daemon-side MCP native-vs-plugin tool registration on the next daemon start.
- **Multi-binding fan-out is structural, not special-cased.** One argus task bound under two orchestrators is reached through two DISTINCT `hera_roles` rows (one per orchestrator). `BuildModel` walks orchestrators → their roles → each role's live binding, so the task surfaces once under EACH orchestrator with zero fan-out logic. The smoke test `TestSmoke_HeraRailMultiBindingUnderTwoOrchestrators` and unit `TestBuildModel_MultiBindingFanOut` pin this — do NOT "optimize" the model into a per-task dedupe, which would collapse the two appearances the locked Q2/Q3 design requires.
- **Freelance-kind roles are HOISTED into a top-level Freelance section, not nested under their orchestrator.** `BuildModel` skips active freelance-kind roles when filling an orchestrator's `Roles` and appends them to `Model.Freelance` instead. This is a 6a read-only interpretation of the "freelance" section (Hera derived it from unmanaged live argus tasks; that data source is out of scope for the read-only hera store). 6b can revisit if real unmanaged-task freelance is wanted.
- **`ready_to_close` (M4) is read from the task-addressed `task_meta` "hera" namespace, NOT the hera tables.** `BuildModel` does one `ListMetaByNamespace("hera")` batch read and flags `RoleView.ReadyToClose` when the role's bound task has `ready_to_close=true`. The rail renders it with the distinct `theme.IconReview` mark, which WINS over the role's idle/working/blocked/done status icon but LOSES to needs-input `(?)` (BUG-A: an actively-blocked worker is not ready to close). A meta read error is non-fatal (the flag just doesn't render).
- **The rail rebuild runs on the tview thread; that's fine because hera-store reads are mutex-guarded and fast — the "never on the UI thread" rule is about GIT, not DB reads.** `Refresher` (the Argus-native analog of Hera's `RailRefresher`) is goroutine-/timer-free: `Schedule()` is driven by the app tick + tab entry and coalesces bursts into one rebuild per debounce window via an injected clock (`SetNow`), so it's deterministic to test. `refreshHera` is `heraPage.Refresh()` on tab entry (forces a flush) and `ScheduleRefresh()` on the tick while `ActiveTab()==TabHera`.
- **`HeraPage.Machine()`, not `Focus()`.** A method named `Focus()` collides with `tview.Primitive.Focus(func(tview.Primitive))` and silently breaks the Primitive interface (the page stops being a valid tview widget). The focus-machine accessor is `Machine()`. The `FocusMachine` is wired for 6b (Advance/Retreat/present-pane rebalance); 6a keeps focus on the rail and only reads `State()` to pick the border-highlight palette.
- **The rail navigates with `j`/`k`/Up/Down and folds with Space — never arrows-for-parent-nav like Hera's upstream rail did.** Historically the rail was BARRED from binding Left/Right because the global handler ate them for tab switching; that arrow-key tab-cycling has since been removed (tab nav is `1`/`2`/`3` only), so Left/Right now fall through to the page: a terminal-focused pane (coord/worker-agent) forwards them to the PTY, a coordinator's details region routes them to the embedded plan widget's cursor (slot/member nav, M7), while the rail leaves them unused (free for future horizontal navigation).
- **`Ctrl+Alt+Left/Right` walk the focus ladder (Retreat/Advance), mirroring `Tab`/`Backtab`.** Handled in `HeraPage.InputHandler`'s top-level key switch BEFORE the per-region forward, so they reach `FocusMachine.Retreat`/`Advance` rather than being forwarded to a focused terminal pane's PTY (a plain Left/Right still forwards). The modifier check is `Modifiers()&(ModCtrl|ModAlt) != 0` — **either** modifier, not strictly both — matching the main agent view's Ctrl+Alt+arrow pane switch (`app.go`); terminals are inconsistent about which of Ctrl/Alt they report for this chord, so the loose check is the proven pattern. This binding lives in the page handler (not `handleGlobalKey`) precisely because plain Left/Right intentionally fall through the global handler to the focused view.
- **Enter on a worker row focuses FocusAgent (right pane); Enter on a coordinator/header focuses FocusCoord (middle pane).** The Enter handler in `handleRailMutation` routes based on `p.detailsMode` (already computed by `applySelection` on cursor move): when `detailsMode` is false (plain worker selection, right region = agent terminal) it calls `SetRegion(FocusAgent)` directly; when `detailsMode` is true (coordinator or worker-bridge sub-coordinator, right region = Details summary) it calls `Advance()` → FocusCoord. Do NOT use `sel.IsCoordinator()` alone here — a worker-bridge sub-coordinator has `IsCoordinator()==false` but `detailsMode==true`, and the right pane is the Details view, not a terminal.
- **No `screen.Sync()`; cover the full bounding rect.** Every region (`Rail.Draw`, `DetailsView.Draw`, `drawRemoteBanner`, and the two `TerminalPane`s) paints through `widget.DrawBorderedPanel` (which blanks its interior) so stale cells can't survive — per the CLAUDE.md UX-rendering rules. The panes' `OnBranchChange` is wired to `a.forceRedraw` (log-only, never Sync); `OnNeedRedraw` bounces a `QueueUpdateDraw`. `TestPanes_NoSyncOnDraw` pins that drawing the full view (live panes + details) calls `Sync` zero times.

## M6c — keyset + thin in-process mutations

- **Mutations are a THIN layer over M1/M4 — single source of truth, no re-implementation.** `internal/tui/hera/ops.go` (`Ops` + the narrow `MutateStore` interface) is a set of small adapters over EXISTING `*db.DB` M1 methods (Archive/Unarchive/Pin/Unpin/Rename/Delete for orchestrators+roles, `UpsertHeraRoleStatus`, `RollHeraWorkerToReview`); it adds targeting + toggle-direction reads + the status ladder + uxlog, nothing more. Worker spawn does NOT live in `Ops` — it reuses the shared `agent.SpawnHeraWorker` primitive (extracted from `daemon.heraSpawnWorker`; the daemon MCP arm is now a thin adapter to it). If you find yourself re-deriving transactional spawn or cascade-delete, STOP and call the shared primitive.
- **The rail keyset routes through `HeraPage` callback fields, mirroring the DAG widget's `OnEnter`/`OnLink` pattern — NOT through a mutator injected into the rail.** `HeraPage` exposes `OnSpawnWorker`/`OnRename`/`OnArchiveToggle`/`OnPinToggle`/`OnStatusAdvance`/`OnStatusRevert`/`OnDelete`/`OnReattach func(Selection)`. `HeraPage.handleRailMutation` (rail-focus only) maps keys → callbacks passing `rail.Selection()`, then falls through to rail nav. The App wires the callbacks to handlers (`heraactions.go`) that own the modal/confirm/refresh orchestration. nil-safe: an unwired callback (remote mode) makes the key inert; `fire()` consumes a key when its callback is wired even on an empty selection so the keystroke never leaks to nav.
- **Every op acts on the SELECTED `(role, orchestrator)` from `Selection`, never the bare task ID — multi-binding isolation.** Deleting role R in orchestrator A removes only R's row (its binding cascades via `DeleteHeraRole`'s FK); the SAME task's role in orchestrator B is a distinct row and survives. `Ops` re-reads the row (`HeraRole`/`HeraOrchestrator`) to decide archive/pin TOGGLE DIRECTION from current state (not the possibly-stale model flag).
- **Delete (Ctrl+D) = ARCHIVE every DB row + reclaim ONLY the worktree/branch/session — ZERO hard deletes (BUG-017, Aaron's explicit rule "the database doesn't get any deletes").** Delete NEVER calls `db.Delete` / `DeleteHeraRole` / `DeleteHeraOrchestrator` / message deletes. It ARCHIVES: role rows via `RetireRole(r, false)` (ends the live binding `user_deleted` + `ArchiveHeraRole` — the same archive-not-delete primitive the `R` key uses), the orchestrator via `Ops.ArchiveOrchestrator` (`ArchiveHeraOrchestrator`, NOT delete), and the argus task via `db.SetArchived` (NOT `db.Delete`) — done by `heraReclaimAndArchiveTask`, which also stops the session and removes the worktree + LOCAL and REMOTE branch (`agent.RemoveWorktreeAndBranch`). The role's INBOX is archived implicitly: because the role is archived (not deleted), its `hera_messages` rows are simply retained attached to an archived role — there is NO message-archive primitive and NONE was added (Option A; `hera_messages` has no `archived_at`). NET: only the worktree dir + git branch are reclaimed; everything else lives in the Archive section. Difference from the `a` key: `a` archives but KEEPS the worktree/session; Ctrl+D archives AND reclaims them. ROLE delete: reclaim+archive the task only when sole-bound (`heraTaskSolelyBoundTo` → `ListHeraLiveBindingsByTask` len==1); a MULTI-bound task is PRESERVED (left fully alone — not archived, worktree kept). COORDINATOR / orchestrator HEADER delete runs the same cascade over the whole subtree (see the cascade bullet below). (One non-hera-row delete remains, accepted + out of scope: `db.SetArchived` on a TASK drops that task's queued LEGACY `task_messages` — a different table from `hera_messages` — established retire/archive behavior; the "no deletes" rule is scoped to hera role/orch/inbox rows.)
- **`s`/`S` step the HERA ROLE STATUS (idle→working→blocked→done ladder), NOT the argus workflow status.** The rail renders role status, so the rail key steps role status — a pure `UpsertHeraRoleStatus` call. The argus task status (pending→…→complete) stays owned by the session lifecycle + the M4 finish policy. Reaching `done` on a WORKER-kind role also calls `RollHeraWorkerToReview` (mirrors the `hera_status("done")` MCP arm, BUG-050) — soft-fail so the status update always lands.
- **Stepping a WORKER OUT of `done` MUST clear `ready_to_close`, else the step is invisible — BUG-024.** `ready_to_close` (stamped by the done-roll) WINS the `statusIcon` precedence over the hera role status, so a `done`/ready_to_close worker renders the review `✓`. Reverting it (`S`) without clearing the mark updates the DB status but the glyph stays pinned to `✓` — the operator's "step out of review" silently does nothing. `Ops.StepStatus` calls `db.ClearHeraReadyToClose(taskID)` (inverse of the roll's stamp; sets `meta:hera.ready_to_close=false`) whenever a worker steps to a NON-`done` status, soft-fail so the status write always lands. It is meta-ONLY — the task's argus workflow status (in_review) is owned by the session lifecycle and is NEVER touched by a status step. (The "(?)" the bug report cited is the legitimate `theme.IconNeedsInput` blocked glyph, not the numeric `(N)` count badge, which is always `fmt.Sprintf(" (%d)")`; cursor stays anchored because `restoreCursor` re-pins by stable `RoleID`.)
- **`s`/`S` target `Selection.StatusRole()`, NOT `Selection.Role` — a coordinator's `✓` cycles from the HEADER (BUG-014).** The coordinator is folded into the orchestrator header (no child row), so a header selection has `Role == nil`. `StatusRole()` falls back to `Orch.CoordRole()`, so `S` moves a coordinator `done → blocked` (rail `✓` clears) and `s` advances it back. BOTH `Ops.StepStatus` and `App.heraStatusStep` must use `StatusRole()` (the actions-layer guard is `StatusRole() == nil`, not `Role == nil`) or the keystroke leaks to nav / no-ops. The `RollHeraWorkerToReview` roll stays GUARDED on `Kind == worker`, so stepping a coordinator to `done` never rolls a task. A header over a coordinator-less orchestrator resolves to nil → silent no-op (`errNoTarget`).
- **The Details `coordinator:` line is task-aware (BUG-015) — role status AND terminal task state, but they are SEPARATE labels.** `coordStatusLabel` = `coordRoleStatusLabel` (the hera role status, preserving the BUG-003 stale-`working`→`live`/`stopped` honesty) + `coordTaskStatusLabel` (ONLY terminal argus states: in_review / complete / failed). It renders `"<role> · task <state>"` (e.g. `live · task complete`); ongoing (in_progress/pending) or unbound tasks add NO suffix, so it stays ONE row (ContentHeight unaffected). `failed` is derived from the bound task's opaque `TaskResult` `{"failed":true}` and WINS over the workflow status — re-stated locally as `coordTaskFailed` rather than imported from `dagview.parseFailed` (unexported there); a malformed/empty blob is tolerated as not-failed. Don't fold the task state INTO `coordRoleStatusLabel` — the role ladder and the workflow status are independent axes.
- **`n` (new orchestrator), `J` (adopt/reparent), `C` (complete-archived), `Ctrl+R` (hera-prune) are intentionally OMITTED in M6c.** (`Ctrl+Z` was omitted in M6c too but is now BOUND to fullscreen — see the "Ctrl+Z fullscreen + suspended-pane revive" section below — to restore plugin parity and close the suspend footgun.) New-orchestrator's canonical path is the `hera_new_orchestrator` MCP tool (an agent becoming a coordinator), and there is no shared in-process primitive combining coordinator-task spawn + orchestrator create + coordinator binding (M4 built only the worker spawn) — adding one would re-implement transactional spawn, which the invariants forbid. Adopt/reparent is the auto-adopt watcher's job (M4). Prune lives on the Tasks tab. Document, don't invent.
- **Spawn runs OFF the main thread; everything else is fast + main-thread.** `heraDoSpawnWorker` dispatches `agent.SpawnHeraWorker` in a goroutine (worktree + session creation is slow) and refreshes via `QueueUpdateDraw`. The pure-DB ops (archive/pin/rename/status/delete-rows) run synchronously on the tview thread (hera-store writes are mutex-guarded and fast — same rule as the M6a reads: the "never on the UI thread" constraint is about GIT, not DB). Project for a spawned worker is resolved from the coordinator's OWN task row (`coordTaskID → task.Project`), authoritative, never `role.ArgusProject` — matching the MCP arm.
- **Destructive ops gate on a generic `modal.ConfirmModal`; text-input ops reuse the generalized input form.** Delete (always) and archive-of-a-LIVE-row (`heraArchivingLive`) open `modal.NewConfirmModal` (y/N, Enter/Esc, no text input). Rename + spawn-prompt use `NewInputForm(title, initial)` — `RenameTaskForm` generalized with a title field, so it inherits the existing `PasteHandler` (bracketed paste fills the field). New modes `modeHeraInput`/`modeHeraConfirm` are dispatched in `handleGlobalKey`'s early modal chain (before the rune switch), so `1`/`2`/`3`/`q` can't leak while a hera modal is open; their close paths `SwitchToPage("hera")` + `SetFocus(heraPage)` (NOT the task list).
- **Remote mode: `heraOps` is nil and the callbacks are unwired (guarded by the `a.db.(*db.DB)` type-assert in `buildUI`), so every Hera-tab mutation key is an inert no-op.** `HeraPage.InputHandler` also returns early on `p.remote`. No panic, no partial write.
- **`agent.SpawnHeraWorker` + `agent.DeriveHeraWorkerName` + `agent.HeraWorkerOrientation` are the shared spawn primitives (moved out of `daemon`/`mcp`).** Both the MCP `hera_spawn_worker` arm and the Hera-view `w` key call them. The role+binding write is an `AfterPersist` hook inside `CreateAndStart`, joining its LIFO compensating stack (role-insert failure unwinds the task+worktree; later session-start failure unwinds the role+binding) — covered by `internal/agent/hera_spawn_test.go` (happy/uniquify/role-fail-unwind/start-fail-unwind).

## Details pane — roster stacked over the plan DAG

> The embedded graph now renders the **plan DAG** (planned + live worker roles, `hera_blocks` blocking edges — the order-of-ops a coordinator authored over `hera_plan*`), NOT the role hierarchy. The retired orchestration-tree projection `heraTreeNodes` (`internal/tui/hera/tree.go`) + `tree_test.go` are DELETED; `internal/tui/dagview` survives ONLY as the layout library `planview` imports (`dagview.Compute` for stage placement). The earlier `depends_on` DAG, standalone DAG tab, `/api/dag`, SPA DAG view, `depswatcher`, and `task_link`/`unlink`/`deps`/`halt`/`set_plan_slug` are all gone, along with `model.Task.DependsOn`/`PlanSlug`.

- **The Details (right) region has TWO modes; a coordinator STACKS roster + plan (no toggle).** A WORKER/leaf selection feeds the AGENT terminal. A COORDINATOR selection renders BOTH at once via `HeraPage.drawDetailsRegion`: the read-only `" Details "` roster on top, the embedded `" Plan "` graph directly below. SAME geometry as roster-over-tree: roster sized to `DetailsView.ContentHeight()`, capped at `h/2`, then `max(_,3)`/`min(_,h)`-clamped for tiny panes; the plan fills the remainder (skipped + rect zeroed when `< 2` rows). The plan widget is the ONLY interactive surface, so `handleDetailsKey` forwards keys to it (j/k/h/l/arrow nav + Enter/Space + Esc) and `MouseHandler` routes coordinator-region clicks to it.
- **`Esc` in the plan view backs out ONE LEVEL and is always CONSUMED by the widget — it never jumps to the rail.** `Widget.EscBack` (bound to `KeyEscape`) has a fixed priority: (1) cursor on a FANNED group → collapse it (un-fan, Member→-1); (2) else `DrillDepth()>0` → `PopOrch` + `OnDrillOut`; (3) else root → consumed no-op. `handleDetailsKey` forwards Esc straight to the widget — do NOT reintroduce the old `Esc-at-DrillDepth0 → focus.ToRail()` escape hatch (removed); the operator leaves the pane via the focus ladder (`Ctrl+Q`/`Tab`), so there's no trap. Un-fan WINS over drill-out: an Esc on a fanned group inside a drilled-in child collapses the group first; the next Esc drills out. `TestInputHandler_EscRouting` (widget, 4 subtests) + `TestDetailsPlan_EscAtRootDoesNotJumpToRail` (page) pin it.
- **Plan-view plain-leaf `Enter` jumps WITHIN the Hera view, NOT to the Tasks tab.** `Plan().OnEnter` is wired by the PAGE (`jumpToLeaf`), not the App — `jumpToLeaf` calls `Rail.SelectByTaskID(id)` (the leaf node id IS the bound task id) which fires `onSelectionChanged`→`applySelection` (rebinds the agent pane), then `focus.SetRegion(FocusAgent)` (or `FocusCoord` if the leaf resolved to a coordinator/sub-coord row, detailsMode). Do NOT re-wire `Plan().OnEnter` in app.go to `openAgentForTask`/`onTaskSelect` — that switched to the Tasks tab (the BUG-002 regression); `heranav.go` (the old `openAgentForTask` hook) was deleted. Group `Enter` (fan/collapse) and sub-coord `Enter` (drill-in) are unchanged. `TestPlanLeafEnter_JumpsWithinHeraNotTasks` + `TestRailSelectByTaskID` pin it.
- **The coordinator Details metadata (Created / Last activity / Agent / Worktree / Repos in scope) is derived PURELY from the rail's `OrchView` projection — no Draw-time or SetOrch-time DB read.** `deriveCoordMeta` (`internal/tui/hera/details.go`) runs over `OrchView.Roles`, cached once in `SetOrch` (NOT recomputed in Draw). (Unchanged by the plan-view work — the roster panel is identical.)
- **`DetailsView.ContentHeight()` MUST stay byte-for-byte in lockstep with `Draw`'s row budget**, because `drawDetailsRegion` sizes the roster panel from it. (Unchanged — see `TestDetails_ContentHeightMatchesDraw`.)
- **The embedded graph renders the PLAN of the selected orchestrator, projected by `heraPlanNodesWithBridge(root, rail.Model().bridgeIndex())` — NOT a provider seam, NOT a tree, NOT `depends_on`.** It is a pure in-memory read over the rail's `Model` (`rebuildPlan` calls it on every `applySelection` when `detailsMode`); no DB call at Draw time (`BuildModel` already attached `OrchView.Blocks` via one bulk `ListHeraBlocks` read). Coordinator roles are NEVER plan nodes (they author the plan); only worker-kind roles project. A planned (never-bound) role → `Node{Planned:true, State:StatePlanned}`; a live/finished role colours from its bound task's status/result. **MUST use the WithBridge form, not the single-arg `heraPlanNodes`** — the bare form leaves `Node.Drillable` false (it can't see sibling orchestrators); the bridge index stamps `Drillable` on a worker whose bound task coordinates a child orchestrator (D6). `rebuildPlan` first pops the drill stack back to root so a stale child frame from the previous selection never lingers.
- **planview↔hera import direction is one-way: `hera` imports `planview`, NEVER the reverse.** The projection (`heraPlanNodes*`) and the drill-in resolution (`HeraPage.drillIntoChild` → `bridgeIndex()` → child `OrchView`) live in `hera` because they need the rail Model; `planview` is a generic widget that knows nothing about hera. The seam is the `OnDrillIn(id)` callback: planview fires it with the node id, the page resolves the child + reprojects + `PushOrch`. This is why the App wires `OnEnter` (jump-to-agent-view, App's concern) but the PAGE wires `OnDrillIn` in `NewHeraPage` (it needs hera internals planview can't reach).
- **The widget is exposed via `HeraPage.Plan()`; the App wires only `OnEnter`** (jump to a leaf node's agent view) + `OnBranchChange`→`forceRedraw` (log-only, never Sync). ## Ctrl+Z fullscreen + suspended-pane revive

- **The Hera view MUST trap `Ctrl+Z` — dropping it created a suspend footgun.** `0x1A` (Ctrl+Z) on a focused pane PTY makes the OS deliver `SIGTSTP` to the agent and suspend it. The external plugin never suffered this because it bound `^Z`→fullscreen, which *consumed* the byte. Native omitted that binding and the raw byte fell through to the pane PTY. `HeraPage.InputHandler` now traps `Ctrl+Z`→`FocusMachine.ToggleFullscreen` and ALWAYS returns (consumes) — even on the rail, where it's a no-op — so the byte can never again reach a PTY. Don't "simplify" this by only consuming `^Z` when a pane is focused: the rail-focus no-op MUST still consume.
- **Fullscreen is an attribute of the FOCUSED pane, cleared on any return to the rail.** `FocusMachine.fullscreen` is carried by `Advance` (zoom moves to the next pane) but cleared by `Retreat`-to-rail, `ToRail` (Ctrl+Q), `rebalance`-to-rail (a pane disappearing), and `SetRegion(FocusRail)` (rail click). The rail has no fullscreen mode. Present-pane flags in `Draw` are computed from the NORMAL split geometry regardless of fullscreen, so the ladder can still traverse the hidden pane (`fullscreenForward` COORD→AGENT needs `agentPresent`).
- **The fullscreen `Draw` branch records the hidden pane's hit-test rect as zero width.** When zoomed, only the rail + focused pane draw; the other region's `coordW`/`agentW` is set to 0 so a stale click/scroll can't land on a region that isn't painted. Same no-Sync + full-rect-coverage rules as the split path.
- **`Enter` revives a STOPPED (suspended) worker, not just a DEAD one — but the two states need different primitives.** `Alive()` cannot tell a SIGTSTP-stopped process from a running one (both keep the session "alive"; the process just stopped, `Wait` hasn't returned). So the page broadens the `Enter` gate to fire `OnReattach` for a dead session (any role) OR a live worker/freelance role (a live coordinator stays navigate-only — operators type into it). `heraReattach` then branches: dead→`startSession`; live worker→`reviveHeraWorker`.
- **`reviveHeraWorker` uses `runner.KickRerender`, NOT the TUI-side `pendingRerenderRestart`+`Stop` path.** The TUI rerender-restart in `handleSessionExitUI` only fires while the operator is viewing the task in the AGENT view (`stillViewing`); from the Hera tab (which is `modeTaskList`) it would settle the worker at `InReview` instead of resuming it. `KickRerender` owns the stop+resume inside the runner/daemon, so the worker comes back via `--session-id` regardless of which tab is active. It needs `a.runner.(agent.SessionRunner)` (both `*Runner` and the daemon client satisfy it; remote apiclient does not → skip).
- **The revive is idle-gated and prompt-aware so it never clobbers real work.** `reviveHeraWorker` only kicks when the session `IsIdle()` (no recent output — the signature of a stopped/stuck agent) AND is not `sessionBlockedOnPrompt` (don't dismiss a pending question). A busy worker is left alone. Reads hit the daemon over RPC → run on a goroutine, dispatch the decision via `QueueUpdateDraw` (mirror of `maybeKickRerender`). `task.SessionID == ""` (Codex pre-capture) skips revive — there's nothing to resume in place.
- **On darwin, `SIGTERM`/`Stop` DOES terminate a stopped process** (so `KickRerender`'s stop reaps a suspended agent and the resume brings it back). This differs from Linux, where a stopped process only reacts to `SIGKILL`/`SIGCONT` — relevant if a future contributor relies on stop-reaps-suspended on the Linux CI runner; the revive's correctness on the operator's machine (darwin) is what was validated live.
- **`Enter` revives from the FOCUSED PANE too, not only the rail (BUG-001).** A focused pane's keys route through `HeraPage.forwardKey`, which used to SILENTLY DROP the keystroke once the session was nil/`!Alive()` (the BUG-013 re-resolve path) — so `Enter` on the "Session not running - press Enter to start" overlay did nothing. Fix: `terminal.TerminalPane` gained `OnReattach func()` + an `InputHandler()` that fires it ONLY when `Enter` is pressed AND the session is nil/`!Alive()`; `forwardKey`'s dead-session branch now routes the event to that `InputHandler` instead of dropping. `bindPane` wires `tp.OnReattach = func() { p.reattachPane(tp) }`; `reattachPane` targets the pane's OWN task (agent pane → `p.sel` worker, coord pane → `Selection{Orch:…}` for the coordinator it shows) and routes through the page's `OnReattach` → `App.heraReattach` — the SAME revive the rail uses. INVARIANT: only-when-not-alive (a live pane's `Enter` must reach the PTY) and nil-guarded, so the task page (which mounts the same widget but never wires `OnReattach`, and writes the PTY via `handleAgentKey` not the pane `InputHandler`) stays inert and unchanged. No new key — `Enter`-to-revive is already documented, so help/README are untouched.

## Two-state EOL — hide vs nuke (BUG-022, supersedes the retire/prune ladder)

> BUG-022 replaced the five-key EOL surface (`a`/`R`/`C`/`Ctrl+R`/`Ctrl+D`) with a TWO-state model and three keys. `R` (retire) and the rail-wide `Ctrl+R` (prune) are REMOVED — their keys, handlers, and the `Model.IsFinished`/`FinishedRoles`/`FullyFinishedOrchestratorIDs` helpers are gone. The bullets below describe the new world; the old "retire → prune ladder" notes were deleted with the keys.

- **BEDROCK RULE: no EOL path hard-deletes a hera row, ever.** "Done with" = gone from the rail + worktree gone from disk + role/orchestrator/inbox/task all retained & retrievable. `DeleteHeraRole` / `DeleteHeraOrchestrator` were REMOVED from the `MutateStore` interface (`ops.go`) so the EOL surface can't even call them — the type system enforces the invariant. Message rows are never deleted either.
- **TWO resting states, distinguished by a second `nuked_at` column on `hera_orchestrators` AND `hera_roles`** (additive, alongside `archived_at`/`pinned_at`): HIDDEN (Tier 1) = `archived_at` set, `nuked_at` NULL → renders in the parent coordinator's nested Archive expando, reversible; NUKED (Tier 2) = `nuked_at` set (and `archived_at` set, so the row leaves the active-name partial unique index and frees its name) → invisible to the rail entirely. The rail-feeding lists (`ListHeraOrchestrators`/`ListHeraRoles`) filter `nuked_at IS NULL`; id lookups (`HeraOrchestrator`/`HeraRole`) still return nuked rows for DB recovery. BuildModel ALSO skips `nuked_at`-set rows defensively (so the model is self-contained even if a reader doesn't filter).
- **`a` = HIDE, worker / sub-coordinator ONLY.** `heraHide` rejects a coordinator-kind role / orchestrator-header selection ("Hide applies to workers and sub-coordinators") because a top-level coordinator has no parent archive to nest under. Hide is the existing archive TOGGLE (`Ops.ArchiveToggle`) — it archives the hera ROLE row ONLY (it does NOT `db.SetArchived` the argus task — Q2 decision: HIDE is RAIL-ONLY, the worker keeps running and still shows in the Tasks tab), KEEPS the session + worktree alive (no `Stop`, no `RemoveWorktreeAndBranch`), is reversible (press `a` again to un-hide → clears `archived_at`, the rail row returns to its exact prior spot), and has NO confirmation. A bridging sub-coordinator is a worker-kind role, so it hides through the same path — and (Q3 decision) its WHOLE subtree COLLAPSES into the parent coordinator's Archive expando with structure retained (see the rail-rendering bullet below), NOT dimmed-in-place.
- **Q3 — hiding a bridging sub-coord folds its whole subtree INTO the parent's Archive expando (`rail.go appendOrchWorkers`).** ALL archived workers (leaf AND bridging sub-coords) route into the per-coordinator `Archive (N)` expando; the expando's `appendWorkerRow` nests a bridging sub-coord's bridged sub-team beneath it (dimmed) when open. The historical orphaning hazard (an archived bridging worker hoisted into the COLLAPSED expando while its child orchestrator was left unplaced → safety-swept flat to a top-level root) is now closed by `structuralReach`: a child whose canonical-parent chain reaches a root is never re-leaked by `buildRows`' safety sweep, so a collapsed expando keeps the child hidden under its hidden parent. This is the deliberate REVERSAL of the earlier "archived bridging worker renders in-place dimmed" rule (which predated `structuralReach`). MUST stay tested at ≥2 levels in BOTH fold states — `TestRail_HiddenSubCoordCollapsesSubtreeIntoExpando` + `TestRail_ArchivedBridgingWorkerHoistsSubtreeToExpando` pin it.
- **`Ctrl+D` = NUKE, any role or coordinator (incl. top-level).** `heraOpenDelete` → `heraNukeRole` (single role) or `heraCascadeNukeFrom` (coordinator / orchestrator header / bridging-sub-coord row → whole `BridgeSubtree`). Nuke stamps `nuked_at` via `Ops.NukeRole`/`NukeOrchestrator` (which also ends the live binding), reclaims the worktree + local/remote branch, stops the session, and archives the bound argus task (`heraReclaimAndArchiveTask` → `db.SetArchived`, NEVER `db.Delete`). Confirm modal is worded "removes … from the rail" + "reclaims … worktree(s)" + "rows retained (recoverable via the DB)".
- **`C` = CLEAR THIS COORDINATOR'S ARCHIVE = nuke its Tier-1 hidden descendants.** `heraClearArchive` walks `Model.SubtreeArchivedWorkers(scopeID)` (the coordinator's hidden worker roles) and runs `heraNukeArchivedRole` on each (= reclaim worktree if reclaimable + `Ops.NukeRole`). Scoped to the SELECTED coordinator's archive, NEVER a global sweep; empty → "nothing to clear". This is the rework of the old `heraPruneDescendants` — the terminal op changed from complete-task-+-`DeleteRole` (a hard delete!) to archive-task-+-`NukeRole`.
- **`C` on a SUB-coordinator scopes via `sel.BridgeChildOrchID`, not `sel.Orch.ID` (BUG-003).** A bridging sub-coord selects as a worker ROW whose `Selection.Orch` is the PARENT orchestrator, so feeding `orch.ID` to `SubtreeArchivedWorkers` walked the parent's WHOLE subtree and over-cleared the parent + every sibling. `heraClearArchive` now mirrors `heraOpenDelete`'s exact disambiguation: when `sel.Role != nil && sel.BridgeChildOrchID != 0`, scope to the CHILD orch id (and name the confirm title after the child via `Model.OrchByID`). A plain top-level coordinator (no `BridgeChildOrchID`) is unchanged.
- **`n` is selection-INDEPENDENT — it must bypass `fire()`.** `fire(cb, sel)` no-ops on an empty selection, so `n` (the new-root-coordinator bootstrap key) is dispatched directly in `handleRailMutation` (`OnNewCoordinator(sel)`), always consuming the key; it receives the Selection only to DEFAULT the project. (`Ctrl+R` is no longer a rail key — it falls through; a focused Hera pane forwards it to the PTY, the rail leaves it unused. The agent-view `Ctrl+R` Claude-session-switcher is unaffected.)
- **All rail mutation keys are suppressed while `/` filtering.** `handleRailMutation` returns `false` at the top when `rail.Filtering()`, so `n`/`C`/`w`/`a`/`Ctrl+D` become filter input. This guard is BEFORE the `event.Key()` switch — keep it there.
- **Multi-binding isolation gate for reclaim is "no live binding belonging to ANOTHER role", not `len(live)==1`.** A hidden (archived) role already has an ENDED binding (`len(live)==0`), so the conservative `heraTaskSolelyBoundTo` (`len(live)==1`) would wrongly preserve it. `heraTaskReclaimable(taskID, roleID)` returns true when every live binding's `RoleID == roleID` (covers 0 and self-only) — the correct reclaim gate for `C`. The conservative single-role `Ctrl+D` on a LIVE role uses `heraTaskSolelyBoundTo` (a live role has exactly one live binding); the cascade uses `heraTaskBoundOutside` (preserve a task bound live OUTSIDE the nuked subtree).
- **Reclaim keys off the role's LATEST binding task (`BridgeTaskID`), not live `TaskID`.** A hidden worker's live binding has already ended, so `TaskID` is empty; `roleReclaimTask` falls back to `BridgeTaskID` (the latest binding regardless of liveness) so `C` still finds the task to archive + worktree to reclaim.
- **Q2 DECISION (locked): HIDE is RAIL-ONLY — it does NOT archive the argus task.** `heraHide` archives only the hera role row; it never calls `db.SetArchived` on the bound task, so a hidden worker keeps running and still shows in the Tasks tab. Only NUKE (`Ctrl+D`/`C`) touches the argus task (archives it + reclaims the worktree). This corrected an earlier design note that said "db.SetArchived in BOTH tiers" — that was wrong for hide. Do NOT add a task-archive to `heraHide`.
- **`w`/`n` reuse the Tasks-tab `NewTaskForm` via a submit OVERRIDE, not a second modal.** `openHeraNewTaskForm` sets `newTaskOnDone` + `newTaskReturnPage="hera"`; `handleNewTaskKey` captures `onDone` BEFORE `closeNewTaskForm` (which clears it) and, when non-nil, calls it instead of the default create-and-start path. `closeNewTaskForm` returns to the Hera tab when `newTaskReturnPage=="hera"`. The form resolves its project against `config.Projects`, so the defaulted coordinator project must be a configured project for `SelectedProject()` to resolve (it always is in production; tests must `SetProject`).
- **`SpawnHeraCoordinator` deletes the orchestrator on ANY failure.** The orchestrator row is created BEFORE `CreateAndStart`; the role+binding LIFO cleanup only covers the role. On a worktree/session failure the primitive explicitly `DeleteHeraOrchestrator`s so no empty orchestrator leaks. The orchestrator name is de-collided via `UniqueHeraOrchestratorName` first, because `CreateHeraOrchestrator` is idempotent by name and would otherwise re-fetch an existing orchestrator and bolt a second coordinator onto it.

## Needs-input "(?)" subtree rollup (BUG-018)

- **The rail's needs-input "(?)" now bubbles up the orchestration tree to the ROOT — a coordinator shows "(?)" when IT or ANY descendant role (transitively across bridges) needs input.** Computed as a MODEL-side rollup in `BuildModel` (`model.go`), exposed as `RoleView.SubtreeNeedsInput`, so `statusIcon` (`rail.go`) stays a pure projection that reads `RoleView.ShowsNeedsInput()` (rollup OR the role's own signal). - **The authoritative per-role needs-input source is the SAME one the task list uses — `App.needsInputIDs` (the idle-gated, sticky `agent.DetectNeedsInput` PTY-tail scan), NOT a new signal.** Native Hera previously had NO per-role needs-input flag (`model.go` "Native has no per-task idle/needs-input flag"), so a blocked worker didn't even show "(?)" on itself. The App pushes the set every tick via `HeraPage.SetNeedsInput` (right next to `tasklist.SetNeedsInput`), `doRefresh` threads it into `BuildModel`, and `buildRoleView` stamps `RoleView.NeedsInput` for live roles. `needsInputOwn()` = `NeedsInput || (HasStatus && Status==blocked)` — the self-asserted hera `blocked` status is folded in so it bubbles identically.

It runs at the END of `BuildModel` because the rollup needs the whole assembled model (bridged sub-orchs only exist once every orchestrator is built).
- **Precedence (in `statusIcon`/`RoleStatusIcon`): needs-input "(?)" now ranks ABOVE `ready_to_close` and above `done`/active-spinner/idle/live (BUG-A).** A descendant needing input surfaces on an ancestor even when the ancestor is idle, working, or `done` — it is the one actionable thing in the subtree. needs-input now also OUTRANKS `ready_to_close`: a worker stamped `ready_to_close` by the done-roll that is ALSO genuinely blocked is not "ready to close" — the actionable `(?)` must win over the now-contradicted close-out glyph, else the user closes a worker that is waiting on them. Because needs-input is content-aware upstream, a `ready_to_close` worker merely idling at its done summary (no interactive affordance) is never flagged and still renders the review glyph. The full order (post-BUG-F) is `needs-input → active-spinner → ready_to_close → failed(red ✕) → done → idle → live → default`.
- **`IsActive()` spinner OUTRANKS `ready_to_close`/`failed`/`done` in `RoleStatusIcon` (BUG-F, the icon-precedence completion of BUG-C).** A worker rolled to `in_review` gets `meta:hera.ready_to_close` (done-roll); when the user reactivates it and it produces output again, `IsActive()` is true (BUG-C) but the OLD order (`ready_to_close` at position 2, `active` at position 5) returned the static review glyph before ever reaching the spinner — a genuinely-working worker looked parked. The fix moves `case in.Active` ABOVE the stale-able resting states, so `active` (the HONEST content-derived `Live && SessionRunning && !SessionIdle` signal, NOT a stale role-status/meta) wins. The resting case is preserved by `IsActive`'s OWN running/!idle gate: the moment the session goes idle or exits, `active` drops false and the `ready_to_close` review / `failed` ✕ / `done` ✓ glyph correctly returns. needs-input stays highest (a blocked worker outranks a merely-producing one; mutually exclusive in practice). Shared 1:1 with the plan-view node (BUG-007): a working plan node also spins — `planNodeIcon`'s `Animated` flag is derived from the classifier's resolved glyph (BUG-012), so it tracks the reorder automatically. For a real BuildModel-produced role `SubtreeNeedsInput` already folds in own, so the OR is redundant in production — keep it anyway so a fixture setting only `Status==blocked` still renders "(?)".

### Clear-propagation + the liveness gate (BUG-023 / BUG-A)

- **The CLEAR path is automatic — the rollup recomputes from scratch on every refresh, so a cleared descendant clears its ancestors transitively with NO extra wiring.** `BuildModel` builds fresh `RoleView`s and re-runs `rollupNeedsInput` each call; `doRefresh` calls it (1) every app tick while the Hera tab is active (`app.go` `ScheduleRefresh` on `ActiveTab()==TabHera`) and (2) after every mutation, including `s`/`S` (`heraStatusStep` → `heraRefresh` → `Refresh()`). There is NO stale `SubtreeNeedsInput` carried between builds. So "ancestor `(?)` stays lit after the descendant resolved" is NEVER a rollup-recompute bug — it is always the INPUT not changing. Do not add a separate clear path; fix the input.
- **The per-role PTY needs-input own-signal is gated on the role's LIVE BINDING (`buildRoleView`: `taskInProgress || rv.Live`, which under the live-binding branch is always-true → trust the content-aware map) — liveness, NOT task status, is the BUG-023 clear condition.** Originally this was gated on `task.Status==in_progress`, because `App.needsInputIDs` was a STICKY marker that lingered in the log tail forever even for a finished worker. Post-BUG-032/034/035 the set is CONTENT-AWARE (a task is in it only while a CURRENT awaiting-input signal shows, and it clears on user input or archive), so the marker no longer lingers on a stale done summary — and the in_progress gate became wrong for a live `in_review` worker that genuinely blocks (BUG-A; `RollHeraWorkerToReview` keeps the binding live). BUG-023 is now carried by liveness: a worker is finished when its SESSION EXITS, which ENDS its binding → `rv.Live` is false → the live-binding branch in `buildRoleView` no longer runs → the role drops from the rollup. A task MISSING from the `Tasks()` snapshot (read failure) leaves `taskInProgress` false but `rv.Live` true, so it still surfaces while live (self-heals next tick).
- **`s`/`S` (hera role status) and the PTY scan are TWO INDEPENDENT `(?)` sources (`needsInputOwn` ORs them) — stepping off `blocked` only clears the STATUS source.** The deliberate `blocked` status was never task-status gated (a coordinator's "I'm blocked" assertion is honest even while the task runs); it clears by stepping the role off `blocked` (`S` → working / `s` → done). If a live worker is parked at a REAL prompt, the PTY source keeps `(?)` lit regardless of the status step — that is correct, not a bug (you cannot dismiss a real pending prompt by toggling status). The stale-marker symptom that once required the in_progress gate is now handled upstream by the content-aware set + the liveness branch.
- **The gate is hera-view-LOCAL — the flat task list keeps its strict `in_progress` `(?)` gate (BUG-006), the Hera rail uses the liveness gate (BUG-A).** Only the rail surfaces a live non-`in_progress` role (a worker in `in_review`, a complete coordinator); the always-flat Tasks tab and the agent-view attention bar (`needsInputInProgress`) and the web `/api/tasks` flag (`computeRuntimeState`) stay `in_progress`-gated, because a finished task in a flat list (no liveness context) correctly shows no `(?)`.

## Left arrow — rail parent navigation (BUG-016)

- **Left arrow is scoped exclusively to `FocusRail` — it does NOT intercept Left from a focused pane.** When a content pane (coordinator or agent terminal) is focused, Left must pass through to `forwardKey` unchanged so the PTY receives it (cursor motion in the shell, vim navigation, etc.). The intercept in `InputHandler` returns early only when `p.focus.State() == FocusRail`.
- **`CursorToParent` walks the flattened `r.rows` slice backwards looking for a row with strictly smaller depth AND kind `rrOrch` or `rrRole` with `collOrchID > 0`.** A plain `rrRole` row without `collOrchID` is NOT a valid parent landing point — it's a worker, not a coordinator. The bridging `rrRole` (collOrchID > 0) represents a nested coordinator that also acts as a worker in the outer team; it is the correct parent for worker-bridge sub-teams.
- **No-op conditions:** cursor already at index 0; cursor depth is 0 with no qualifying ancestor above; rows above exist but none pass the kind filter (e.g. a freelance role below a section header, no `rrOrch` above it). `CursorToParent` silently no-ops in all these cases — no panic, no state change.
- **This is NOT the BUG-001 pattern.** BUG-001 was a key leaking from the rail into a pane unintentionally. BUG-016 deliberately adds a rail-only binding. The distinction is the `FocusRail` guard: any key that should be rail-only must return early BEFORE the per-region `forwardKey` dispatch. Do not route rail-scoped keys through `forwardKey`.

## Pane-focused Tab/Shift-Tab pass through to the agent PTY (BUG-019)

- **Once a TERMINAL pane is focused, `Tab`/`Backtab` MUST fall through to `forwardKey` (the agent PTY), NOT walk the focus ladder — otherwise the agent's own autocomplete is dead** (`/plugi`+Tab can't complete to `/plugin`). The `Tab`/`Backtab` arm of `HeraPage.InputHandler` is gated on `terminalPaneFocused()`: when true it `break`s out of the key switch so control reaches the per-region `forwardKey`; when false (rail or coordinator-Details region) it still `Advance`/`Retreat`s the `FocusMachine`. `keyenc.Encode` already maps `KeyTab→\t` and `KeyBacktab→\x1b[Z`, so `forwardKey` emits the right bytes with no special-casing.
- **Smart-Tab (detect autocomplete, else nav) is NOT possible** — the TUI only forwards bytes; the inner agent owns autocomplete state and never signals whether it consumed Tab. So it's unconditional PASSTHROUGH, mirroring the main agent view's BUG-003 Tab handling.
- **`terminalPaneFocused()` is `FocusCoord || (FocusAgent && !detailsMode)`.** The coordinator pane is ALWAYS a terminal (passthrough applies even when its session is dead — `forwardKey` drops gracefully). The agent region is a terminal only for a worker/leaf selection; a coordinator selection renders the read-only Details/plan region, which has no PTY, so Tab/Backtab keep walking the ladder there (Backtab retreats to coord). Don't fold the details case into passthrough — there's nothing to forward to.
- **The no-trap guarantee survives without Tab:** entering a pane from the rail is still `Tab` (the rail isn't a terminal pane), pane↔pane movement is the existing `Ctrl+Alt+←/→` ladder, and `Ctrl+Q` (`ToRail`, handled unconditionally before the gate) always escapes to the rail. Any future change that makes a pane forward Tab MUST keep one of these escapes reachable.
- **The BUG-007 status bar and the help overlay both follow this.** The pane-focused (`heraFocus != 0`) hint set in `statusbar.go` drops the `Tab pane` hint and shows the `^⌥←→ pane` ladder; the RAIL hint set keeps `Tab pane` (entering a pane from the rail is fine). The `Hera View (rail)` help section advertises "enter pane (then Tab → agent autocomplete)" and the `ctrl+alt+← / →` ladder — `help_test.go` pins both substrings.

## ctrl+y copy agent-staged clipboard (focused-pane scoped)

- **`ctrl+y` copies the staged clipboard payload for the FOCUSED pane's task, not a single global active task.** The Hera view shows several tasks at once (coordinator pane + worker pane), so the copy resolves `HeraPage.FocusedTerminalTaskID()` (= `coordBound` when `FocusCoord`, `agentBound` when `FocusAgent && !detailsMode`, else "") and the App's `copyStagedClipboardForHeraPane(taskID)` looks the payload up directly via the daemon-backed `clipboardAccessor` — it does NOT reuse the agent view's `activeAgentTaskID` cache (that cache is single-task and meaningless here).
- **The intercept is UNCONDITIONAL whenever a terminal pane is focused — it no longer gates on `clipReady`.** `ctrl+y` always fires `OnCopyClipboard` and consumes the key on a focused terminal pane, staged or not; nothing forwards to `forwardKey` anymore (an intentional trade-off — in-agent vim/emacs yank on ctrl+y no longer works inside a Hera pane, mirroring the same change in the main agent view). `clipReady` is still refreshed each tick by `App.refreshHeraClipboardHint()` for the single focused pane's task, but it now drives ONLY the border-title hint below; `copyStagedClipboardForHeraPane` decides copy-vs-"Nothing to copy" itself by checking the accessor directly.
- **The `(ctrl+y copy)` border-title affordance is set in `Draw`, not once at construction.** `Draw` recomputes both pane titles each frame: the focused terminal pane gets the hint suffix when `clipReady`, the other stays bare. Keep the affordance ASCII (single-cell runes) — the border-title truncation math assumes single-width runes, the same constraint the agent header's hint documents.
- **`OnCopyClipboard` is daemon-only and nil-safe.** Wired only in local mode; under the in-process runner the copy method type-asserts `clipboardAccessor`, fails, logs a `[hera]` no-op, and flashes "Nothing to copy" (same feedback as the nothing-staged path — ctrl+y is always intercepted either way). In remote mode the page is inert (InputHandler returns early), so `ctrl+y` never fires.
