# Native Hera View (`internal/tui/hera`)

M6a scaffolds the native Hera view: a `HeraPage` (rail | coordinator pane | agent pane) replacing the old DAG tab. Only the LEFT rail is live and READ-ONLY; the two right panes are placeholders (6b adds PTY feeds; 6c adds mutations). M6b makes the two right panes REAL terminal feeds and wires rail selection to them.

## M6b — pane feeds from the in-process runner

- **Panes are fed from the in-process runner's ring buffer, NOT SSE — Hera's `proxy/` fan-out has no Argus equivalent and is not ported.** The coord/agent panes are `terminal.TerminalPane`s (the same widget the main agent view uses). A `SessionResolver func(taskID) agentview.TerminalAdapter` seam (App wires it to `runner.Get`) hands the pane a live session; the TerminalPane POLLS that session's ring via `RecentOutput*` on every Draw (it does NOT `AddWriter`). The daemon-owned PTY ring is the single source — there is no SSE/HTTP hop and no `ArgusStateCache` polling. Remote mode (`nil` reader) never sets a resolver and never feeds the panes.
- **The coord-vs-agent session-selection rule (LOCKED — documented in `panes.go`):** the HERA (middle) pane ALWAYS shows the *selected orchestrator's coordinator* task session (`Selection.CoordTaskID()`), regardless of whether a coordinator or worker is selected — constant coordinator context. The AGENT (right) region is mode-switched by the selected role's kind: a **coordinator** selection renders the read-only `DetailsView` worker roster (no terminal, agent pane unbound); a **worker/freelance/leaf** selection feeds the AGENT terminal from that role's bound task.
- **Multi-binding is disambiguated by the role's orchestrator, NEVER the bare task ID.** `Rail.Selection()` resolves the containing `OrchView` from the selected `RoleView.OrchID` (`Model.OrchByID`), so a task that is worker in A and coordinator in B yields two different `Selection`s: selecting the A-role feeds the AGENT pane from the shared task + the HERA pane from A's coordinator; selecting the B-role feeds the HERA pane from the shared task (B's coordinator = itself) + renders B's roster. `Selection` is the single value threaded to the 6c mutation extension point (`HeraPage.SelectionContext()`).
- **PTY size alignment (CLAUDE.md rule 5): a hera pane and the main agent pane compute the SAME size for the same rect — they are the same `TerminalPane` widget.** When binding a session, `bindPane` calls `ForceResyncPTY()` so a session previously sized for the full-width main agent view gets resized DOWN to the narrower hera pane on the next Draw (without it, the seeded `ptyCols` matches `wantCols` and no resize fires, leaving the agent painting at the stale width). `SyncPanes()` (App tick GOROUTINE + spinner loop, never a QueueUpdateDraw callback) issues the Resize RPC off the main thread. It is safe to call off-tab: a pane that wasn't drawn this frame has zero `pendingResize`, so an off-tab `SyncPanes` can't fight the main agent view's resize of the same task. Never reach for `Sync()` to fix a size mismatch — fix the alignment.
- **Main-thread-safe pane reads only.** Pane operations on the tview thread use the lock-free/local SessionHandle methods (`Alive`, `RecentOutput*`, `WriteInput`, `Session()`) — never the RPC-blocking `PID/IsIdle/PTYSize/InitialPTYSize`. The blocking `SyncPTYSize`→`Resize` RPC runs only from the tick goroutine via `SyncPanes`. `SetSession`/`SetTaskID`/`applySelection`/`reconcileSessions` are main-goroutine-only (SetSession resets emulator state).
- **`reconcileSessions` (App tick, main thread) only does the nil→live UPGRADE.** A pane bound to a task with no live session yet (coordinator/worker still starting) gets its session attached on a later tick. A pane already holding a (live or dead) session is left alone — a fresh selection or refresh rebinds it. `doRefresh` re-runs `applySelection` after `SetModel` because the rebuild replaces the model's backing arrays, invalidating the prior `Selection` pointers (task IDs usually match, so `bindPane` no-ops and emulators survive).
- **PR indicator reads the daemon-populated `"pr"` namespace (keys `state`/`url`), like the task list — best-effort, never fetched.** The plan said `meta:iris.pr_url`, but Argus's canonical cached PR state is `task_meta` namespace `"pr"`; `DetailsView` shows a `PR` mark for a roster task whose `pr` meta has a non-empty `url`. `doRefresh` reads it once via `ListMetaByNamespace("pr")`.
- **`TerminalPane.SetBorderTitle` is the only change to the shared agent surface.** It defaults to `" Agent "`; the hera coordinator pane sets `" Coordinator "` so the same widget reads correctly in both surfaces. The DAG render mode of the Details pane is deferred to M7; mutations to M6c.

- **The second tab is `TabHera` (enum slot `widget.TabHera == 1`), so the `2` hotkey is stable.** `switchTab`'s second arm always routes to the `"hera"` page via `switchToHeraTab2` — the native Hera view is the only second-tab option now (the legacy `"dag"` page was deleted along with `depends_on`). `cfg.Hera.Enabled` no longer toggles the view; it only gates daemon-side MCP native-vs-plugin tool registration on the next daemon start.
- **Multi-binding fan-out is structural, not special-cased.** One argus task bound under two orchestrators is reached through two DISTINCT `hera_roles` rows (one per orchestrator). `BuildModel` walks orchestrators → their roles → each role's live binding, so the task surfaces once under EACH orchestrator with zero fan-out logic. The smoke test `TestSmoke_HeraRailMultiBindingUnderTwoOrchestrators` and unit `TestBuildModel_MultiBindingFanOut` pin this — do NOT "optimize" the model into a per-task dedupe, which would collapse the two appearances the locked Q2/Q3 design requires.
- **Freelance-kind roles are HOISTED into a top-level Freelance section, not nested under their orchestrator.** `BuildModel` skips active freelance-kind roles when filling an orchestrator's `Roles` and appends them to `Model.Freelance` instead. This is a 6a read-only interpretation of the "freelance" section (Hera derived it from unmanaged live argus tasks; that data source is out of scope for the read-only hera store). 6b can revisit if real unmanaged-task freelance is wanted.
- **`ready_to_close` (M4) is read from the task-addressed `task_meta` "hera" namespace, NOT the hera tables.** `BuildModel` does one `ListMetaByNamespace("hera")` batch read and flags `RoleView.ReadyToClose` when the role's bound task has `ready_to_close=true`. The rail renders it with the distinct `theme.IconReview` mark, which WINS over the role's idle/working/blocked/done status icon. A meta read error is non-fatal (the flag just doesn't render).
- **The rail rebuild runs on the tview thread; that's fine because hera-store reads are mutex-guarded and fast — the "never on the UI thread" rule is about GIT, not DB reads.** `Refresher` (the Argus-native analog of Hera's `RailRefresher`) is goroutine-/timer-free: `Schedule()` is driven by the app tick + tab entry and coalesces bursts into one rebuild per debounce window via an injected clock (`SetNow`), so it's deterministic to test. `refreshHera` is `heraPage.Refresh()` on tab entry (forces a flush) and `ScheduleRefresh()` on the tick while `ActiveTab()==TabHera`.
- **`HeraPage.Machine()`, not `Focus()`.** A method named `Focus()` collides with `tview.Primitive.Focus(func(tview.Primitive))` and silently breaks the Primitive interface (the page stops being a valid tview widget). The focus-machine accessor is `Machine()`. The `FocusMachine` is wired for 6b (Advance/Retreat/present-pane rebalance); 6a keeps focus on the rail and only reads `State()` to pick the border-highlight palette.
- **The rail navigates with `j`/`k`/Up/Down and folds with Space — never arrows-for-parent-nav like Hera's upstream rail did.** Historically the rail was BARRED from binding Left/Right because the global handler ate them for tab switching; that arrow-key tab-cycling has since been removed (tab nav is `1`/`2`/`3` only), so Left/Right now fall through to the page: a terminal-focused pane (coord/worker-agent) forwards them to the PTY, a coordinator's details region routes them to the embedded DAG's cursor (M7), while the rail leaves them unused (free for future horizontal navigation).
- **`Ctrl+Alt+Left/Right` walk the focus ladder (Retreat/Advance), mirroring `Tab`/`Backtab`.** Handled in `HeraPage.InputHandler`'s top-level key switch BEFORE the per-region forward, so they reach `FocusMachine.Retreat`/`Advance` rather than being forwarded to a focused terminal pane's PTY (a plain Left/Right still forwards). The modifier check is `Modifiers()&(ModCtrl|ModAlt) != 0` — **either** modifier, not strictly both — matching the main agent view's Ctrl+Alt+arrow pane switch (`app.go`); terminals are inconsistent about which of Ctrl/Alt they report for this chord, so the loose check is the proven pattern. This binding lives in the page handler (not `handleGlobalKey`) precisely because plain Left/Right intentionally fall through the global handler to the focused view.
- **No `screen.Sync()`; cover the full bounding rect.** Every region (`Rail.Draw`, `DetailsView.Draw`, `drawRemoteBanner`, and the two `TerminalPane`s) paints through `widget.DrawBorderedPanel` (which blanks its interior) so stale cells can't survive — per the CLAUDE.md UX-rendering rules. The panes' `OnBranchChange` is wired to `a.forceRedraw` (log-only, never Sync); `OnNeedRedraw` bounces a `QueueUpdateDraw`. `TestPanes_NoSyncOnDraw` pins that drawing the full view (live panes + details) calls `Sync` zero times.

## M6c — keyset + thin in-process mutations

- **Mutations are a THIN layer over M1/M4 — single source of truth, no re-implementation.** `internal/tui/hera/ops.go` (`Ops` + the narrow `MutateStore` interface) is a set of small adapters over EXISTING `*db.DB` M1 methods (Archive/Unarchive/Pin/Unpin/Rename/Delete for orchestrators+roles, `UpsertHeraRoleStatus`, `RollHeraWorkerToReview`); it adds targeting + toggle-direction reads + the status ladder + uxlog, nothing more. Worker spawn does NOT live in `Ops` — it reuses the shared `agent.SpawnHeraWorker` primitive (extracted from `daemon.heraSpawnWorker`; the daemon MCP arm is now a thin adapter to it). If you find yourself re-deriving transactional spawn or cascade-delete, STOP and call the shared primitive.
- **The rail keyset routes through `HeraPage` callback fields, mirroring the DAG widget's `OnEnter`/`OnLink` pattern — NOT through a mutator injected into the rail.** `HeraPage` exposes `OnSpawnWorker`/`OnRename`/`OnArchiveToggle`/`OnPinToggle`/`OnStatusAdvance`/`OnStatusRevert`/`OnDelete`/`OnReattach func(Selection)`. `HeraPage.handleRailMutation` (rail-focus only) maps keys → callbacks passing `rail.Selection()`, then falls through to rail nav. The App wires the callbacks to handlers (`heraactions.go`) that own the modal/confirm/refresh orchestration. nil-safe: an unwired callback (remote mode) makes the key inert; `fire()` consumes a key when its callback is wired even on an empty selection so the keystroke never leaks to nav.
- **Every op acts on the SELECTED `(role, orchestrator)` from `Selection`, never the bare task ID — multi-binding isolation.** Deleting role R in orchestrator A removes only R's row (its binding cascades via `DeleteHeraRole`'s FK); the SAME task's role in orchestrator B is a distinct row and survives. `Ops` re-reads the row (`HeraRole`/`HeraOrchestrator`) to decide archive/pin TOGGLE DIRECTION from current state (not the possibly-stale model flag).
- **Delete semantics are deliberately conservative for multi-binding safety (a documented divergence from Hera's DeleteRole).** Deleting a ROLE destroys the underlying argus task + worktree ONLY when that task has exactly ONE live binding (`heraTaskSolelyBoundTo` → `ListHeraLiveBindingsByTask` len==1, reuses the App's transactional `deleteTask`); a MULTI-bound task is PRESERVED (deleting it would end the other orchestrator's binding to the same task). Deleting an ORCHESTRATOR cascades its hera rows (roles+bindings) but PRESERVES every underlying argus task — one keystroke must not wipe N live worktrees. Orphaned tasks are deleted individually from the Tasks tab.
- **`s`/`S` step the HERA ROLE STATUS (idle→working→blocked→done ladder), NOT the argus workflow status.** The rail renders role status, so the rail key steps role status — a pure `UpsertHeraRoleStatus` call. The argus task status (pending→…→complete) stays owned by the session lifecycle + the M4 finish policy. Reaching `done` on a WORKER-kind role also calls `RollHeraWorkerToReview` (mirrors the `hera_status("done")` MCP arm, BUG-050) — soft-fail so the status update always lands.
- **`n` (new orchestrator), `J` (adopt/reparent), `C` (complete-archived), `Ctrl+R` (hera-prune), `Ctrl+Z` (fullscreen) are intentionally OMITTED in M6c.** New-orchestrator's canonical path is the `hera_new_orchestrator` MCP tool (an agent becoming a coordinator), and there is no shared in-process primitive combining coordinator-task spawn + orchestrator create + coordinator binding (M4 built only the worker spawn) — adding one would re-implement transactional spawn, which the invariants forbid. Adopt/reparent is the auto-adopt watcher's job (M4). Prune lives on the Tasks tab. Document, don't invent.
- **Spawn runs OFF the main thread; everything else is fast + main-thread.** `heraDoSpawnWorker` dispatches `agent.SpawnHeraWorker` in a goroutine (worktree + session creation is slow) and refreshes via `QueueUpdateDraw`. The pure-DB ops (archive/pin/rename/status/delete-rows) run synchronously on the tview thread (hera-store writes are mutex-guarded and fast — same rule as the M6a reads: the "never on the UI thread" constraint is about GIT, not DB). Project for a spawned worker is resolved from the coordinator's OWN task row (`coordTaskID → task.Project`), authoritative, never `role.ArgusProject` — matching the MCP arm.
- **Destructive ops gate on a generic `modal.ConfirmModal`; text-input ops reuse the generalized input form.** Delete (always) and archive-of-a-LIVE-row (`heraArchivingLive`) open `modal.NewConfirmModal` (y/N, Enter/Esc, no text input). Rename + spawn-prompt use `NewInputForm(title, initial)` — `RenameTaskForm` generalized with a title field, so it inherits the existing `PasteHandler` (bracketed paste fills the field). New modes `modeHeraInput`/`modeHeraConfirm` are dispatched in `handleGlobalKey`'s early modal chain (before the rune switch), so `1`/`2`/`3`/`q` can't leak while a hera modal is open; their close paths `SwitchToPage("hera")` + `SetFocus(heraPage)` (NOT the task list).
- **Remote mode: `heraOps` is nil and the callbacks are unwired (guarded by the `a.db.(*db.DB)` type-assert in `buildUI`), so every Hera-tab mutation key is an inert no-op.** `HeraPage.InputHandler` also returns early on `p.remote`. No panic, no partial write.
- **`agent.SpawnHeraWorker` + `agent.DeriveHeraWorkerName` + `agent.HeraWorkerOrientation` are the shared spawn primitives (moved out of `daemon`/`mcp`).** Both the MCP `hera_spawn_worker` arm and the Hera-view `w` key call them. The role+binding write is an `AfterPersist` hook inside `CreateAndStart`, joining its LIFO compensating stack (role-insert failure unwinds the task+worktree; later session-start failure unwinds the role+binding) — covered by `internal/agent/hera_spawn_test.go` (happy/uniquify/role-fail-unwind/start-fail-unwind).

## Details pane — roster stacked over the orchestration tree

> The `depends_on` DAG was retired (Hera orchestration replaced it). The embedded graph now renders the **orchestration tree** (the role hierarchy), not `depends_on` edges. The standalone DAG tab, `/api/dag`, the SPA DAG view, `depswatcher`, and the `task_link`/`unlink`/`deps`/`halt`/`set_plan_slug` MCP + REST surface are all gone, along with `model.Task.DependsOn`/`PlanSlug`.

- **The Details (right) region has TWO modes; a coordinator STACKS roster + tree (no toggle).** A WORKER/leaf selection feeds the AGENT terminal. A COORDINATOR selection renders BOTH at once via `HeraPage.drawDetailsRegion`: the read-only `" Details "` roster on top, the embedded `" Orchestration Tree "` graph directly below. The roster is sized to `DetailsView.ContentHeight()`, capped at `h/2` so the tree keeps the larger share, then `max(_,3)`/`min(_,h)`-clamped for tiny panes; the tree fills the remainder (skipped when `< 2` rows). The tree is the ONLY interactive surface, so `handleDetailsKey` forwards EVERY key to it (j/k/arrow cursor nav + Enter) and `MouseHandler` routes coordinator-region clicks to it.
- **The embedded graph renders the orchestration SUBTREE of the selected orchestrator, projected by `heraTreeNodes` (`internal/tui/hera/tree.go`) — NOT a provider seam, NOT `depends_on`.** It is a pure in-memory read over the rail's `Model` (`rebuildDAG` calls `heraTreeNodes(p.rail.Model(), p.sel.Orch)`); there is no `DAGNodeProvider`, no `scopeTasksToOrch`, no `dagNodesFromTasks`, no DB call. The subtree is discovered by multi-binding BFS in memory (orchestrator C is a child of P when C's live coordinator task is bound as a non-coordinator worker under P). Each worker gets a SYNTHETIC edge to its orchestrator's coordinator; a bridge task collapses to one node (keyed by task ID) carrying both a parent edge and child edges, stitching the subtrees. The coordinator is the root (no self-edge → cycle-safe). This is why a fresh coordinator+workers orchestrator now renders a real tree instead of the empty `depends_on` graph it used to.
- **`rebuildDAG` fires on `applySelection` whenever `detailsMode`** (selecting/switching coordinators reprojects unconditionally). No orch selected → empty graph, no panic. `doRefresh`→`applySelection` keeps it fresh after a store change.
- **The widget is reused verbatim — `HeraPage.DAG()` exposes it; the App wires only `OnEnter`** (jump to a node's agent view). The `OnLink`/`OnUnlink`/`OnHalt` callbacks and the `l`/`L`/`h` keys were removed with `depends_on`. Embedding caveats unchanged: retitled `" Orchestration Tree "` (`SetTitle`), `OnBranchChange`→`forceRedraw` log-only (never Sync), full-rect coverage via the widget's own `DrawBorderedPanel`. `TestDetailsDAG_NoSyncOnDraw` pins the no-Sync rule; `TestDetailsDAG_DrawStacksBothPanels` pins that both `" Details "` and `" Orchestration Tree "` render at once (and asserts no stray `" DAG "`). Node colour comes from the bound task's argus status (`RoleView.TaskStatus`/`TaskResult`), populated in `BuildModel` via the new `HeraReader.Tasks()` method.

## Rail parity — nesting, coordinator fold, spinner, PR cell, cascade delete

> Supersedes the earlier "rail is flat" / "coordinator renders as its own child row" notes above. The rail now nests sub-orchestrators and folds the coordinator into the header.

- **The bridge keys off each role's LATEST binding regardless of liveness, NOT the live binding — excluding only the operator-teardown end reasons `reparented`/`user_deleted`.** `db.ListHeraLatestBindings` = `MAX(binding id) per role` (id is monotonic, so highest id == latest). `BuildModel` fills `RoleView.BridgeTaskID`/`LinkEndReason` from it; `OrchView.CoordBridgeTaskID()` is the child's structural key. An ended-but-not-torn-down link (a coordinator whose task finished) STILL nests its child. The DB `SubtreeOrchIDs` SQL (a `latest` CTE) and the in-memory `workerTaskSet`/`heraTreeNodes` apply the identical rule. `roleBridges(r)` = `r.Live || !HeraEndReasonIsTeardown(r.LinkEndReason)`. `bridgeTaskID(r)` falls back to `TaskID` when `BridgeTaskID` is unset (hand-built test fixtures) — production always sets it.
- **The coordinator role is FOLDED into the orchestrator header — it never renders as its own child row.** `appendOrch` skips `HeraKindCoordinator` roles; `drawOrchRow` prepends the coordinator's status glyph (via `OrchView.CoordRole()`). `liveRoleCount` excludes coordinators so `(N)` counts agents. Consequence: a HEADER selection IS a coordinator selection — `Selection.IsCoordinator()` returns true when `Role==nil && Orch!=nil`, and `Selection.FocusTaskID()` resolves the coordinator task so Enter/reattach on a worker-less header revives the coordinator. Tests select the coordinator by landing on the orch header, not a coord row.
- **Rail nesting is `buildRows`→`appendOrch`(header)→`appendOrchWorkers`(recursive). A `placed` set guarantees single placement AND breaks bridge cycles; `consumedSet` picks roots; an active "safety sweep" (render any active orch left `!placed`) prevents a pure A↔B cycle from vanishing; PINNED orchs are always top-level roots.** A bridging worker row carries `collOrchID = child.ID` (Space folds the child subtree, chevron+coord-marker drawn on it). The worker row IS the child's coordinator (same multi-binding task) so NO separate child header is drawn. Archived bridges nest DIMMED in place (`dim` propagates down); archived roots fall to the bottom Archive section only when `!placed`.
- **The in-memory rail/tree bridge MUST match `db.SubtreeOrchIDs` exactly: a child nests when its coordinator's latest-binding task has ANY non-teardown latest binding under the parent — through a WORKER role OR the parent's own COORDINATOR role.** Honouring only worker rows under-nests: a coordinator that spawned a sub-team via `hera_new_orchestrator` is coordinator-bound in BOTH orchestrators (one agent, two coord roles, same task), so the child has no worker row to host it. `coordBridgeParentOf(p,c)` = same coord bridge task AND `p.coordRoleID < c.coordRoleID`; this also breaks the symmetric A↔B "cycle" (`SubtreeOrchIDs` includes each from the other) by **earlier coordinator role id = parent**. `Model.coordBridgeChildren` feeds `consumedSet`, `BridgeSubtree`, and `appendOrchWorkers` (which nests the child as its own sub-orch HEADER under the parent — there is no worker surrogate). `tree.go` BFS adds the same edge.
- **`consumedSet` must equal what rendering actually PLACES, or the safety sweep flattens the difference to top-level roots.** This caused the second half of the under-nesting bug: an ARCHIVED bridging worker was hoisted into the collapsed per-coordinator Archive expando (never `appendWorkerRow`'d), yet `consumedSet` still consumed its child → child unplaced → safety-swept flat. Fix: `appendOrchWorkers` keeps an archived worker that `workerBridgeChild(...) != nil` IN PLACE (dimmed row) so its child nests; only archived LEAF workers fold into the expando. `SubtreeOrchIDs` has no parent-side archived-role filter, so this matches it. The archived worker ROW dims, but its live child subtree dims only from inherited `dim` or the child's OWN `Archived` (an active child under an archived bridge stays normal). Verified on a COPY of live `~/.argus/data.sql`: 7 rendered roots (was ~24), no migration.
- **The bridging worker row keeps its PARENT worker selection context (conservative) for pane binding and most mutations — but Ctrl+D cascades the WHOLE nested subtree.** `Selection.BridgeChildOrchID` carries the child id (set when a role row's `collOrchID > 0`). `heraOpenDelete` branches on it: `heraCascadeDeleteSubtree` walks `Model.BridgeSubtree(childID)`, shows a DESTRUCTIVE confirm modal enumerating orchestrators/agents/worktrees removed, and on confirm destroys every task with NO live binding OUTSIDE the subtree (session+worktree+branch) then deletes each orchestrator. A task bound under a non-subtree parent is preserved (multi-binding safety). The destroy predicate `heraTaskBoundOutside(taskID, subtreeIDs)` drives BOTH the count and the action, so the warned worktree count never undercounts an INTERNAL bridge task (bound under two subtree orchestrators) in a depth≥2 cascade. The subtree snapshot is point-in-time (modal-open) but every op re-validates live, so a stale pointer never destroys the wrong row. A non-bridging row keeps the conservative single-role delete. (This is the one place selection acts on the child, not the worker — Aaron's explicit call 2026-06-16.)
- **Per-coordinator `Archive (N)` expando is distinct from the bottom Archive section.** `appendOrchWorkers` hoists a coordinator's ARCHIVED roles out of inline rendering into a per-coord expando (collapsed by default, `coordArchiveOpen[orchID]`, `railRow.archiveOwner`). The bottom Archive section (`collArchive`/`archiveCollapsed`) is for archived ROOT orchestrators. Both are `rrArchiveExpando`; `drawRow`/`ToggleCollapse` branch on `archiveOwner > 0`.
- **The rail spinner animates on REAL session activity (`RoleView.IsActive` = live binding + bound argus task `in_progress`), NOT the hera `working` role-status — BUG-003.** The hera role Status (`idle`/`working`/`blocked`/`done`) is a manual/MCP-set ladder value that NEVER reconciles down: it stays `working` after the session idles, stops, or dies. Binding the spinner to it (the original rail-parity #8 code) made stopped/idle/days-old roles animate. `statusIcon` now derives the spinner from `role.IsActive()` (`Live && TaskStatus == "in_progress"`), mirroring the plugin's `stateGlyph` (spinner on `in_progress`+running). Precedence: `ready_to_close` > `blocked`/`done` role-status > `IsActive()` spinner > `idle` role-status > `Live` (moon-stars) > unbound dimmed. **`blocked`/`done` outrank activity** (a deliberate "I'm blocked" assertion must show needs-input even while the task is still `in_progress`). Native has NO per-task idle/needs-input flag (the plugin sourced those from the API), so a live `in_progress` task sitting idle still counts active; the reported stale cases are excluded because they are not `Live` or no longer `in_progress`. `coordStatusLabel` (Details) applies the same honesty: stale `working` → `live` (binding alive) or `stopped` (binding gone), never `working`. Keep `statusIcon` pure (frame in, no `time.Now()` inside) so tests pass explicit frames; `Rail.animFrame` is recomputed from wall-clock each `Draw` (`spinnerFrame()` mirrors the task list). The spinner only advances while the app's spinner loop redraws (any session actively running).
- **The PR cell on rail rows reads the same `prMeta` ("pr" namespace) the Details roster uses — `Rail.SetPRMeta` is called from `doRefresh`.** A managed role whose bound task has a non-empty `url` renders a right-aligned `PR` tag, reserving width so the name truncates instead of overwriting it. Best-effort; never fetched by the view.
