## CI Gate Troubleshooting (`make pre-pr`)

`make pre-pr` mirrors `.github/workflows/ci.yml` step-for-step (build → vet → fmt-check → lint-pr → vuln → test-cover-gate). Steps run in sequence and the first failure short-circuits the rest, so a formatting miss hides downstream test/lint/coverage failures until fixed — always run the **full** `pre-pr` locally to surface everything in one pass. Per-gate failure recipes:

- **`fmt-check`** — run `make fmt` first; goimports rewrites the tree. An unformatted file is the most common CI miss.
- **`test-cover-gate`** — filtered coverage dropped below the 88% floor. Add tests for code you touched (or under-covered platform-agnostic code) until it clears; the floor ratchets up, never down. Do NOT lower `-min`. Filtered coverage drifts ~0.2% darwin↔linux from platform branches (e.g. `internal/agent/sandbox.go`) — target platform-agnostic code for reliable margin.
- **`lint-pr`** — uses `--new-from-rev=origin/master`, so it only flags issues your diff introduced (incl. `staticcheck` deprecations like `SA1019` on new lines). Fix them; no blanket `//nolint`.
- **`vuln`** — CI runs govulncheck with `continue-on-error: true`, so Go stdlib-only CVEs (`Found in: <pkg>@go1.x.y`, "Standard library") never block CI (fixable only by bumping the toolchain). Confirm the failure is toolchain-only (fails on a clean `origin/master` tree too), note it in the PR, run the remaining gates individually. Module-level findings in bumpable deps still must be fixed. **Locally, `make pre-pr`'s `vuln` step has no such tolerance — it's a hard failure**, so a stale local toolchain (`asdf`/etc. resolving a `go` newer than `go.mod`'s bare `go 1.x.y` line, e.g. `go1.26.1` used with no pinned `toolchain`) blocks the whole gate. The durable fix confirmed in this repo: add a `toolchain go1.x.y` line to `go.mod` pinning a patch release with the stdlib CVEs already fixed upstream — `go.sum` is untouched (no module change), and it resolves the gate permanently instead of needing the "note it in the PR" workaround on every future PR.
- **`test-cover-gate` flakes in `internal/agent` under full-suite `-race` on a loaded macOS dev machine** — real-PTY tests panic with `session.go: invalid memory address or nil pointer dereference` after a setup error `device not configured` (macOS PTY-device exhaustion when many packages' subprocess/PTY tests run concurrently). `go test ./internal/agent/...` in isolation passes cleanly; `go test -p 1 ./...` (fully serialized across packages) also passes with normal coverage. Confirm via that isolation/serialization split before suspecting a real regression — do NOT weaken or skip the affected tests. Not observed to reproduce on CI (Linux runners, different PTY limits).
- **The same class of flake also hits `internal/tui/terminal` (many `x/vt.SafeEmulator` goroutines each backed by an `io.Pipe`, same resource-contention shape as a PTY) — and, less often, `internal/tui` itself** — a per-package 120s timeout under full-suite `-race`, surfaced as a goroutine dump with everything parked in `io.(*pipe).read`/`SafeEmulator.Read` (`internal/tui/terminal`) or mid-`db.OpenInMemory()`/`sql.Open` (`internal/tui`), never a real panic. `go test ./internal/tui/terminal/...` in isolation passes in ~90s; confirmed reproducing with a fully clean tree (no diff at all) via `git stash`, so it is NOT a signal that a given change caused it — it's whichever package happens to be mid-flight when the loaded machine's scheduler starves it past 120s. Same diagnosis recipe as the `internal/agent` case above: isolate or serialize (`-p 1`) before suspecting a regression.
- **A third member of that family: `internal/api`'s `TestTailscaleIPFromCLI_AcceptsCGNATOutput` times out at exactly its 5s budget under full-suite `-race`, and passes in ~0.1s in isolation.** It writes a `/bin/sh` shim to a `t.TempDir()` and shells out through `tailscaleIPFromCLI`, so it is fork-latency-bound, not network-bound — nothing about it touches a real Tailscale daemon, and a clean re-run of `make test-cover-gate` passes. The exact-5.00s duration in the failure line is the tell: a genuine failure of this test asserts on the parsed IP and fails fast, so a timeout-shaped failure is contention. Same recipe: re-run or isolate before suspecting a regression, and do NOT raise the timeout to paper over it.
- **`go build`/`go vet`/`make` can fail with `mkdir /Users/<you>/.argus/cache: operation not permitted` when run from inside a sandboxed Claude Code Bash tool** — the default `GOCACHE` (`~/.argus/cache/go-build`, set by this repo's own shell env) sits outside the sandbox's writable set even though sibling `~/.argus/*` directories (session data, the live daemon's DB) are readable. This is the *agent's own* sandbox, unrelated to `internal/sandbox`'s SBPL profiles for argus's spawned agents (`fix-argus-cache-sandbox-write` in `gotchas/sandbox.md`), and it doesn't reproduce for a normal terminal session. Work around it per-invocation: `export GOCACHE=<scratchpad-dir>/gocache && mkdir -p "$GOCACHE"` before `go build`/`go test`/`go vet`/`make *` — the scratchpad dir is always writable. Don't try to fix this by touching repo config; there's nothing in the repo to fix.
- **`TestHeraActions_NukeRolePrunesSoleBoundTaskOnceSessionSettled` looked like a member of the contention family above but wasn't — it's a genuine ordering race in `heraNukeRole`/`heraDoCascadeNuke`/`heraNukeArchivedRole`, not scheduler starvation.** All three called `heraReclaimAndArchiveTask` (which backgrounds `heraPruneReclaimedTask` — a `db.PruneTasks` call that re-verifies no-live-hera-binding at delete time) *before* `Ops.NukeRole` synchronously ends the role's binding. On a scheduler that lets the new goroutine run before the caller's next line (empirically: GitHub Actions' runners, essentially never this repo's dev machines), the prune's read wins the race, observes the binding still live, and skips the delete for good — nothing in a bare TUI/test process retries it (only the daemon's periodic reconciliation sweep would in production). First "fix" (widening the poll deadline 2s→8s) still failed on CI at the full 8s, which is what exposed this as a real bug instead of contention: a lost race doesn't resolve no matter how long you wait for it. Fixed by reordering all three call sites so `NukeRole` ends the binding before the reclaim (and its async prune) is ever started — the multi-binding *decision* (`heraTaskSolelyBoundTo`/`heraTaskBoundOutside`/`heraTaskReclaimable`) still runs first, since that needs the binding to still be live to count correctly. Lesson: a deadline that keeps failing after a generous widen is a signal to go find the actual gate, not to widen further.
