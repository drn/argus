# Argus bridge (Claude Code mod + shadow comparator)

Non-obvious invariants for `internal/bridgemod` (the embedded mod), `internal/bridge` (daemon
state + comparator) and the `internal/api` bridge endpoints.

## Source of truth

- **A transcript id is not a process identity.** BuildCmd exports a new `ARGUS_BRIDGE_GENERATION` per launch; the mod echoes it, and supervisor SessionInfo relays it. Resume can reuse a transcript id; recycle/rerender/restart must stay scraper-sourced until that launch's mod reports. A failed generation RPC returns empty, never the cached old generation.
- **A heartbeat must reconstruct busy and dialog state after a daemon bounce.** Event freshness alone cannot make an empty Hub's default `busy=false` authoritative while an existing turn is running; heartbeat snapshots carry busy, needs-input, kind and confidence. Retired boot ids cannot regain authority through late buffered posts.
- **Corroborate only uncertain permission input, never the whole live bridge verdict.** Resolve pending-or-running (or missing-confidence) permission input as bridge AND raw scraper input; bridge busy remains authoritative, and quiescence uses the resolved input. Keep raw scraper state apart from published verdicts to avoid feeding an earlier exact dialog back into a later permission; source logs change only with real liveness/authority changes.
- **Raw permission state still gates delivery and feeds the separate shadow permission bucket.** Display corroboration must never authorise writing into a session or establish claim-settlement absence; comparing corroborated input to the scraper in that diagnostic bucket is a tautology that hides every disagreement.
- **Cost source handoffs baseline without charging.** The first transcript after bridge reporting saves its raw token offset, and the first bridge report after transcript accounting saves its cumulative USD offset. The source, offset and accrued cost are persisted atomically on binding-owned state; a transition turn may be undercounted, never charged twice. `/clear`/lower cumulative counters start new epochs; hot reload with unchanged cumulative cost does not.
- **Rate-limit freshness is measurement freshness, not heartbeat freshness, and accounts never borrow readings.** Named accounts with no usable live bridge remain unknown; per-account headless probes are a named follow-up. The existing hidden probe measures only the default account.
- **The TUI snapshot is fetched off the UI thread.** Local RPC and remote REST snapshots override final task/Hera sets after scraper computation, retaining fallback state machines. Web/macOS read the same verdicts through task/Hera/status responses and existing events; the in-process runner keeps scraping.

## The mod

- **AbovePrompt must always call `await next(e)`, and return it whole when hidden.** The engine permits one hooks module and one unqualified hook per event per mod; lifecycle UI work shares the reporting hooks. Live Claude 2.1.310 with managed `cc-plugin-sec-default` confirmed AbovePrompt, toast, command.register and command.run work (unlike prompt.compose).
- **When drawing the band, drop a beneath of `type: 'engine'`; keep any other.** That is core's own AbovePrompt, which draws only surveys (the band already yields on `hasSurvey`). A tree another plugin drew beneath is not `engine` and must stay. **The empty row between the band and the prompt box is NOT this component and is NOT fixable from a mod:** live replays of 12 session logs (2.1.310) show it is the engine's fixed spacer between the transcript and the prompt box. Sessions that never drew a band have it too, and the band is inserted above it. No AbovePrompt prop or slot option controls it. Replay the session log at the authored width before chasing a band layout bug.
- **`fetchSnapshot` throws for "daemon unreachable" and returns null for "nothing to show"; keep the two apart.** A throw keeps the previous atom and sets the mod-only `offline` flag, so the band shows `⚠ bridge offline` instead of vanishing. A null (no `ARGUS_TASK_ID`, or a daemon too old for the snapshot shape) clears the atom and hides the band. Folding either into the other either hides the outage or shows a stale band forever.
- **Band styling is nested `Text` runs inside one outer `Text`.** `find({ text: /argus:/ })` matches both the outer row and the nested `argus:` label, so tests that count rows filter on `props.wrap`. State colors are theme keys, so they follow the person's theme. The only raw color is the `argus:` label, `rgb(59,130,246)`, kept identical to the statusline's label.
- **Band rendering reads only the session atom; refresh is background single-flight work.** Running sessions pick up effective band/toast switches on turn completion, measurement or a 15s timer. Inspecting mail never marks it read or claims delivery; a refresh immediately before plugin submission observes arrivals before the model can drain its inbox. Seen identities survive mod reload in session state; suppressed arrivals do not toast later on re-enable.
- **Embed the mod's `types/index.d.ts` contract as runtime content, but never `.claude-plugin/types`.** The former declares session atoms; the latter is the engine-generated development SDK symlink. Add new runtime UI files to SupervisorSpawnPaths and bump/re-record the spawn surface.

- **Budget nudges use idle `prompt.submit`, not `prompt.compose`.** Live tmux verification showed the managed `cc-plugin-sec-default` plugin skips other mods' compose hooks, matching phase 1's classic-hook bypass. The Stop hook keeps its increment/pending gates and stamps last-nudged context after enqueue; measurement stamps and the hard-stop remain. Recycle/rerender safety still uses terminal predicates (named follow-up).
- **Set local busy before any await in `turn.start`.** Otherwise an idle poll can submit during session-id synchronization. Delivery polling and acknowledgment stay single-flight and outside hook dispatch; network timeout never triggers prompt resubmission.

- **`tool.check` verdict `ask` does NOT mean a dialog appeared.** A settings `PermissionRequest` hook can auto-approve it within ~1s (this setup auto-approves Bash). The mod only reports a permission needs-input when the call is *still pending* after a 1.5s grace; `AskUserQuestion`/`ExitPlanMode` are the exceptions (the call itself is the dialog, pending from `tool.call` pre to post). Verified live: a Write ask reported, an auto-approved Bash ask did not.
- **Never use `classic.PermissionRequest` / `classic.Notification` from the mod.** They are skipped when a managed plugin runs first (the Thanx org's `cc-plugin-sec-default`).
- **The only "approved and now running" signal is the `ToolProgress` render (the `(ctrl+b to run in background)` pill).** Without it a permission ask stays pending through the whole approved execution, so the daemon had to AND it with the scraper, which missed real dialogs on busy screens (live: 26 settled `needs_input_permission` disagreements, one held 137s with a parallel shell running). The mod now drops a call once its pill renders and reports the rest as `pending`, which the daemon trusts like `exact`. Tools that draw no pill (MCP, web fetch, a subagent's call, a second call sharing one pill) keep (?) until `tool.call` post. The render hook must return `next(e)` untouched and fire its report without awaiting it.
- **`/clear` does not re-fire `session.start`.** The mod re-reads `$.session.id()`/`model()` on every `turn.start` and re-emits `session.start` on change (verified live: id changed after `/clear`).
- **A hot reload re-runs `register` and resets module variables**, so `seq` restarts. Events carry a per-load `boot` id; the daemon dedupes by (`boot`, `seq`) and treats a new `boot` as a fresh baseline.
- **`claude plugin validate` follows `$` only into top-level function declarations of the module (or imported ones).** Helpers that take `$` must be `function` declarations at file top, not closures or consts inside `register`; per-load state is passed explicitly (`Bridge` object). Gating hooks (`tool.check`, `tool.call`) need `.catch(($, e, next) => next(e))` to fail open.
- **`$.env.get(name)` needs a string-literal name**; the mod reads only `ARGUS_TASK_ID`, `HOME` and `ARGUS_BRIDGE_DIR` (the last overrides the `$HOME/.argus` dir that holds `api-token`/`api-port`, used to live-test without touching the real one).
- **No hook ever awaits delivery.** `Reporter.emit` enqueues and starts a single-flight background drain (later emits and the 15s heartbeat also drain); only the post itself is raced against `$.clock.sleep(2000)` since `$.http.fetch` has no timeout. Awaiting delivery in a hook cost up to ~8s per turn against a daemon that accepts but never answers and could blow the 10s hook budget (the engine then prints a dim "hook skipped" line). A drain that ends with events queued behind it re-kicks itself, unless it stalled on a retryable failure; a *throwing* env must be mapped to that stalled state, or the re-kick spins forever (found by the hung-env test).
- **A non-2xx other than 401 clears the cached port** (the port may now belong to another server, which must not keep receiving the master token); the daemon removes `api-port` on clean shutdown, but only while the file still names its own port (a takeover daemon may have rewritten it).
- **First-party permission telemetry is unavailable to user mods in 2.1.310.** Validation and live load both reject `telemetry.log {to:'anthropic'}` as reserved for built-in plugins; collector hooks cannot substitute for those rows. If a future engine admits them, first-party permission props lack `tool_use_id`, requiring FIFO correlation by `toolName` and the existing heuristic fallback when no `tengu_tool_use_*` rows are observed; until then the mod relies on the grace-period heuristic plus the `ToolProgress` running signal (above).
- **Subagent asks ARE reported** (an ask or AskUserQuestion inside a subagent blocks the user), so `tool.check`/`tool.call` are not filtered on `agentId`; subagent `turn.start`/`turn.complete` still are, so they never drive busy/idle. The main `turn.complete` resets the tracker.
- **A new `boot` resets the hub's busy/needs-input state** — otherwise a stopped or restarted mid-turn session comes back live still busy or still holding a dialog.
- **`register.test.ts` cannot drive the permission-ask path**: the test harness mints a different `tool_use_id` for the plugin's `tool.call` than a test can name on `tool.check`. It is unit-tested in `tracker.test.ts` and was verified live.
- **Dev setup:** `.claude-plugin/types` is a gitignored symlink to the plugin-authoring skill's `types/` dir (path contains the Claude version; re-point it after an upgrade). Type-check with `npx --yes --package typescript tsc -p internal/bridgemod/mod/argus-bridge`; then `claude plugin validate` and `claude plugin test` on the same dir. `.gitignore` lists `.claude-plugin/types` WITHOUT a trailing slash on purpose: a slash-only pattern does not match a symlink and the link got committed once.

## Embedding and loading

- **`go:embed` uses explicit file patterns, not a directory.** A directory pattern skips the dot-dir `.claude-plugin/`; `all:` would try to embed the types symlink and `node_modules`. `TestEmbedCoversRuntimeFilesOnDisk` fails if a runtime file is added to the mod dir without the patterns picking it up (the mod would pass `claude plugin test` and break in production).
- **The mod ships inside the *supervisor's* binary**, because BuildCmd runs there. The mod files are therefore in `SupervisorSpawnPaths`: any mod edit changes the spawn-surface digest and must be re-recorded (and bumped if observable). A stale supervisor spawns sessions with an old mod or none.
- **Materialization is content-addressed** (`~/.argus/cache/bridge-mod/<hash>/argus-bridge`, `.complete` marker written into the temp dir BEFORE the rename) so a hot-reloading Claude never sees a directory mutate under it. **Never `RemoveAll` an existing hash dir** — a markerless one cannot be produced by us, and removing it raced concurrent first launches into handing out a path another launch had just deleted (reviewer reproduced 25/1600 callers; `TestMaterialize_ConcurrentFirstLaunch` checks the path inside each goroutine, since the deletion is transient). Old hash dirs are not swept.
- **The location is under `cache/` because a sandboxed session may write only `~/.argus/cache`**, and the engine writes `.claude-plugin/types/` into every `--plugin-dir` folder it hot-reloads (seen in the materialized dir in the unsandboxed live run). A real sandbox-exec load check could NOT be run (sandbox-exec cannot nest inside an argus sandbox), so the move follows that evidence; confirm under the real profile when dogfooding.
- **An argus sandbox cannot write `~/.argus`**, so a smoke harness that calls the real `EnsureBridgeMod` from inside a sandbox fails to materialize; stub it with `agent.SetEnsureBridgeModForTest` + `bridgemod.Materialize(tmp)`.

## Daemon and comparator

- **Neither the daemon nor the supervisor calls `uxlog.Init`**, so `uxlog.Log` is a no-op in both (BuildCmd, where materialize failures happen, runs in the supervisor). Every bridge log site (`bridge.defaultLogf`, the ingest handler, the BuildCmd materialize failure) therefore also writes to `slog`; `[bridge]` lines reach `ux.log` only from the TUI process.
- **`api-port` is written right after `ListenAndServe`** (atomic temp+rename, 0600); the port moves under `bindWithRetry`, and sessions outlive a daemon bounce through the supervisor. The mod re-reads it on any connection failure.
- **Idle is compared as "screen quiescent"**: bridge idle = `!busy || needs_input`, because the scraper's idle is also true while parked on a question. Comparing raw `!busy` would count every dialog as a disagreement.
- **Only a *live* bridge is compared** (newest event, heartbeats included, under 45s old); otherwise the tick counts as `no_bridge`, never a disagreement. A disagreement counts only after the 10s settle window (scraper lag ~3s + 5s tick); shorter ones are `settling`. Counters are per task per tick, not per event.
- **The comparator hooks in at exactly two places** (`idleWatcherTick` after the final idle set and `detectNeedsInputTick`'s `needsInputNow`) through `Server.observeBridge`, which is gated on `[bridge] enabled`. It must stay side-effect free on the verdicts; phase 2 swaps this seam.
- **Live-run finding (phase 1 dogfood, local harness: real api.Server + real BuildCmd + real claude, in-process runner, no TUI):** idle agreed on 329/329 non-settling ticks (zero disagreements). needs_input disagreed for minutes after a dialog was answered: bridge correctly `false`, scraper `true`. Checked and NOT an input-origin artifact: the answering keystroke arrived as `write_origin=user`, and the scraper did clear at the answer (`left needs-input` 2s later). The flag is a stale-text false positive: after the answer, the last 16KB raw tail the scraper scans still contains the answered dialog's numbered options (`DetectNeedsInput`, `DetectNeedsInputScreen`, `ParkedSelectionSignal` all stay true on that tail; a small follow-up turn does not push the widget out of the window), and when the content fingerprint then changes the BUG-067 rule re-arms the flag as a "distinct later prompt" (re-entered ~15s after the clear in one run; in another run it never re-entered within 40s). Not tested under the supervisor or with a larger follow-up turn; treat the rate as indicative, not a population number.
