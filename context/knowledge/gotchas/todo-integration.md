# To-Do List Integration

- **Live config resolution, not startup-only wiring.** Every other `mcp.Server.Set*Manager` is called once before `ListenAndServe` and its *existence* (nil-check) is the whole gate — the underlying DB/runner it wraps is what stays live. `SetTodoManager` is different on purpose: `resolveTodoBackend()`/`todoToolsActive()` call `TodoConfigStore.Config()` (satisfied by `*db.DB`, which re-reads the DB config table + config.toml overlay on every call, per `db.Config()`) fresh on **every** `tools/list`/`tools/call`, not just once. That is the entire mechanism behind "a backend selected in Settings appears immediately, no daemon restart" — there is no watcher, no re-wiring, no mutex-guarded hot-swap. Don't add one; the existing live-read is sufficient and simpler.
- **An unknown/misconfigured backend name is treated identically to "no backend configured."** `todo.Get` erroring (bad name) makes `todoToolsActive()` false, so the `todo_*` tools vanish from `tools/list` and `tools/call` returns a JSON-RPC `-32601 unknown tool` — not a distinct "todo management not configured" tool-error. This is deliberate (matches the openspec `todo-list-integration` spec) but easy to "fix" into a more helpful error by someone who hasn't read the spec; don't.
- **Argus never caches or mirrors to-do items.** `todo_list` (and every mutation) queries the configured backend live on every call — no DB table, no in-memory cache. This is a deliberate anti-second-source-of-truth choice, not a missing feature.
- **Things 3 backend (`internal/todo/things3`) is macOS-only and stateless.** `newForOS` gates on `runtime.GOOS` (injectable for tests — the real `New` always passes `runtime.GOOS`, since this dev host is itself macOS and there's no other way to exercise the non-darwin branch). Every method shells out to `osascript` fresh via `exec.CommandContext` — no persistent connection to leak, reconnect, or go stale.
- **`todo_delete` on Things 3 means "move to Trash," not permanent erasure** — the same semantics as deleting a to-do in the app itself. AppleScript's `delete` command doesn't support a from-Trash purge; don't read a successful `todo_delete` as unrecoverable.
- **AppleScript output parsing uses two control characters as delimiters** (`fieldSep = \x1f`, `recordSep = \x1e`), chosen because a real to-do title/notes will essentially never contain them — but `escapeAS` strips both from any user-supplied text anyway as a defensive backstop against desyncing the row parser.
- **The `not found` signal is an explicit AppleScript-side sentinel (`existsGuard`/`notFoundSentinel`), not stderr text-matching.** Every id-addressed mutation (`update`/`complete`/`delete`) opens with `if not (exists to do id "...")` and returns a fixed sentinel string instead of letting Things 3 raise its own AppleScript exception — parsing Apple's exact exception wording would be fragile across OS/app versions.
- **Settings UI (`internal/tui/settings.go`, `catTodo`) explicitly skips overwriting `todoProject`/`todoTag` from `Refresh()` while `editingTodoProject`/`editingTodoTag` is true** — this is a new guard, not copied from the pre-existing Metis vault-path field (which does *not* have this guard and can be clobbered by a concurrent `Refresh()` mid-edit). Added deliberately for todo's fields; consider backporting to the vault path if that gap is ever hit in practice.
- **Only one backend is ever active, enforced structurally, not by runtime validation.** `config.TodoConfig` is a scalar `Backend string` plus one sub-table per known backend (mirrors `Defaults.Backend` for agent CLIs) — there is no list/map of backends, so "two backends active at once" isn't a state the type system allows, not a case handled at runtime.
- **`todo_*` tools require `[kb] enabled = true`, same as every other MCP tool family.** The MCP HTTP server itself (`internal/mcp`) is only constructed in `daemon.go` inside `if cfg.KB.Enabled { ... }` — this predates the todo feature and applies to `task_*`/`schedule_*`/`hera_*` too, but it's an easy trap for someone who only wants to-do tools and never turns on the (confusingly named, unrelated-sounding) Knowledge Base flag. Documented in README's `[todo]` and MCP-tools sections; not fixed structurally here since decoupling MCP-server startup from `cfg.KB.Enabled` is a bigger, separate change.
- **`todoToolsActive()`'s inactive-backend log line is deduped per-`Server` instance** (`lastTodoErr`/`todoErrMu`), not logged unconditionally. That function runs on every single `tools/list` poll, so an unresolved misconfiguration (e.g. a typo'd backend name) would otherwise flood the log forever; only a *changed* error re-logs.
- **`things3.Update`'s `Title` follows `Create`'s same non-blank rule — `Notes` does not.** A non-nil `*UpdateInput.Title` that trims to empty is rejected (Things 3 to-dos always have a name); a non-nil `*UpdateInput.Notes` that's empty is a valid "clear the notes" request and goes through unchanged, per the partial-update idiom's own documented semantics (`internal/todo/todo.go`'s `UpdateInput` doc comment).
- **Settings' `cycleTodoBackend` validates a candidate backend before persisting it, but only in local mode.** It calls `sv.todoProbe` (defaults to `todo.Get`, which for `things3` means `newForOS(runtime.GOOS, ...)` — a cheap, side-effect-free OS check, no AppleEvents) and, on failure, sets `sv.todoBackendErr` (shown in the detail pane, cleared on the next successful cycle or the next `Refresh()`) instead of persisting the broken selection. Gated on `!sv.remote`: in `--remote` mode this TUI process's own `runtime.GOOS` is not the daemon's host OS, so a client-side probe there would be checking the wrong machine — `--remote` skips it and relies on the daemon's own graceful degradation (`todoToolsActive()` hides the tools) instead.
- **`newForOS`/Settings' probe only check the host OS — neither confirms Things 3 is actually installed or running.** Construction succeeding on macOS means nothing more than "this host is darwin." If Things 3 isn't installed (or isn't reachable), that surfaces as an ordinary per-call tool error on the first real `todo_*` call, not as a config-time "unavailable" rejection the way an unregistered backend name or a non-macOS host is. Don't read a successful `todo.Get("things3", ...)` as proof the app is actually there.
- **Every Settings test that cycles to a real backend needs a `todoProbe` stub, not a bare `testSettingsView(t)`.** Because the probe above calls the real `todo.Get`/`things3.New` by default, any test exercising `cycleTodoBackend`'s success path transitively hits the macOS-only constructor — this bit twice in the same PR (once in `things3_test.go`'s own new tests, then again here in `settings_test.go`'s pre-existing tests, once the probe started actually being called) before `testSettingsView` was given a default always-succeeding fake `todoProbe`. Only `TestSettingsView_TodoBackendCycle_RealProbeOnDarwin` deliberately bypasses that fake (and skips on non-macOS) to keep the real wiring covered at all.
