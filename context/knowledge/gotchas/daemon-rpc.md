## Daemon & RPC

- **Task→Complete requires an OBSERVED clean exit; everything else is recoverable (InReview).** The single authoritative predicate is `daemon.ExitInfo.CleanExit()` = `!Stopped && Err == "" && !StreamLost` (process ended on its own, zero exit code — e.g. Ctrl-D / `/exit`). Both LOCAL flip sites derive from it so they can never disagree: the daemon's `transitionTaskOnExit` (authoritative for headless/PWA, computed from the real `exitErr`) and the TUI's `handleSessionExitUI` (idempotent retry — in-process builds the equivalent `ExitInfo` and calls `CleanExit()`, so the predicate is byte-identical). **The `--remote` (`apiclient`) path is intentionally different:** the SSE client only sees the stream close, never the agent's exit code, so `apiclient.SessionExitInfo` maps every exit to non-clean → InReview. That's the correct conservative answer for a client that *can't observe* a clean exit; the remote daemon's own `transitionTaskOnExit` still records the authoritative status in its DB, surfaced to the remote TUI via `/api/tasks`. (Pre-existing remote behavior, unchanged here.) A non-zero exit / missing-binary fast-fail (`exit 127`) arrives as a non-empty `Err` → InReview, NOT Complete — the rule is timing-independent (no wall-clock "did work happen" heuristic). **Any INFERENCE of termination (the TUI tick reconciliation from session-list absence) must land InReview, never Complete — it has no exit event and cannot know the agent finished.** (So the false-reconciliation guards in the bullets below now prevent a wrong *InReview*, not a wrong *Complete* — the guard reasoning is unchanged either way.) The daemon-client `removeSession` path also defends the invariant: if the `GetExitInfo` RPC fails it forces `StreamLost=true` rather than letting a zero-value `ExitInfo` read as a clean exit (which would wrongly Complete the task).
- **Hera worker tasks NEVER self-complete (BUG-050 / finish policy, M4) — TWO triggers, ONE shared helper.** A worker-bound task lands `InReview` (even on a clean exit) with `meta:hera.ready_to_close=true` (best-effort soft-fail) instead of `Complete` — workers are closed out by the coordinator/human. Both triggers route through `db.RollHeraWorkerToReview(taskID)` so they can't drift; it acts ONLY when the task holds a live worker-kind binding AND is currently `InProgress` (never auto-completes, never clobbers a human-set in_review/complete), touches DB status + meta only (never the session — the live agent keeps running), and is idempotent. **(1) PRIMARY = `hera_status("done")`** (`toolHeraStatus`, gated on the caller's RESOLVED role kind == worker): Claude workers finish their report and go *idle* rather than exiting, so this is the common path; a roll failure is logged, never surfaced, so the status update always succeeds. **(2) BACKSTOP = session exit** (`transitionTaskOnExit`): catches workers whose session actually ends — the helper runs first and, if it flips, the #707 branch is skipped. Coordinator/freelance and non-hera tasks are NOT rolled and follow the unchanged #707 `CleanExit` rule. The exit check lives inside `transitionTaskOnExit`, which the runner's `onFinish` skips on `pendingRestart` (a kick-rerender restart never stamps or flips). The TUI's `handleSessionExitUI` mirrors the exit backstop via the same helper (type-asserts `a.db` to a local `heraFinishStore`; `--remote` skips, remote daemon authoritative) to preserve the "all flip sites never disagree" invariant — in daemon mode the daemon's `onFinish` runs before the stream close that wakes the TUI, so the mirror is usually a no-op; load-bearing in daemon-less in-process mode where the TUI is the only flip site. `meta:hera.ready_to_close` is a SEPARATE signal from `InReview` (workflow state vs "done, awaiting close-out"), consumed by M6's rail + task-list rendering.
- **Daemon-startup hera-binding reconciliation (risk e).** `heraadopt.ReconcileBindings(d.db)` runs in `Serve` right after `ReconcileStaleSessions`: it ends (reason `task_missing`) any live hera binding whose argus task row no longer exists — the row was deleted while the daemon was down so the `tasks.Delete` cascade hook never fired. Idempotent (an already-ended binding is no longer live), so it is safe on every boot.
- **The reconcile→InReview vs daemon→Complete race is closed by runner ordering — do not reorder.** The runner's exit goroutine fires `onFinish` (the daemon's `transitionTaskOnExit`, which writes the terminal status) BEFORE `delete(r.sessions, taskID)` (`runner.go`: "fire callback while session is still in the map"). So the session stays visible in `RunningAndIdle()`/`ListSessions` until AFTER the daemon has written Complete/InReview; by the time the TUI tick observes the session gone and runs reconciliation, the DB row has already left InProgress and reconcile's `StatusInProgress` guard skips it. If you ever move `delete(r.sessions)` before `onFinish`, the tick could observe absence while the row is still InProgress and reconciliation would wrongly flip a cleanly-exited task to InReview. The skip is pinned by `TestReconcileSkipsNonInProgress`.
- **Reconciliation must distinguish RPC failure from empty running set.** `Client.Running()` returns `nil` on RPC error vs `[]string{}` when daemon confirms no sessions. Check `runningIDs != nil && !daemonRestarting` before reconciling — during restart the new daemon has no sessions, so reconciliation would incorrectly flip all InProgress tasks to InReview (a false termination).
- **Exactly one daemon may bind the socket — enforced by an flock, not the pid file.** `Serve` acquires an exclusive `flock` on `~/.argus/daemon.lock` (held for the process lifetime) after `killExistingDaemon` and before `net.Listen`. The pid-file kill is racy: when a launchd job (`com.drn.argus.daemon`, `RunAtLoad`) and the TUI's `AutoStart` both fire at login, both pass the pid check, both `os.Remove(sockPath)`+`net.Listen` (unlink+rebind always succeeds), and both end up listening — a **split-brain** where the agent session lives in one daemon's runner while the TUI's input/stream RPCs land on the other. Symptom: keyboard input vanishes (WriteInput hits the session-less daemon) and `StartSession` returns "session already exists" (hits the one that has it), with the stream handler logging "session not found" in a tight retry loop. The flock makes the losing daemon exit cleanly via `ErrDaemonAlreadyRunning` → `runDaemon` returns exit 0. Because the launchd plist sets `KeepAlive{SuccessfulExit=false}`, a clean (code 0) loss is NOT respawned. Never `os.Remove` the lock file (contenders must open the same inode); `cleanup` only `Close()`s the fd. `daemonLockTimeout` (default 2s) is a var so tests can shrink it; it exists to absorb the gap between `killExistingDaemon`'s async SIGKILL and the kernel releasing the dead process's flock. **Serial takeover (one daemon SIGTERMs its predecessor via `killExistingDaemon`, predecessor exits, successor binds) is expected and fine — the lock only forbids _coexistence_, not handoff.**
- **All daemon RPC calls must have a timeout.** `net/rpc.Client.Call()` blocks indefinitely. Use the `c.call()` wrapper with `select + time.After`. The buffered channel (`make(chan error, 1)`) is critical to prevent goroutine leak.
- **Stream loss ≠ process exit.** Use `StreamLost` flag to distinguish. When `isSessionAlive()` returns `reachable=false`, treat as stream lost, not exit. **The `<-rs.done` path in `connectStream`'s retry loop must also use `removeSessionStreamLost`** — `Client.Close()` during daemon restart closes `done`; using `removeSessionStreamLost` makes the intent explicit. (Defense-in-depth: `removeSession` now also forces `StreamLost=true` on ANY `GetExitInfo` RPC failure, so a zero-value ExitInfo can no longer read as a clean exit and wrongly Complete the task — but prefer the explicit StreamLost call here so the intent is local and obvious.)
- **`client.Get()` must return `nil` for any non-alive session.** Check `!info.Alive` alone — PID is stale between `onFinish()` and `delete(r.sessions)`.
- **Daemon health check uses `Ping()`, not `refreshTasks()`.** Ping fails fast; refreshTasks blocks on RPC.
- **Never call `refreshTasks()` from the tview main goroutine.** It blocks on RPC. Use `refreshTasksAsync()` (spawns goroutine + QueueUpdateDraw) or `refreshTasksLocal()` (reuses cached IDs, no RPC). Use `refreshTasksLocal` when only DB state changed (delete/prune); use `refreshTasksAsync` when session state may have changed.
- **Most `SessionHandle` reads on `RemoteSession` block on a `SessionStatus` RPC.** `PID`, `IsIdle`, `PTYSize`, `InitialPTYSize`, `WorkDir` all call `refreshInfo()` which fires the RPC. Don't call them from the tview main goroutine; do the read in a background goroutine and dispatch the result back via `QueueUpdateDraw`. Lock-free / local-only methods that ARE safe on the main goroutine: `Alive` (channel select), `Done`, `Err`, `RecentOutput`/`Tail` (local ring buffer), `AddWriter`/`RemoveWriter`. The `SessionHandle` interface doc enumerates this. `maybeKickRerender` was the regression that prompted this rule — it called `IsIdle()` and `InitialPTYSize()` from `onTaskSelect` and stalled the UI for the full RPC round-trip.
- **Never call `refreshTasksAsync()` between `db.Add(task)` and `startSession()`.** The async RPC snapshot captures running IDs before the session exists, then reconciliation sees InProgress + not-in-running-set → flips it to InReview (a false termination). Use `refreshTasksLocal()` instead (no RPC, no reconciliation race).
- **`refreshTasksAsync` (and any other async RPC->reconciliation path) must capture `startGen` before the RPC and check it in the callback.** Without this guard, a session exit calling `refreshTasksAsync` while another task is starting captures stale runningIDs that don't include the new session — reconciliation flips it to InReview (a false termination). Same guard pattern as `onTick`.
- **Task creation must call `SelectByID` before `onTaskSelect`.** The ordering is `refreshTasksLocal()` → `tasklist.SelectByID(id)` → `onTaskSelect(task)`. Without `SelectByID`, the cursor stays on the previous row — when the user exits agent view, the task list highlights the wrong task. `SelectByID` must come before `onTaskSelect` because agent view covers the task list; the cursor position matters on return.
- **`startSession` must bump `startGen` before `runner.Start()`.** The tick goroutine captures `runningIDs` via RPC independently — if it snapshots before the session exists, the stale IDs reach reconciliation (which runs on the tview goroutine AFTER startSession). `onTick` captures `startGen` before the RPC; the `QueueUpdateDraw` callback checks if it changed and passes `nil` runningIDs to skip reconciliation for that tick. Next tick gets fresh IDs.
- **Always use `RunningAndIdle()` instead of separate `Running()` + `Idle()`.** They share the same `ListSessions` RPC — calling both separately doubles RPC overhead and doubles head-of-line blocking risk on the single `net/rpc` connection.
- **Daemon cleanup must run on the `Serve` goroutine, not `Shutdown`.** `Shutdown()` runs on a non-main goroutine — process may exit before cleanup completes. `signal.Stop(sigCh)` must be called after the handler goroutine exits.
- **Daemon restart must preserve `SessionID` on tasks.** Clearing it loses conversation history. On re-launch, `--resume <id>` picks up where it left off.
- **Rebuilding the binary does NOT update the running daemon.** Kill and restart: `kill -TERM $(cat ~/.argus/daemon.pid)`. The TUI also detects this on startup (via `Daemon.BootInfo` RPC + binary mtime compare) and prompts the user with a Restart/Skip modal — but only when it connected to a pre-existing daemon, not one it just `AutoStart`-ed (the auto-started daemon was forked from the same binary, so a check would always falsely show "in sync").
- **`Daemon.BootInfo` records `os.Executable()` + `EvalSymlinks` at `New()`, NOT at `Serve()`.** The mtime captured must reflect the binary the daemon process was loaded from. Capturing at `Serve()` is fine in practice but capturing at `New()` is more obviously correct since it pairs with `bootedAt`. Both run before any RPC can be served, so neither racing with the staleness check is possible. The argusd symlink in `~/.argus/` is resolved via `EvalSymlinks` so the recorded path matches what the TUI's `os.Executable()` resolves to.
- **`onFinish` must fire before session removal.** Callback runs OUTSIDE `r.mu` (to avoid deadlock), then `delete(r.sessions)` in a second lock section.
- **`startSession` must revert state on Start failure but ONLY clear the SessionID it generated in this call.** Reset to Pending, zero StartedAt, and clear SessionID iff this call minted it (track with a `generatedSessionID` local). A pre-existing SessionID — from a prior successful run, e.g. a Claude task being resumed after a daemon restart cascade — must survive transient failures so the next retry can still `--resume` the conversation. Unconditional clearing was the cause of "after daemon+TUI reboot, pressing Enter started a fresh session with the original prompt re-injected" (the failed first restart wiped the saved ID, so the second Enter saw `SessionID==""` and went down the fresh-task path). `SetStatus(StatusPending)` doesn't clear StartedAt — explicit zero required.
- **Daemon session exits must be wired to TUI via `client.OnSessionExit`.** Without this, tasks stay InProgress forever in daemon mode.
- **`restartDaemon` must re-wire `OnSessionExit` on the new client.**
- **The tick reconciliation always lands stale InProgress tasks in InReview (never Complete).** (Supersedes a removed `daemonFreshStart` first-tick-vs-subsequent distinction: there is no longer a "Complete" branch — see the evidence-based-completion bullet at the top of this section. Startup orphans are handled separately by `ReconcileStaleSessions`, also → InReview.) The remaining job of the `runningIDs != nil && !daemonRestarting` + `recentStarts` grace guards is purely to avoid a FALSE reconciliation during RPC failure / restart cascade — they still apply.
- **Daemon restart cascade: health check must have a 30s cooldown between restart attempts.** Without the cooldown, each auto-resume failure triggers another restart, creating a feedback loop (13 restarts in 40 seconds observed). The cascade kills sessions that were just started, causing orphaned processes and stale `connectStream` goroutines. **Both restart paths must set `lastDaemonRestart`** — the health check path AND the manual Settings `OnRestartDaemon` callback. Without setting it on manual restart, the health check can trigger another restart immediately (no cooldown).
- **`onTick` must read `a.runner` under `a.mu`.** The tick goroutine reads `a.runner` for `RunningAndIdle()`. During a restart cascade, `restartDaemon`'s `QueueUpdateDraw` writes a new client to `a.runner` on the tview goroutine. Without synchronization, the tick can use a stale client whose `ListSessions` returns empty → reconciliation flips all InProgress tasks to InReview (a false termination).
- **`Client.Close()` must signal `closed` channel before closing sessions.** `connectStream` goroutines check `c.closed` at the top of each retry iteration. Without this, old goroutines from a replaced client keep connecting to the new daemon's socket, flooding it with "session not found" requests.
- **Reconciliation must skip tasks started within the last 5 seconds (`recentStarts` grace period).** Belt-and-suspenders alongside `startGen`. After a restart cascade, `ListSessions` can return stale data if the RPC goes to an intermediate daemon. The grace period protects recently-started tasks from false reconciliation.
- **SessionID must be populated before first `runner.Start` for Claude backends, and captured post-exit for Codex.** Claude uses `--session-id <uuid>` on first run and `--resume <uuid>` on subsequent runs. Codex captures its ID from `~/.codex/state_5.sqlite` after exit. Without a SessionID, `resume` is always false and every start is a fresh conversation.
- **Claude's SessionID is NOT pinned-once — it is re-captured on every exit so `/clear` is honored.** A Claude `/clear` mints a brand-new conversation UUID; the originally-pinned `--session-id` is now stale and resuming it reopens the *pre-`/clear`* conversation. `CaptureClaudeSessionID` delegates to `claudesession.List` (the single discovery/parse path for `~/.claude/projects/<encoded-cwd>/*.jsonl`) and returns its newest-activity-first top entry. `NeedsSessionRecapture` gates this: Claude → always recapture; Codex/Pi → only while SessionID is empty (their IDs are stable across resumes); unknown → never. **Encoding (`claudesession.EncodeProjectDir`) replaces every non-alphanumeric byte with `-` and does NOT collapse runs** — broader than `piEncodeCwd` (which only maps `/ \ :` and wraps in `--…--`); e.g. `/Users/x/.argus/wt` → `-Users-x--argus-wt`. **Newest-by-mtime is only correct because each Argus task owns a unique worktree** (so its project dir is scoped to that one task) **and sub-agent (Task tool) records interleave into the main transcript file** rather than spawning separate files — so no sidechain filtering is needed. On capture error the existing SessionID is kept (never clobbered); the write is skipped when the captured UUID equals the stored one (common no-`/clear` exit), avoiding redundant DB writes and log spam.
- **A manual session pick (Ctrl+R session switcher) must end with the chosen transcript as the newest-by-mtime file, or the next exit's auto-recapture reverts the pick.** `CaptureClaudeSessionID` is "newest mtime wins." Resuming a chosen session and doing any work appends to its `<uuid>.jsonl` and bumps its mtime, so the common "switch and keep working" flow converges (auto-heal agrees with the pick). The only revert window is "pick an OLDER session, then exit before that session's transcript becomes newest" — guard it by `os.Chtimes`-bumping the chosen transcript at select time. Both the switcher and this fix now share one parser: `internal/agent.CaptureClaudeSessionID` delegates to `claudesession.List` (deduped 2026-06-05; the agent-side `claudeEncodeCwd` and `<uuid>.jsonl` regex were removed). `List` orders by newest activity (max message timestamp, file-mtime fallback), so the `os.Chtimes`-bump guidance still applies.
- **Both exit sites gate Claude recapture on `NeedsSessionRecapture`, NOT on `SessionID == ""`.** The daemon's `captureSessionIDPostExit` and the TUI's `handleSessionExitUI` capture goroutine both dropped the old `SessionID != ""` short-circuit (Claude's ID is always non-empty). The TUI snapshots the task whenever `Worktree != ""` and makes the recapture decision *inside* the goroutine so the filesystem read never blocks the tview main goroutine.
- **Codex/Claude session ID capture (`CaptureCodexSessionID` / `CaptureClaudeSessionID`) must run off the tview main goroutine.** They open a SQLite connection / read a directory which can block. Use a background goroutine + `QueueUpdateDraw` to persist.
- **Self-update (`Daemon.UpdateSelf`) must NOT shut down the daemon itself.** The RPC only runs `go install`. The TUI calls `restartDaemon()` after a successful update, and the web API spawns a successor daemon inside a goroutine after the HTTP response is flushed. Shutting down inside the RPC handler would close the connection before the client receives the install output.
- **The web `POST /api/update` must flush the success response before spawning the successor.** Once the new daemon's startup runs `killExistingDaemon`, the current process gets SIGTERM and any pending HTTP write disappears. The handler writes the JSON, calls `Flusher.Flush()`, then sleeps 500ms in a goroutine before `exec.Command(os.Executable(), "daemon", "start")`.
- **`UpdateSelf` RPC must use a long timeout — the default 2s `rpcTimeout` will always trip.** `go install ./...` regularly takes 30s+ on a cold module cache. The client wraps `Daemon.UpdateSelf` with `callWithTimeout(...updateSelfTimeout)` (10 minutes); without this override the TUI returns `ErrRPCTimeout` even though the daemon-side build keeps running and eventually completes, leaving the user with a fresh binary on disk and a stale daemon still running.
- **`os.Executable()` after `go install` resolves to the freshly-installed binary.** On macOS `go install` writes to a temp file and renames it over `$GOBIN/argus`, so the path stored in the running process still resolves to the new bytes. `spawnSuccessorDaemon` relies on this to exec the new daemon via `exec.Command(os.Executable(), "daemon", "start")` after a successful update.
- **`onTaskSelect(task, autoStart)` auto-starts sessions when `autoStart=true` for any non-complete, non-archived task without a running session.** No explicit `startSession` call is needed after `onTaskSelect` — adding one causes a double-start. Pass `autoStart=false` for navigation-only entry (e.g., `navigateAgentTask`). The "user left pending view" path in `handleNewTaskKey` is the one exception (calls `startSession` without `onTaskSelect`). Condition excludes completed and archived tasks.
- **`selfupdate.Run` uses `git fetch origin master` + `git reset --hard origin/master`, not `git pull --ff-only`.** The source clone exists only to produce binaries — we don't preserve local commits or care about the current branch's tracking state. Using `pull --ff-only` made update fail with "no tracking information for the current branch" whenever the clone happened to be on a feature branch with no upstream. Reset-hard is destructive but intentional: whatever's on origin/master is exactly what gets installed.
- **`clipboard.Store` lives on `Daemon` and is shared with both the API server (HTTP + SSE subscribe) and the MCP server (`argus_clipboard_set` tool) via interfaces.** In-process TUI (no daemon) has no clipboard — the feature is gated by a `clipboardAccessor` type assertion on `agent.SessionProvider` and stays dormant when the assertion fails.
- **Subscribers in `clipboard.Store.Subscribe` MUST `defer unsubscribe()` immediately after registration.** Without it, an HTTP handler that returns through any non-loop path leaks the subscriber callback, and subsequent Set/Clear calls keep firing into a no-longer-drained buffered channel until it overflows and starts dropping (silently broken UI updates).
- **Daemon test names that hit Unix sockets MUST stay short.** macOS `sun_path` caps at 104 bytes; with the `/var/folders/...TestName123456789/001/test.sock` template, names longer than ~30 chars trip the limit and the daemon's listener silently fails to bind. `waitForSocket` returns "socket did not appear" 5 seconds later. Use abbreviations like `TestDaemon_Clip` instead of `TestDaemon_ClipboardRoundTrip`.
- **LaunchAgent `Install()` must bootout an already-loaded job before bootstrapping the new plist.** `launchctl bootstrap` errors with `Bootstrap failed: 37: The specified service is already loaded` if the label is already in the gui/$UID domain. The probe is `launchctl print gui/$UID/<label>` (exit 0 = loaded); on success bootout first, then bootstrap. Skipping bootout silently leaves the OLD plist active — the user thinks the rebuild is wired in but launchd is still running the previous binary path.
- **The LaunchAgent plist's `ProgramArguments[0]` must point at a stable path that survives `go install`.** Use the `~/.argus/argusd` symlink (created by `EnsureDaemonSymlink`), not `os.Executable()` directly. `go install` rewrites `$GOBIN/argus` via tmp+rename, so the symlink target stays valid; pinning the plist to the resolved binary path also works but locks the plist to whichever GOBIN was active at install time. Reinstall after relocating the binary.
- **`StreamHeader.Since` must be set to `rs.buf.TotalWritten()` on every stream attach, not just first connect.** Without `Since`, every reconnect (network blip, daemon restart, kick-restart gap, retry budget) replays the full daemon ring on top of bytes the client already has in its local ring — x/vt re-emulates the duplicated cursor-position sequences and renders a stale status bar overlapping the live one. The HTTP `/stream?since=N` endpoint already does this via `AddWriterFrom`; the daemon Unix-socket stream gets the equivalent by routing through `AddWriterFromTolerant` with `header.Since`. Client uses `rs.buf.TotalWritten()` (lock-free atomic) at attach time so retries skip bytes already received.
- **Use `AddWriterFromTolerant`, not `AddWriterFrom`, for net.Conn-backed writers (daemon stream).** `AddWriterFrom` holds `s.mu` through the replay so it can guarantee gap-free attach at exactly `offset` — but the constraint is that `w.Write` MUST NOT block, or readLoop stalls waiting on the same mutex. `conn.Write` to a Unix-socket peer can block on kernel socket flow control (typical 256KB send buffer, but partially filled if there are multiple slow writers attached). `AddWriterFromTolerant` mirrors `AddWriter`'s pattern: snapshot replay under lock, release, write replay, re-acquire briefly to append the writer — accepting a tiny gap (≤ one readLoop iteration's bytes) in exchange for non-blocking-writer safety. Use `AddWriterFrom` for the API's channelWriter (drop-on-full, non-blocking); use `AddWriterFromTolerant` for raw network conns. RemoteSession (TUI client) no-ops both since streaming is daemon-side.
- **`KeepAlive { SuccessfulExit = false }` is the right policy — `KeepAlive: true` would fight `argus daemon stop`.** With unconditional KeepAlive, every clean shutdown immediately respawns the daemon, making `daemon stop` and `daemon restart` racy. The dict form makes launchd respect zero-exit shutdowns while still recovering from crashes.
- **`runDaemon` must `os.Chdir($HOME)` at startup — the daemon's cwd would otherwise be non-deterministic.** `agent.CreateWorktree` chdirs the project path for `git worktree add`, so a relative project path (e.g. one a sloppy autocomplete stored) only resolves when the daemon's cwd matches where it was created — `$HOME`. The launchd plist sets `WorkingDirectory=$HOME`, but the TUI's auto-start fallback (`internal/daemon/client/autostart_fork.go`) execs the daemon without `cmd.Dir`, so it inherits wherever `argus` was launched (a repo dir, when running a local build). Symptom: agents silently fail to spawn with `chdir <relative>: no such file or directory` only under the auto-started daemon, never the launchd one. Pinning cwd in `runDaemon` makes both launch paths behave identically. Non-fatal (absolute paths work regardless); logged to `daemon.log`. The real fix for the relative path is absolutizing it at the source (see `gotchas/worktree.md`) — this is defense-in-depth.
- **The LaunchAgent plist MUST include an `EnvironmentVariables` block that sets PATH explicitly, with `$HOME/.local/bin` baked in literally.** launchd starts processes with a bare `/usr/bin:/bin:/usr/sbin:/sbin` and does NOT expand `$HOME` inside the plist's `EnvironmentVariables` dict. When the daemon forks a child via `sh -c 'claude --resume <uuid>'`, the shell resolves PATH against whatever the daemon inherited — and the native `claude` binary installs to `~/.local/bin/claude` (Anthropic's installer default), which isn't on launchd's bare PATH. Symptom: every `--resume` (and every fresh `--session-id` task) fails with `exit status 127` and 31 bytes of output literally reading `sh: claude: command not found`, but only under the launchd-spawned daemon — daemons started from a terminal-launched `argus` work because they inherit the shell's PATH. The fix is in `renderPlist` (cover `<home>/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, plus the standard four); after editing, the user must reinstall the agent (bootout + bootstrap) so the new plist is actually loaded — the running daemon won't pick up the PATH change.
- **`inputLoop`'s drain MUST stop at bracketed-paste boundaries.** Two back-to-back `WriteInput` calls each carrying a complete `\x1b[200~..\x1b[201~` cycle (one paste per file when the outer terminal splits a multi-file drag-drop) get coalesced into one RPC and arrive at the PTY as one buffer; the inner CLI's bracket-paste parser then treats the second `[200~` as starting a fresh paste that replaces the first, dropping all but the last file. `drainInput` checks `bytes.HasSuffix(buf, "\x1b[201~")` and flushes immediately when the boundary is reached, sending each paste cycle as its own RPC. The fix preserves coalescing for plain typing.
- **Any helper that fork/execs `os.Executable()` with `daemon start` MUST refuse when running under a `*.test` binary.** Both `client.AutoStart` (TUI restart path) and `api.spawnSuccessorDaemon` (web `/api/update` path) check `isTestBinary()` and return a sentinel error (`ErrTestBinary` / `errSpawnFromTestBinary`). Without the backstop the forked child is the test binary itself — Go's test framework treats `daemon start` as positional args, runs `m.Run()`, and re-hits the test that triggered the fork, spawning another orphan. Two real fork bombs were observed (one in `internal/tui` from `TestApp_HandleRestartDaemonKey_RestartChosen`, one in `internal/api` from `TestSpawnSuccessorDaemon`), each pegging multiple CPU cores at ~85% and **overwriting the user's real `~/.argus/argusd` symlink** to point at a temp test binary that vanished when the test ended. Tests that exercise these paths must (a) override the call site (e.g. `App.restartDaemonFn`) where possible, (b) assert the backstop fires, and (c) still `t.Setenv("HOME", t.TempDir())` as defense in depth.
- **The PR-status poller goroutine body is extracted into `runPRPoller` so its `d.done`-gated exit is testable WITHOUT binding a socket.** `Shutdown()` blocks on `<-d.ready`, which only `Serve` closes — so a shutdown test that goes through `Serve`/`Shutdown` needs a real Unix socket (and trips the macOS 104-byte `sun_path` limit / "socket did not appear" flakes). The fix is to launch `runPRPoller` directly in the test and `close(d.done)`; that is exactly what every gated goroutine sees on real shutdown. Mirror this for any future `d.done`-gated background loop rather than spinning up `Serve`.
- **The poller only touches non-archived tasks that have a non-empty `Branch`, under a bounded worker pool (`prPollConcurrency`, ≤4 concurrent `gh` procs).** Eligibility is computed up front so the logged count is exact; archived or branchless tasks are never fetched and never get a `pr` meta row. The per-tick work lives in `pollPRStatesOnce` so tests drive a single pass instead of racing the 60s ticker.

- **`BuildCmd` MUST force `TERM=xterm-256color` + `COLORTERM=truecolor` onto every agent spawn — agents inherit the daemon's env, and a launchd-started daemon has NO TERM at all.** The LaunchAgent plist's `EnvironmentVariables` sets only PATH; launchd's bare env carries no terminal identity. Agents spawned/resumed by such a daemon detect "no color support" and render monochrome (Claude falls back to reverse-video-only output — PTY logs show `[7m`/`[27m` as the only SGR). Daemons auto-started by the TUI inherit the user's shell env, so color survived some restarts and not others, which disguised the bug as "color randomly lost after rebooting argus" and got it conflated with the unrelated OSC 0x9C title leak (both surfaced after restarts). The agent's controlling terminal is argus's in-process x/vt emulator (truecolor-capable) regardless of daemon provenance, so forcing both keys is always correct. Later entries win per `exec.Cmd.Env` dedup semantics.

## Session-supervisor (P1 — dark binary)

- **The supervisor lives in package `daemon` (`supervisor.go`), NOT a new package — and it must.** Its exit-caching-only `onFinish` writes `core.exitInfos` and closes `core.streams`, and its `cleanup` calls `core.runner.StopAll()`; `sessionCore`'s `exitInfos`/`streams`/`mu`/`runner` are all unexported, so a separate package literally cannot mount the core. Same-package reuse is what makes the supervisor share the daemon's R/S protocol (`handleStream`, the 10 promoted session RPCs), singleton helpers, and types byte-for-byte. P1 is purely additive: nothing connects, the daemon is untouched (still uses its in-process runner).
- **The supervisor's singleton trio is fully independent of the daemon's and must stay that way.** `Supervisor.Serve` passes its OWN socket (`~/.argus/supervisor.sock` → `singletonPathsForSock` → `supervisor.pid`/`supervisor.lock`) to `killExistingDaemon(sp.pid)` + `acquireSingletonLock(sp.lock,…)`. `killExistingDaemon` here targets ONLY the supervisor pid; it can never SIGTERM the daemon, and the daemon's own takeover never touches the supervisor's flock/pid. Two independent flocks = no split-brain (P0 proved two locks coexist; `lock_test.go:TestSingletonPaths_IndependentLocks`). A daemon bounce leaves the supervisor — and every agent — alive.
- **The supervisor's `onFinish` is exit-caching-ONLY — never give it the daemon's DB-flipping closure.** It builds the same `ExitInfo{Err,Stopped,LastOutput,PendingRestart}` and closes stream conns (so the shape crossing supervisor→daemon is identical to daemon→TUI today), but does NOT flip task status, recapture session IDs, clear the clipboard, or emit events — the supervisor has no DB. Because the supervisor is the always-parent, its `Cmd.Wait()` observes the REAL exit code, so #707's `ExitInfo.CleanExit()` distinction (clean self-exit vs crash vs stop) is preserved structurally; P2's daemon fetches the cached `ExitInfo` via `GetExitInfo` and does the flip. Like the daemon's, the closure captures a not-yet-assigned `*sessionCore` by reference and reads it only post-exit (after `core = newSessionCore(...)` has run) — same happens-before as `Daemon.New`.
- **The supervisor holds NO database handle — it takes a `cfgFn func() config.Config` instead.** `runner.Start` needs backends to `BuildCmd`, so `cmd/argus session-supervisor start` opens the DB solely to inject `database.Config` as the supervisor's `cfgFn`; the `*Supervisor` type stays free of persistence coupling. A nil `cfgFn` falls back to `config.DefaultConfig` so the binary is runnable and tests stay DB-free. (P2 may instead carry config in an expanded `StartReq`; that's a deferred protocol decision.)
- **The R/S protocol is versioned from day one via `Hello` (`ProtocolVersion` const + `HelloResp`), registered under service name "Daemon".** Registering under "Daemon" (not "Supervisor") is deliberate: a future supervisor-client (P2) drives the supervisor with the EXISTING `internal/daemon/client` code unchanged. The protocol is additive-only — bump `ProtocolVersion` when adding an RPC/field, never remove or repurpose, because `go install` + daemon restart does NOT restart a live supervisor, so a newer daemon must talk to an older supervisor (design §4.4). `status` subcommand reports the version; the supervisor exposes `Hello`, the daemon does not (distinct surface).
- **The supervisor forks PTY children, so `runSupervisor` MUST redirect slog + stdlib log to `~/.argus/supervisor.log` before serving (via `configureProcessLogging`), and never write fd 1/2 after startup.** Mirrors `runDaemon`'s inline redirect; the daemon relies on detached-stderr=/dev/null but the supervisor must be safe both detached (P2 Setsid-fork) and foreground (manual/test `start`). No Dup2 is needed (unlike the TUI — there's no alt-screen to corrupt); the two `slog.SetDefault`/`log.SetOutput` calls are the whole guard, pinned by `cmd/argus:TestConfigureProcessLogging_DoesNotReachStderr`.

## Session-supervisor (P2 — daemon connects, default-OFF flag)

- **`cfg.Supervisor.Enabled` is the gate (default false ⇒ in-process runner, byte-identical to pre-P2).** Parsed in `db/config.go` from `kv["supervisor.enabled"]` (mirrors `kb`/`api`/`hera`; absent ⇒ false), with the `config.toml` overlay winning over the DB. When OFF the daemon's `New` mounts an in-process `*agent.Runner` exactly as before and the entire ON path below is dead code; the OFF proof is the unchanged daemon/api/agent suites.
- **`d.runner` is typed `agent.SessionRunner` (a SessionProvider superset), NOT concrete `*agent.Runner`.** SessionRunner adds the four methods the daemon's API server + resize/resume paths drive beyond SessionProvider: `StartOrReattach`, `KickRerender`, `NeedsInputIDs`, `SetNeedsInputIDs`. `*agent.Runner` already satisfies it (so OFF is unchanged) and the supervisor-client `*client.Client` now does too (so it can BE `d.runner`). The remote-TUI `apiclient.Provider` deliberately stays on the narrower SessionProvider — widening SessionRunner never forces the HTTP client to grow methods it can't serve. `sessionCore.runner`, `api.Server.runner`, and `api.New`'s param all moved to the interface.
- **The daemon CANNOT import `internal/daemon/client` (client imports daemon — cycle), so the supervisor-client is INJECTED via the `daemon.SupervisorClient` interface + `Daemon.UseSupervisorRunner`.** `cmd/argus/runDaemon` reads the flag, builds the client (`connectSupervisor`), and calls `d.UseSupervisorRunner(c)` BEFORE `d.Serve` so every consumer (sessionCore RPC, depswatcher, scheduler, MCP, API, notifier) captures the client. `UseSupervisorRunner` reassigns `d.runner = c`, sets `d.supClient = c`, and wires `c.OnSessionExit(d.handleSessionExit)`. The in-process runner `New` created is left dormant (never starts a session, so its onFinish never fires).
- **Exit handling is one sink — `Daemon.handleSessionExit(taskID, ExitInfo)` — fed by BOTH modes.** OFF: the in-process runner's onFinish builds ExitInfo from the real `Cmd.Wait` (StreamLost always false) and calls it. ON: the supervisor-client's `OnSessionExit` relay calls it with the ExitInfo it fetched from the supervisor via `GetExitInfo`. #707 is preserved structurally — the supervisor is the always-parent, observes the real exit code, caches it (P1), and the daemon runs the UNCHANGED `transitionTaskOnExit`/`CleanExit()` against its DB.
- **`handleSessionExit` short-circuits on `StreamLost`: it caches the StreamLost ExitInfo but does NOT flip status or recapture.** A lost relay means the process MAY still be alive on the supervisor, so flipping to Complete/InReview would violate #707 ("Complete only on an observed clean exit"). Caching the *StreamLost* ExitInfo (not skipping the cache) is load-bearing: the daemon's own TUI clients fetch it via `GetExitInfo`, and an empty ExitInfo would `CleanExit()==true` and wrongly Complete the task. The `GetExitInfo`-RPC-failure ⇒ force `StreamLost` backstop (client `removeSession`) now guards the supervisor→daemon boundary exactly as it has always guarded daemon→TUI — so a failed relay propagates as StreamLost across BOTH hops, never as a fabricated clean exit.
- **`Daemon.cleanup` is mode-aware: ON mode `Close`s the client and does NOT `StopAll` (or write the bounce file).** This is the whole point of the supervisor — its agents MUST survive the daemon bounce. `d.supClient != nil` selects the branch: supervised ⇒ detach only; in-process ⇒ the pre-P2 `writeLiveTasksFile` + `StopAll`. Pinned by `TestCleanup_SupervisorMode_DoesNotStopAgents` (fake SupervisorClient asserts `StopAll` not called, `Close` is) and its OFF counterpart.
- **Recapture stays DAEMON-side on the exit relay (design §5, NOT the §8 "supervisor-runs" recommendation).** `handleSessionExit` fires `go d.captureSessionIDPostExit` for non-StreamLost exits — same code OFF and ON. Rationale: the supervisor is DB-free and doesn't retain task backend/worktree info post-exit; the daemon already has a working capture against its DB + the worktree, which lives on the shared filesystem both processes see (`~/.claude`, `~/.codex`, the worktree dir), and the relay only fires AFTER the supervisor observed `Cmd.Wait`, so the backend state file is already written. Zero protocol change, no double-capture, no supervisor DB coupling. StreamLost skips it (process may still be alive → reading "post-exit" state would be premature).
- **Config reaches the supervisor via its `cfgFn` (P1 DB read), NOT an expanded StartReq.** `BuildCmd` consumes a broad slice of `config.Config` (backends map, defaults, per-project sandbox/backend overrides, global sandbox); shipping it per-`StartSession` would either serialize most of the config schema on the wire (coupling the "frozen" protocol to config — the opposite of the goal) or force a `BuildCmd` refactor out of P2 scope. cfgFn keeps the protocol frozen; the supervisor's infrequent `Config()` reads are SQLite-multiprocess-safe. (`StartReq`-carried config remains a possible future cleanup if the no-DB constraint ever hardens.)
- **The supervisor-client generalizes `internal/daemon/client` for a SECOND consumer (the daemon), so `RemoteSession` now FANS OUT.** Pre-P2 `RemoteSession.AddWriter*` were no-ops (the TUI polls `RecentOutputTail`). For the double-proxy (supervisor `readLoop` → daemon RemoteSession ring → daemon `handleStream` → TUI conn), the stream reader now tees incoming bytes to a real `writers` set mirroring `agent.Session.readLoop` (snapshot under lock, write outside it so a blocking net.Conn can't stall the reader, drop errored writers). The original TUI consumer never registers writers, so the fan-out is dormant there — bytes still land in the ring for pollers. `ListSessions` likewise branches on a capability assertion: in-process runner → iterate live `*agent.Session` (byte-identical); supervisor-client → relay the supervisor's already-built `SessionInfo` via `ListSessionInfo` (the daemon can't iterate the supervisor's in-process sessions).
- **`KickRerender` is the one additive RPC (ProtocolVersion 1→2) — it cannot be composed client-side from Stop+Start.** The runner's `pendingRestart` bookkeeping (which keeps the intervening exit from flipping task status) MUST run where the session lives, so the client RPCs `Daemon.KickRerender` (carrying the task projection; cfg resolved supervisor-side via cfgFn) to the supervisor's real runner. Against a v1 supervisor the method is absent and the RPC errors — `api.maybeKickRerender` already treats a kick error as a non-fatal no-op, so an older supervisor degrades to "no rerender" rather than breaking. The TUI's own kick path is unaffected (it does `sess.Stop()` + a local `pendingRerenderRestart` flag, never `Daemon.KickRerender`).
- **Auto-start + version-skew: the daemon `Setsid`-forks `session-supervisor start` when supervisor.sock has no live Ping, then handshakes via `Hello` — and NEVER auto-restarts a live supervisor on protocol skew.** `client.AutoStartSupervisor` mirrors `AutoStart` (same `*.test` fork-bomb backstop; `buildSupervisorStartCmd` is split out so a test asserts the argv + Setsid without forking). `connectSupervisor` requires a successful `Hello` before committing (a half-broken supervisor is worse than the in-process fallback) and on skew logs + proceeds within the running supervisor's capabilities — restarting it would SIGHUP its agents (design §4.4). The skew decision is the pure `daemon.SupervisorProtocolMatch` so it's unit-testable (the connect glue forks/dials and is coverage-exempt). Any supervisor-connect failure falls back to the in-process runner — a broken supervisor must never take the daemon offline.
- **P2 does NOT change bounce/re-attach (that's P3).** In ON mode a daemon restart still runs the existing `ReconcileStaleSessions` (flips orphan InProgress→InReview) — for the common first-start case it's a no-op, and re-attaching live supervisor sessions instead of flipping them is P3's job. P2 only proves the daemon can DRIVE agents through the supervisor while both run.

## Session-supervisor (P3 — re-attach live sessions on daemon bounce, ON-mode only)

- **`Daemon.ReconcileOnStartup()` is the single mode-aware startup reconcile — Serve calls it (and tests drive it directly so they never bind a socket).** It replaced the three inline `ReconcileStaleSessions` + `ReconcileBindings` + `replayBounceSignals` calls in `Serve`. OFF (`d.supClient == nil`): byte-identical to pre-P3 — flip EVERY stale InProgress→InReview, then `replayBounceSignals` from the live-tasks file. ON (`d.supClient != nil`): `reattachSupervised` (below). `heraadopt.ReconcileBindings` runs in BOTH modes (keyed on task-row existence, not session liveness — a re-attached task's row exists so its hera binding survives the bounce for free; pinned by `TestReconcileOnStartup_Supervised_ReattachLiveFlipOrphan`). The OFF replay-from-file path stays exclusive to OFF: supervisor-mode `cleanup` never writes the file, so the file branch would only ever double-fire.
- **ON-mode re-attach startup order (design §3.4): query live set → re-attach (arm relay) → reconcile ONLY true orphans → signal ONLY orphans.** `reattachSupervised` calls `d.supClient.Running()` for the supervisor's authoritative live task-ID set, calls `Get(id)` on each live ID to re-attach, then `agent.ReconcileStaleSessionsExcept(db, liveSet)` flips InProgress→InReview for tasks NOT in the live set (true orphans — the supervisor also died/restarted), then `sendBounceSignals` posts `ARGUS_BOUNCED` to those orphans only. Re-attached tasks stay InProgress and get NO signal (they were never interrupted). Pure re-attach (supervisor kept everything) ⇒ zero flips, zero signals.
- **The re-attach `Get(id)` loop is LOAD-BEARING for #707 across the bounce — not just for output replay.** `Get` opens a stream (`StreamHeader{Since:0}`, supervisor replays its ring, daemon local ring rebuilds) AND — critically — arms the supervisor-client's exit relay (`connectStream` → `removeSession` → `OnSessionExit` → `handleSessionExit`). Without an armed relay, a re-attached session that later exits cleanly while NO TUI/PWA client is attached would never reach `handleSessionExit` and the task would never flip to Complete. So the daemon must eagerly `Get` every live session on startup, not wait for a client to attach. Proven by `TestSupReattachComplete` (real Supervisor + bounce + sentinel-gated clean exit → Complete).
- **`Running()==nil` (RPC failure) MUST skip the ON-mode reconcile entirely — do not treat it as "no sessions alive".** The real `*client.Client.Running()` returns `nil` on RPC error vs a non-nil (possibly empty) slice when the supervisor authoritatively reports its set. `reattachSupervised` bails on nil (logs, flips nothing): flipping live agents to InReview on an unconfirmed empty set is a false termination. An authoritative empty set (supervisor up but holding nothing — e.g. it crashed and restarted clean) IS non-nil, so genuine all-orphan cases still reconcile + signal. Mirrors the TUI's `runningIDs != nil` guard. Pinned by `..._LiveSetQueryFails_SkipsReconcile` (nil) and `..._AllOrphans` (empty).
- **`agent.ReconcileStaleSessionsExcept(db, alive)` is the reusable primitive; `ReconcileStaleSessions` is now a thin `Except(db, nil)` wrapper.** It flips InProgress→InReview for every task EXCEPT those in `alive` and RETURNS the flipped IDs (the true orphans) so the caller signals exactly them. Nil `alive` ⇒ flips all (the in-process equivalent). `sendBounceSignals(db, ids)` is the extracted ARGUS_BOUNCED inner loop shared by `replayBounceSignals` (file-fed, OFF) and `reattachSupervised` (orphan-fed, ON).
- **OFF mode is byte-identical to pre-P3 — proven by the unchanged `replayBounceSignals`/`writeLiveTasksFile` suite passing.** The flag gates the entire re-attach path via `d.supClient != nil`; no behavior change when the supervisor is disabled.

## Session-supervisor (P4 — default ON + rollback)

- **`cfg.Supervisor.Enabled` now defaults to TRUE (absent key ⇒ supervisor mode), mirroring `hera.enabled` exactly.** The base value moved to `true` in `config.DefaultConfig` (NOT in `db/config.go`, whose parse logic is unchanged — absent key inherits the now-true default, explicit `"true"`/`"false"` still win). The OFF (in-process) path is the same code as P2/P3 and is **retained one release as the supported rollback**, NOT deleted: an explicit `supervisor.enabled = false` in the DB or `config.toml` restores the daemon's in-process runner (byte-identical to pre-P2). config.toml still wins over the DB, so a power user's `[supervisor] enabled = false` is a valid rollback even with the DB unset (`TestDB_Config_SupervisorTOMLRollback`).
- **Operational model after the flip: restarting the DAEMON is cheap, restarting the SUPERVISOR interrupts agents.** A daemon bounce (upgrade, config change, self-update, crash) re-attaches to the live supervisor sessions (P3) — the in-flight turn survives. Only `argus session-supervisor stop`/restart SIGHUPs the agents (PTY master close). So: iterate on coordination by bouncing the daemon freely; touch the supervisor only when its (frozen, versioned) protocol genuinely changes, and never auto-restart a live supervisor on version skew (P2, design §4.4).
- **Cold start with the default ON: no daemon + no supervisor → TUI launch auto-starts the daemon → the daemon auto-starts the supervisor → agents run under it.** `cmd/argus/runDaemon` reads the now-true default, calls `connectSupervisor` (Connect, else `AutoStartSupervisor` Setsid-fork, then `Hello`), and `UseSupervisorRunner`s the client before `Serve`. The `*.test` fork-bomb backstop (`AutoStartSupervisor` ⇒ `ErrTestBinary` under `go test`) keeps a test run from re-exec'ing the test binary as `session-supervisor start`. `TestSupColdStart` (client pkg) pins the full ordering in isolation: absent-socket Connect fails → AutoStartSupervisor refuses (backstop) → an in-process Supervisor stood up on the same socket → Connect+Hello succeed → mount makes supervisor mode active (`d.Runner()` is the client) → a session round-trips supervisor→daemon to Complete. Any connect failure still falls back to the in-process runner — a broken supervisor never takes the daemon offline.
- **OFF→ON migration (the one-time transition the default flip creates): the first supervisor-mode start DISCARDS any stale `live-tasks-at-shutdown.json` the last in-process run wrote.** Those old in-process agents died with the old daemon; `reattachSupervised` orphans + signals their rows exactly once (the fresh supervisor reports an authoritative empty live set). The leftover file would otherwise sit unread (ON mode skips `replayBounceSignals`) and double-fire on a later ON→OFF rollback, so `ReconcileOnStartup`'s supervisor branch calls `discardStaleLiveTasksFile`. No data migration is needed — sessions are `--resume`-able; subsequent starts are pure supervisor-mode re-attach. Pinned by `TestReconcileOnStartup_Supervised_FirstStartAfterOffRun` (stale row → InReview + exactly one ARGUS_BOUNCED + file removed). `discardStaleLiveTasksFile` is defensive cleanup, not a new mechanism; supervisor-mode `cleanup` never writes the file.
- **#707 cache-vs-EOF race (P4 e2e caught it; PRE-EXISTING on master, fixed here): `handleStream` MUST wait for the exit-info cache before returning, or a crashed task wrongly flips Complete.** A session's stream conn gets closed by TWO racers off the same `sess.Done()`: (1) `handleStream` returning on its `<-sess.Done()` arm → `handleConn`'s `defer conn.Close()` → the stream client sees EOF and fetches `GetExitInfo`; (2) the runner's exit goroutine running `onFinish`, which caches the ExitInfo (the real `Err`) and THEN closes the conns. `sess.Done()` closes in `waitLoop` BEFORE `onFinish` runs, so if (1) wins the client's `GetExitInfo` reads **"not found" → a zero-value ExitInfo → `CleanExit()==true` → Complete**. The `GetExitInfo`-RPC-**failure** backstop does NOT cover this: the RPC SUCCEEDS, it just returns empty (the cache wasn't written yet). Fix: `handleStream`'s `<-sess.Done()` arm calls `awaitExitInfoCached(taskID, 5s)` (poll `c.exitInfos` every 2ms) before returning, so the EOF the client observes is always strictly post-cache. The race is general — it bites daemon→TUI (OFF) identically, which is why master flaked. Proven deterministically: a temporary 150ms sleep before the cache write made `TestSupCrash` flip Complete with `removeSession err="" cleanExit=true rpcErr=<nil>` (RPC succeeded, empty payload); the fix makes it `err="exit status 1" cleanExit=false` → InReview even WITH the widening delay. Pinned by `TestSupCrashRelayErr` (relay delivers `Err!="" && !CleanExit`). P2's matrix used SYNTHETIC ExitInfo at `handleSessionExit`, so it never exercised the fetch-races-cache window — the e2e crash test is the first real crashing process through supervisor→GetExitInfo→transition.
- **`RemoteSession.close()` MUST be idempotent (`sync.Once`), like `Client.closeOnce`.** The session's own `connectStream` goroutine (on exit/stream-loss) and `Client.Close()` (iterating every session on shutdown — test cleanup, `restartDaemon` client swap, supervisor-mode daemon cleanup) race to close the same `done` channel. The old `select{<-done: default: close(done)}` was a non-atomic check-then-close — two racers both took the default → "close of closed channel" panic under parallel -race load (PRE-EXISTING on master). Mirrors the `Client.closeOnce` fix one level down. Pinned by `TestH_CloseIdempotent` (50 concurrent `close()` callers, no panic).
- **`callWithTimeout` MUST guard `c == nil || c.rpc == nil` BEFORE spawning the dispatch goroutine — a nil rpc deref there is an UNRECOVERABLE process-killing SIGSEGV.** The dispatch is `go func() { ch <- rpc.Call(...) }()`; the deref happens in a DETACHED goroutine, so no `recover` (not the main-goroutine `defer recover`, not a test's) can catch it — it crashes the whole binary. A normal `Connect`'d client always has a non-nil `c.rpc` (set once in the constructor literal, NEVER reassigned), so this never fires in production; but a partially-constructed client (`rpc` never set, still its zero value — e.g. the `&Client{closed: ...}` test scaffolds, or a teardown race leaving a lingering `inputLoop`/`connectStream` goroutine holding such a client) turns a recoverable "no connection" into a SIGSEGV. (`rpc` is set once in the constructor and is NOT nilled on `Close`, so the unlocked read stays race-free.) The guard returns `ErrClientClosed`, which every caller already handles as an ordinary RPC failure (log + safe default; `removeSession` forces `StreamLost`, preserving #707). Capture `rpc := c.rpc` once and call `rpc.Call` (not `c.rpc.Call`) in the goroutine. Diagnosing it from a stack: a nil `c.rpc` faults with `net/rpc.(*Client).send`/`.Go(0x0,...)`/`.Call` frames ABOVE `callWithTimeout.func1`; a nil `c` receiver instead faults at the field-load with NO net/rpc frames — both are covered by the single guard. Pinned by `TestC_CallNoRPC` (direct call, nil receiver, a background `inputLoop` on an rpc-less client, and `Close()` on one all return cleanly, no crash). `Close()` is nil-rpc-guarded the same way (`if c.rpc != nil { c.rpc.Close() }`) so a partial client can't panic on shutdown either. **This is NOT a use-after-close bug: concurrent `rpc.Call` + `rpc.Close()` on a live jsonrpc client is safe (`net/rpc` serializes via its mutexes) — only an absent/zero rpc faults.**
