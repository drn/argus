## Context

Today, `internal/agent.BuildCmd` (`internal/agent/agent.go` ~L662-723) gives Claude-backend sessions two things no other backend gets, both gated strictly on `IsClaudeBackend(backend.Command)`:

1. `--add-dir <workspace>` pointing at `internal/skills.EnsureBuiltinSkills()`'s materialized output (`~/.argus/skills/.claude/skills/<name>/SKILL.md`), so Claude Code auto-loads argus's builtin skills.
2. `--append-system-prompt-file <path>` pointing at `internal/routing.EnsureBuiltinRouting()`'s materialized output — the hera/argus-task orientation prose.

On top of that, Claude Code itself natively auto-discovers `CLAUDE.md` (global `~/.claude/CLAUDE.md` and repo-local `CLAUDE.md`) with zero Argus involvement.

**This design was revised mid-review** after fetching Codex's and opencode's own current documentation (`learn.chatgpt.com/docs/build-skills`, `opencode.ai/docs/skills`, `opencode.ai/docs/rules`) turned up native mechanisms that were not known when the first draft was written. The findings, confirmed against first-party docs (not just third-party blog summaries):

- **Codex CLI** natively scans for `SKILL.md`-format skills at `.agents/skills` walking from cwd up to the repo root, plus `$HOME/.agents/skills` (user-level, cross-repo), plus admin (`/etc/codex/skills`) and system-bundled locations. Pure filesystem discovery, no MCP involved. It does **not** read `CLAUDE.md`, and reads only repo-local `AGENTS.md` — a global `~/.codex/AGENTS.md` is claimed by third-party sources but is absent from OpenAI's own docs and reported unreliable in upstream GitHub issues.
- **opencode** natively scans `.opencode/skills`, `.claude/skills`, and `.agents/skills` (project-local, walking up to the git worktree root) plus their global/home-level counterparts (`~/.config/opencode/skills`, `~/.claude/skills`, `~/.agents/skills`), surfaced to the model via opencode's own native `skill` tool (a catalog-then-on-demand-fetch shape, filesystem-backed rather than MCP-backed). opencode also supports an explicit `skills` array in `opencode.json`/`opencode.jsonc` (project or global) naming arbitrary additional directories (or even HTTP catalogs) to scan, additive on top of the default locations. opencode's *instruction*-file discovery (separate from skills) is a strict precedence chain, not an unconditional read of any one file: repo-local `AGENTS.md` **wins whenever present**; repo-local `CLAUDE.md` is read **only as a fallback when no repo-local `AGENTS.md` exists**; then the global `~/.config/opencode/AGENTS.md` **wins whenever present**; the user's real global `~/.claude/CLAUDE.md` is read **only as a fallback when no global `~/.config/opencode/AGENTS.md` exists** (a documented Claude-Code-compatibility layer). Each compatibility layer is independently disableable via `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT`, and `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`.
- **Codex** additionally has its own first-party, non-`.agents/skills` skill directory at `$CODEX_HOME/skills/` (defaults to `~/.codex/skills/`, overridable via the `CODEX_HOME` env var), separate from its bundled `$CODEX_HOME/skills/.system/` content — this is the location Codex's own bundled `skill-installer` skill documents installing third-party skills into. Empirically confirmed locally (see below): a probe skill placed at `~/.codex/skills/argus-verify-test/SKILL.md` appeared in `codex debug prompt-input`'s rendered catalog alongside the `.system/` and `.agents/skills/` entries.

MCP wiring (`internal/inject/codex`, `internal/inject/opencode`) already works today for Codex/opencode and needs no change for MCP tool registration itself — but Decision 2 below extends the existing `internal/inject/opencode` config-merge mechanism to also inject a `skills` array entry, reusing the same idempotent-merge machinery for a different config key.

The operator (Aaron) has already ruled out writing any file into the target repo's worktree to close the remaining gap, even a `.git/info/exclude`-scoped one — see Decision 1. This is a different concern from writing to a global, non-worktree, home-directory location (Decision 2), which Argus already does for Claude's `--add-dir` workspace.

**Empirical verification performed during this review** (not just documentation research): with `codex-cli 0.139.0` installed locally, `codex debug prompt-input "hello"` (renders the actual model-visible prompt with no model call) run from this repo — which has a `CLAUDE.md` and no `AGENTS.md` — confirmed both halves of the premise directly: (1) a real `<skills_instructions>` catalog block was present, listing skills from `$CODEX_HOME/skills/.system/*`, `$CODEX_HOME/skills/*` (non-`.system`, confirmed via the probe skill above), and `~/.agents/skills/*` (pre-existing real content on this machine, not fabricated for the test) — name, description, and file path per entry, with explicit "skill bodies live on disk at the listed paths" instructions; (2) this repo's `CLAUDE.md` content did not appear anywhere in the rendered prompt, confirming Codex genuinely does not pick it up natively.

## Goals / Non-Goals

**Goals:**

- Give Codex and opencode sessions the same *skill discoverability* Claude sessions get today, using each CLI's own native discovery mechanism rather than a bespoke one.
- Give Codex sessions the same *CLAUDE.md content* Claude sessions get today (opencode already has this natively — see Non-Goals).
- Give both Codex and opencode sessions the same *hera/routing orientation* content Claude sessions get today, since neither CLI has an unconditional, always-loaded injection point for argus-owned content the way Claude's `--append-system-prompt-file` is.
- Do all of the above without writing any file into the project's worktree.
- Keep the Claude-backend path completely unchanged.

**Non-Goals:**

- **Re-delivering CLAUDE.md content to opencode.** opencode already natively reads repo-local `CLAUDE.md` (as an `AGENTS.md` fallback) and the user's real global `~/.claude/CLAUDE.md` (as a documented compatibility fallback). Prepending that same content to opencode's prompt would be pure duplication — wasted tokens with no behavioral benefit — so this change deliberately excludes opencode from the CLAUDE.md portion of the prefix.
- **Detecting or compensating for opencode's Claude-compat env vars being disabled.** If a user or project sets `OPENCODE_DISABLE_CLAUDE_CODE` (or the narrower `_PROMPT`/`_SKILLS` variants), opencode's native CLAUDE.md/skills pickup silently stops, and this design does not detect that condition or fall back to prompt-prefixing in response — see Open Questions.
- **Relying on Codex's global `~/.codex/AGENTS.md`** (or the differently-named `~/.agents/AGENTS.md` some sources cite) to deliver CLAUDE.md or routing content. Considered and rejected for this version — see Decision 3.
- The `pi` backend. There is no `internal/inject/pi` package, so `pi` sessions cannot reach argus's MCP server at all today, and this change does not add that wiring.
- Writing `AGENTS.md`, `.git/info/exclude`, or any other file into the worktree — considered and explicitly rejected, not merely deferred (Decision 1).
- Changing the MCP config-injection mechanism itself (`internal/inject/codex`, `internal/inject/opencode`) — it already works and needs no change, and (following the native-discovery finding) this change no longer touches `internal/mcp/` at all.
- Achieving byte-for-byte parity with Claude Code's own `CLAUDE.md` discovery semantics (e.g. its directory-walk-upward behavior for nested `CLAUDE.md` files) for Codex's prompt-prefix path. This change reads the same two sources Argus already knows how to find (global `~/.claude/CLAUDE.md`, worktree-root `CLAUDE.md`) — it does not reimplement Claude Code's full discovery algorithm.

## Decisions

### Decision 1: No worktree writes, for either skills or CLAUDE.md/orientation content

**Chosen:** every delivery mechanism in this change either (a) writes to a global, non-worktree, Argus-managed location (skills — Decision 2), or (b) is pure in-memory prompt content with no filesystem write at all (CLAUDE.md/orientation — Decision 4).

**Rejected:** writing an `AGENTS.md` file into the worktree for Codex (which natively reads `AGENTS.md` the way Claude reads `CLAUDE.md`) or a repo-local skills directory. Rejected because the operator does not want Argus writing any file into a project's worktree that could contaminate the repo or affect any other user of the system. A `.git/info/exclude`-scoped (local, untracked, git-invisible) variant was also considered and rejected on the same principle, not on implementation-risk grounds — the objection is to the write itself, not to whether it would leak into a commit.

### Decision 2: Vendor-scoped skill materialization, not the generic cross-tool path

**Chosen:** rather than the generic, maximally-shared `~/.agents/skills/` cross-tool convention (visible to any tool implementing the same emerging convention — community sources found during research name Cursor and Gemini CLI alongside Codex and opencode), each backend gets a narrower, vendor-scoped target:

- **Codex:** materialize the same embedded builtin skill bodies (`internal/skills.builtinFS`, already used for the Claude-targeted `~/.argus/skills/.claude/skills/` workspace) to `$CODEX_HOME/skills/<name>/SKILL.md` (respecting the `CODEX_HOME` env var; defaulting to `~/.codex/skills/`) — Codex's own first-party sanctioned location for installed skills, empirically confirmed above. Idempotent (rewrite only on content diff, remove stale directories), mirroring `EnsureBuiltinSkills`'s existing behavior exactly.
- **opencode:** extend the existing `internal/inject/opencode` idempotent config-merge mechanism (the same code path that already safely merges the `mcp.argus` entry into `~/.config/opencode/opencode.json` without disturbing unrelated keys) to additionally ensure a `skills` array entry pointing at Argus's own managed skills workspace is present — using opencode's own documented `skills` config key (`opencode.ai/docs/config`) rather than a bare shared directory.

**Why not the generic `~/.agents/skills/` path for either:** it's the maximal-blast-radius option. Both alternatives above are strictly narrower — Codex's own vendor directory is Codex-only; opencode's explicit config-array entry is opencode-only and lives in a file a human can inspect and audit, unlike an implicit filesystem convention.

**Why not a per-task-namespaced directory** (the first form this concern was raised in): rejected because (a) the materialized content is entirely deterministic — derived solely from Argus's embedded builtin skill set, with zero per-task variation — so there is nothing to namespace *by*; every task would produce byte-identical output, meaning namespacing would only add directories to clean up with no corresponding benefit; (b) for opencode specifically, a per-task-namespaced `skills` array entry would require mutating the shared global `opencode.json` on every task spawn and teardown — trading a static, idempotent, occasionally-redundant-but-harmless materialization for a dynamic, order-sensitive, multi-writer config mutation with real race potential, which is a strictly worse version of the exact hazard this decision exists to avoid.

**Why the remaining write-concurrency risk is bounded:** both targets reuse the same "atomic write only if content differs" pattern (`atomicWriteIfDifferent`) the existing Claude-targeted `EnsureBuiltinSkills` already relies on for identical reasons (deterministic content, potentially-concurrent callers across daemon/workers on the same machine). Since every writer computes and writes identical bytes, a race between two concurrent Argus processes materializing at the same time converges on the same correct result — at worst a redundant no-op write, never a torn or incorrect one.

**Why the remaining cross-session visibility is acceptable:** any Codex or opencode session on the machine — argus-spawned or not — will see these skill names and descriptions in its catalog once materialized, since neither vendor-scoped target is task- or invocation-scoped. This mirrors the already-shipped `mcp-injection` capability's own precedent: argus's MCP tools (`hera_*`, `iris_*`, `kb_*`) are already globally registered into every Codex/opencode session's config regardless of argus-context, and the codebase already treats that as an acceptable trade-off. Extending the same posture to skill catalogs — whose descriptions name argus-specific mechanisms unlikely to match an unrelated task — is consistent with, not a new departure from, that established precedent.

**Consequence:** this entirely replaces the original design's skill catalog (rendered into the prompt) and the new MCP tool for on-demand full-body reads — see Decision 5 (superseded).

### Decision 3: Do not target Codex's global `~/.codex/AGENTS.md`

**Considered:** writing argus's routing orientation and/or CLAUDE.md content into a global Codex instructions file instead of prompt-prefixing it, mirroring how the routing prose is delivered to Claude via a file (`--append-system-prompt-file`) rather than inline prompt text.

**Rejected for this version:** (a) the exact path is inconsistently named across sources (`~/.codex/AGENTS.md` vs `~/.agents/AGENTS.md`) and absent from OpenAI's own documentation entirely — only third-party blogs and a GitHub feature-request issue describe it; (b) an existing GitHub issue reports Codex sometimes failing to load it even where it is expected to; (c) unlike the skills workspace (Decision 2, an Argus-exclusive namespace with no collision risk), a global `AGENTS.md` is a file the user may already populate with their own cross-project standards — writing into it safely would require the same kind of careful idempotent-section-merge `internal/inject` already does for shared config files (`~/.codex/config.toml`, `~/.claude.json`), which is more implementation complexity than a stateless per-spawn prompt-prefix for uncertain reliability payoff. Revisit once (if) Codex's global-AGENTS.md loading is confirmed reliable and officially documented.

### Decision 4: Backend-differentiated prompt prefix for CLAUDE.md and routing orientation

**Chosen:** the remaining gap — CLAUDE.md content and routing orientation, for whichever backend doesn't already get them natively — is still delivered by prepending to the plain prompt string already passed uniformly to every backend (`task.Prompt`), exactly as the original design proposed, but the block's *contents* now differ by backend:

- **Codex:** global `~/.claude/CLAUDE.md` + repo-local `CLAUDE.md` + routing orientation.
- **opencode:** routing orientation only (CLAUDE.md excluded per the Non-Goals above).

This is consistent with the existing codebase pattern: hera already prepends orientation content directly into a role's spawn prompt today (`HeraCheckInOrientation` for workers, `HeraSubCoordinatorOrientation` for sub-coordinators, in `internal/agent/hera_spawn.go`) rather than writing it to a file, so prompt-prefixing for non-Claude context is an extension of an established Argus mechanism, not a novel one.

### Decision 5 (superseded): skill catalog + on-demand MCP tool

The first draft of this design proposed rendering a name+description skill catalog into the non-Claude prompt prefix, plus a new MCP tool (modeled on the "Skills Over MCP" convention — draft spec extension SEP-2640, reference implementation at skillsovermcp.com) for fetching a skill's full body on demand. **Superseded by Decision 2**: both Codex and opencode already implement exactly this shape (catalog discovery + on-demand full-body read) natively via filesystem scanning, so building a second, Argus-specific version of it would be redundant. Kept here, struck through in effect, so the record of why the design changed mid-review is not lost.

## Risks / Trade-offs

- **[Risk] Third-party-sourced claims about Codex's global AGENTS.md path are unverified and inconsistent** → **Mitigation:** this design does not depend on that path at all (Decision 3); it uses only mechanisms confirmed in first-party docs (`.agents/skills` at the documented repo/user/admin/system locations, and opencode's documented `AGENTS.md`/`CLAUDE.md` fallback chain).
- **[Risk] opencode's Claude-compat env vars can silently disable native CLAUDE.md/skills pickup** (`OPENCODE_DISABLE_CLAUDE_CODE*`) → **Not mitigated in this design** — flagged as an accepted gap and an open question rather than silently assumed away.
- **[Risk] Routing-orientation prefix cost is still paid on every non-Claude spawn** (unlike `--append-system-prompt-file`, which references a file by path once materialized) → **Mitigation:** this is now a much smaller cost than the original design (no skill catalog, no skill bodies, no repo CLAUDE.md for opencode) — just the routing prose for both backends, plus CLAUDE.md content for Codex only. Still worth measuring before shipping broadly — see Open Questions.
- **[Risk] Multiple spawn paths could drift** (`agent.CreateAndStart`, `startSession`, hera's `SpawnHeraWorker`, headless task creation) if the prefixing logic is duplicated per callsite → **Mitigation:** not resolved here; see Open Question 1. Whichever insertion point is chosen, it should be a single shared function per concern (prefix assembly, skill materialization), not copy-pasted per callsite.
- **[Risk] A project with no `CLAUDE.md` produces an oddly-empty or malformed prefix for Codex** → **Mitigation:** the CLAUDE.md section must be independently omittable — see Open Question 4.
- **[Trade-off] Reading global `~/.claude/CLAUDE.md` and repo `CLAUDE.md` from Go for the first time** (previously read only by Claude Code and, per this research, by opencode itself) means Argus now has an implicit content-format dependency on whatever Claude Code's own CLAUDE.md conventions are, even though nothing here parses that content — it is treated as opaque text and concatenated, not interpreted, so this dependency is shallow (read-and-paste, not parse-and-act).

## Migration Plan

No data migration. This is new command-construction and new skill-materialization behavior with no schema changes and no persisted new state. Rollout is a normal code change: land the vendor-scoped skill materialization (Decision 2: `$CODEX_HOME/skills/` for Codex, the `opencode.json` `skills` array entry for opencode) and the backend-differentiated `BuildCmd` prompt-prefix branch together, verify against a live Codex and/or opencode session (confirming native skill discovery picks up the new path, and — for opencode — confirming CLAUDE.md content is genuinely not duplicated), then ship. Rollback is deleting the new materialization call and prompt-prefix branch — no stored state to reverse.

## Open Questions

1. **Insertion point.** Given the multiple spawn paths that can originate a fresh task (`agent.CreateAndStart`, `startSession`, hera's `SpawnHeraWorker`, headless task creation via `internal/daemon/headless.go`), where should prompt-prefixing (and the skill materialization call) actually happen — a single shared helper called from deep inside `BuildCmd` itself (mirroring where the existing Claude-only `EnsureBuiltinSkills`/`ensureBuiltinRoutingFn` calls already live), versus wiring it per-callsite? Not resolved here — pick before implementation.
2. **Token/prompt-size cost.** Now much smaller than the original design (no skill catalog, no skill bodies, no repo CLAUDE.md for opencode) but still worth measuring against a real Codex/opencode context window before shipping broadly, especially since it's paid on every spawn rather than once (the way file-based injection is).
3. **opencode Claude-compat disablement.** Should Argus detect `OPENCODE_DISABLE_CLAUDE_CODE`/`_PROMPT`/`_SKILLS` (e.g. by checking the project's or user's opencode config/env) and fall back to prompt-prefixing CLAUDE.md content for opencode when the native path is disabled, or accept the gap as a known limitation for anyone who has turned off opencode's Claude-Code compatibility? Not resolved here.
4. **Graceful omission.** What should the Codex prefix block look like when there's no `CLAUDE.md` at all (global, repo, or both)? Likely: omit the section's heading entirely rather than emit an empty or "none found" placeholder — but the exact per-section behavior needs to be pinned down as part of implementation, and is deliberately left open here rather than assumed.

### Resolved: shared-materialization-target collision/leakage risk

Raised during coordinator review: writing argus's builtin skills to a single global, unscoped directory risks (a) concurrent Argus workers on the same machine colliding on the write, and (b) leaking argus-specific skills into unrelated, non-argus Codex/opencode sessions on the same box. Resolved via Decision 2 above rather than left open:

- Checked whether Codex/opencode support pointing skill discovery at an arbitrary or task-scoped path via config override, per the coordinator's first preference. **opencode does** (the `skills` config array) — used directly. **Codex does not**, for the generic cross-tool convention; its only relevant override is `CODEX_HOME`, which governs its entire state directory (config, auth, sessions), not skills alone, and is too broad a knob to repurpose for per-task skill scoping without materially changing how Codex sessions authenticate and persist state — rejected as disproportionate.
- Task-scoped namespacing under `$HOME` (the coordinator's suggested fallback) was considered and rejected for both backends: the materialized content has no per-task variation (it's always the same embedded builtin skill set), so there is nothing to namespace by, and for opencode specifically it would trade a static, idempotent, occasionally-redundant write for a dynamic multi-writer config mutation on every task spawn/teardown — a worse version of the exact race risk being avoided.
- Landed instead on vendor-scoped (not task-scoped) targets — Codex's own `$CODEX_HOME/skills/` directory, opencode's own `skills` config array — which are narrower than the generic cross-tool path (Codex-only and opencode-only respectively, rather than visible to any tool implementing the same convention) while remaining collision-safe via the same idempotent atomic-write-on-diff pattern the existing Claude materialization already uses. Remaining cross-session visibility (non-argus sessions of the same backend still see the catalog entries) is accepted as bounded, mirroring the already-shipped `mcp-injection` capability's identical trade-off for MCP tool registration.
