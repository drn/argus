## Context

Argus's rebindable keymap (`internal/tui/keymap`) resolves a physical keypress → `Action` per `Context` (`CtxGlobal`, `CtxTaskList`, `CtxAgent`, `CtxFilePnl`, `CtxDiff`, `CtxSettings`, `CtxHeraRail`). Every dispatch site calls `Resolve(ctx, event)` and switches on the result; the same metadata (`defaultSpecs`/`actionLabels`/`contextOrder`) already drives the generated `?` help overlay (`modal.SectionsFromKeymap`). Today's task switcher (`ActAgentSwitcher`, `ctrl+k`) is `CtxAgent`-only — dispatched from `handleAgentKey`'s interception block (`app.go:2975-2985`) into `a.openTaskSwitcher()` (`app.go:4616`), which builds entries from `a.tasks`/`a.needsInputIDs` (already sorted needs-input-first, `app.go:4650-4661`) and opens `TaskSwitcherModal` in grouped mode.

The native Hera view (`internal/tui/hera`) has its own, largely separate key-dispatch surface: `HeraPage.InputHandler` (`page.go:627`) has a top-level switch of LITERAL (non-keymap) cases — `Ctrl+Z` (fullscreen toggle), `Tab`/`Backtab` (focus-ladder-or-passthrough), `Ctrl+Q` (to-rail), `Ctrl+Y` (clipboard copy), `Ctrl+Alt+arrows`/`Cmd+arrows` (focus/rail nav) — that run regardless of which region (`FocusRail`/`FocusCoord`/`FocusAgent`) has focus, followed by a per-region dispatch: `FocusRail` → `handleRailMutation` (which DOES resolve `CtxHeraRail` actions) then rail nav; `FocusCoord`/`FocusAgent` → `forwardKey` (raw bytes to the live PTY), with `FocusAgent`-in-`detailsMode` (a coordinator's Details/plan region) getting a `handleRailMutation` pre-check first (BUG-010). Neither `ctrl+j` nor `ctrl+k` appears anywhere in this Hera dispatch chain today — `ctrl+k` falls all the way through to `forwardKey` and leaks into the agent's PTY.

Separately, the Hera rail's needs-input signal is already a first-class, well-tested rollup: `RoleView.NeedsInput`/`SubtreeNeedsInput` (computed once per `BuildModel` in a post-pass, `rollupNeedsInput`, crossing bridges via the same `BridgeSubtree` traversal that drives nesting and cascade-delete) already bubbles "does this subtree need input" to every ancestor, and `drawOrchRow` already renders a `(?)` on a coordinator-less or coordinator-folded header from it (BUG-028) — but that rollup today decorates AT MOST the header; it never reveals what's underneath. This change's rail-reveal feature is the first consumer that walks the tree and asks "which rows must render regardless of fold state."

## Goals / Non-Goals

**Goals:**

- A single keyboard chord jumps to the highest-priority actionable item (needs-input) from anywhere, including from inside a live Hera pane.
- A second chord opens a searchable index of "what can I do right now" that actually runs the picked action, cutting the round-trip through the `?` help overlay (read-only today) down to zero.
- Rail visibility of a buried blocked worker without requiring the operator to manually unfold every ancestor.

**Non-Goals:**

- **Web/macOS parity.** Hera interaction is TUI-only today by existing, documented design (`CLAUDE.md` Frontend Parity: "the web and macOS Hera tabs are read-only rosters"). The switcher's Hera reach and the rail's partial-fold reveal are Hera-rail-rendering concerns with no web/macOS equivalent surface to touch. The command palette's content is the TUI's own rebindable keymap — there is no analogous "keymap" concept on the web SPA or the macOS app to palette-ize. All three pieces of this change are therefore TUI-only; this is a named Non-Goal, not a silent gap.
- **No standalone "jump to next `(?)`" hotkey and no `Ctrl+G`.** The switcher's needs-input-first default sort (Decision 1) fully covers this need; a second dedicated hotkey would be redundant.
- **The command palette does not surface Hera's hardcoded literal page-level actions** (Ctrl+Z fullscreen toggle, Ctrl+Y clipboard copy, the Cmd/Ctrl+Alt+arrow focus-ladder nav) — those are not modeled as keymap `Action`s today (they are literal `tcell.Key` cases in `HeraPage.InputHandler`, deliberately outside the rebindable system). The palette's stated data source is `keymap`'s own metadata; folding non-keymap literals into it would require promoting them to real `Action`s first, which is out of scope here.
- **No feature flag / rollback toggle.** Per this repo's Breaking Changes Policy (single user, no back-compat), the rebind and the pane-focus interception changes ship directly.

## Decisions

### 1. `ctrl+j` = unified task/role switcher (rebind, not new dispatch)

`ActAgentSwitcher`'s default moves from `ctrl+k` to `ctrl+j` in `defaultSpecs[CtxAgent]` — a one-line change; the existing `CtxAgent` interception block in `handleAgentKey` needs no other change (it already resolves `CtxAgent` and switches on the action, not the literal key).

**Hera reach is a new, Hera-page-local literal case**, not a new keymap action: `HeraPage.InputHandler`'s top-level switch (`page.go:641`) gains a `case tcell.KeyCtrlJ:` alongside the existing `Ctrl+Z`/`Tab`/`Ctrl+Q`/`Ctrl+Y` cases — same "always intercepted regardless of focus region" pattern (fires whether `FocusRail`, `FocusCoord`, or `FocusAgent` is current), calling a new `p.OnSwitcher func()` callback the App wires to the (extended, see Decision 3) `a.openTaskSwitcher()`. This deliberately mirrors the existing asymmetry already present for `Ctrl+Z`/`Ctrl+Y` (rebindable `Action` in the classic agent view via `CtxAgent`, hardcoded literal inside Hera) rather than inventing a new mechanism — Hera's page-level keys have never gone through `keymap.Resolve`, and extending `CtxHeraRail` (which is rail-mutation-scoped and only consulted from `FocusRail`) to also cover pane focus would strain that context's existing meaning for no benefit, since nothing about the switcher is rail-mutation-shaped.

**Alternative considered:** model a new `hera_rail.switcher` `CtxHeraRail` action and consult it from both `handleRailMutation` and a new pane-focus check. Rejected — `CtxHeraRail`'s `Resolve` is only ever called from `handleRailMutation`, which only runs under `FocusRail` (plus the narrow `detailsMode` pre-check); reaching it from a plain terminal pane (`FocusCoord`/non-details `FocusAgent`) would require threading `Resolve` calls into `forwardKey` itself, a bigger and riskier change than one literal case.

### 2. `ctrl+k` = command palette, dispatched from `handleGlobalKey`'s unconditional switch

A new `ActGlobalPalette` (`global.palette`, default `ctrl+k`) is added to `CtxGlobal`'s `defaultSpecs`/`actionLabels`/`contextOrder` — a normal, rebindable, help-overlay-visible action. Its dispatch, however, is NOT the usual gated `if !suppressRune { Resolve(CtxGlobal, event) }` block (`app.go:2767`, gated `a.mode != modeAgent` per-case) — it is resolved and switched on at the TOP of `handleGlobalKey`, in the same unconditional structural section that already special-cases `Ctrl+C`/`Ctrl+Q` regardless of `a.mode` (`app.go:2718-2755`). This is the one piece of NEW cross-cutting plumbing: an action can be BOTH a normal rebindable `Action` (config override + help row) AND resolved unconditionally ahead of the mode gate — a pattern that doesn't exist yet (today's unconditional cases are all hardcoded literals, e.g. `tcell.KeyCtrlQ`), but is a small, additive generalization: call `Resolve(CtxGlobal, event)` once, early, and special-case `ActGlobalPalette` before the `suppressRune`/mode gate; everything else in that block is unchanged.

**Hera pane focus:** `ctrl+k` no longer reaches `HeraPage.InputHandler` at all once `handleGlobalKey` intercepts it — this REPLACES today's raw pass-through to the PTY in Hera pane/coordinator focus (see Risks below).

**Applicable-action set per focus region** (what the palette lists, filtered by current context):

| Current state | Palette shows |
|---|---|
| Classic agent view (`modeAgent`) | `contextOrder[CtxAgent]` |
| Task list (`modeTaskList`, Tasks tab) | `contextOrder[CtxGlobal]` (non-agent-gated subset) ∪ `contextOrder[CtxTaskList]` |
| Hera rail focus | `contextOrder[CtxGlobal]` ∪ `contextOrder[CtxHeraRail]` (acting on `rail.Selection()`) |
| Hera pane/coordinator focus (incl. Details/plan) | `contextOrder[CtxHeraRail]` (acting on `rail.Selection()`, same target-resolution precedent as the existing BUG-010 in-details-mode routing) ∪ the subset of `contextOrder[CtxGlobal]` not otherwise reachable by a raw keypress there |

The last row is flagged as an **Open Question** below — it is a genuine design fork the brief didn't pin down (see Open Questions).

**Invocation mechanism ("dispatch an action right now") — additive per-context registries, not a switch-to-map rewrite:**

For each palette-relevant context, build `map[keymap.Action]func()` once (at `App`/`HeraPage` construction), where each entry is a THIN wrapper around the SAME named method the existing physical-key switch case already calls (e.g. `ActAgentSwitcher → a.openTaskSwitcher`, `ActGlobalTabHera → func(){ a.switchTab(widget.TabHera) }`, `ActHeraSpawn → func(){ p.fire(p.OnSpawnWorker, p.rail.Selection()) }`). Where a switch case's body is more than one call today, the body is extracted into a single named method first (mechanical refactor, behavior-preserving) so both the physical-key switch and the registry call the identical implementation — no logic is duplicated, and the existing switches are left in place (lower risk / smaller diff than rewriting them to map lookups). The palette, given a user-picked `Action`, looks it up in the current context's registry and calls it directly — no synthetic `tcell.EventKey` is ever constructed. A registered func keeps whatever runtime guard its switch case had (e.g. `ActAgentPaneLeft`'s `!a.agentZen && a.agentFocus > focusTerminal`), so an entry that's technically listed but not applicable at invoke time safely no-ops, matching what the physical key would do — the palette's context filtering (above) is a best-effort narrowing, not a correctness requirement.

**Modal:** a new `CommandPaletteModal`, structurally mirroring `TaskSwitcherModal`'s filter/cursor mechanics (type-to-filter, arrow nav, Enter-confirm) — a new type because the row shape (label + resolved-hotkey column) differs from a task/role row, not because the interaction model differs.

### 3. Switcher becomes genuinely unified (tasks + Hera roles, one entry-building path)

`openTaskSwitcher`'s entry-building is extended to include Hera role bindings alongside plain argus tasks — one function, not two divergent paths — reusing the SAME needs-input union `needsInputForHeraRail` already computes (`heraManaged` ∪ plain in-progress tasks) as the candidate set, sorted needs-input-first (existing comparator, unchanged) then alphabetically. This is a deliberate, small expansion of scope beyond "make it reachable from Hera": since the entry list is unified, invoking `ctrl+j` from the CLASSIC agent view can now also land on a Hera-managed role, not just a flat task — a natural consequence of "unified," not drift, and lower-risk than maintaining two entry-building code paths that would need to independently stay in sync with the needs-input rollup.

**Ancestor expansion on select** reuses the exact `jumpToLeaf` pattern (`page.go:249-264`): `Rail.Model().OrchIDsForTask(id)` → `Rail.EnsureAncestorsExpanded(orchID)` per ancestor (walks `canonicalParents()`, fold-independent) → `Rail.SelectByTaskID(id)` → `focus.SetRegion(FocusAgent` or `FocusCoord` per `detailsMode)`.

**Multi-binding caveat (flagged, not fully resolved — see Open Questions):** a task bound under two orchestrators renders as two distinct rail rows (the "Multi-binding fan-out is structural" invariant). The switcher entry list, when it includes Hera roles, should in principle carry one entry per (task, orchestrator) pair to match — but `SelectByTaskID` itself only lands on the first matching row for a bare task ID. For v1 this is accepted as-is (identical to today's other `jumpToLeaf`-driven landings, which have the same limitation) rather than threading an explicit `OrchID` disambiguator through the entry/selection path.

### 4. Rail partial-fold reveal — extend `appendOrchWorkers`, don't fork a parallel traversal

The reveal is implemented as ONE new branch inside the EXISTING `appendOrchWorkers` recursion (`rail.go`, the same function that already handles nesting/bridges/pinning/archiving), not a second, parallel traversal function. Today: `isCollapsed(orch) == true` ⇒ skip all children, render header only (decorated with `(?)` via the existing `SubtreeNeedsInput` rollup when applicable, BUG-028). New branch: `isCollapsed(orch) && orch.SubtreeNeedsInput` ⇒ still render the header, but for each immediate child (role, or bridged sub-orchestrator), recurse into it ONLY if that child's own `ShowsNeedsInput()`/`SubtreeNeedsInput` is true (i.e. it needs input itself or a further descendant does); a child failing that check is skipped entirely, exactly as today (no "N more hidden" placeholder — full pruning, per the proposal's example). The recursion is naturally self-similar: a revealed child that is ITSELF a closed sub-coordinator re-applies the same collapsed-but-needs-input branch, so a chain of closed ancestors peeks all the way down to the leaf. Multiple needs-input leaves under one coordinator each get their own revealed path (the branch does not stop at the first match).

**Rejected alternative:** a separate `appendOrchWorkersRevealed` traversal reusing only the needs-input predicate. Rejected because `rail.go`'s nesting logic carries ~15 documented, individually-hard-won invariants (`canonicalParents`, `structuralReach`, bridge-cycle guards, pinned-vs-active ordering, archive-expando hoisting) — a parallel implementation would need to re-satisfy all of them independently and would drift the moment either path changed. Extending the one true traversal with an additional gate keeps every existing invariant automatically satisfied for revealed rows (they ARE normal rows in `r.rows`, so cursor stepping, selection, drawing, and mutation-by-`Selection` all work unmodified with zero special-casing downstream).

**Fold state is untouched.** `Space` (`ToggleCollapse`) still means exactly what it means today — the reveal is a pure rendering enhancement layered on top of the existing collapsed state, not a new fold state. Revealed rows are fully normal, selectable rows (no dimming, no distinct visual treatment beyond the ancestor's own pre-existing `(?)` marker) — a user can navigate onto and act on them (mutations key off `Selection`, which doesn't care about ancestor fold state).

## Risks / Trade-offs

- **[Risk] `ctrl+j` is ASCII LF (0x0A) — some terminal apps/readline configs treat a literal LF as an alternate "accept"/Enter.** → Mitigation: this is the SAME risk class as today's shipped `ctrl+k` task-switcher interception (0x0B, vertical tab) in the classic agent view — an already-accepted precedent, just a different byte. No reports of the existing `ctrl+k` interception causing trouble; treat `ctrl+j` the same way and revisit only if reports surface.
- **[Risk] `ctrl+k`/`ctrl+j` no longer reach a focused Hera pane's PTY (BREAKING, by design).** → Mitigation: explicitly documented, precedented by the existing Ctrl+Z fullscreen intercept (`gotchas/hera-view.md`: "the external plugin never suffered this... native omitted that binding and the raw byte fell through"). The Ctrl+Z case was justified because passthrough was actively harmful (SIGTSTP-equivalent session orphaning); THIS case is a deliberate feature trade-off, not a harm-avoidance — cite both precedents but do not conflate them; state plainly in the PR/CHANGELOG that in-PTY uses of literal ctrl+j/ctrl+k (e.g. a nested vim session's own bindings) are no longer reachable from inside a Hera pane.
- **[Risk] The "applicable action set in Hera pane focus" fork (Decision 2 table, last row) is a genuine open design question**, not fully specified by the original brief. → Mitigation: flagged explicitly in Open Questions for human confirmation before implementation of that specific row; the other three rows are unambiguous and can proceed regardless.
- **[Risk] Multi-binding disambiguation in the unified switcher is incomplete** (Decision 3 caveat). → Mitigation: accepted as a known, pre-existing-shaped limitation (matches `jumpToLeaf`'s existing behavior for other callers); not a regression introduced by this change.
- **[Risk] Extracting switch-case bodies into named methods for the registry (Decision 2) touches otherwise-stable dispatch code across `app.go` and `heraactions.go`.** → Mitigation: mechanical, behavior-preserving refactor; each extraction gets a smoke test asserting the physical key still resolves identically pre/post-refactor before the registry is wired to anything new.

## Migration Plan

Single PR, no data/schema migration, no feature flag (per this repo's Breaking Changes Policy). `openspec archive hera-nav-palette` runs in the same PR before merge, per this project's CLAUDE.md. Rollback is a plain revert (no persisted state to unwind — keybindings and rail rendering are pure code/config).

## Open Questions

1. **Hera pane-focus palette reach:** should the command palette, when opened from a live Hera terminal pane (`FocusCoord` / non-details `FocusAgent`), include the `CtxGlobal` actions that a raw keypress currently CANNOT reach there (`q`/`1`/`2`/`3`/`?`, suppressed by `heraPaneFocused()` to protect against accidental typing into the PTY)? The palette is an explicit, filtered, Enter-confirmed action — a categorically lower accidental-input risk than a bare keystroke — so this design leans toward YES (include them), but this reverses a deliberately protective BUG-001 guard for a NEW entry point and deserves explicit confirmation before implementation.
2. **Visual treatment of revealed rail rows:** the proposal's ASCII example shows revealed rows rendered identically to a normal open fold (Decision 4). Confirm no distinct dimming/indicator is wanted before the leaf `(?)` (e.g. a "peeking through a closed fold" cue distinct from "this fold is actually open") — Decision 4 currently assumes none is needed.
