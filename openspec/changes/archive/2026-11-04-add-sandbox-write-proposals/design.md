## Decisions

1. **Approval is structurally unreachable from agents.** MCP gets exactly one write tool (propose). Decision routes use `requireMaster` (agents/device/scope tokens and `argus_api_get`'s device-stamped in-process GET get 403/no route). A test enumerates `tools/list` and fails if any tool name matches approve/reject/apply for sandbox proposals.
2. **Existing storage, new queue.** Proposals live in a new `sandbox_proposals` table (id, task_id, project, entries JSON `[{path,reason}]`, status pending|approved|rejected, scope, applied_paths JSON, created_at, decided_at, decided_by). Applying writes the existing per-project `projects.sandbox_extra_write` CSV or global `sandbox.extra_write` config key; no new config keys.
3. **Compare-and-set decisions.** Status flips with `UPDATE ... WHERE status='pending'`; double-approve is a 409. If the config write fails the row is reverted to pending.
4. **Validation: hard errors vs warnings.** `ValidateWritePath` failures (malformed, `/`, `~/`, commas, control chars) reject the whole call on propose and on approve (covers edits). `agent.SandboxPathWarning` returns a warning for sensitive/overbroad paths (denylist above); these are accepted, stored on the entry as `warning`, returned in the propose result, and shown prominently in every approval UI. Dedupe against the existing target list; paths already granted are reported as no-ops, not errors.
5. **Scope.** Project resolved from the task's `Project`; approver picks `project` (default) or `global`. A task with no project can only be approved global.
6. **Timing.** Sandbox profile is generated at spawn, so approval returns `takes_effect: "new_sessions"` and UIs say "restart affected tasks". A `config.toml` override of the same key can still shadow the DB write (documented gotcha, not detected).
7. **Abuse bounds.** Max 20 paths/call, 500-char reason, 10 pending proposals per task; duplicate pending path sets are merged into the existing proposal.
8. **UI placement.** No new global keybinding: TUI shows proposal rows at the top of Settings > Sandbox reusing existing Settings keys (Enter approve, `e` toggle project/global, `d` reject) plus a System warning with the pending count; no new keybindings or modal. Web: a panel in Settings. Remote TUI uses apiclient with its master token; local TUI calls the DB directly (a human at the keyboard). macOS app lists/decides through its existing master-token REST client.
9. **Only MCP requests are gated.** Manual edits in TUI/web Settings keep today's behavior (immediate, master-gated for web) with no proposal step.
