## Why

Two gaps surfaced after the hera-nav-palette change (ctrl+j unified switcher, ctrl+k command palette, rail partial-fold reveal) landed and was archived. First, a live QA pass found ctrl+j genuinely dead in the plain Tasks tab: `ActAgentSwitcher` (`ctrl+j`) only ever resolved from `handleAgentKey` (`modeAgent`), and the native Hera view's own reach is a separate hardcoded literal case in `HeraPage.InputHandler` — neither covers the plain task list, so the keypress fell through to `TaskListView`'s own `InputHandler`, which has no case for it, and was silently swallowed. Second, Aaron revisits the ORIGINAL idea for the whole nav-palette effort — a dedicated, popup-free "jump straight to the next `(?)`" hotkey — which was deliberately deferred out of hera-nav-palette in favor of the switcher's needs-input-first default sort. On reflection a single dedicated chord (no list, no typing, just jump) is still worth having alongside the switcher, since it serves a different interaction shape: an operator who already knows they want "the next blocked thing" doesn't need to open a picker at all.

## What Changes

- **Bug fix**: `ctrl+j` (the unified task/role switcher) now also works from the plain Tasks tab (`modeTaskList`, `TabTasks`). `handleGlobalKey` resolves `CtxAgent`'s own `agent.switcher` binding directly (not a new `CtxTaskList` action) when the plain task list is active, so a config override of `agent.switcher` applies there too, matching the classic agent view's behavior. Fixes a real, exposed bug in `closeTaskSwitcherModal`, which assumed Hera was the only non-agent origin — it now restores focus based on the current tab exactly as `closeCommandPaletteModal` already does.
- **New capability**: a global `ctrl+g` action (`global.jump_needs_input`) jumps directly to the highest-priority role needing input — no popup, no list, no typing — reachable from anywhere (the classic fullscreen agent view, the plain Tasks tab, and both Hera rail and Hera pane/coordinator focus), via the SAME unconditional-dispatch-ahead-of-the-mode-gate section `global.palette` (`ctrl+k`) already established. Pressing it again cycles forward to the next `(?)` in rail order (Pinned → Active depth-first → Freelance → Archive), wrapping around; a single remaining candidate keeps re-selecting itself. Landing on a role nested under a folded ancestor fully expands the fold first (reusing the `JumpToTask` ancestor-expand + reattach + focus sequence the switcher's Hera landing already uses).
- A top-level orchestrator's own coordinator role is deliberately EXCLUDED from the `ctrl+g` candidate set even when it itself needs input: `appendOrchWorkers` folds a top-level coordinator's role entirely into the `rrOrch` header row (never emitting it as its own `row.role`-bearing row), so `SelectByTaskID` — which only ever matches `row.role` — could never land a jump on it. Offering it as a candidate would produce a "found but unreachable" dead cycle stop. A nested sub-coordinator is unaffected (it bridges as an ordinary role-bearing worker row in its parent orchestrator), so its own need IS a reachable candidate.

## Capabilities

### Modified Capabilities

- `keybindings`: `agent.switcher` (`ctrl+j`) is now resolved directly from `handleGlobalKey` when the plain Tasks tab is active (previously dead there); a new `global.jump_needs_input` (`ctrl+g`) `CtxGlobal` action is added, dispatched unconditionally ahead of the mode gate exactly like `global.palette`.
- `hera-view`: a new `Rail.NextNeedsInputTaskID` scan-and-cycle method and `HeraPage.JumpToNextNeedsInput` (reusing `JumpToTask`) back the new `ctrl+g` reach into the native Hera view from every focus region (rail, coordinator pane, agent pane).

- **No DB/schema changes.** No MCP tool changes. No REST endpoint changes.
