## Why

Claude-backend sessions get project context and skill access for free — whether spawned as a hera coordinator, worker, or freelance role, or as a plain non-hera task: Claude Code natively auto-discovers `CLAUDE.md` files, and `internal/agent.BuildCmd` additionally injects argus's builtin skills (`--add-dir`) and hera/routing orientation prose (`--append-system-prompt-file`) — but strictly gated on `IsClaudeBackend`. Codex and opencode sessions get neither today: their CLIs have no equivalent flags, and Argus writes nothing into their worktree to fill the gap.

Research into both CLIs' own current documentation (`developers.openai.com`/`learn.chatgpt.com` for Codex, `opencode.ai/docs` for opencode) shows the gap is narrower than it first appeared, and shrinking it further would duplicate work the CLIs already do natively:

- **Both Codex and opencode already natively discover `SKILL.md`-format skills** from filesystem locations that include a user-level, non-worktree path: Codex scans `.agents/skills` from cwd up through the repo root, plus `$HOME/.agents/skills`, `$CODEX_HOME/skills` (its own first-party installed-skills directory), and admin/system paths; opencode scans the same `.agents/skills` paths (project and `~/.agents/skills`) plus `~/.claude/skills`, and additionally supports an explicit `skills` config array naming arbitrary extra directories, surfaced to the model via a native on-demand `skill` tool. Argus's builtin skill bodies (`internal/skills`, already `go:embed`-ded and already materialized to `~/.argus/skills/.claude/skills/` for Claude's `--add-dir`) just need vendor-scoped, non-worktree materialization targets that each CLI already knows to look for — see What Changes for why a vendor-scoped target was chosen over the generic cross-tool path.
- **opencode already natively reads `CLAUDE.md`, but only as a fallback**: its instruction-file discovery is a strict precedence chain — repo-local `AGENTS.md` wins whenever present, with repo-local `CLAUDE.md` read only when no `AGENTS.md` exists; the global `~/.config/opencode/AGENTS.md` wins whenever present, with the user's real global `~/.claude/CLAUDE.md` read only as a documented Claude-Code-compatibility fallback when it's absent (each layer independently disableable via `OPENCODE_DISABLE_CLAUDE_CODE*` env vars, which this change does not detect or compensate for — see design.md). Either way, opencode itself decides which file wins — there is nothing to build for opencode's CLAUDE.md path.
- **Codex has no `CLAUDE.md` equivalent** — it reads only its own `AGENTS.md`, and only repo-local (a global `~/.codex/AGENTS.md` is claimed by third-party sources but is not in OpenAI's own docs and is reported unreliable). This gap is real and this change addresses it.
- **Neither CLI has an unconditional, always-injected orientation hook** the way Claude's `--append-system-prompt-file` is. Skills are trigger-based (loaded when the model judges one relevant), not guaranteed to be read at session start the way argus's self-gating hera/routing orientation prose needs to be. This gap is real for both backends and this change addresses it.

## What Changes

- **Skill parity (Codex + opencode), via native discovery, not a new tool.** Materialize argus's existing embedded builtin skill bodies to a vendor-scoped target per backend, narrower than the generic cross-tool `.agents/skills` convention: for **Codex**, `$CODEX_HOME/skills/<name>/SKILL.md` (Codex's own first-party installed-skills directory, defaulting to `~/.codex/skills/`); for **opencode**, an entry in its own `skills` config array pointing at Argus's managed skills workspace, added via the existing idempotent `internal/inject/opencode` config-merge mechanism. No prompt content, no new MCP tool, no catalog rendering: each CLI's own discovery does the work, exactly as Claude's `--add-dir` already does for the Claude path. See design.md Decision 2 for why a vendor-scoped target was chosen over the generic `~/.agents/skills/` path (narrower blast radius; the generic path is visible to any tool implementing the same emerging convention, not just Codex/opencode).
- **CLAUDE.md / orientation parity, via a narrower, backend-differentiated prompt prefix:**
  - **Codex** gets a context block prepended to its initial spawn prompt containing the global `~/.claude/CLAUDE.md` content (if present), the repo-local `CLAUDE.md` content at the worktree root (if present), and the builtin hera/routing orientation prose Claude receives via `--append-system-prompt-file`.
  - **opencode** gets only the routing orientation prose prepended — its CLAUDE.md content is deliberately **excluded** from the prefix because opencode already loads it natively; duplicating it would double the token cost for no benefit.
  - This applies to every spawn of the affected backend regardless of hera role (coordinator, worker, freelance) or whether the task is hera-bound at all, since the underlying mechanism (`BuildCmd`) constructs the command once per task launch, not once per hera role.
- Claude backend is **unchanged** — it keeps native `CLAUDE.md` discovery plus the existing `--add-dir`/`--append-system-prompt-file` injection.
- **Rejected alternative**: writing an `AGENTS.md` file into the worktree (Codex natively reads `AGENTS.md` the way Claude reads `CLAUDE.md`). Rejected on principle — the operator does not want Argus writing any file into a project's worktree that could contaminate the repo or affect any other user of the system, including via `.git/info/exclude` (still a worktree-local write, still rejected). This is a distinct concern from the vendor-scoped skill materialization above, which writes only to global, non-worktree locations (Codex's own `$CODEX_HOME/skills/`, or a config-array entry in opencode's own config file) — the same class of write Argus already makes for Claude's `--add-dir` workspace.
- **Rejected alternative**: materializing skills to the generic, maximally-shared `~/.agents/skills/` cross-tool convention instead of a vendor-scoped target. Considered, but rejected in favor of the narrower per-backend targets above after coordinator review — see design.md Decision 2 for the full reasoning (collision-safety via deterministic idempotent writes, and why a per-task-namespaced path was considered and rejected).
- **Rejected (for now) alternative**: writing argus's routing orientation (or CLAUDE.md content) into Codex's global `~/.codex/AGENTS.md` instead of prompt-prefixing it. Rejected because that path is not documented by OpenAI's own docs (only third-party sources, with inconsistent naming across them), is reported unreliable, and — being a file the user owns and may have their own content in — would need careful idempotent-merge handling (like the existing MCP config-injection pattern) to avoid clobbering it. A stateless per-spawn prompt-prefix is safer for a first version; see design.md Open Questions for revisiting this later.
- **Non-goal**: the `pi` backend has no MCP injection at all (no `internal/inject/pi` package) and is out of scope for this change.
- **No longer in scope** (superseded by the native-discovery finding above): the previously-drafted skill catalog rendered into the prompt, and the new MCP tool for on-demand full skill-body reads. Native filesystem discovery on both CLIs already provides the "catalog + on-demand full-body read" shape those would have built by hand.

## Capabilities

### New Capabilities

(none — this change extends existing capabilities rather than introducing a new one)

### Modified Capabilities

- `agent-execution`: adds a requirement that Codex backend spawn prompts are prefixed with a context block (global + repo CLAUDE.md, routing orientation) and opencode backend spawn prompts are prefixed with routing orientation only (CLAUDE.md deliberately excluded, already native to opencode), parallel to and independent of the existing Claude-only `--append-system-prompt-file`/`--add-dir` injection requirements, which are unchanged.
- `skill-provisioning`: adds requirements to materialize the same embedded builtin skill bodies to vendor-scoped targets for native discovery — `$CODEX_HOME/skills/<name>/SKILL.md` for Codex, and a `skills` config-array entry in opencode's own config for opencode — alongside the existing Claude-targeted `~/.argus/skills/.claude/skills/` materialization.

## Impact

- `internal/agent/agent.go` (`BuildCmd`) — new backend-differentiated non-Claude branch building the prefix block (Codex: full block; opencode: routing-only); existing Claude branch untouched.
- `internal/skills/builtin.go` — a second materialization function (or a parameterized target) alongside `EnsureBuiltinSkills`, writing the same embedded skill bodies to `$CODEX_HOME/skills/<name>/SKILL.md` for Codex.
- `internal/inject/opencode` — extend the existing idempotent config-merge logic to also ensure a `skills` array entry is present, alongside the existing (unchanged) `mcp.argus` entry logic.
- `internal/routing/` — reused as-is (`BuiltinContent`/`EnsureBuiltinRouting`) for the routing-orientation portion of the prefix; no changes needed.
- A new small reader for global `~/.claude/CLAUDE.md` and repo-local `CLAUDE.md` content (new code — Argus does not currently read either file for any purpose; only Claude Code itself reads them natively).
- No change to `internal/inject/codex` (MCP wiring already works and is unrelated to this change) or to `internal/inject/pi` (does not exist; out of scope). `internal/inject/opencode` changes per above.
- No change to `internal/mcp/` — the previously-planned new tool is no longer needed.
- No files written into any project's worktree — skill materialization and the CLAUDE.md/orientation prefix are both non-worktree (global home-directory materialization, and in-memory prompt content, respectively).
