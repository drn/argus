## Why

`RoleView.ShowsNeedsInput()` — the single classifier that drives the needs-input "(?)" glyph on every coordinator-shaped surface (the rail's collapsed orchestrator header, a bridging worker row that is itself a nested sub-coordinator, the Details pane's coordinator status line, a Details roster row, and the plan-DAG node icon) — currently returns `SubtreeNeedsInput || needsInputOwn()`. `SubtreeNeedsInput` is a rollup: true when the role ITSELF or ANY descendant anywhere in its orchestration subtree needs input. So today a coordinator's icon lights up "(?)" not only for its own blocked session but for any blocked descendant, transitively, across bridged sub-orchestrators.

This rollup existed to solve a real problem: a closed (collapsed) coordinator fold could otherwise hide a blocked descendant with no visible cue at all. But the rail has since shipped a separate, independent mechanism that solves the exact same problem more precisely — the partial-fold-reveal (`appendOrch`/`appendOrchWorkers`/`appendOrchRevealPath`/`appendWorkerRow`/`appendPinnedRole`), which peeks through ANY closed ancestor fold, at any depth, and unconditionally renders the SPECIFIC row of any needs-input descendant, without mutating fold state. This has been verified across every nested shape the rail supports: a plain worker under one collapsed coordinator, a worker nested two or more collapsed levels deep, and a coordinator-spawned nested sub-team header reached via `coordBridgeChildren`.

Because the descendant is now ALWAYS independently visible through the reveal, the rollup badge on a coordinator-shaped row is redundant — and worse, ambiguous: today, seeing "(?)" on a coordinator's own icon does not tell the operator whether the coordinator ITSELF is blocked (actionable in that pane right now) or merely hosts a blocked descendant elsewhere in the tree (actionable somewhere else, already visible via the reveal). Dropping the rollup from every coordinator-shaped icon makes "(?)" mean exactly one thing everywhere it appears: this role's own live session or status needs input, never "something somewhere in my subtree does."

## What Changes

- `RoleView.ShowsNeedsInput()` (`internal/tui/hera/model.go`) drops the `SubtreeNeedsInput ||` term and returns `needsInputOwn()` alone. Because `roleStatusInputs` (`internal/tui/hera/rail.go`) — the single shared classifier feeding the rail's `statusIcon`, the Details pane's coordinator status line and roster rows (`details.go`), and the plan-DAG node icon (`plan.go`'s `planNodeIcon`) — reads `role.ShowsNeedsInput()`, this one change propagates the narrowing to all five render surfaces with no other code change required.
- `drawOrchRow`'s BUG-028 coordinator-less-orchestrator fallback (`internal/tui/hera/rail.go`: `else if o.SubtreeNeedsInput { ... }`, reached when an orchestrator's coordinator role was deleted/nuked and there is no "own" signal to fall back to) is removed outright — not narrowed, eliminated, since there is no own-signal case to narrow it to. A coordinator-less orchestrator header never renders a needs-input indicator; the blocked descendant is exposed exclusively via the reveal.
- The `SubtreeNeedsInput` COMPUTATION itself (`rollupNeedsInput`, `orchSubtreeNeedsInput`) is UNCHANGED — same transitive cross-bridge walk, same cycle-safety, same archived-role exclusion. It continues to exist and continues to gate the partial-fold-reveal mechanism (`appendOrch`'s `if o.SubtreeNeedsInput { ...revealOnly... }` and the equivalent gates elsewhere), which is unaffected by this change and remains the sole way a descendant's needs-input surfaces without expanding a closed ancestor.
- `ctrl+g`'s candidate check (`railRow.needsInputTaskID`) already keyed off `needsInputOwn()` directly and never read the rollup — untouched, no change needed.
- Archived-role exclusion from the rollup (a hidden role's own signal, or a hidden bridging row's subtree, never counting toward an ancestor) is a separate, pre-existing, deliberate feature — untouched.
- Existing tests that asserted the rollup driving a coordinator's OWN icon are updated to assert the new (narrowed) behavior; the two whole-screen BUG-028 integration tests keep passing but for a different reason (the revealed descendant row supplies the "(?)" rune now, not the header), so their docstrings/comments are corrected to describe that; new coverage is added for the two previously-untested surfaces (Details coordinator status line, Details roster rows).

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `hera-view`: four requirements change.
  - "Status-icon precedence on role rows" — drops the "OR its subtree rollup" clause from the needs-input precedence rule; a role's icon (on any surface) is driven by its own signal only.
  - "Needs-input '(?)' propagates up the orchestration tree to the root" — REMOVED. Superseded: no ancestor's icon surfaces a descendant's rollup anymore, including the coordinator-less-header fallback this requirement documented. The underlying computation it also documented (transitive, cycle-safe, archived-exclusion) is unchanged and now belongs entirely to the reveal mechanism's existing requirement.
  - "Needs-input '(?)' CLEARS and propagates up when a descendant resolves" — REMOVED. Superseded for the same reason: there is no ancestor icon rollup left to clear. A role's OWN needs-input clearing (content-aware signal resolves, or its live binding ends) is unaffected and is not what this requirement described.
  - "Live plan node icons are 1:1 with the rail" — the BUG-012 scenario's "or a descendant in its subtree does" clause is dropped; needs-input on a plan node is now own-signal-only, matching the rail.
  - A new requirement, "Needs-input '(?)' reflects only a role's own signal on every surface," is ADDED to state the resulting behavior plainly and cross-reference the untouched "Rail reveals the ancestor path to a hidden needs-input descendant through closed folds" requirement as the mechanism that keeps a blocked descendant visible.

This is a real, separate, pre-existing gap independent of the rollup question this change addresses; fixing it needs new reveal logic, not a display-clause change, and is left as a named follow-up (see design.md Non-Goals).
- No API, schema, keymap/help, or migration changes.
