## Context

`internal/profiles` defines the diligence-profile schema: a profile maps each of thirteen canonical archetypes to an optional `{model, effort, window}` triple (`profiles.Archetype`), plus a `[rigor]` block and an opaque `[panel]` block. Hera worker spawn consumes this at `internal/agent/agent.go`'s `ResolveModel` → `resolveProfile`: `task.Model` override → `profile[task.Archetype].Model` (validated against the resolved backend's model allow-list) → backend default. This chain is daemon-side only (profile files live under `~/.argus/profiles` and a worktree's `.argus/profiles`, both EPERM inside the sandbox) and has no exported, standalone `(profile, archetype) → (model, effort)` helper — the lookup is a single inlined expression, `p.Archetype[arch].Model`, inside `resolveProfile`.

`mcp__argus__profile_resolve(cwd, [profile])` (`internal/mcp/profiles.go`) is the sandboxed agent's only path to a resolved profile body. It reuses the same `profiles.Loader.ValidateName` call `resolveProfile` uses (same precedence, same fail-open semantics) and returns the **entire** resolved profile — every archetype's `{model, effort, window}`, `[rigor]`, and `[panel]` — as one JSON blob, not scoped to a single archetype or to hera. It already works from any `cwd`, hera-bound or not.

One consumer of this already exists: the `hera-spawn-review` skill reads `profile_resolve`'s `panel` field (`finders`, `[[panel.lens]]`, `synthesizer`) and spawns each finder as a native Claude sub-agent via the `Agent` tool with `model = <finder id>` — but only after checking the id is one of four **known in-session models** (`opus`/`sonnet`/`haiku`/`fable`, mirroring `internal/review.knownInSessionModels`); a foreign backend id (e.g. `codex`) is explicitly skipped rather than spawned, since the `Agent` tool can only run in-session Claude models. This in-session/foreign-backend split is exactly the constraint any archetype-driven native dispatch must also respect — a profile's `model` field is validated against the union of *all* configured backends (so it may legitimately be a codex model name), but only a subset of that space is usable as the `Agent` tool's `model` parameter.

**A confirmed defect discovered during this investigation**: `profiles.Archetype` and `profiles.Rigor` have `toml` tags but no `json` tags. `encoding/json.Marshal` falls back to the exported Go field name, so `profile_resolve`'s wire output is PascalCase (`"Model"`, `"Effort"`, `"ReviewPasses"`) — verified with a live call. The `diligence-profiles` base spec already documents these as lowercase/snake_case (`model`, `effort`, `review_passes`), and `internal/mcp/profiles_test.go`'s existing `TestProfileResolve_ArchetypePassthroughVerbatim` unmarshals into a lowercase-tagged struct and passes anyway, because Go's `json.Unmarshal` matches keys case-insensitively when no exact match exists — masking the bug from the one test that would otherwise catch it. Any consumer that reads the raw JSON directly (an LLM agent following a documented convention, `jq`, a non-Go script) hits the actual casing, not the documented one.

## Goals / Non-Goals

**Goals:**

- Make `profile_resolve`'s archetype entries usable, as-is, as the source of "model (+ effort where supported) for archetype X" by a caller with no hera-specific plumbing.
- Fix the JSON casing so the wire contract matches what the base spec already documents.
- Document one convention — generalizing what `hera-spawn-review` already does for the `review` archetype's panel — that any coordinator or pipeline skill can follow to resolve archetype→model for a sequence of native sub-agent stages, without re-deriving the fail-open/fallback rules each time.
- Make the in-session-vs-foreign-backend model gate (already implicit in `hera-spawn-review`'s finder-dispatch logic) an explicit, reusable rule, since blindly forwarding an archetype's `model` value into `Agent(model=...)` would pass an invalid value whenever a profile's archetype resolves to a non-Claude backend model (profiles are validated against the union of *all* configured backends, not just Claude).

**Non-Goals:**

- No new MCP tool. `profile_resolve` already returns every archetype's full entry in one call — a per-archetype tool would mean *more* round-trips for a multi-stage pipeline, not fewer, and there is no existing Go helper to extract cheaply (confirmed: `agent.resolveProfile`'s lookup is a single inlined expression, not a standalone function, and it additionally does backend-allow-list validation that has no equivalent for in-session dispatch).
- No change to hera worker spawn resolution (`internal/agent.ResolveModel`/`resolveProfile`) — that path is unaffected and out of scope.
- No effort *application* for native dispatch beyond documenting the gap. The built-in `Agent` tool has no effort parameter at all as of this change (confirmed against its current schema); `Workflow`'s `agent()` does accept `opts.effort` (`low`/`medium`/`high`/`xhigh`/`max`, a superset of a profile's three-value enum), so effort is threadable there today, but implementing a full application layer for the `Agent` tool is blocked on that tool itself, not on anything in this repo.
- No changes to `hera-spawn-review`, `hera-review`, `hera`, or `hera-plan` — those skills are out of scope for this change (two of them are owned in parallel by a sibling workstream chunk). The new skill documents the pattern as a standalone, reusable reference; a future chunk may choose to have `hera-spawn-review` delegate to it, but that is not part of this change.

## Decisions

**D1 — Fix the casing, don't add a compatibility shim.** Add `json:"model,omitempty"` / `json:"effort,omitempty"` / `json:"window,omitempty"` to `profiles.Archetype`, and `json:"review_passes,omitempty"` / `json:"gating,omitempty"` / `json:"security_spot_check,omitempty"` to `profiles.Rigor`. Rejected alternative: leave the casing and document "read `Model` not `model`" — this would permanently encode a bug into the convention this change is trying to establish, and `profile_resolve` is new enough (no known non-Go consumer yet) that fixing it now costs nothing.

**D2 — No new MCP tool; extend the existing contract via documentation + a skill.** Considered a thinner `archetype_resolve(cwd, archetype) → {model, effort}` tool wrapping `profile_resolve`. Rejected: `profile_resolve` already returns the full archetype map in one call, which is *better* for a multi-stage pipeline than a per-archetype tool (one call up front vs. N round-trips); the per-archetype logic that would live inside such a tool is genuinely small (a map lookup + a four-value membership check), and per §Non-Goals there's no existing Go-side helper to reuse that would make the tool cheap to build. Adding Go surface (a new tool, new tests, another thing to keep in sync with `profile_resolve`'s own resolution semantics) buys little over documenting the two-line lookup.

**D3 — The in-session model gate is load-bearing, not optional; a mismatch substitutes the closest tier rather than dropping model selection.** A profile's archetype `model` is validated against the union of *every configured backend's* models (`internal/profiles/validate.go`), so it may resolve to e.g. a codex model name. The `Agent` tool only runs in-session Claude models and has no path to any other backend at all — unlike hera worker spawn, there is no fallback session that could actually run a foreign model. The convention forwards `model=` as-is only when the resolved value is one of `opus`/`sonnet`/`haiku`/`fable`; otherwise it substitutes the closest available in-session Claude tier (a coarse, name-based heuristic: a foreign flagship model → `opus`, a foreign cheap/mini-class model → `haiku`, anything ambiguous → `sonnet`) and loudly notes the substitution. **Revised from the original "omit and note" design** (coordinator follow-up, see PR #864 review): omitting the model entirely could land on *any* tier via the caller's own default, unrelated to what the archetype was actually configured for — a coarse but archetype-aware substitute is a better approximation of intent than an unrelated default, even though there is no validated cross-vendor quality mapping backing the heuristic. `Workflow`'s `agent()` accepts the same in-session enum for its `model` param, so the same gate and substitution rule applies there too.

**D4 — Ship a skill, not just prose in a spec.** A convention that only lives in an OpenSpec requirement is invisible to a coordinator mid-session (specs are not loaded context). Shipping `.claude/skills/resolve-archetype-model/SKILL.md` gives it a `Skill()`-loadable, discoverable home, matching how `hera-review`'s methodology is a separate skill from `hera-spawn-review`'s glue. The spec still normatively describes the convention's behavior (fail-open rules, the model gate) so it's testable/reviewable independent of the skill's prose.

## Risks / Trade-offs

- **[Risk] The casing fix is technically a breaking wire-format change.** → **Mitigation:** `profile_resolve` is recent, and the only known consumer (`hera-spawn-review`) reads `panel` (an untyped map, unaffected) rather than `archetype`/`rigor`. No release/dogfood period has depended on the current PascalCase per the investigation for this change. Fixing now, before any convention locks onto it, is strictly cheaper than fixing later.
- **[Risk] A hand-rolled convention (vs. a machine-checked tool) can drift or be applied inconsistently across skills.** → **Mitigation:** the fail-open/gate rules are specified normatively in the `archetype-native-dispatch` capability (testable claims, not just prose), and the shipped skill is the single authoritative copy other skills can reference instead of re-deriving their own.
- **[Risk] Effort remains unusable for the most common native-dispatch mechanism (the `Agent` tool).** → **Mitigation:** documented as an explicit, named gap (mirroring the existing "Fable pin... check the tool's schema before assuming otherwise" gotcha style already established in `hera-spawn-review`) rather than silently ignored or overclaimed as solved.
- **[Risk] The foreign-model substitution heuristic (D3) is a name-based guess, not a validated cross-vendor tier mapping** — it can misclassify a foreign model whose name doesn't match the flagship/cheap hints. → **Mitigation:** the skill states plainly that this is best-effort, always emits a loud note naming both the original and substituted model so the mismatch is auditable, and defaults to the middle (`sonnet`) tier on ambiguity rather than guessing toward either extreme.

## Migration Plan

Additive except for the casing fix, which changes the on-wire shape of the two typed sub-objects `profile_resolve` returns. No data migration (profiles are on-disk files and TOML parsing is unaffected — only the outbound JSON marshaling changes); no rollback plan needed beyond reverting the tag change. Lands on `argus/model-tiering` via a normal PR, per this workstream's standing convention.
